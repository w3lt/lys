The chat route emits exactly nine SSE payload variants, defined by
`chatApiStreamEventSchema` in `@lys/protocol`. The reply-events route emits
`reply-snapshot` followed by the seven generation variants (`title`, `delta`,
`done`, `interrupted`, `error`, `tool-approval`, `tool-call`), defined by
`chatReplyEventSchema`.

## Event variants

| Event name                         | Payload fields                                                                      | Meaning                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `start-new-conversation-turn`      | `conversation`, `userMessage`, `assistantMessage`                                   | The backend created a new conversation and persisted the first turn.                                 |
| `start-existing-conversation-turn` | `userMessage`, `assistantMessage`                                                   | The backend persisted a new turn on an existing conversation.                                        |
| `title`                            | `title`                                                                             | The persisted conversation title, generated or reconciled.                                           |
| `delta`                            | `content`                                                                           | One non-empty assistant text fragment.                                                               |
| `done`                             | `finishReason`                                                                      | Successful assistant completion with `stop` or `length`.                                             |
| `interrupted`                      | none                                                                                | The reply ended before the model finished.                                                           |
| `error`                            | `message`                                                                           | A user-presentable chat generation error string.                                                     |
| `tool-approval`                    | `call`                                                                              | The reply waits for the person to allow or reject this tool call.                                    |
| `tool-call`                        | `call`                                                                              | The reply waits for the client to run this call of a client tool.                                    |
| `reply-snapshot`                   | `conversationTitle`, `assistantMessage`, `pendingToolCalls`, `pendingToolApprovals` | Reply-events route only: the stored reply and its unanswered calls and prompts when following began. |

## Payload details

### `start-new-conversation-turn`

Includes:

- full `conversation` metadata, whose `title` is `null` until a title is
  generated
- one persisted user message
- one persisted assistant message in `streaming` state

### `start-existing-conversation-turn`

Includes:

- one persisted user message
- one persisted assistant message in `streaming` state

The desktop uses its current active conversation metadata together with these
messages to build the new transcript state.

### `title`

Carries the non-empty persisted conversation title. For an existing titled
conversation, the backend sends it immediately after the turn-start event so a
desktop that missed an earlier delivery can reconcile its metadata. This does
not request another title from the model. For an untitled conversation, the
backend persists the first successfully assigned generated title before it
sends the event.

The backend makes up to three title-generation attempts per turn, set by
`titleGenerationMaxAttempts` in `src/config.ts`. Only a reply that cannot be
used as a title, such as JSON with the wrong shape or a title longer than
`generatedTitleMaxLength`, leads to another attempt. JSON wrapped in one
Markdown code fence is accepted. An HTTP, connection, or cancellation failure
ends title generation for the turn. Before that, the OpenAI SDK retries a
connection failure, timeout, or 408, 409, 429, or 5xx response up to two more
times, so one attempt can send up to three HTTP requests.

When one title task produces no usable candidate or backend shutdown cancels
it, that task sends no `title` event. Stopping the reply or closing the stream
does not cancel it. A turn started after that task ended requests generation
when the conversation is still untitled; a turn started while it is still
running requests none and receives no `title` event. If a title was saved but its event was not
delivered, a later existing turn sends the stored title again. The backend logs
title-task failures instead of sending an `error` event.

### `delta`

Carries one non-empty `content` fragment. The desktop appends it to the current
streaming assistant message.

### `done`

Carries:

```json
{
  "type": "done",
  "finishReason": "stop"
}
```

The only accepted `finishReason` values are `stop` and `length`.

### `interrupted`

Carries no fields. Sent when the reply was stopped, superseded by a newer turn
in its conversation, deleted with its conversation, or cancelled by backend
shutdown. The stored reply, if it still exists, is `interrupted` with exactly
the content delivered before this event. No `delta` or `done` follows it; a
`title` can.

### `tool-approval`

Carries one tool call the backend shows to the person before anything runs,
in the same shape as a `tool-call` event's `call`. The backend's tool approval
service sends it for every call of a tool that is not saved as Just run,
client and backend tools alike; a call of a tool on Just run gets no prompt.
The client shows the call and answers with the
[tool-approval route](/reference/api/#tool-approvals). After `allowed`, a
backend tool runs in the backend, and a client tool's call comes back as a
`tool-call` event under the same `id`. The event is live only: a client that
was not following when it was sent finds the call in the next
`reply-snapshot`'s `pendingToolApprovals`.

### `tool-call`

Carries one call of a client tool that the reply waits for the client to run:

```json
{
  "type": "tool-call",
  "call": {
    "id": "0199c8a1-2f4e-7c3b-9a1d-5e6f7a8b9c0d",
    "toolName": "read_text_file",
    "arguments": { "path": "/Users/me/notes/todo.md" }
  }
}
```

`id` is a UUIDv7 the backend made for the call. `toolName` names a tool the
request offered, and `arguments` holds the model's values by argument name:
strings, numbers, or Booleans, already checked against the tool's definition.
An optional argument the model left out is absent. A call whose arguments do
not match never reaches the client; the backend answers it itself, and the
model reads the error. A call of a backend tool, such as `read_page` or
`web_search`, never arrives here: once allowed, the backend runs it itself.

The backend sends this event only once the call may run: at once for a tool
saved as Just run, otherwise after the person allowed its `tool-approval`
prompt. The client runs it without asking again and answers with the
[tool-result route](/reference/api/#tool-results). When a round's calls
arrive, their prompts and the run requests of calls that need no prompt are
sent in the model's order; the next round starts once every call has an
answer. The model's text in a round that calls tools is streamed and stored
like any other text. The event is live only: nothing stores it, and a client
that was not following when it was sent finds the call in the next
`reply-snapshot`'s `pendingToolCalls`.

### `reply-snapshot`

The first event of every reply-events stream. `assistantMessage` is the stored
reply, including every delta sent before this event, so later `delta` events
continue from exactly its content. `conversationTitle` is the stored title, or
`null`. `pendingToolCalls` lists the calls sent to run and not yet answered
with their result, and `pendingToolApprovals` the prompts not yet answered,
each in the order sent and in the same shape as an event's `call`; both are
empty when the reply is not generating. Each reaches a follower once, either
here or as a later `tool-call` or `tool-approval` event. When the reply's
generation has already ended, the stream closes right after this event.

### `error`

Carries a non-empty `message` string that reports a chat generation failure.
The desktop presents it inline and may also mark the current assistant message
as failed locally. Title-generation failures never produce `error` events.

## What is not on the current stream

- No `event_id`
- No `session_id`
- No `emitted_at`
- No replay marker such as `stream.resumed`
- No tool results, and no record of which tools ran

## Event ordering today

Every valid chat stream begins with one turn-start event. After that:

1. `start-new-conversation-turn` or `start-existing-conversation-turn`
2. for a titled existing conversation, its stored `title` event arrives next
3. zero or more rounds: each round's text as `delta` events, then, when the
   round calls tools, its `tool-approval` and `tool-call` events in the
   model's order, and the `tool-call` event of each allowed client tool's call
   when its answer arrives. When an
   earlier round sent text, a later round's first `delta` starts with a blank
   line (`\n\n`)
4. exactly one of `done`, `interrupted`, or `error`
5. for a conversation without a stored title, a generated `title` may arrive
   before, during, or after the chat events

A `title` event can still arrive after the reply's final event, because title
generation runs independently; the stream closes after both have settled. A
turn without a title task, including one sent while an earlier turn of its
conversation is still generating a title, closes after its reply.
Closing the stream never cancels either task. A reply-events stream follows
the same order after its `reply-snapshot`, starting from wherever the reply
was when the snapshot was read.

A stream can also close without any of `done`, `interrupted`, or `error`: the
backend closes a follower that falls 4,096 events behind, and a reply whose
final state cannot be stored sends none. Such a close says nothing about the
reply's outcome; following the reply again, or reading its conversation,
returns the stored state.
