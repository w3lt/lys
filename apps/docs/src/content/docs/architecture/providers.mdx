Lys currently integrates with one local model runtime: LM Studio.

## Current stack

| Concern          | Current implementation                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- |
| Model inventory  | `LlmService.listModel()` uses `@lmstudio/sdk` to list downloaded models and annotate which are loaded.              |
| Model loading    | `POST /api/v1/llm/load` loads one model through LM Studio and returns its metadata.                                 |
| Chat generation  | `ChatService.completeChatStream()` uses the `openai` SDK against LM Studio's OpenAI-compatible `/v1` HTTP endpoint. |
| Title generation | `ChatService.generateTitle()` uses the same endpoint with a separate prompt and structured output parsing.          |

## Request path

```text
Desktop chat store -> Fastify /api/v1/chat -> ChatService -> LM Studio /v1
Fastify /api/v1/llm/* -> LM Studio SDK/client
```

The current desktop settings UI does not call the LLM routes. Its Model tab is
not a usable alternative path: the pane requires a `SettingsContext.Provider`
that the current settings view does not mount. The list route uses the
application-scoped `LlmService`; the load route currently constructs an LM
Studio client inside its handler.

## What the backend assumes today

- LM Studio is running on `127.0.0.1:1234`.
- Chat requests can be satisfied by an OpenAI-compatible HTTP endpoint.
- Inventory and load operations are available through the LM Studio SDK.
- No external credential exchange is required to reach the local runtime.

## Limitations

- There is no provider registry or adapter plugin system.
- There is no automatic fallback between providers or models.
- There is no request budgeting, quota tracking, or provider-specific telemetry.
- The desktop Model, Generation, and Conversation settings tabs are currently
  unusable because their required context provider is not mounted.

## Coming soon

- Multiple providers or adapter abstractions
- Fallback and retry policy across model runtimes
- Usable Model, Generation, and Conversation settings tabs
- Persistent model selection shared between settings and chat
- Provider-specific configuration and health reporting
