# Desktop unit test coverage

This is the coverage inventory of the desktop renderer's unit suite (#132). It maps each repository-owned source module to the boundary its tests exercise, the dependencies the tests control, and what the tests cannot prove. Update it in the same change as the tests it describes.

The suite was delivered in parts: `src/lib` and `src/app` first, then components, renderer hooks, and views (`src/components`, `src/views`, `src/App.tsx`), and last the renderer code that `main` gained meanwhile with #128 (tool calls), #143 (load settings), #152 (built-in agents), and #157 (backend tools). #164 (web search) added the Secrets pane, the key check, and tool availability with their tests. The Rust host belongs to the native suite (#133), and flows through the real app belong to the E2E suite (#134).

## Running the suite

```sh
pnpm --filter @lys/desktop test             # run once
pnpm --filter @lys/desktop run test:watch   # rerun on change
pnpm --filter @lys/desktop exec tsc         # typecheck the renderer and the suite
```

The `Desktop unit tests` workflow (`.github/workflows/desktop-unit-tests.yml`) runs the typecheck and the suite on every pull request and on every push to `main`. Vitest fails a run that finds no test files.

## Environment and substitution

- Tests run in Vitest with jsdom. They need no LM Studio, no running backend, no Tauri runtime, and no developer settings or database.
- **Backend:** `support/backendFake.ts` replaces the global `fetch` with an in-process backend that answers only the routes a case declares. Every case starts with a backend that declares no route (`test/unit/setup.ts`), so no case can reach a real backend; a case that expects requests starts its own. Any request the case did not declare fails it, and so does a request whose body is not JSON text. Abort follows the platform `fetch`: an aborted signal rejects before the route runs, a later abort rejects the pending response or errors its body, and the route's body is cancelled. Success bodies come from fixtures validated by the `@lys/protocol` and `@lys/share` schemas. Malformed bodies appear only in cases that test their rejection. A case makes a request fail as an unreachable backend does only with `createTransportFailure()`; any other exception a route raises fails the case.
- **Native host:** `support/nativeHostFake.ts` answers Tauri IPC through Tauri's `mockIPC` seam. Any undeclared command fails the case. `test/unit/setup.ts` removes the IPC double and unmounts rendered trees after every case.
- **Stores:**
  - Factories that take their dependencies (`createChatViewStore`, `createConversationHistoryStore`, and the slice factories) receive the real HTTP wrappers over the fake backend, plus in-test providers (backend availability, clock, model, and generation controls).
  - Singleton stores (`useLysStore`, `useAgentStore`, `useToolStore`, `useToolCallStore`, `useChatViewStore`) are imported fresh for each case with `vi.resetModules()`. Their state is arranged only through zustand's public `setState`.
  - Components and the stores they read are imported together, fresh for each case, so a rendered tree never shares a store with another case.
  - No repository module is replaced with `vi.mock`, and no production export was added for tests.
- **DOM gaps:** jsdom lays nothing out and has no clipboard, `scrollTo`, `ResizeObserver`, or drag data store. Cases that need one install it for themselves: a clipboard double, a `scrollTo` recorder, scroll measurements on the scrolled element, drop events whose files are readable only while dispatched, as a browser's are, and images reported as loaded (`support/imageHostFake.ts`), because jsdom never loads one and Base UI shows an avatar image only once it has. Base UI menus are opened with the keyboard, because jsdom does not reproduce the pointer press that opens them; slider thumbs stay hidden until measured, so they are queried as hidden elements. Shiki highlighting runs for real.
- **Time:**
  - Fake timers control `setTimeout`, `Date`, and `performance.now` where a contract depends on them. A case that only needs a fixed wall clock fakes `Date` alone, so rendering keeps real timers. Hover delays run on fake timers with hover events dispatched synchronously (`support/rendering.ts`), because user-event cannot complete under fake timers.
  - `AbortSignal.timeout` is not under fake-timer control, so the one-second health-check bound is checked against the real clock (lower bound only).
  - `support/settlement.ts` provides the macrotask barrier, which also works under fake timers, plus settlement readers and controlled promises.

## Proof limits

- The fake backend proves how the renderer builds requests and decodes declared responses. It does not prove compatibility with a running backend (#134) or real network behavior beyond the platform `fetch` semantics it reproduces.
- The fake native host proves command names, arguments, and handling of results and rejections. It does not prove the Rust commands' behavior (#133).
- Component tests observe semantic DOM, focus, and callbacks in jsdom. Layout, scrolling, real pointer opening of menus, tooltip placement, WebKit drag data, and assistive-technology output need the real app (#134).
- Some ownership checks guard races that the abort path already ends, so mutating them changes nothing observable:
  - In the agent store, the success-path ownership checks for list pages and agent reads. A superseded read is aborted and, with platform `fetch` semantics, settles through the failure path, which is covered.
  - In the chat-view store, the dispatcher's stale-token returns, because the event handlers reject a stale token themselves.
  - In `useLysStore.setSettings`, resetting `generationSave` to idle before the autosave starts, because the autosave immediately replaces it with `saving`.
- `useLysStore.stopBackend` keeps the stop pending when the stop command reports a process that still runs. No case reaches that branch: the Rust `stop_backend` returns only a stopped status or an error, and a fake must not report an outcome the command cannot. A failed stop is covered (#162).
- Some component guards repeat a guard the store or Base UI already applies, so removing them changes nothing observable: the composer's drag-over check while unavailable, the settings view's running check before reading the inventory, the agent editor's Escape check while a change is pending, the agents pane's running check before reading agents, and the slider's own single-thumb label.
- In the tool-call store, three guards cannot be reached through the singleton, and one effect cannot be observed:
  - Stopping a follow only while it is still the reply's current one: a reply is never followed twice at once.
  - Ignoring calls when the follow ended while the tool settings were read: a reply's events are handled one at a time, so its follow cannot end during that read.
  - Skipping a call that is already held, which the store checks twice. Removing both checks fails cases; removing either one does not.
  - Aborting the follow's signal when the follow stops: the stream is already cancelled by then.
- In the model slice, the ownership checks between the steps of an operation. A released request is aborted, and an aborted step or inventory read never reaches the backend, so a case interrupted during a step passes without them. The check after the inventory read is covered.
- In the load configuration components, removing these changes nothing a case can arrange:
  - The approval card's check for a call without arguments: every listed tool takes at least one, and a fixture must match its tool.
  - The reload control's availability check: the store releases the inventory when the model runtime is unavailable, so no model is edited then.
  - The load editor's key by model: a typed context length is committed when the box loses focus, which choosing another model always causes first.
  - The slider adapter's handling of a single number or of no position, and the stepper's guard for an unset count: the slider reports its positions as a list, and the step-down button is disabled while no count is set.
- `model-load-configuration.ts` validates the committed default file when the module is evaluated. An invalid file cannot be arranged without replacing the module, which this suite does not do.
