The current backend surface is small and lives entirely under the `@lys/protocol`
route definitions.

## Routes

| Method   | Path                                                                            | Request body                                                                       | Response                                                   |
| -------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `GET`    | `/api/v1/heath`                                                                 | none                                                                               | `{ ok: true }`                                             |
| `GET`    | `/api/v1/llm/list`                                                              | none                                                                               | `{ llms: LlmInfo[] }`                                      |
| `GET`    | `/api/v1/llm/:modelId/health`                                                   | none                                                                               | Loaded-state health observation                            |
| `POST`   | `/api/v1/llm/load`                                                              | `{ modelId: string, configuration?: ModelLoadConfiguration }`                      | `LlmInfo`                                                  |
| `PATCH`  | `/api/v1/llm/unload`                                                            | `{ modelId: string }`                                                              | `204` or typed Problem Details                             |
| `GET`    | `/api/v1/llm/runtime`                                                           | none                                                                               | `{ status: "connecting" \| "connected" \| "unreachable" }` |
| `POST`   | `/api/v1/llm/runtime/connect`                                                   | none                                                                               | Settled `{ status }`, or service-busy Problem Details      |
| `GET`    | `/api/v1/conversations`                                                         | none; optional `query`, `cursor`, `limit` query parameters                         | Conversation list page                                     |
| `GET`    | `/api/v1/conversations/:conversationId`                                         | none                                                                               | Conversation with ordered messages                         |
| `PATCH`  | `/api/v1/conversations/:conversationId`                                         | `{ title: string }`                                                                | Conversation metadata                                      |
| `DELETE` | `/api/v1/conversations/:conversationId`                                         | none                                                                               | Bodyless `204`                                             |
| `GET`    | `/api/v1/agents`                                                                | none; optional `cursor`, `limit` query parameters                                  | Built-in agents and a page of stored agents                |
| `POST`   | `/api/v1/agents`                                                                | `{ code?, name, bio, systemPrompt }`                                               | `201` agent with `Location`, or `409` Problem Details      |
| `GET`    | `/api/v1/agents/:agentCode`                                                     | none                                                                               | Agent with its system prompt                               |
| `PATCH`  | `/api/v1/agents/:agentCode`                                                     | at least one of `{ name, bio, systemPrompt }`                                      | Changed agent, or `409` for a built-in agent               |
| `DELETE` | `/api/v1/agents/:agentCode`                                                     | none                                                                               | Bodyless `204`, or `409` for a built-in agent              |
| `POST`   | `/api/v1/chat`                                                                  | `conversation`, `message`, `model`, required `generationOptions`, optional `tools` | `text/event-stream`                                        |
| `GET`    | `/api/v1/chat/:conversationId/replies/:assistantMessageId/events`               | none                                                                               | `text/event-stream` (reply snapshot, then live events)     |
| `POST`   | `/api/v1/chat/:conversationId/replies/:assistantMessageId/stop`                 | none                                                                               | Bodyless `204`, or `409` Problem Details                   |
| `POST`   | `/api/v1/chat/:conversationId/replies/:assistantMessageId/tool-results/:callId` | `{ status, reason?, content }`                                                     | Bodyless `204`, or `409` Problem Details                   |

`/api/v1/heath` is the current spelling in both the shared protocol package and
the Fastify route registration.

List, load, health, and unload requests answer `503` with
`urn:lys:problem:llm:runtime-unavailable` while the backend has no connected
LM Studio runtime. The runtime-status route never contacts LM Studio; the
runtime-connect route waits for one shared connection attempt.

Every request body is limited to 1 MiB (1,048,576 bytes), Fastify's default,
except a tool result, which is limited to 8 MiB (8,388,608 bytes) so that a
1 MiB file read still fits after JSON escaping. A larger body is refused with
`413 Payload Too Large` before the route runs, so nothing is stored or
changed. The response is Fastify's JSON error body, with
`code` `FST_ERR_CTP_BODY_TOO_LARGE`, not Problem Details.

## Chat request body

```json
{
  "conversation": {
    "kind": "existing",
    "id": "0198f5a5-7b9b-7e0b-9b0f-87d9d6a5f72d"
  },
  "message": "Tell me what changed",
  "model": "google/gemma-4-12b-qat",
  "generationOptions": {
    "temperature": 0.7,
    "replyCeiling": 2048
  }
}
```

`conversation` names the conversation the turn starts or continues; its `kind`
selects one of two forms:

- `{ "kind": "new", "agentCode": "caliginia" }` starts a new conversation,
  created before the first stream event, that the named agent answers: a
  built-in agent (`caliginia`, `lysiptera`) or a stored one. A valid code that
  no agent has returns the agent-not-found Problem Details response below with
  `404`, and nothing is stored.
- `{ "kind": "existing", "id": "<UUIDv7>" }` continues a stored conversation
  with the agent it was started with, so it names no agent. An unknown
  identifier returns the conversation-not-found Problem Details response below.
  A stored conversation whose agent no longer exists, as after that agent was
  deleted, returns `409` with `urn:lys:problem:conversation:agent-missing`,
  and nothing is stored; see
  [a conversation whose agent was deleted](#a-conversation-whose-agent-was-deleted).

`message` and `model` must be non-empty strings. Every turn sends the system
prompt its agent has when the turn starts, so editing a stored agent changes
its conversations from their next message. Continuation
uses the system prompt of the conversation's agent, prior user messages, non-empty completed or
interrupted assistant messages, then the current user message exactly once.
Failed and empty assistant messages are excluded from context. A reply still
streaming in the conversation becomes interrupted when the new turn is created,
so its partial text is included.

`generationOptions` is required and has no protocol-level default:

| Field          | Accepted value                                  | Effect                                                                  |
| -------------- | ----------------------------------------------- | ----------------------------------------------------------------------- |
| `temperature`  | Required number from `0` through `1`, inclusive | Forwarded as the completion sampling temperature.                       |
| `replyCeiling` | Optional non-negative integer, in tokens        | Forwarded as `max_completion_tokens`; omission becomes `null` upstream. |

Both numeric fields use number coercion before validation. The request, its
`conversation`, and the generation-options objects reject unknown fields, so a
`conversation` with both an `id` and an `agentCode`, or a top-level
`conversationId` as earlier versions sent, is rejected with `400`. Missing
required options or invalid values are rejected with `400` before generation. The desktop translates
a saved zero reply ceiling into omission; API callers should omit the field for
that behavior, since an explicit API value of `0` is forwarded unchanged. These
controls affect chat completion; title generation uses a separate request.

### Tools

A request can offer the model the client's tools for this turn:

```json
{
  "tools": {
    "definitions": [
      {
        "name": "read_text_file",
        "description": "Read one UTF-8 text file and return its complete text.",
        "group": "files",
        "access": "reads",
        "arguments": [
          {
            "type": "string",
            "name": "path",
            "description": "Absolute path of the file.",
            "required": true
          }
        ]
      }
    ]
  }
}
```

`definitions` lists at least one tool definition, each name once, in the shape
`toolDefinitionSchema` from `@lys/share` validates. It lists only the client's
switched-on tools; tools the backend runs itself are added by the backend.
Without `tools`, the turn is one round with no tools. The desktop sends `tools`
only to a model whose `trainedForToolUse` is true; the backend does not check
this itself ([#135](https://github.com/w3lt/lys/issues/135)). A reply can make any number of tool calls
([#136](https://github.com/w3lt/lys/issues/136)).

## Chat response shape

Accepted chat turns respond as SSE. A missing conversation, a new
conversation naming a code no agent has, or a stored conversation whose agent
no longer exists returns JSON Problem Details before the stream starts, and
nothing is stored: no message, and no failed reply. Each event payload must match one of
the eight variants documented in [SSE events](/reference/sse-events/).

Closing a chat stream stops only that client's observation. The backend keeps
generating and storing the reply and its title. To stop a reply, send
`POST /api/v1/chat/:conversationId/replies/:assistantMessageId/stop`; it
answers `204` after the reply is stored final (`interrupted`, or `completed`
or `failed` when the reply ended before the stop) and does not cancel title
generation. When no
generation is running for the reply it answers `409` with
`urn:lys:problem:chat:reply-not-generating`.

To follow a reply again, open
`GET /api/v1/chat/:conversationId/replies/:assistantMessageId/events`. Its
first event is a `reply-snapshot` with the stored reply and conversation
title; live events follow while the generation runs. A missing conversation
returns the conversation-not-found problem and a missing reply returns `404`
with `urn:lys:problem:chat:reply-not-found`.

## Tool results

While a reply waits on a tool call, the client that runs the tool answers it
with
`POST /api/v1/chat/:conversationId/replies/:assistantMessageId/tool-results/:callId`,
where `callId` is the `id` of the call's `tool-call` event or of its entry in
`reply-snapshot.pendingToolCalls`. One request answers one call.

```json
{ "status": "succeeded", "content": "The file's text" }
```

```json
{
  "status": "failed",
  "reason": "declined",
  "content": "The person declined this call. They said: not that folder"
}
```

`content` is the exact text the model reads; a succeeded result can be empty,
such as for an empty file, and a failed one cannot. `reason` says why a call
failed and is not shown to the model: `declined` when the person said no or
switched the tool or tool calls off, `toolFailed` when the tool ran and
reported a failure, and `runFailed` when the client could not run it.

The route answers a bodyless `204` once the answer is accepted, and the
reply's loop continues. A call that is unknown, already answered, or whose
reply ended returns `409` with `urn:lys:problem:chat:tool-call-not-pending`
and changes nothing, so repeating a request whose response was lost is
harmless. The backend sets no time limit on a pending call. It waits until
the call is answered, the reply is stopped, or the backend shuts down. A newer
turn in the conversation or deleting the conversation does not end the wait yet
([#137](https://github.com/w3lt/lys/issues/137)).

## Conversation history

All conversation identifiers must be UUIDv7; malformed identifiers return `400`.
List responses have exactly `conversations`, `storedCount`, `matchCount`, and
`nextCursor`. Counts include all stored conversations and all matches before
pagination, respectively. Each summary contains `id`, nullable `title`,
`createdAt`, `updatedAt`, and nullable `preview`; it does not expose `agentCode`.
A preview contains only `role` and full `content`.

| Parameter | Contract                                                                                                                                                                         |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `query`   | Optional; trimmed to 1–200 UTF-16 code units when supplied. Blank queries are rejected. Unicode case-insensitive literal substring search covers titles and all message content. |
| `limit`   | Integer from 1–50; defaults to 30.                                                                                                                                               |
| `cursor`  | Opaque, at most 2048 characters; reuse with the same trimmed query. Malformed, unsupported, or differently bound cursors return `400`.                                           |

Results are ordered by `updatedAt DESC, id DESC`, with keyset pagination. The
next cursor is `null` at the end. Each response reads counts, page, and previews
from one snapshot; subsequent pages reflect later database changes.
Search previews select the latest non-empty matching message, falling back to
the latest non-empty message for a title-only match. Unfiltered lists select the
latest non-empty message; conversations without one have `preview: null`.

`GET` by identifier returns conversation metadata, including `agentCode`, the
code of the agent that answers it, and
messages ordered by creation time then identifier. The code stays after its
agent is deleted, so it may name no agent. `PATCH` accepts
only `title`, trims it to 1–120 UTF-16 code units, and returns updated metadata. Repeating
a rename is idempotent; renaming never changes activity time or list position.
`DELETE` cascades to messages and returns `204` without a body. Late generation
writes after deletion do not recreate the conversation. Allowed development and
Tauri origins support DELETE preflights.

Missing conversations on GET, PATCH, DELETE, or chat continuation return `404`
with `Content-Type: application/problem+json`:

```json
{
  "type": "urn:lys:problem:conversation:not-found",
  "title": "Conversation not found",
  "status": 404,
  "detail": "Conversation 0198f5a5-7b9b-7e0b-9b0f-87d9d6a5f72d was not found.",
  "instance": "/api/v1/conversations/0198f5a5-7b9b-7e0b-9b0f-87d9d6a5f72d"
}
```

Chat creates its user/assistant pair atomically, persists each delta before
sending it to every stream following the reply, and stores a terminal status
before `done`. Partial content survives
failure or cancellation. Title generation runs only for an untitled conversation
without a title task already running, and publishes a title only if the
conditional database write succeeds. On startup,
remaining streaming assistants become interrupted with refreshed message
timestamps; conversation activity time and history order do not change.

## Agents

There are two kinds of agent. A built-in agent ships with the backend:
Caliginia (`caliginia`) and Lysiptera (`lysiptera`). It has a `code`, a `name`,
a `bio`, and a `systemPrompt`, belongs to the release, and can be neither
changed nor deleted. A stored agent is a definition the user created: a `code`, a `name`, a `bio`, a
`systemPrompt`, and the `createdAt` and `updatedAt` timestamps. The code is the
agent's identity and never changes: a lowercase slug of 1–64 characters made of
`a`–`z` and `0`–`9` in hyphen-separated groups, compared exactly. A malformed
code in a path returns `400` before any lookup. Request bodies reject unknown
fields; the name is trimmed to 1–64 UTF-16 code units, the bio to 1–128, and the
system prompt must not be blank after trimming. Text containing a lone UTF-16
surrogate, which UTF-8 cannot carry unchanged, is rejected. The system prompt
has no length limit of its own; only the 1 MiB request body limit above bounds
it. Invalid bodies return `400` and change nothing.

List responses have exactly `builtInAgents`, `agents`, `storedCount`, and
`nextCursor`. `builtInAgents` holds every built-in agent's `code`, `name`, and
`bio`, in the order the backend ships them, and is the same on every page.
`agents` holds one page of stored agents: each
summary contains `code`, `name`, `bio`, `createdAt`, and `updatedAt`. Neither
exposes `systemPrompt`, which `GET` by code returns. `GET` by code returns the
agent with a `kind`: `"built-in"`, without timestamps, or `"custom"` for a
stored agent, with them.

| Parameter | Contract                                                                                                  |
| --------- | --------------------------------------------------------------------------------------------------------- |
| `limit`   | Integer from 1–50; defaults to 30.                                                                        |
| `cursor`  | Opaque, at most 2048 characters, taken from the previous page. Malformed or foreign cursors return `400`. |

Stored agents are ordered by `createdAt ASC, code ASC`, with keyset pagination, and
`storedCount` counts every stored agent, never the built-in ones. Neither key changes after creation,
so an update never moves an agent between pages. Each response reads the count
and the page from one snapshot; later pages reflect later changes. The next
cursor is `null` on the last page.

`POST` stores a new agent and answers `201` with the stored agent and a
`Location: /api/v1/agents/<code>` header. CORS does not expose `Location`, so a
browser client on another origin, such as the desktop app, uses the returned
`code` instead. `code` is optional:

- A given code is stored exactly. If another agent already has it, a built-in
  agent's included, the request returns `409` with
  `urn:lys:problem:agent:code-taken` and stores nothing.
- Without a code, the backend derives one from the name: it decomposes the
  name with Unicode compatibility decomposition (NFKD), which removes accents
  and turns forms such as `𝐖` or `ﬁ` into ASCII, then lowercases it, joins the
  remaining ASCII letters and digits with single hyphens, and cuts the result
  to fit 64 characters. `Web Researcher` becomes `web-researcher` and `Trợ lý`
  becomes `tro-ly`. A letter without an ASCII form, such as `đ`, acts as a
  separator. A name in which no letter or digit has an ASCII form, such as
  `日本語`, gives `agent`. When the code is taken, by a stored or a built-in
  agent, `-2`, `-3`, and so on are added, so the name `Caliginia` gives
  `caliginia-2`.

Creating an agent is not idempotent: repeating a request without a code creates
another agent. After a lost response, list the agents to find out whether it
was created. Names need not be unique.

`PATCH` replaces only the given fields, trimmed, and stores the time of the
change as `updatedAt`, even when the values are unchanged. The body cannot
contain `code`, and an empty body returns `400`. `DELETE` removes the agent
permanently and returns `204` without a body. A conversation the deleted agent
answered keeps its messages and its agent code; see
[a conversation whose agent was deleted](#a-conversation-whose-agent-was-deleted).

`PATCH` or `DELETE` on a built-in agent changes nothing and returns `409` with
`Content-Type: application/problem+json`:

```json
{
  "type": "urn:lys:problem:agent:built-in",
  "title": "Built-in agent cannot be changed",
  "status": 409,
  "detail": "Agent caliginia is built in and cannot be changed or deleted.",
  "instance": "/api/v1/agents/caliginia"
}
```

A missing agent on GET, PATCH, or DELETE returns `404` with
`Content-Type: application/problem+json`:

```json
{
  "type": "urn:lys:problem:agent:not-found",
  "title": "Agent not found",
  "status": 404,
  "detail": "Agent web-researcher was not found.",
  "instance": "/api/v1/agents/web-researcher"
}
```

The chat endpoint returns the same problem, with `instance` `/api/v1/chat`,
when a new conversation names a code that no built-in or stored agent has.

A taken code returns `409` with the same media type, `type`
`urn:lys:problem:agent:code-taken`, `title` `Agent code taken`, and `instance`
`/api/v1/agents`.

### A conversation whose agent was deleted

A conversation keeps the code of the agent it was started with. When that
agent is deleted, the conversation stays stored and readable, but it accepts
no new message: the chat endpoint answers `409` with
`Content-Type: application/problem+json` before it stores anything, so the
conversation gains no message and no failed reply.

```json
{
  "type": "urn:lys:problem:conversation:agent-missing",
  "title": "Conversation agent missing",
  "status": 409,
  "detail": "The agent web-researcher that answers this conversation no longer exists.",
  "instance": "/api/v1/chat"
}
```

The conversation accepts messages again once an agent is stored under that
code, and that agent then answers it. Built-in agents cannot be deleted, so a
conversation a built-in agent answers never reaches this state.

## LLM metadata shape

`LlmInfo` currently includes:

- `modelKey`
- `format`
- `displayName`
- `path`
- `sizeBytes`
- optional `paramsString`, `architecture`, and `quantization`
- `vision`
- `trainedForToolUse`
- `maxContextLength`
- `loaded`

`GET /api/v1/llm/list` returns `llms` ordered by `modelKey`, then by `path`.

## Model load request

`POST /api/v1/llm/load` takes the model to load and, optionally, the settings
LM Studio loads it with:

```json
{
  "modelId": "google/gemma-4-12b-qat",
  "configuration": {
    "contextLength": 16384,
    "evalBatchSize": 512,
    "flashAttention": true,
    "offloadKVCacheToGpu": true,
    "numExperts": 4
  }
}
```

| Field                               | Type    | Meaning                                                           |
| ----------------------------------- | ------- | ----------------------------------------------------------------- |
| `modelId`                           | string  | Non-empty model key or alias that LM Studio resolves              |
| `configuration.contextLength`       | integer | Context window the model is loaded with, in tokens                |
| `configuration.evalBatchSize`       | integer | Prompt tokens evaluated together in one batch                     |
| `configuration.flashAttention`      | boolean | Whether the model is loaded with flash attention                  |
| `configuration.offloadKVCacheToGpu` | boolean | Whether the KV cache is kept in GPU memory rather than in RAM     |
| `configuration.numExperts`          | integer | Experts active per token; only mixture-of-experts models use this |

- `configuration` and each setting in it are optional. LM Studio decides every
  setting the request leaves out, so a request with only `modelId` loads the
  model with LM Studio's own settings.
- A request that sets `contextLength` also turns LM Studio's auto-fit off for
  that load. Auto-fit is LM Studio's own choice of context length and model
  placement from the available resources. The LM Studio SDK (2.0.0) sends it
  as off whenever a context length is set, and refuses the two together. The
  desktop sets a context length on every load it starts.
- Each integer is a whole number from 1 to 4,294,967,295.
- The backend answers `400` before starting a load when `configuration` is
  `null` or not an object, holds a setting other than the five above, or holds
  a value of the wrong type or outside the range.
- The backend does not compare `contextLength` with the model's
  `maxContextLength`. LM Studio decides what happens with a value the model
  cannot use.
- The settings apply to this load only. The backend does not store them.

The backend passes the settings to the LM Studio SDK's load call, which sends
each of them to LM Studio.

## Model operation admission

Inventory, health, load, unload, and LM Studio connection attempts share one
queue with one active operation and at most eight waiting. Accepted operations
execute in arrival order. When all nine positions are occupied, each of these
endpoints returns `503 Service Unavailable` with `Content-Type:
application/problem+json`:

```json
{
  "type": "urn:lys:problem:llm:service-busy",
  "title": "LLM service busy",
  "status": 503,
  "detail": "The LLM service queue is full. This operation was not accepted. Try again after pending model operations finish."
}
```

This response means the operation was never accepted and performed no runtime
work. The caller may submit it again after capacity becomes available. The backend
does not retry automatically or promise a retry time. A disconnected request that
was already accepted continues to occupy capacity until its operation settles.

## Model operation cancellation

`POST /api/v1/llm/load` and `PATCH /api/v1/llm/unload` do not support user
cancellation. After the backend accepts an operation, disconnecting the client
does not cancel it. Accepted operations remain owned by the backend until success
or failure, and shutdown waits for them before releasing runtime resources.

Model health checks follow the same completion-only lifetime as inventory:
disconnecting the client does not cancel an accepted query. The runtime's
inventory RPC has no enforced completion deadline, so an unresponsive engine
can keep the query and shutdown pending.

Chat inference is cancelled only by the reply-stop route or by backend
shutdown; closing a chat stream does not cancel it. A newer turn or a deletion
also ends a reply's inference, once the model sends its next content. A reply
waiting for a tool result writes nothing, so it is not ended this way
([#137](https://github.com/w3lt/lys/issues/137)). See the
[provider cancellation policy](/architecture/providers/#cancellation-policy).

## Model health responses

`GET /api/v1/llm/:modelId/health` checks whether a fresh, validated loaded-model
inventory contains the requested canonical model key. Encode the key as one
URL segment; for example, `provider/model` becomes
`/api/v1/llm/provider%2Fmodel/health`. The key must contain 1–100 decoded
characters, matching the router's existing path-parameter limit.

The check generates no text and never loads or unloads a model. `ready` means
the runtime answered and reported a matching loaded instance. It does not prove
that a subsequent inference will succeed. Results are observations of changing
runtime state and use `Cache-Control: no-store`.

Completed checks return `200 OK` with one of these JSON shapes:

```json
{
  "modelId": "provider/model",
  "status": "ready",
  "latencyMs": 4
}
```

```json
{
  "modelId": "provider/model",
  "status": "not-ready",
  "reason": "model-not-loaded",
  "latencyMs": 4
}
```

`model-not-loaded` covers both unknown keys and models without a loaded
instance. `runtime-unavailable` means the inventory could not be obtained or
validated, so loaded state could not be established. Internal failure details
are logged and excluded from the response.

`latencyMs` is a non-negative safe integer measuring the loaded-inventory query.
It excludes time waiting in the service queue and HTTP
transmission, and does not measure generation speed. A full queue returns the
`503` service-busy Problem Details response documented above; it is distinct
from an accepted check returning a negative observation.

## Model unload responses

The request body must contain only `modelId`, and its value must be a non-empty
canonical model key. Invalid bodies are rejected with `400 Bad Request` before
the backend accesses the LLM runtime.

`PATCH /api/v1/llm/unload` attempts every loaded runtime instance currently
observed with that model key. It returns `204 No Content` when a fresh
reconciliation snapshot contains no matching instance. This is an observation
of that snapshot, not a guarantee that another runtime client will not load a
new matching instance afterward. Expected failures use
`application/problem+json` with stable `type`, `title`, and `status` fields.
Operation failures include an occurrence-specific `detail`; admission refusal
uses the fixed four-field service-busy body shown above:

| Status | Problem type                              | Meaning                                                      |
| ------ | ----------------------------------------- | ------------------------------------------------------------ |
| `404`  | `urn:lys:problem:llm:model-not-found`     | No matching instance was initially loaded.                   |
| `503`  | `urn:lys:problem:llm:runtime-unavailable` | No LLM runtime is connected, or the backend cannot query it. |
| `503`  | `urn:lys:problem:llm:unload-failed`       | Reconciliation still found matching instances.               |
| `503`  | `urn:lys:problem:llm:service-busy`        | The shared queue is full; no unload was accepted.            |

Operation-failure bodies may also include an `instance` identifier for one
occurrence. The service-busy body has fixed `type`, `title`, `status`, and `detail`
fields and does not accept an `instance` field.
