Paths on this page use `$LYS_HOME` for the
[Lys home directory](/reference/configuration/#lys-home-directory): `~/.lys`
unless the `LYS_HOME` environment variable selects another directory.

## `$LYS_HOME/settings.json`

The desktop host owns a JSON settings file at `$LYS_HOME/settings.json`.

- created automatically when the file is missing
- stores the `runtime`, `model`, and `generation` groups described in
  [Configuration](/operate/configuration/)
- parsed as JSON on load and rewritten as pretty-printed JSON when the Tauri
  `save_settings` command is called

The desktop loads this file at initialization and autosaves generation edits.
That save path preserves the runtime and model groups already on disk; runtime
and model edits in the UI remain session-only.

## `$LYS_HOME/lys_db.sqlite`

The backend stores conversations in a SQLite database at
`$LYS_HOME/lys_db.sqlite`.

The database runs in write-ahead-log mode, so `lys_db.sqlite-wal` and
`lys_db.sqlite-shm` sit beside it. They usually remain after the app quits,
because the desktop stops the backend without a clean close, and
`lys_db.sqlite-wal` can then hold recent conversations that are not yet in
`lys_db.sqlite`. They are part of the database: copy, move, or delete all three
together, and only while the backend is stopped. A power loss or operating-system crash can lose the
last few writes; an application crash cannot.

The checked-in schema currently creates:

- `conversations`
- `conversation_messages`
- one index on `(conversation_id, created_at, id)`
- triggers that keep `conversations.updated_at` in sync

SQLite `PRAGMA user_version` tracks the applied migration level. On startup the
backend applies any missing forward migrations and refuses to open a database
whose version is newer than the binary understands.

## Lifecycle notes

- The settings file is created by the Tauri host on first settings load.
- The SQLite file is opened once by the backend's database owner when the
  backend's services start, before the conversation service is created.
- The backend does not create the Lys home directory. A standalone backend
  started with `pnpm backend:dev` uses `~/.lys`, which must already exist; the
  desktop creates the Lys home when initializing a missing settings file. See
  [Running Lys locally](/develop/running/).
- Both files live in the same Lys home directory, so user data and app settings
  currently share one root. Release builds also start their backend from the
  `runtime/` directory there.

## WebView theme storage

The desktop theme is stored separately from the Lys home directory under the
`lys.theme` WebView `localStorage` key. Its valid values are `dark` and `light`.

## What is not documented yet

The repository does not currently provide an evidenced contract for:

- exporting conversations to another format
- pruning or rotating stored conversation data
- relocating either file on its own; `LYS_HOME` moves both together
- moving existing files when `LYS_HOME` changes; Lys does not copy them, so an
  empty new directory starts with default settings and an empty database
- diagnostics bundles that package these files or projections of them
