The desktop application is a React app rendered inside a Tauri window. It owns
presentation state, not durable conversation storage.

## Main responsibilities

| Area                | Current implementation                                                                                                                                                                                                                             |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| App shell           | `App.tsx` swaps between chat and settings views and runs startup initialization.                                                                                                                                                                   |
| Chat UI             | `ChatView` renders the transcript, composer, jump-to-latest controls, and the past-conversations dialog.                                                                                                                                           |
| Message rendering   | `MarkdownMessage` renders assistant replies as Markdown with KaTeX math and highlighted, copyable code blocks.                                                                                                                                     |
| Chat state          | `src/lib/store/chat-view` owns the active conversation, the agent selected for a new one, request lifecycle, conversation opening, and error presentation.                                                                                         |
| History state       | `src/lib/store/conversation-history` owns the past-conversations dialog, its search and pages, and rename and delete calls.                                                                                                                        |
| Agent state         | `src/lib/store/agents` owns the list of built-in and stored agents, the Agents pane's editor and draft, and the agent create, update, and delete calls.                                                                                            |
| Tool state          | `src/lib/store/tools.ts` owns the Tools pane's list of every tool, the app's and the backend's, the session-only Tool calls switch, and the offer each request makes from them.                                                                    |
| Tool calls          | `src/lib/store/tool-calls` follows each running reply, shows the backend's approval prompts, runs the client tools' calls the backend sends, and sends every answer.                                                                               |
| Tool approvals      | `src/lib/store/tool-settings.ts` owns each tool's switch and its Ask me or Just run, saved as the `tools` group of `settings.json`, and their automatic save.                                                                                      |
| Shell/runtime state | `src/lib/store/index.ts` tracks which view is open, whether the backend and vmo run, and settings loaded from Tauri; `vmo-runtime.ts` owns vmo's state and its start and stop, and `runtime-autostart-settings.ts` saves the two startup switches. |
| Model lifecycle     | `src/lib/store/model-actions.ts` owns real inventory, load, unload, and health requests shared by settings and the composer.                                                                                                                       |
| SSE consumption     | `src/lib/apis/http/chat.ts` opens chat and reply-events SSE streams, validates events with Zod, and sends reply stops, approval answers, and tool results.                                                                                         |
| Theme               | `src/app/theme.ts` applies light or dark mode and stores the choice as `lys.theme` in WebView `localStorage`.                                                                                                                                      |

## Chat state split

The desktop currently has six separate state systems:

| Store                   | Owns                                                                                                                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chat Zustand store      | Active conversation, the agent selected for a new conversation, request and open tokens, local abort controllers, streamed reply parts and sources, the staged files and the last refusal of one, inline error text |
| History Zustand store   | Dialog visibility, search query, displayed conversation pages, the row being renamed or confirmed, pending renames and deletes                                                                                      |
| Agent Zustand store     | Every listed built-in and stored agent, the open editor or read-only view and its draft, the save attempt, the pending save or delete, the most recently saved agent                                                |
| Tool Zustand store      | The tool list read from the desktop and the backend, tool calls on or off, each tool's switch                                                                                                                       |
| Tool-call Zustand store | Every approval prompt and tool call held until the backend takes its answer, and the reply follows that deliver them                                                                                                |
| Shell Zustand store     | Active top-level view, loaded settings (each tool's saved approval included), backend process status, startup progress                                                                                              |

The transcript shown in the window is built from backend events for the current
request, or from the stored transcript read when a past conversation is opened.
Shell state such as backend status is managed independently.

## Streaming path

1. The composer calls `sendMessage`.
2. The chat store opens `POST /api/v1/chat`. The request offers the
   switched-on tools when tool calls are on and the loaded model was trained
   for tool use, and carries the staged files, each with its name and base64
   content; the tray loses them once the turn starts.
3. The desktop parses SSE frames with `EventSourceParserStream`.
4. Each payload is validated against `chatApiStreamEventSchema`.
5. The store applies `start-*`, `reply-part`, `reply-part-delta`, `sources`,
   `done`, `interrupted`, `title`, or `error` events to local immutable
   conversation state, and hands the reply to the tool-call store, which
   answers its `tool-approval` and `tool-call` events. A `reply-part` replaces
   the part with the same `id` or is added after the others, a
   `reply-part-delta` extends its part, and `sources` merge into the
   conversation's sources by number. When the reply ends, by any final event,
   its waiting and running calls are shown as stopped, as the backend stores
   them.

The composer shows Stop while the turn is awaited or the reply streams, and
Send otherwise. After `done`, `interrupted`, or `error`, the stream can stay
open for a title; sending the next message then stops following it, and the
backend still saves the title. The desktop then learns that title only from
the next turn's start event, from reopening the conversation, or from the
history dialog; delivering it live is tracked in
[issue #96](https://github.com/w3lt/lys/issues/96).

The desktop keeps no replay log and does not reconnect a dropped stream on its
own. Showing a conversation whose reply is still generating, after an open or a
failed open, follows that reply again from a stored `reply-snapshot`. Quitting
the app also ends the backend; a reply still generating then keeps its
persisted parts and is marked interrupted when the backend next starts.

## Context meter

The composer's context meter shows how much of the loaded model's context
window the next message would take. While the composer could send, the
`useChatContextMeasurement` hook asks
[`POST /api/v1/chat/context`](/reference/api/#chat-context-measurement) to
measure what sending would build: the shown conversation, or the agent a new
one would start with; the loaded model; and the tools the Tools pane would
offer, reading the tool list first when tool calls are on for a model trained
for tool use and the list was never read. It measures again when any of
those, or the shown conversation's stored messages, change; a newer
measurement abandons the older one, whose result is never shown. While a reply
is awaited or a conversation opens, nothing is measured and the meter keeps
its last numbers.

The backend counts the agent's system prompt, the offered tool definitions,
the stored messages a turn includes, and the markup around the new message
with the model's tokenizer; the composer adds an estimate of the trimmed
draft's text at 3.7 characters per token and the reply ceiling as the
reserve. The window is the context length the
model is loaded with. The panel lists, in send order, the agent instructions,
tool definitions, earlier messages, your message, the room left or the amount
over, and the reserve. While the request fits, the label counts what it takes
against the window. The bar fills with the request's share and then, striped,
with the reserve's share, and the panel names the striped part while it is
drawn. Counts carry
`~`. The meter never claims that earlier
messages are shortened or summarized: every round sends every message a turn
includes. Each staged image is counted as the backend counts a stored one,
`⌈width ÷ 28⌉ × ⌈height ÷ 28⌉` tokens up to 1,280; staged text files are not
counted, because the model reads them on request, and the panel says so while
one is staged.

Send is disabled while the current measurement, the draft, and the reserve
exceed the window. While a newer measurement is pending, before the first one
settles, and when the window cannot be measured (the model is not loaded in LM
Studio, LM Studio cannot be reached, or the request fails), the meter says so
and sending stays allowed, because the backend checks every round before sending
it. "Change the window" opens the Model pane, where the model's load
configuration sets the context length for its next load.

## Composer attachments

The composer's add menu and drops on the field stage files in the chat store,
which owns the tray (`lib/store/chat-view/attachments.ts`). A selection is
admitted in two steps, so a file is read only once its name and size pass: the
name must satisfy the shared attachment name rules and must not be staged
already, ignoring case, and a message carries at most 8 files of at most
10 MiB each and 20 MiB together, the limits of `@lys/share`. Each admitted
file is then read whole and classified from its bytes, as the backend
classifies it: an image (PNG, JPEG, or WebP) can be staged only while the
loaded model has `vision`, a text file only while it is trained for tool use,
and any other content is refused. Each file is admitted on its own, so a
refused file does not keep the others of its selection out. One refusal per
selection is reported in the status line under the tray, such as "The file
notes.md is already uploaded" or "Images need a model with vision": the first
refusal by name or size, else the first by content or by the loaded model; a
repeated refusal is announced again. A file that cannot be read keeps its
whole selection out of the tray, and its failure is the refusal reported. A
selection made before the conversation is reset or closed and not staged yet
is dropped: it joins no tray and reports no refusal. Selections are admitted
one after another, so a second drop is checked against the first. The tray shows each file's kind and name, and an image's
estimated tokens; a file can be removed from it.

Sending the draft sends the staged files with it and takes them out of the
tray once the turn starts; a file staged after Send was pressed stays. A
starter prompt is sent without the staged files, which stay staged, and a
request the backend refuses keeps them. Opening another conversation keeps the
tray; starting a new conversation clears it. A message still needs text:
files alone do not make it sendable. A long paste stays in the draft and is
sent as text; nothing turns it into a file. The transcript lists a message's
attachments under its text, by kind and name, from the turn-start event and
when the conversation is reopened.

## Assistant message rendering

`LysMessage` lays a reply out from its parts (`reply-presentation.ts`):

- **Reasoning**, when the reply has any: one disclosure, closed at first,
  labelled `Thinking` while the reply streams its reasoning and `Thought for
Ns` afterwards, the seconds the reasoning parts took. It holds every
  reasoning part's text.
- **Steps**: the rounds that called tools, in one disclosure, closed at first,
  labelled with the number of steps and tool calls and, once the reply ended,
  `Worked for Ns`: the time from the reply's start to the latest change of
  any of its parts. Time a call waited for approval counts. A call still
  open when the reply ended, because the person stopped it or the turn
  failed, counts until that end. A call that startup recovery interrupted
  keeps the time of its last change before Lys stopped, so time Lys spent
  closed is not counted. The steps are a list named `Steps`, and each step
  shows the text its round wrote and its calls, in a list named `Tool calls`.
  Each call (`ToolCallStep`) is a disclosure naming the tool, what the call is
  about (its first text argument), and its state: Waiting for approval,
  Running, Done, Failed, Rejected, or Stopped. Open, it shows the arguments
  as named values, or as written when they are not a JSON object, and the
  plain text of the result, labelled `Rejection` for a rejected call. The
  store parses a call's arguments once, when the call arrives
  (`reply-parts.ts`), not on every render.
- **Answer**: the text of the last round when that round called no tools,
  rendered as Markdown. While a round streams, its text is shown here until
  its calls arrive and move it into the steps.
- **Sources** (`ReplySourceList`), when there are any: the sources the
  answer cites, in the order it first cites them, under `Sources · N cited`,
  then, in a closed `N more` disclosure, the sources its succeeded calls found
  without citing, each with the tool that found it. With nothing cited there
  is no cited list, and the disclosure reads `Sources · N found`. Only the
  answer's `[n]` markers count as cited: a step's text shows no links. The
  cited numbers come from the same Markdown tree, parsed with the same
  syntax extensions, that the citation links are made from
  (`citation-markers.ts`), so a source is listed as cited exactly when a
  marker in the answer links to it. The sources are a plain group, not a
  landmark; the cited list is named by its heading.

Each disclosure's accessible name is its visible label followed by the
reply's position, such as `Thought for 3s, reply 2`, so the same control of
two replies has different names. A call's result, and its arguments when they
are shown as written, scroll within a bounded height; each is a focusable
region named by its label, its call, and its reply, such as `Result of
web_search night moths, reply 2`, which a keyboard reaches with Tab and
scrolls with the arrow keys.

A reply links and lists only the sources its model read: those its own
succeeded calls showed, and those the calls of an earlier completed or
interrupted reply showed. A failed reply is left out of later turns'
context, so the sources only it showed can be cited in that reply alone.

The transcript keys every message, the streaming reply included, by its
identifier, so when a reply ends the same elements update in place: the
disclosures the person opened stay open and focus stays where it was. A
reply whose own sources did not change is not rendered again when another
reply finds sources.

`MarkdownMessage` renders the answer with `react-markdown`. Each `[n]` marker
in prose, with `n` written without leading zeros, whose number is one of the
sources the reply may cite becomes a small numbered link to that source
(`markdown-citations.ts`), named `n, source: title`, which shows the source's
title and site while the pointer rests on it. Markers in code, math, links,
and link references, and markers of other numbers, stay as written; an
escaped marker such as `\[1\]` reads as the prose `[1]`, so it is linked and
counted. Links open in a new tab without a referrer. `remark-math` and `rehype-katex` render
`$…$` inline math and `$$…$$` display math with KaTeX, whose stylesheet
`src/index.css` imports.

Each fenced code block shows its language and a Copy button. Shiki
(`@shikijs/rehype`) highlights a block whose language it bundles, loading that
language's grammar the first time a reply uses it. Token colors are CSS
`light-dark()` pairs from the GitHub Light and GitHub Dark themes, so they
follow the app's `color-scheme` and change with the theme without highlighting
again. A block without a language, or in one Shiki does not bundle (names are
case-sensitive, so `TS` is not `ts`), is labelled `Text` and shown without
highlighting. Copy writes the block's plain text without its final newline,
never the highlighting markup.

Rendering is asynchronous. Until a message's first pass finishes, it shows
plain GitHub Flavored Markdown without citation links, link handling, math,
and code-block handling; the first
reply in a session also waits for Shiki to start. While a reply streams, the
previous rendering stays visible until the new text is processed.

## Conversation history

The Past conversations button in the composer, or Command+K or Control+K,
toggles a history dialog above the composer. Opening it reads the first page
of `GET /api/v1/conversations`, 30 entries at a time. Typing in the search
field reads again with the trimmed query after a 200 ms pause in typing, so
the backend receives one list request per pause rather than per keystroke.
Enter in the search field reads a search still waiting for that pause at once
and then opens its first row. Older pages load on request.
Rows can be renamed in place or deleted after confirmation through the
conversation `PATCH` and `DELETE` routes. While the backend is not running,
these actions fail inline without sending a request.

Closing the dialog cancels a pending list read and saves a changed title that
is still being edited. Renames and deletions already sent continue after the
dialog closes and record their outcome.

Choosing a row closes the dialog and opens that conversation. The chat store
first stops following any active reply, which keeps generating on the backend,
then reads `GET /api/v1/conversations/:conversationId`. The previous
conversation stays visible until the read succeeds, and no message can be sent
while it is pending. A missing conversation or failed read keeps the previous
conversation and shows an inline error. When the conversation then shown,
opened or kept, ends with a reply that is still generating, the chat store
follows it from a stored snapshot. The next message sends the opened
conversation as `{ kind: "existing", id }`, so the backend continues it. Deleting the conversation the
chat view presents, or learning that it no longer exists, resets the view to a
new conversation.

## Backend and LM Studio status

The shell store tracks three facts separately. The Tauri host reports whether
the backend process exists. The store reports the backend as `running` only
after `GET /api/v1/heath` answers: it checks every 250 ms, each check bounded
to one second, for up to 30 seconds, and shows **Backend not responding**
(`unresponsive`) when the process stays alive without answering. On the
backend card, the heading is a polite status region, "Backend status"; the
address and uptime line sits outside it, so the uptime is not announced every
second. Once the backend runs, the store reads `GET /api/v1/llm/runtime`,
joining the backend's startup attempt through
`POST /api/v1/llm/runtime/connect` while it is still `connecting`.

The Runtime pane's LM Studio card shows `unknown`, `connecting`, `connected`,
or `unreachable` with the address `127.0.0.1:1234`. Its **Refresh** button is
the only control that asks the backend to reconnect. A failed model request
re-reads the status, so a lost LM Studio appears as not reachable without
polling. The composer banner names the first missing prerequisite—the
backend, LM Studio, or model weights—and opens the settings pane that fixes
it. `initialize` shows the shell as soon as settings load; the backend and vmo
then start in the background, together and without waiting for each other,
each when its startup switch is on or the host already owns its process. A
vmo the host is still stopping, as after a window reload during Stop, is
joined instead: the card shows the stop, and vmo stays stopped whatever its
switch says.

## vmo status

vmo, the page reader `read_page` uses, has its own card in the Runtime pane,
under the backend card. The Tauri host owns the process; the store's vmo slice
owns what the card shows: `starting`, `running`, `stopping`, `stopped`, or
`unresponsive` (**vmo not responding**). A start asks the host to start vmo
unless it owns a running one, then checks every second for up to ten minutes,
long enough for a first start that pulls vmo's images; every start fetches the
reader image's `latest` tag. Each check reads the owned process first and asks
vmo's health route only while it runs, so a vmo that has already exited never
shows as `running`. The health route answers for whatever listens on vmo's
port, though: while the owned vmo is still starting, another vmo there, such as
one left by a Lys that died without quitting
([#202](https://github.com/w3lt/lys/issues/202)), makes the card say
`running`. vmo shows `stopped` when its process exits before it answers, and
`unresponsive` when it runs ten minutes without answering. A stop shows
`stopping` while vmo deletes its VMs, up to 60 seconds, and joins a stop
already in progress.

Start is offered only while vmo is stopped, and Stop while it runs or is not
responding, as on the backend card. Both cards' buttons show "Start" and
"Stop"; for assistive technology they are named "Start vmo" and "Stop vmo"
here, and "Start backend" and "Stop backend" on the backend card. The vmo
actions never reject: a kill after the stop timeout ("vmo didn't stop in time
and was killed. It may have left VMs running."), a failed start, and a failed
stop show as a problem line on the card until the next start or stop. The
heading, the address line, and the problem line form one polite, atomic status
region, "vmo status", that stays mounted, so a change of status and its
problem are announced as one message. After a failed start or stop the
store reads vmo's status again: while vmo's process is alive, running or still
stopping, or when its status cannot be read, the card shows **vmo not
responding** with the failure, so Stop stays offered and joins a stop in
progress; otherwise it shows **vmo stopped** with it.
Once vmo is `running`, the card stops checking, as the backend card does: a
vmo that stops answering later is noticed when a turn offers `read_page`.

The switches "Start it when Lys opens" and "Start vmo when Lys opens" change
the settings at once and save both to the `runtime` group of `settings.json`,
serialized with the other group saves; the latest switches win. A status line
under the two cards says "Lys couldn't save the startup switches. The next
launch follows the switches last saved; changing a switch tries again." when
the save fails. The line is a polite status region that stays mounted and
empties when a later save starts. Under each switch's heading, the line saying
what off means is the switch's accessible description. The switches are read
from disk at each launch and each window reload, so an unsaved switch applies
to no later session.

## Model settings

The shell store refreshes `GET /api/v1/llm/list` when LM Studio becomes
connected and on entry into settings while it stays connected. While LM Studio
is not connected, the model list is empty, model actions are disabled, and the
pane explains how to recover. A manual Refresh action picks up changes made in
LM Studio. Inventory metadata and each model's `loaded` flag drive the model
rows and composer menu; several models may be loaded at once.

Load sends `{ modelId, configuration }` to `POST /api/v1/llm/load`. Unload sends
`{ modelId }` to `PATCH /api/v1/llm/unload` and accepts its bodyless `204`
response. Both operations reconcile the inventory afterward, including when the
command fails, because a lost acknowledgement does not establish whether weights
changed. Requests are serialized locally and mutations are never retried
automatically.

### Load configuration

Every load the desktop starts, from the Runtime pane or from a model row, sends
that model's load configuration. The store builds it when the load is admitted:
each setting is the model's own stored value when it has one, then the stored
default's, then the committed default's, and the context length is lowered to
the model's `maxContextLength` from the inventory. Edits made while the load is in flight
do not change what it sent. The composer's "Load model" action opens the Model
pane and starts no load.

The Model pane's "load configuration" section edits the configuration of the
selected default model. With no default model selected it edits nothing, even
while a model is loaded, and asks to choose one; the selection lasts for the
session, so after a restart the section waits for a choice. It has five rows: context length, eval batch size, flash attention, KV cache on
GPU, and active experts. An edit is stored for that model only, applies to its
next load, and is saved automatically to the `models` part of the
`loadConfiguration` group of `settings.json`; the save keeps the `default` that
is in the file. Active experts reads "auto" until it is set, because LM Studio
reports no expert counts ([#144](https://github.com/w3lt/lys/issues/144)).

The store holds the per-model settings as a map keyed by model key. The file
keeps them as one `models` object, and only the Tauri settings adapter handles
that object: it builds the map when it loads the document and the object when
it saves it.

The backend does not report the settings a loaded model runs with
([#145](https://github.com/w3lt/lys/issues/145)), so the store keeps its own
record for each model it observes as loaded:

- For a model Lys loaded in this session, the record is the configuration that
  load sent. When the stored settings differ from it, each changed row shows
  the loaded value, and a line under the rows lists what a reload would apply.
- For a model found already loaded, the record is the configuration stored
  when it was first observed. It only shows whether the settings changed since.
  The pane then says that changes apply on the next load.

"Reload now" unloads the model and loads it again with its stored configuration,
as one operation. If the unload fails, no load starts. If the load fails after
the unload, the model stays unloaded and the failure is shown. Stopping the
backend or losing LM Studio discards the records.

Test calls `GET /api/v1/llm/:modelId/health` with the canonical key encoded as
one path segment. Its result reports a fresh loaded-state observation and query
latency, not inference success. The frontend validates responses against the
shared protocol and exposes request failures inline.

The application store owns requests across pane changes. Stopping the backend
invalidates pending observations before aborting their local HTTP transport;
a late response cannot restore obsolete residency. LM Studio owns weights
separately from the backend process, so a reconnect queries their actual state.
Until the inventory can be read again, the Runtime pane shows the model state
as unavailable rather than as no model loaded, and the Composer label keeps
naming the chosen default.

The Composer label, send eligibility, and chat request use that same compact
runtime projection. The [default-model setting](/reference/configuration/#persisted-settings-json)
defines the preference and fallback selection. A send is admitted only while
the backend is running and the projection is loaded. A submission rejected
because no model is eligible produces an inline chat error without discarding the draft or conversation;
Model settings provide inventory refresh and load controls for recovery. The
chat store samples that model key once at submission, so a later selection
change applies only to a later request.

## Generation settings

Generation edits apply to the next chat request. Temperature uses the API's
inclusive `0`–`1` range. The optional reply ceiling uses an on/off switch and
a token slider. Switching it off stores zero and omits `replyCeiling`
from the request, so the backend does not receive a zero-token limit.
Switching it back on restores the application default. The slider's usual
range ends at the `loadedContextLength` the inventory reports for the loaded
model, or at 32,768 tokens while none is known, and expands to include an
existing saved ceiling rather than silently clamping it.
The model's actual context capacity and stopping behavior still apply.

Generation edits automatically persist only the generation group through Tauri.
The store reads the existing settings document and preserves its runtime and
model groups before invoking `save_settings` with `{ newSettings }`. Saves
are serialized in the application store and continue across pane changes;
edits made during a write are coalesced into the latest settings and saved next.
Failures remain visible and can be retried or replaced by a newer edit; a
completion cannot overwrite newer edits or label those edits as saved. Future
messages use the latest settings, including after restart once the save completes;
already submitted requests keep their original settings. The read-modify-write operation
does not coordinate with external editors of the settings file.

## Agent settings

The Agents pane shows the built-in agents and manages the agents stored by the
backend through the
[agent API](/reference/api/#agents). It reads every built-in and stored agent
when it appears and whenever the backend starts running, the stored ones one
page of 50 after another,
because names are checked for uniqueness against all of them; a read stops
with a failure past 1,000 agents. The chat view reads the same list when it
appears and whenever the backend starts running. A displayed list stays on screen while it is
read again. A status line above the agents says why they are not shown: the
backend is not running, or a read failed, which offers Retry. When the status
appears because the control holding focus disappeared with the list or an
editor, focus moves to Retry or to the status line.

The pane lists the built-in agents first, in their own section, then the
user's agents oldest first, each with its name, code, and bio. A built-in
agent ships with Lys and cannot be changed or deleted: opening one shows its
name, bio, and system prompt read-only, with Duplicate, which opens a copy as
a new agent of the user's own.
Opening one of the user's agents reads it with its system prompt into an editor; New agent opens
an empty one. The editor edits the name, bio, and system prompt, and for a new
agent an optional code. The name, bio, and prompt are marked required, and the
code field states the format it accepts. Typed codes keep only lowercase
letters, digits, and single hyphens; `use name` fills the code from the name,
and an empty code lets the backend derive one. Limits come from `@lys/share`,
and the counters measure the trimmed text, as it is saved. Saving checks the
draft first: a blank name, bio, or prompt, a name or bio over its limit once
trimmed, a name another agent has (ignoring case), or a malformed or listed
code is shown and nothing is sent; built-in agents count among the listed
names and codes. Under the system prompt, of a built-in agent as of the
user's own, a measure states its length in characters, its tokens estimated
at 3.7 characters per token, and the share of the window they take: the
`loadedContextLength` the inventory reports for the loaded model, as the
composer's context meter uses. While no model is loaded, or the inventory
does not report its context length, the share is left out. Once the field is marked invalid, focus moves
to it. Names need not be unique to the backend, so a stored agent that keeps
its own name can be saved even when another agent shares it. The backend still
refuses a code taken since the list was read. Duplicate opens a copy as a new
agent under a free name, and Delete asks for confirmation.

The agent store owns the editor and every change, so a draft survives leaving
and returning to the pane, and a save or delete continues across pane changes.
Settled changes are applied to the displayed list; a list read still pending
is replaced, since it may answer from before the change. The same holds when an
agent being opened or saved turns out to be gone. A creation whose response is
lost may still have stored the agent, so the editor says the save could not be
confirmed and the list is read again; an agent that was stored then appears,
and its name and code count as taken. Saving is unavailable while the list is
read again, so a draft is never checked against a list that read may change.
Editing an agent changes its conversations from their next message, because
every turn sends the agent's current system prompt.

### Choosing a conversation's agent

The composer's agent menu, left of the weights menu, names the agent that
answers. Before the first message it lists the built-in agents, then the
user's own, each with its bio and tagged `selected` or `built-in`; choosing
one selects the agent of the new conversation, and Edit agents opens the
Agents pane. The chat store keeps the selection, which starts on Caliginia,
survives starting another conversation, and is not saved across restarts. A
selected agent that is no longer listed when the message is sent is replaced
by Caliginia.

Once a conversation is shown, or its first reply is awaited, its agent is
fixed: the menu shows a lock, says the agent stays for the whole conversation,
and offers Start a new one, which starts a new conversation and leaves the
menu open on the choices. The transcript tags every reply with the name of
the conversation's agent, and the message field, its placeholder, the
generating status, and the tool-call announcement name it too.

When the agent list has been read and no agent has the conversation's code,
its agent was deleted. The conversation stays readable, replies are tagged
with the code, the message field and Send are disabled, and a notice above
the field offers a new conversation. The notice's status line stays in the
page while it is empty, so the sentence is announced when it appears, and
focus stays where it is. New conversation in the notice starts a conversation
and moves focus to the message field once that conversation is shown, when
the field can take focus again. Start a new one in past conversations moves
focus the same way. While the list is unread the desktop does not claim a
deletion: sending stays possible, and the backend's refusal is shown as the
same sentence. A deleted agent's code is never free again, so its
conversations stay read-only; only a conversation whose agent was removed
before version 11 of the database accepts messages again once an agent is
stored under its code.

## Tool settings

The Tools pane lists Lys's tools. Client tools run in the desktop app and work
with files, the clock, and the saved location on the user's machine; the tool store reads them from the
[`list_tools` command](/architecture/host/#client-tool-list). Backend tools run
in the backend and reach the web; the store reads them from
[`GET /api/v1/tools`](/reference/api/#tool-list). Both lists are read when the pane
first appears, client tools first; a failed read of either list, or a name both
lists share, shows the failure above the pane with Retry. Tools are grouped by
their `group` (`files`, `web`, `time & place`), and each group says how many of
its tools are on.

Each row shows the tool's name, what it does with the machine (`reads` or
`network`), where it runs (`in Lys` for a client tool, `in backend` for a
backend tool), its description, an estimate of the tokens it adds to each
request, and a switch. The estimate measures the function tool a model receives, built
by `buildToolFunctionFormat` from `@lys/share`, with the composer's text
estimator, so it varies with the model's tokenizer. Expanding a row, one at a
time, shows the tool's arguments with their type and whether they are required;
an enum argument shows `enum · N` and its accepted values. It also shows where
the tool runs and whether Lys asks before it runs.

The tool-calls card holds the master switch and a status line. The status line
names the loaded model and how many tools are offered with their summed
estimate. When the loaded model's `trainedForToolUse` is false, Lys offers it
no tools: a card says the model isn't trained for tool calls, and every control
below it recedes and is disabled. An expanded row closes while the controls are
locked and opens again when they unlock.

Tool calls on or off and each tool's switch apply to the next chat request,
because they decide only which tools a request offers; switching a tool off
while a reply runs does not stop that reply's calls. A tool that only reads
this machine starts on; a tool that sends requests off the machine (`network`)
starts off. Switching a tool saves its choice in the `tools.switches` object
of `settings.json`, alongside its approval, so it holds after a restart; a
tool the person never switched has no entry and stays at its default, also
when a later build adds it. The Tool calls switch lasts for the session
only.

Every tool, network tools included, offers both approvals and starts on Ask
me. The note under "Before it runs" says what each does: on Ask me, "Each call
waits for you with its arguments. Nothing runs until you allow it."; on Just
run, a tool that only reads this machine "Runs the moment the model asks,
without showing you the call.", and a `network` tool "Sends its request off
this machine the moment the model asks, without showing you what it sends."
Choosing Just run saves the tool's name in the `tools.justRun` list of
`settings.json`, and choosing Ask me removes it, so the approval holds after a
restart. The application store owns that list and the switches: a change
shows at once and is saved automatically, serialized with the other group
saves. The backend reads the saved list when each round of tool calls arrives,
so an approval applies from the next round once it is saved. A status line
under the tools says "Saving tool choices…" while a save runs; when one fails,
it says that each switch applies until Lys quits but Just run keeps following
the choices last saved until a save works, and offers Retry saving. A name
that Lys does not list now, such as a backend tool whose list could not be
read, is kept and has no effect.

A backend tool that cannot run now, such as `web_search` without a saved
Tavily API key or `read_page` while vmo is not ready, keeps its row: its
switch is disabled and shows off, a note under the row says why and what to
do. For `read_page` it says "vmo, Lys's page reader, isn't ready. See
Settings → Runtime." While the app shell is mounted, the tool store reads a
list it has already read again whenever the backend starts running, or vmo
becomes running, stopped, or not responding while the backend runs, so the row
locks and unlocks without waiting for a refused request; the new read starts
after any read in flight. A list never read is left for whoever needs it
first. For a missing key it says "Needs a
Tavily API key. Add one in Settings → Secrets." and Open Secrets selects the
Secrets pane. For a key in `settings.json` that isn't valid, or a settings file
that cannot be read, it says to fix `secrets.tavilyApiKey` or the file by hand
and shows no button: the host cannot load either file at startup, and a save
from the pane would replace the file with the settings loaded earlier. The
person's choice is kept and applies again once the tool can run; group counts
and the offered totals count only tools that are on and can run.

Below the tools, a "your location" section holds the location `get_location`
returns: City, Region, and Country fields, each labelled, described by the
hint "Each field is optional and holds up to 100 characters.", and filled
with the saved location. The section stays shown while the tools are read or
cannot be read, and the tool lock does not apply to it. Enter or Save stores
the trimmed fields, a blank field as `null`, only when they are valid and
differ from the saved location; emptying every field and saving removes the
location, and Escape discards the edit. Fields changed while a save runs
keep that newer edit once the save succeeds. A field whose text is too long or
holds a control character is marked invalid and described by what to change.
A polite status line says first that a save runs or failed, which keeps the
edit; otherwise that the edit is invalid or unsaved; otherwise whether a
location is saved. The application store's location slice owns the save,
serialized with the other group saves, and changes its location only once the
file holds the new one, because the tool reads the file.

## Secrets

The Secrets pane holds the keys of the services Lys calls on the person's
behalf; today one card, Tavily, the service `web_search` sends queries to.
The card shows the service's state (`no key`, `in use`, `verified` after an
accepted check, or `rejected`), an API key field with a show button and a
link to Tavily's key page, Save, and, once a key is saved, Test and Remove.

The field is a password field, starts empty, and shows the saved key masked as
its placeholder (its first 5 and last 4 characters for a key of 16 or more
characters). Typing makes a draft; Save, or Enter, saves a draft that is a
valid key different from the saved one, after removing surrounding whitespace,
and Escape discards it. An invalid draft says why and cannot be saved. A save
replaces only the `secrets` group of `settings.json`, serialized with the other
group saves; Remove saves `null`. After a save or removal, the pane reads the
tool list again, so `web_search`'s availability in the Tools pane follows the
key. Test asks the backend to check the saved key with Tavily and shows the
result, with the plan's credits when Tavily reports them. Test is unavailable
while a check or a save runs, so a check never reports on a key that a running
save or removal is replacing. The application store owns the save and the
check; a check that finishes after a newer save is dropped. The status line is
a polite live region that describes the field.

## Tool calls

A chat request offers the switched-on tools when tool calls are on and the
loaded model's `trainedForToolUse` is true: client tools by their definitions,
backend tools by name in `backendToolNames`, leaving out every backend tool
that cannot run now. For such a model it also names, in
`switchedOffToolNames`, every listed tool whose switch is off, and, in
`unavailableTools`, every switched-on backend tool that cannot run now with
the list's reason, so the backend can tell the model why a tool it needs
cannot be used instead of letting it guess. While tool calls are off, the
request names no tool and sends `areToolCallsSwitchedOff` instead, without
reading the tool list, so the backend tells the model tool calls are off. If
the tool list cannot be read while tool calls are on, the request fails with
an inline error and nothing is sent. A model that is not trained for tool use
gets none of these fields. The composer's context meter measures the same fields. When the backend still refuses an offered
tool that cannot run (its key was removed since the list was read), the request
fails with an inline error that says which tool and what to do, and the tool
list is read again so the next request leaves the tool out.

The backend's tool approval service decides which calls need the person: every
call of a tool that is not saved as Just run, client and backend tools alike,
except `read_attachment` and the agent state tools, which run without
approval (see the
[backend's tool approval](/architecture/backend/#tool-approval)). The
desktop does not decide; it reads neither the switches nor the saved Just run
list when a call arrives.

The tool-call store follows every reply the chat store starts or follows on
its own reply-events connection, so tool calls keep moving while another
conversation is shown. It takes each prompt from a `tool-approval` event or the
snapshot's `pendingToolApprovals`, and each call to run from a `tool-call`
event or the snapshot's `pendingToolCalls`, once. A held call keeps its step,
approval or run, so a client tool's prompt and its later run request share one
identifier, and an answered call stays held while the store follows its reply,
so a snapshot built before the answer arrived does not bring it back:

1. A prompt the desktop cannot show (a tool it does not list, or arguments it
   cannot describe) is answered `showFailed` at once. A backend tool's call is
   checked too, so the card never describes a URL or a query the backend would
   not send; a query holding a character hidden on screen is refused by the
   same rule the backend applies.
2. Every other prompt waits for the person.
3. A call to run is run at once and its result sent; a call the desktop
   cannot run is answered `runFailed`. Nothing is shown. The desktop does not
   check that the person allowed the call, so a call that another local
   caller allowed through the backend runs too, in place of its card (see
   [Candid limits](/architecture/security/#candid-limits) and
   [#171](https://github.com/w3lt/lys/issues/171)).

A waiting call shows a card above the composer field: the tool, what it does
with the machine, where it runs, a plain sentence such as "Read
/Users/me/notes/todo.md. Nothing is changed.", "Read the location you saved in
Settings → Tools. Nothing is changed.", "Read
https://example.com/page.", with the full URL,
or "Search the web for “latest Node.js release”. Sends the query to Tavily
(api.tavily.com).", with the full query, and its arguments on request. Reject sends the composer's text as the reason;
Allow once answers `allowed`, after which the backend runs its tool or sends a
client tool's call back to run; Allow anyway does the same while keeping the
text. In the field, Escape rejects,
Enter with an empty draft allows, and Enter with text rejects with that text.
Several calls wait in the model's order, one card at a time.

A read sends the file's text, a search sends its report as JSON, and a
declared tool failure sends the failure as JSON. A backend tool's result goes
from the backend to the model; the desktop receives it only as part of the
stored call, in a `reply-part` event while the reply streams and in the
reply's parts of a `reply-snapshot` or of the stored conversation, and shows
it in the reply's steps.
Approval answers go
to the [tool-approval route](/reference/api/#tool-approvals) and results to
the [tool-result route](/reference/api/#tool-results). When an answer cannot
be sent, the card says so and Try again sends the same answer without running
the tool again. An allowed answer still in flight when the call's run request
arrives does not hold the run back. When the reply ends, by finishing, Stop, or backend shutdown, its
waiting calls disappear. A newer turn in the conversation or deleting the
conversation does not end a waiting reply yet
([#137](https://github.com/w3lt/lys/issues/137)). After a renderer reload, a
call still waiting is found again through the reply's snapshot when its
conversation is shown. Quitting the app stops the backend, so its waiting calls
are gone and the reply is marked interrupted when the backend next starts.

## Current limitations

- Runtime edits other than the two startup switches remain session-only.
  Generation settings, load configurations, and the startup switches save
  automatically; a failed save leaves the edits available for the current
  session.
- The vmo card stops checking once vmo is `running`, so a vmo that crashes
  later still shows `running` until it is stopped or restarted; `read_page`
  is then refused when a turn offers it, and the tool list is read again.
- The context meter measures again only when its inputs change, so a
  measurement that failed while the model-operation queue was busy stays
  unknown until the conversation, the model, or the tools change.
- The KV cache load setting has no effect with the installed LM Studio SDK; see
  the [load request](/reference/api/#model-load-request).
- Model observations refresh on LM Studio connection, entry into settings,
  manual refresh, and model operations. The LM Studio status changes only on
  backend start, Refresh, and failed model requests; it is not polled. Changes
  made by another LM Studio client between observations are not pushed to the
  desktop.
- The composer's attachment tray takes only files the loaded model can use: an
  image only for a model with vision, a text file only for one trained for
  tool use, and nothing while no loaded model is listed. An image pasted from
  the clipboard is not staged; images are chosen or dropped as files. The
  transcript shows an attachment's kind and name only, without a preview or a
  way to open it.
- The Tavily API key is stored as plain text in `settings.json`, protected
  only by the file's owner-only permissions; there is no keychain storage.
- The Tool calls switch lasts for the session only; after a restart it is on
  again. Each tool's switch and approval are saved.
- There is no "Allow for this chat": each call on Ask me is asked about.
- Switching a tool or tool calls off does not stop a reply already running;
  it applies from the next message.
- The reply's steps show each call's result as plain text only; no tool has
  a view of its own. The reasoning summary shows `Thinking` without a running
  count of seconds, and a citation's hover shows the source's title and site,
  not the passage it supports.
