The current backend surface is small and lives entirely under the `@lys/protocol`
route definitions.

## Routes

| Method   | Path                                                                              | Request body                                                                                         | Response                                                               |
| -------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `GET`    | `/api/v1/heath`                                                                   | none                                                                                                 | `{ ok: true }`                                                         |
| `GET`    | `/api/v1/llm/list`                                                                | none                                                                                                 | `{ llms: LlmInfo[] }`                                                  |
| `GET`    | `/api/v1/llm/:modelId/health`                                                     | none                                                                                                 | Loaded-state health observation                                        |
| `POST`   | `/api/v1/llm/load`                                                                | `{ modelId: string, configuration?: ModelLoadConfiguration }`                                        | `LlmInfo`                                                              |
| `PATCH`  | `/api/v1/llm/unload`                                                              | `{ modelId: string }`                                                                                | `204` or typed Problem Details                                         |
| `GET`    | `/api/v1/llm/runtime`                                                             | none                                                                                                 | `{ status: "connecting" \| "connected" \| "unreachable" }`             |
| `POST`   | `/api/v1/llm/runtime/connect`                                                     | none                                                                                                 | Settled `{ status }`, or service-busy Problem Details                  |
| `GET`    | `/api/v1/conversations`                                                           | none; optional `query`, `cursor`, `limit` query parameters                                           | Conversation list page                                                 |
| `GET`    | `/api/v1/conversations/:conversationId`                                           | none                                                                                                 | Conversation with ordered messages and numbered sources                |
| `PATCH`  | `/api/v1/conversations/:conversationId`                                           | `{ title: string }`                                                                                  | Conversation metadata                                                  |
| `DELETE` | `/api/v1/conversations/:conversationId`                                           | none                                                                                                 | Bodyless `204`                                                         |
| `GET`    | `/api/v1/agents`                                                                  | none; optional `cursor`, `limit` query parameters                                                    | Built-in agents and a page of stored agents                            |
| `POST`   | `/api/v1/agents`                                                                  | `{ code?, name, bio, systemPrompt }`                                                                 | `201` agent with `Location`, or `409` Problem Details                  |
| `GET`    | `/api/v1/agents/:agentCode`                                                       | none                                                                                                 | Agent with its system prompt                                           |
| `PATCH`  | `/api/v1/agents/:agentCode`                                                       | at least one of `{ name, bio, systemPrompt }`                                                        | Changed agent, or `409` for a built-in agent                           |
| `DELETE` | `/api/v1/agents/:agentCode`                                                       | none                                                                                                 | Bodyless `204`, or `409` for a built-in agent                          |
| `GET`    | `/api/v1/tools`                                                                   | none                                                                                                 | `{ tools: ToolDefinition[], unavailableTools }`                        |
| `POST`   | `/api/v1/tools/web_search/key-check`                                              | `{}`                                                                                                 | `{ status: "accepted" \| "rejected" \| "unavailable" \| "failed", … }` |
| `POST`   | `/api/v1/chat`                                                                    | `conversation`, `message`, `model`, required `generationOptions`, optional `tools` and `attachments` | `text/event-stream`                                                    |
| `POST`   | `/api/v1/chat/context`                                                            | `conversation`, `model`, optional `tools`                                                            | `ChatContextMeasurement`, or typed Problem Details                     |
| `GET`    | `/api/v1/chat/:conversationId/replies/:assistantMessageId/events`                 | none                                                                                                 | `text/event-stream` (reply snapshot, then live events)                 |
| `POST`   | `/api/v1/chat/:conversationId/replies/:assistantMessageId/stop`                   | none                                                                                                 | Bodyless `204`, or `409` Problem Details                               |
| `POST`   | `/api/v1/chat/:conversationId/replies/:assistantMessageId/tool-results/:callId`   | `{ status, reason?, content? }`                                                                      | Bodyless `204`, or `409` Problem Details                               |
| `POST`   | `/api/v1/chat/:conversationId/replies/:assistantMessageId/tool-approvals/:callId` | `{ status, reason?, content? }`                                                                      | Bodyless `204`, or `409` Problem Details                               |

`/api/v1/heath` is the current spelling in both the shared protocol package and
the Fastify route registration.

List, load, health, unload, and chat-context requests, and a chat request
that reads a model's capabilities for an attachment, answer `503` with
`urn:lys:problem:llm:runtime-unavailable` while the backend has no connected
LM Studio runtime. The runtime-status route never contacts LM Studio; the
runtime-connect route waits for one shared connection attempt.

Every request body is limited to 1 MiB (1,048,576 bytes), Fastify's default,
except a tool result, which is limited to 8 MiB (8,388,608 bytes) so that a
1 MiB file read still fits after JSON escaping, and a chat request, which is
limited to 32 MiB (33,554,432 bytes) so that a message can carry its
attachments. A larger body is refused with
`413 Payload Too Large` before the route runs, so nothing is stored or
changed. The response is Fastify's JSON error body, with
`code` `FST_ERR_CTP_BODY_TOO_LARGE`, not Problem Details.

## Chat request body

```json
{
  "conversation": {
    "kind": "existing",
    "id": "0198f5a5-7b9b-7e0b-9b0f-87d9d6a5f72d"
  },
  "message": "Tell me what changed",
  "model": "google/gemma-4-12b-qat",
  "generationOptions": {
    "temperature": 0.7,
    "replyCeiling": 2048
  },
  "attachments": [{ "name": "notes.md", "content": "SGVsbG8sIHdvcmxkIQ==" }]
}
```

`conversation` names the conversation the turn starts or continues; its `kind`
selects one of two forms:

- `{ "kind": "new", "agentCode": "caliginia" }` starts a new conversation,
  created before the first stream event, that the named agent answers: a
  built-in agent (`caliginia`, `lysiptera`) or a stored one. A valid code that
  no agent has returns the agent-not-found Problem Details response below with
  `404`, and nothing is stored.
- `{ "kind": "existing", "id": "<UUIDv7>" }` continues a stored conversation
  with the agent it was started with, so it names no agent. An unknown
  identifier returns the conversation-not-found Problem Details response below.
  A stored conversation whose agent no longer exists, as after that agent was
  deleted, returns `409` with `urn:lys:problem:conversation:agent-missing`,
  and nothing is stored; see
  [a conversation whose agent was deleted](#a-conversation-whose-agent-was-deleted).

The agent is looked up when the request arrives and again when the turn is
stored, after its attachment files are written, so a conversation or agent
deleted in between gets the same `404` or `409` problem, and the written
files are deleted again.

`message` and `model` must be non-empty strings. Every turn sends the system
prompt its agent has when the turn starts, so editing a stored agent changes
its conversations from their next message. Continuation
uses the system prompt of the conversation's agent, prior user messages, the
rounds of completed and interrupted replies, then the current user message
exactly once. Each round sends its text and the tool calls that have a
result, followed by those results; reasoning and calls without a result are
never sent back, and a round with neither text nor such a call is left out.
Failed replies are excluded from context. A reply still streaming in the
conversation becomes interrupted when the new turn is created, so its partial
rounds are included.

`generationOptions` is required and has no protocol-level default:

| Field          | Accepted value                                  | Effect                                                                  |
| -------------- | ----------------------------------------------- | ----------------------------------------------------------------------- |
| `temperature`  | Required number from `0` through `1`, inclusive | Forwarded as the completion sampling temperature.                       |
| `replyCeiling` | Optional non-negative integer, in tokens        | Forwarded as `max_completion_tokens`; omission becomes `null` upstream. |

Both numeric fields use number coercion before validation. The request, its
`conversation`, and the generation-options objects reject unknown fields, so a
`conversation` with both an `id` and an `agentCode`, or a top-level
`conversationId` as earlier versions sent, is rejected with `400`. Missing
required options or invalid values are rejected with `400` before generation. The desktop translates
a saved zero reply ceiling into omission; API callers should omit the field for
that behavior, since an explicit API value of `0` is forwarded unchanged. These
controls affect chat completion; title generation uses a separate request.

### Attachments

`attachments` is optional. When present it lists 1 to 8 files sent with the
message, each with its `name` and base64 `content`, in the order the person
attached them. A name is non-empty, neither `.` nor `..`, holds no `/` and no
control character (NUL included), has at most 255 UTF-8 bytes, and appears
once in the request ignoring case, which folds `ß` and `SS` together; the
files decode to at most 10 MiB each and 20 MiB together. The route accepts
bodies up to 32 MiB and answers a larger one with `413`; every other route
keeps its own limit, listed above. A request that breaks these rules
is rejected with `400` before anything is stored. The limits are constants of
`@lys/share` (`MAXIMUM_ATTACHMENT_BYTES`, `MAXIMUM_MESSAGE_ATTACHMENT_BYTES`,
and `MAXIMUM_MESSAGE_ATTACHMENT_COUNT`), which the desktop applies before it
sends.

What a file is comes from its bytes, never from its name: a PNG, JPEG, or
WebP file with a readable header is an image, bytes that decode as UTF-8
without a NUL character are a text file, and anything else returns `400` with
`urn:lys:problem:chat:attachment-unsupported`; see
[an attachment Lys cannot send](#an-attachment-lys-cannot-send). When the
request or the conversation holds an attachment, the route reads from LM
Studio's inventory whether `model` has `vision` and `trainedForToolUse`, so a
full model-operation queue answers `503` with
`urn:lys:problem:llm:service-busy` and a missing runtime `503` with
`urn:lys:problem:llm:runtime-unavailable`, nothing stored; a request without
attachments in a conversation without any never reads the inventory. An
image attached for a model without vision, or for a model the inventory does
not list, returns `409` with `urn:lys:problem:chat:image-needs-vision`; see
[an image for a model without vision](#an-image-for-a-model-without-vision).

The files are written under
`$LYS_HOME/attachments/<conversation id>/<message id>/<name>` before the turn
is stored, and the stored user message carries each file's record, numbered
after the conversation's earlier attachments. Every turn sends the model each
user message's text followed by the list of its files; a model with vision
gets each image with its message, on every turn; a model trained for tool use
is offered `read_attachment` while the conversation holds a text file, and
reads it in parts when it needs it. See
[attachments](/architecture/backend/#attachments).

### Tools

A request can offer the model the client's tools and the backend's tools for
this turn:

```json
{
  "tools": {
    "definitions": [
      {
        "name": "read_text_file",
        "description": "Read one UTF-8 text file and return its complete text.",
        "group": "files",
        "access": "reads",
        "runner": "client",
        "arguments": [
          {
            "type": "string",
            "name": "path",
            "description": "Absolute path of the file.",
            "required": true
          }
        ]
      }
    ],
    "backendToolNames": ["read_page"]
  }
}
```

`definitions` lists the client's switched-on tools, each name once, in the
shape `toolDefinitionSchema` from `@lys/share` validates, each with `runner`
`client`; it may be empty. `backendToolNames` names switched-on tools the
backend runs, each once, as [`GET /api/v1/tools`](#tool-list) lists them; it is
optional. Together they offer at least one tool, and no name appears in both.
A request that breaks these rules, names a backend tool the backend does not
run, or offers `read_attachment` as a client or backend tool, returns `400`
before anything is stored; the backend adds the reader to a turn itself. A
request that offers a
backend tool that cannot run now, such as `web_search` without a usable
Tavily API key or `read_page` while vmo is not ready, returns `409` with
`urn:lys:problem:chat:backend-tool-unavailable` before anything is stored; see
[an offered tool that cannot run](#an-offered-tool-that-cannot-run). The model is offered client
tools first, then backend tools, each in request order. Without `tools`, the
turn is one round with no tools. The desktop sends `tools`
only to a model whose `trainedForToolUse` is true; the backend does not check
this itself ([#135](https://github.com/w3lt/lys/issues/135)). A reply can make any number of tool calls
([#136](https://github.com/w3lt/lys/issues/136)).

### Tools the turn does not offer

A request can tell the backend about the tools it does not offer, so the
model can say why a tool it needs cannot be used instead of guessing what the
tool would return. With tool calls on, it names the tools the person switched
off and the switched-on backend tools that cannot run now:

```json
{
  "switchedOffToolNames": ["get_location", "search_files"],
  "unavailableTools": [{ "name": "web_search", "reason": "api-key-missing" }]
}
```

With tool calls off, it says only that:

```json
{ "areToolCallsSwitchedOff": true }
```

All three fields are optional:

- `switchedOffToolNames` lists 1 to 64 tool names, each once, in the tool
  name format. A name the backend does not list is allowed.
- `unavailableTools` lists 1 to 64 backend tools, each once, in the shape
  [`GET /api/v1/tools`](#tool-list) lists them in its `unavailableTools`: a
  `name` and a `reason`, one of `api-key-missing`, `api-key-invalid`,
  `settings-unreadable`, and `page-reader-not-ready`. A name the backend does
  not run returns `400`. The reason is the client's reading of the tool list;
  the backend does not check it again.
- `areToolCallsSwitchedOff` is `true` or absent; absence means tool calls are
  on. A request that sends it offers no `tools` and names nothing in
  `switchedOffToolNames` or `unavailableTools`.

A tool appears at most once across `tools`, `switchedOffToolNames`, and
`unavailableTools`, and neither list names `read_attachment`, which has no
switch and which the backend adds to a turn itself. A request that breaks
these rules returns `400` before anything is stored.

Every round of the turn sends the agent's system prompt followed by the notes
these fields call for, each after a blank line:

- with `areToolCallsSwitchedOff`, one note saying tool calls are turned off in
  Settings → Tools, and asking the model to say so, and that they can be
  turned on there, when a request needs a tool it is not offered;
- otherwise, a note naming the switched-off tools in request order, asking
  the model to say a needed one is turned off and can be turned on in
  Settings → Tools, then a note naming each unavailable tool in request order
  with why it cannot run and what fixes it: a Tavily API key to add in
  Settings → Secrets, a key to fix or remove as `secrets.tavilyApiKey` in
  `settings.json`, a `settings.json` to fix by hand, or vmo to start in
  Settings → Runtime.

Each note asks the model not to guess what a tool would return or claim to
have used it. A call the model still makes to a named tool, or to any tool it
is not offered while tool calls are off, is neither asked about nor run, even
when the turn offers no tool: its step fails with a result saying the tool is
turned off, that tool calls are off, or that it cannot run now and why, which
the model reads in the next round. A call of an unknown name in a turn that
offers no tool and names none still fails the reply.

The desktop sends these fields only to a model whose `trainedForToolUse` is
true. With tool calls on, it names every listed tool whose switch is off, and
every switched-on backend tool the list reports as unable to run, with the
list's reason. With tool calls off, it sends `areToolCallsSwitchedOff` without
reading the tool list. `read_attachment` is still offered while the
conversation holds a text file.

## Chat response shape

Accepted chat turns respond as SSE. A missing conversation, a new
conversation naming a code no agent has, a stored conversation whose agent no
longer exists, an offered backend tool that cannot run now, an attachment Lys
cannot send, an image for a model without vision, or a model-capability read
LM Studio cannot answer returns JSON Problem Details before the stream
starts, and nothing is stored or written: no message, no file, and no failed
reply. Each event payload must match one of
the eleven variants documented in [SSE events](/reference/sse-events/).

Closing a chat stream stops only that client's observation. The backend keeps
generating and storing the reply and its title. To stop a reply, send
`POST /api/v1/chat/:conversationId/replies/:assistantMessageId/stop`; it
answers `204` after the reply is stored final (`interrupted`, or `completed`
or `failed` when the reply ended before the stop) and does not cancel title
generation. When no
generation is running for the reply it answers `409` with
`urn:lys:problem:chat:reply-not-generating`.

To follow a reply again, open
`GET /api/v1/chat/:conversationId/replies/:assistantMessageId/events`. Its
first event is a `reply-snapshot` with the stored reply, the conversation
title, and the conversation's sources; live events follow while the
generation runs. A missing conversation
returns the conversation-not-found problem and a missing reply returns `404`
with `urn:lys:problem:chat:reply-not-found`.

## Chat context measurement

`POST /api/v1/chat/context` reports how much of the loaded model's context
window a conversation takes before its next message. The composer's context
meter calls it; nothing is stored and the model generates nothing.

```json
{
  "conversation": {
    "kind": "existing",
    "id": "01992f3a-5b6c-7d8e-9f01-23456789abcd"
  },
  "model": "google/gemma-4-12b-qat",
  "tools": { "definitions": [], "backendToolNames": ["web_search"] }
}
```

`conversation`, `model`, `tools`, `switchedOffToolNames`, `unavailableTools`,
and `areToolCallsSwitchedOff` follow the
[chat request body](#chat-request-body); there is no `message` and no
`generationOptions`. The backend builds the context a turn's first round would
send, with an empty new message in place of the text: the answering agent's
current system prompt, followed by the notes about the
[tools the turn does not offer](#tools-the-turn-does-not-offer) when the
request names any or switches tool calls off, the
stored messages a turn includes, the empty message,
and the tools a turn would offer, client tools first, then the backend's,
then `read_attachment` when the conversation holds a text file for a model
trained for tool use. It counts them with the loaded model's tokenizer and
answers `200`:

```json
{
  "contextLength": 8192,
  "systemPromptTokens": 2268,
  "toolTokens": 412,
  "historyTokens": 1032,
  "historyMessageCount": 4,
  "messageMarkupTokens": 8
}
```

| Field                 | Meaning                                                                       |
| --------------------- | ----------------------------------------------------------------------------- |
| `contextLength`       | Context length the model is loaded with; the smallest of its loaded instances |
| `systemPromptTokens`  | Tokens of the agent's system prompt, with the notes about unoffered tools     |
| `toolTokens`          | Tokens of the offered tool definitions; `0` when none are offered             |
| `historyTokens`       | Tokens of the stored messages the next turn would include                     |
| `historyMessageCount` | Number of those messages                                                      |
| `messageMarkupTokens` | Tokens the new message takes without its text; a client adds the text's count |

- Each count is the text's tokens plus a fixed allowance for the chat
  template's markup: 8 tokens per message, 16 per tool call of an earlier
  round, and 160 once when tools are offered. The backend does not render the
  model's template.
- Messages a turn leaves out, failed and empty replies, are not counted.
- A stored user message is measured with its attachment list and, when the
  model sees images, with its images, each counted from its stored sides as
  `⌈width ÷ 28⌉ × ⌈height ÷ 28⌉` tokens up to 1,280. The measurement only
  checks that each image's file is still on disk, without reading it; an
  image whose file is gone is measured as the placeholder sentence a turn
  sends instead. When a stored message
  holds a text file and the model is trained for tool use, `read_attachment`
  is measured after the offered tools, as a turn offers it. Whether the model
  sees images and is trained for tool use is read from the inventory only
  when a stored message has an attachment. A client adds the same estimate
  for each image it would send.
- An offered backend tool is measured whether or not it can run now; the chat
  request refuses one that cannot.
- The model is matched like a chat request names it: by its model key, as LM
  Studio lists it. A model that is not loaded is never
  loaded; the route answers `503` with `urn:lys:problem:llm:model-not-loaded`.
- The measurement runs through the
  [model operation queue](#model-operation-admission), so it waits behind a
  load in progress, and a full queue answers `503` with
  `urn:lys:problem:llm:service-busy`.
- A new conversation naming an unknown agent, a conversation that is not
  stored, and a conversation whose agent was deleted get the same `404` and
  `409` problems as the chat request. A backend tool name the backend does not
  run is refused with `400`.
- Every response carries `Cache-Control: no-store`.

The chat request makes the same measurement before every round of a reply; see
[the context window check](/architecture/backend/#context-window-check).

## Tool list

`GET /api/v1/tools` lists every tool the backend runs, each name once, in the
order Settings shows them, and the listed tools that cannot run now:

```json
{
  "tools": [{ "name": "read_page" }, { "name": "web_search" }],
  "unavailableTools": [{ "name": "web_search", "reason": "api-key-missing" }]
}
```

(Definitions shortened.) Every definition has `runner` `backend`. The
definitions are fixed for one backend build: `read_page`, which reads one
public web page through vmo, and `web_search`, which searches the web through Tavily
(both group and access `network`). Availability is read again on every
request. For `web_search`, `reason` is `api-key-missing` (no Tavily API key is
saved), `api-key-invalid` (the saved key fails the key format), or
`settings-unreadable` (the settings file cannot be read as a settings
document). For `read_page`, it is `page-reader-not-ready`: vmo did not answer
`GET /health` at `127.0.0.1:8080` with `200` within one second. Each name in
`unavailableTools` is a listed tool, once. The list reads the settings file
and asks vmo's health route, contacts nothing else, and never contains the
key. `read_attachment`, the attachment reader, is not listed and cannot be
offered by name: the chat route adds it to a turn by itself; see
[attachments](#attachments).

### Key check

`POST /api/v1/tools/web_search/key-check` reads the saved Tavily API key and
asks Tavily's usage endpoint about it, through the same client and limits as
a search; it changes nothing in Lys and is not cancelled when the client
leaves. Each check that reaches Tavily with the key spends two of the
account's Tavily credits. The body must be the empty JSON object `{}`, sent as
`application/json`: the check takes no input, but a request with a JSON body
needs a CORS preflight, so a page on another site cannot make the backend send
the key to Tavily. Another body is answered with `400`, or `415` for a media
type the backend cannot parse, before the key is read. It answers `200` with
one of:

| `status`      | Other fields                                                                                  | Meaning                                        |
| ------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `accepted`    | `credits`: `{ used, limit }` or `null`                                                        | Tavily accepted the key just now               |
| `rejected`    | none                                                                                          | Tavily refused the key (HTTP 401 or 403)       |
| `unavailable` | `reason`: `api-key-missing`, `api-key-invalid`, or `settings-unreadable`, as in the tool list | No usable key is saved; nothing was sent       |
| `failed`      | `reason`: `rate-limited`, `timed-out`, `unreachable`, `provider-error`, or `invalid-response` | The check could not tell whether the key works |

`credits` comes from the account's plan usage and limit when Tavily reports
them; `limit` is `null` when Tavily reports none. Both are whole credits: a
fraction Tavily reports is rounded up. The answer never contains the key.

## Tool approvals

The backend decides which tool calls need the person: every call of a tool
that is not saved as Just run, client and backend tools alike, except
`read_attachment`, which runs without approval. It shows such a
call with a `tool-approval` event, and the client answers it with
`POST /api/v1/chat/:conversationId/replies/:assistantMessageId/tool-approvals/:callId`,
where `callId` is the `id` of the event's call or of its entry in
`reply-snapshot.pendingToolApprovals`. One request answers one prompt.

```json
{ "status": "allowed" }
```

```json
{
  "status": "rejected",
  "reason": "declined",
  "content": "The person declined this call. They said: not that folder"
}
```

After `allowed`, the backend runs a backend tool itself, stores its result
with the call, and gives it to the model; the client sees that result in the
call's `reply-part` event. For a client tool, it sends the call to run with a
`tool-call` event under the same `id`. After `rejected`, nothing runs and the model reads
`content`. `reason` is not shown to the model: `declined` when the person
rejected the call, and `showFailed` when the client could not show it, such as
a tool it does not list or arguments it cannot describe.

The route answers a bodyless `204` once the answer is accepted, and the
reply's loop continues. A prompt that is unknown, already answered, or whose
reply ended, and a call that waits for its result instead, return `409` with
`urn:lys:problem:chat:tool-call-not-pending` and change nothing, so repeating
a request whose response was lost is harmless. The backend sets no time limit
on a prompt; it waits as for a [tool result](#tool-results).

## Tool results

A `tool-call` event asks the client to run one call of a client tool: one the
person allowed, or one whose tool is saved as Just run. The client runs it
without asking again and answers with
`POST /api/v1/chat/:conversationId/replies/:assistantMessageId/tool-results/:callId`,
where `callId` is the `id` of the call's `tool-call` event or of its entry in
`reply-snapshot.pendingToolCalls`. One request answers one call. Calls of
backend tools never come here; the backend runs them itself.

```json
{ "status": "succeeded", "content": "The file's text" }
```

```json
{
  "status": "failed",
  "reason": "toolFailed",
  "content": "{\"code\":\"fileNotFound\"}"
}
```

`content` is the text the model reads; for a tool whose access is `network`,
the backend first removes invisible characters from it and adds a line
saying how many, as for every network tool's result. A succeeded result can be empty,
such as for an empty file, and a failed one cannot. `reason` says why a call
failed and is not shown to the model: `toolFailed` when the tool ran and
reported a failure, and `runFailed` when the client could not run it.

The route answers a bodyless `204` once the result is accepted, and the
reply's loop continues. A call that is unknown, already answered, waiting for
approval instead, or whose reply ended returns `409` with
`urn:lys:problem:chat:tool-call-not-pending` and changes nothing, so repeating
a request whose response was lost is harmless. The backend sets no time limit
on a pending call.
It waits until the call is answered, the reply is stopped, or the backend
shuts down. A newer turn in the conversation or deleting the conversation does
not end the wait yet ([#137](https://github.com/w3lt/lys/issues/137)).

## Conversation history

All conversation identifiers must be UUIDv7; malformed identifiers return `400`.
List responses have exactly `conversations`, `storedCount`, `matchCount`, and
`nextCursor`. Counts include all stored conversations and all matches before
pagination, respectively. Each summary contains `id`, nullable `title`,
`createdAt`, `updatedAt`, and nullable `preview`; it does not expose `agentCode`.
A preview contains only `role` and full `content`: a user message, or one text
part of a reply shown with the role `assistant`.

| Parameter | Contract                                                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `query`   | Optional; trimmed to 1–200 UTF-16 code units when supplied. Blank queries are rejected. Unicode case-insensitive literal substring search covers titles, user messages, and the text parts of replies. |
| `limit`   | Integer from 1–50; defaults to 30.                                                                                                                                                                     |
| `cursor`  | Opaque, at most 2048 characters; reuse with the same trimmed query. Malformed, unsupported, or differently bound cursors return `400`.                                                                 |

Results are ordered by `updatedAt DESC, id DESC`, with keyset pagination. The
next cursor is `null` at the end. Each response reads counts, page, and previews
from one snapshot; subsequent pages reflect later database changes.
Search previews select the latest matching user message or reply text part,
falling back to the latest one for a title-only match. Unfiltered lists select
the latest user message or reply text part; conversations without one have
`preview: null`. Reasoning and tool calls are never searched or previewed.

`GET` by identifier returns conversation metadata, including `agentCode`, the
code of the agent that answers it,
messages ordered by creation time then identifier, each user message with its
`attachments` and each reply with its `parts` in stored order, and `sources`,
the conversation's numbered sources in number order. The code stays after its
agent is deleted, so it may name no agent. `PATCH` accepts
only `title`, trims it to 1–120 UTF-16 code units, and returns updated metadata. Repeating
a rename is idempotent; renaming never changes activity time or list position.
`DELETE` cascades to messages, reply parts, attachment records, and sources,
then removes the conversation's attachment folder, and returns `204` without
a body; a folder that cannot be removed is logged and the delete still
succeeds. Late generation
writes after deletion do not recreate the conversation. Allowed development and
Tauri origins support DELETE preflights.

A user message's `attachments` lists the files sent with it, in sending order,
empty when none: each with its `number`, which counts up across the
conversation from 1, its `name`, `kind` (`image` or `text`), and `sizeBytes`,
and, for an image, its `mediaType` (`image/png`, `image/jpeg`, or
`image/webp`), `width`, and `height`. The turn-start events carry the same
records. No route serves the files themselves.

```json
{
  "kind": "image",
  "number": 2,
  "name": "photo.png",
  "sizeBytes": 48213,
  "mediaType": "image/png",
  "width": 640,
  "height": 480
}
```

Missing conversations on GET, PATCH, DELETE, or chat continuation return `404`
with `Content-Type: application/problem+json`:

```json
{
  "type": "urn:lys:problem:conversation:not-found",
  "title": "Conversation not found",
  "status": 404,
  "detail": "Conversation 0198f5a5-7b9b-7e0b-9b0f-87d9d6a5f72d was not found.",
  "instance": "/api/v1/conversations/0198f5a5-7b9b-7e0b-9b0f-87d9d6a5f72d"
}
```

Chat creates its user/assistant pair atomically, persists each reply part,
fragment, tool call change, and source before sending it to every stream
following the reply, and stores a terminal status before `done`. Partial parts
survive failure or cancellation, and a reply's waiting and running calls are
stored as interrupted when it ends. Title generation runs only for an untitled conversation
without a title task already running, and publishes a title only if the
conditional database write succeeds. On startup,
remaining streaming assistants become interrupted with refreshed
timestamps, and their waiting and running calls become interrupted with their
timestamps kept; conversation activity time and history order do not change.

## Agents

There are two kinds of agent. A built-in agent ships with the backend:
Caliginia (`caliginia`) and Lysiptera (`lysiptera`). It has a `code`, a `name`,
a `bio`, and a `systemPrompt`, belongs to the release, and can be neither
changed nor deleted. A stored agent is a definition the user created: a `code`, a `name`, a `bio`, a
`systemPrompt`, and the `createdAt` and `updatedAt` timestamps. The code is the
agent's identity and never changes: a lowercase slug of 1–64 characters made of
`a`–`z` and `0`–`9` in hyphen-separated groups, compared exactly. A malformed
code in a path returns `400` before any lookup. Request bodies reject unknown
fields; the name is trimmed to 1–64 UTF-16 code units, the bio to 1–128, and the
system prompt must not be blank after trimming. Text containing a lone UTF-16
surrogate, which UTF-8 cannot carry unchanged, is rejected. The system prompt
has no length limit of its own; only the 1 MiB request body limit above bounds
it. Invalid bodies return `400` and change nothing.

List responses have exactly `builtInAgents`, `agents`, `storedCount`, and
`nextCursor`. `builtInAgents` holds every built-in agent's `code`, `name`, and
`bio`, in the order the backend ships them, and is the same on every page.
`agents` holds one page of stored agents: each
summary contains `code`, `name`, `bio`, `createdAt`, and `updatedAt`. Neither
exposes `systemPrompt`, which `GET` by code returns. `GET` by code returns the
agent with a `kind`: `"built-in"`, without timestamps, or `"custom"` for a
stored agent, with them.

| Parameter | Contract                                                                                                  |
| --------- | --------------------------------------------------------------------------------------------------------- |
| `limit`   | Integer from 1–50; defaults to 30.                                                                        |
| `cursor`  | Opaque, at most 2048 characters, taken from the previous page. Malformed or foreign cursors return `400`. |

Stored agents are ordered by `createdAt ASC, code ASC`, with keyset pagination, and
`storedCount` counts every stored agent, never the built-in ones. Neither key changes after creation,
so an update never moves an agent between pages. Each response reads the count
and the page from one snapshot; later pages reflect later changes. The next
cursor is `null` on the last page.

`POST` stores a new agent and answers `201` with the stored agent and a
`Location: /api/v1/agents/<code>` header. CORS does not expose `Location`, so a
browser client on another origin, such as the desktop app, uses the returned
`code` instead. `code` is optional:

- A given code is stored exactly. If another agent already has it, a built-in
  agent's included, the request returns `409` with
  `urn:lys:problem:agent:code-taken` and stores nothing.
- Without a code, the backend derives one from the name: it decomposes the
  name with Unicode compatibility decomposition (NFKD), which removes accents
  and turns forms such as `𝐖` or `ﬁ` into ASCII, then lowercases it, joins the
  remaining ASCII letters and digits with single hyphens, and cuts the result
  to fit 64 characters. `Web Researcher` becomes `web-researcher` and `Trợ lý`
  becomes `tro-ly`. A letter without an ASCII form, such as `đ`, acts as a
  separator. A name in which no letter or digit has an ASCII form, such as
  `日本語`, gives `agent`. When the code is taken, by a stored or a built-in
  agent, `-2`, `-3`, and so on are added, so the name `Caliginia` gives
  `caliginia-2`.

Creating an agent is not idempotent: repeating a request without a code creates
another agent. After a lost response, list the agents to find out whether it
was created. Names need not be unique.

`PATCH` replaces only the given fields, trimmed, and stores the time of the
change as `updatedAt`, even when the values are unchanged. The body cannot
contain `code`, and an empty body returns `400`. `DELETE` removes the agent
permanently and returns `204` without a body. A conversation the deleted agent
answered keeps its messages and its agent code; see
[a conversation whose agent was deleted](#a-conversation-whose-agent-was-deleted).

`PATCH` or `DELETE` on a built-in agent changes nothing and returns `409` with
`Content-Type: application/problem+json`:

```json
{
  "type": "urn:lys:problem:agent:built-in",
  "title": "Built-in agent cannot be changed",
  "status": 409,
  "detail": "Agent caliginia is built in and cannot be changed or deleted.",
  "instance": "/api/v1/agents/caliginia"
}
```

A missing agent on GET, PATCH, or DELETE returns `404` with
`Content-Type: application/problem+json`:

```json
{
  "type": "urn:lys:problem:agent:not-found",
  "title": "Agent not found",
  "status": 404,
  "detail": "Agent web-researcher was not found.",
  "instance": "/api/v1/agents/web-researcher"
}
```

The chat endpoint returns the same problem, with `instance` `/api/v1/chat`,
when a new conversation names a code that no built-in or stored agent has.

A taken code returns `409` with the same media type, `type`
`urn:lys:problem:agent:code-taken`, `title` `Agent code taken`, and `instance`
`/api/v1/agents`.

### A conversation whose agent was deleted

A conversation keeps the code of the agent it was started with. When that
agent is deleted, the conversation stays stored and readable, but it accepts
no new message: the chat endpoint answers `409` with
`Content-Type: application/problem+json` before it stores anything, so the
conversation gains no message and no failed reply.

```json
{
  "type": "urn:lys:problem:conversation:agent-missing",
  "title": "Conversation agent missing",
  "status": 409,
  "detail": "The agent web-researcher that answers this conversation no longer exists.",
  "instance": "/api/v1/chat"
}
```

The conversation accepts messages again once an agent is stored under that
code, and that agent then answers it. Built-in agents cannot be deleted, so a
conversation a built-in agent answers never reaches this state.

### An offered tool that cannot run

A chat request that offers a backend tool that cannot run now stores nothing:
the chat endpoint answers `409` with `application/problem+json`, for the first
such tool in offer order. `toolName` and `reason` are extension members.

```json
{
  "type": "urn:lys:problem:chat:backend-tool-unavailable",
  "title": "Backend tool unavailable",
  "status": 409,
  "detail": "web_search is unavailable: no Tavily API key is saved.",
  "instance": "/api/v1/chat",
  "toolName": "web_search",
  "reason": "api-key-missing"
}
```

For `page-reader-not-ready`, `detail` is "read_page is unavailable: vmo,
Lys's page reader, is not ready."

The desktop shows the error and reads the tool list again, so its next
request leaves the tool out.

### An attachment Lys cannot send

A chat request with an attachment that is neither UTF-8 text nor a PNG,
JPEG, or WebP image stores nothing: the chat endpoint answers `400` with
`application/problem+json`, for the first such attachment in request order.
`fileName` is an extension member.

```json
{
  "type": "urn:lys:problem:chat:attachment-unsupported",
  "title": "Attachment unsupported",
  "status": 400,
  "detail": "The file report.pdf is not a text file or an image Lys can send.",
  "instance": "/api/v1/chat",
  "fileName": "report.pdf"
}
```

The desktop classifies a file the same way when it is chosen and refuses such
a file with the same sentence, so it does not send this request; it shows the
sentence if the backend ever answers it.

### An image for a model without vision

A chat request that attaches an image for a model whose inventory entry has
no `vision`, or that the inventory does not list, stores nothing: the chat
endpoint answers `409` with `application/problem+json`, for the first image
in request order. `fileName` and `model` are extension members.

```json
{
  "type": "urn:lys:problem:chat:image-needs-vision",
  "title": "Image needs vision",
  "status": 409,
  "detail": "The image photo.png needs a model with vision, and google/gemma-4-12b-qat cannot see images.",
  "instance": "/api/v1/chat",
  "fileName": "photo.png",
  "model": "google/gemma-4-12b-qat"
}
```

The desktop stages an image only while the loaded model has vision, so it
sends this request only when the model changed between staging and sending;
it then shows the sentence and keeps the files staged.

## LLM metadata shape

`LlmInfo` currently includes:

- `modelKey`
- `format`
- `displayName`
- `path`
- `sizeBytes`
- optional `paramsString`, `architecture`, and `quantization`
- `vision`
- `trainedForToolUse`
- `maxContextLength`
- `loaded`
- on a loaded model only, `loadedByLys` and optional `loadedContextLength`

`GET /api/v1/llm/list` returns `llms` ordered by `modelKey`, then by `path`.
An entry is one of two shapes, told apart by `loaded`; an entry with
`loaded: false` carries neither of the two loaded fields, and a client
refuses one that does.

On a loaded model, `loadedByLys` is `true` when at least one of its loaded
instances is one Lys loaded, and `false` when another program, such as LM
Studio's own window or `lms`, loaded them all. Lys unloads only the instances
it loaded; see [Instances Lys loaded](/architecture/providers/#instances-lys-loaded).
It is `false` on every model while the backend cannot read
`$LYS_HOME/loaded_models.json`.

On a loaded model, `loadedContextLength` is the context length it is loaded
with, in tokens: the smallest among its loaded instances, the window a chat
request to it is measured against. It is absent on a loaded model whose
instances were gone by the time the list measured them. The
[load response](#model-load-request) never carries it, since the load does
not observe it; the next list read does. The load response always carries
`loaded: true` and `loadedByLys: true`.

## Model load request

`POST /api/v1/llm/load` takes the model to load and, optionally, the settings
LM Studio loads it with:

```json
{
  "modelId": "google/gemma-4-12b-qat",
  "configuration": {
    "contextLength": 16384,
    "evalBatchSize": 512,
    "flashAttention": true,
    "offloadKVCacheToGpu": true,
    "numExperts": 4
  }
}
```

| Field                               | Type    | Meaning                                                           |
| ----------------------------------- | ------- | ----------------------------------------------------------------- |
| `modelId`                           | string  | Non-empty model key or alias that LM Studio resolves              |
| `configuration.contextLength`       | integer | Context window the model is loaded with, in tokens                |
| `configuration.evalBatchSize`       | integer | Prompt tokens evaluated together in one batch                     |
| `configuration.flashAttention`      | boolean | Whether the model is loaded with flash attention                  |
| `configuration.offloadKVCacheToGpu` | boolean | Whether the KV cache is kept in GPU memory rather than in RAM     |
| `configuration.numExperts`          | integer | Experts active per token; only mixture-of-experts models use this |

- `configuration` and each setting in it are optional. LM Studio decides every
  setting the request leaves out, so a request with only `modelId` loads the
  model with LM Studio's own settings.
- A request that sets `contextLength` also turns LM Studio's auto-fit off for
  that load. Auto-fit is LM Studio's own choice of context length and model
  placement from the available resources. The LM Studio SDK (2.0.0) sends it
  as off whenever a context length is set, and refuses the two together. The
  desktop sets a context length on every load it starts.
- Each integer is a whole number from 1 to 4,294,967,295.
- The backend answers `400` before starting a load when `configuration` is
  `null` or not an object, holds a setting other than the five above, or holds
  a value of the wrong type or outside the range.
- The backend does not compare `contextLength` with the model's
  `maxContextLength`. LM Studio decides what happens with a value the model
  cannot use.
- The settings apply to this load only. The backend does not store them.

The backend passes the settings to the LM Studio SDK's load call, which sends
each of them to LM Studio, together with an identifier of the instance's own,
such as `google/gemma-4-12b-qat@lys-7f3c9a`. It saves that identifier in
`$LYS_HOME/loaded_models.json` before the load starts. When that file cannot
be read, or the save fails, no load starts and the request fails with `500`.

## Model operation admission

Inventory, health, load, unload, and LM Studio connection attempts share one
queue with one active operation and at most eight waiting. Accepted operations
execute in arrival order. When all nine positions are occupied, each of these
endpoints returns `503 Service Unavailable` with `Content-Type:
application/problem+json`:

```json
{
  "type": "urn:lys:problem:llm:service-busy",
  "title": "LLM service busy",
  "status": 503,
  "detail": "The LLM service queue is full. This operation was not accepted. Try again after pending model operations finish."
}
```

This response means the operation was never accepted and performed no runtime
work. The caller may submit it again after capacity becomes available. The backend
does not retry automatically or promise a retry time. A disconnected request that
was already accepted continues to occupy capacity until its operation settles.

## Model operation cancellation

`POST /api/v1/llm/load` and `PATCH /api/v1/llm/unload` do not support user
cancellation. After the backend accepts an operation, disconnecting the client
does not cancel it. Accepted operations remain owned by the backend until success
or failure, and shutdown waits for them before releasing runtime resources.

Model health checks follow the same completion-only lifetime as inventory:
disconnecting the client does not cancel an accepted query. The runtime's
inventory RPC has no enforced completion deadline, so an unresponsive engine
can keep the query and shutdown pending.

Chat inference is cancelled only by the reply-stop route or by backend
shutdown; closing a chat stream does not cancel it. A newer turn or a deletion
also ends a reply's inference, once the model sends its next content. A reply
waiting for a tool result writes nothing, so it is not ended this way
([#137](https://github.com/w3lt/lys/issues/137)). See the
[provider cancellation policy](/architecture/providers/#cancellation-policy).

## Model health responses

`GET /api/v1/llm/:modelId/health` checks whether a fresh, validated loaded-model
inventory contains the requested canonical model key. Encode the key as one
URL segment; for example, `provider/model` becomes
`/api/v1/llm/provider%2Fmodel/health`. The key must contain 1–100 decoded
characters, matching the router's existing path-parameter limit.

The check generates no text and never loads or unloads a model. `ready` means
the runtime answered and reported a matching loaded instance. It does not prove
that a subsequent inference will succeed. Results are observations of changing
runtime state and use `Cache-Control: no-store`.

Completed checks return `200 OK` with one of these JSON shapes:

```json
{
  "modelId": "provider/model",
  "status": "ready",
  "latencyMs": 4
}
```

```json
{
  "modelId": "provider/model",
  "status": "not-ready",
  "reason": "model-not-loaded",
  "latencyMs": 4
}
```

`model-not-loaded` covers both unknown keys and models without a loaded
instance. `runtime-unavailable` means the inventory could not be obtained or
validated, so loaded state could not be established. Internal failure details
are logged and excluded from the response.

`latencyMs` is a non-negative safe integer measuring the loaded-inventory query.
It excludes time waiting in the service queue and HTTP
transmission, and does not measure generation speed. A full queue returns the
`503` service-busy Problem Details response documented above; it is distinct
from an accepted check returning a negative observation.

## Model unload responses

The request body must contain only `modelId`, and its value must be a non-empty
canonical model key. Invalid bodies are rejected with `400 Bad Request` before
the backend accesses the LLM runtime.

`PATCH /api/v1/llm/unload` stops, one after another, the loaded instances of
that model key that Lys loaded: those whose identifiers are in
`$LYS_HOME/loaded_models.json`. It never stops an instance another program
loaded. It returns `204 No Content` when a fresh reconciliation snapshot
contains none of the stopped instances, and saves the file without them; when
that save fails, it still returns `204` and logs a warning. This is an
observation of that snapshot, not a guarantee that another runtime client will
not load a new instance of the model afterward. Expected failures use
`application/problem+json` with stable `type`, `title`, and `status` fields.
Operation failures include an occurrence-specific `detail`; admission refusal
uses the fixed four-field service-busy body shown above:

| Status | Problem type                              | Meaning                                                                                                                                                                        |
| ------ | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `404`  | `urn:lys:problem:llm:model-not-found`     | No instance of the key that Lys loaded was initially loaded, including while `loaded_models.json` cannot be read; `detail` is `Model "<key>" has no instance that Lys loaded.` |
| `503`  | `urn:lys:problem:llm:runtime-unavailable` | No LLM runtime is connected, or the backend cannot query it.                                                                                                                   |
| `503`  | `urn:lys:problem:llm:unload-failed`       | Reconciliation still found an instance it tried to stop.                                                                                                                       |
| `503`  | `urn:lys:problem:llm:service-busy`        | The shared queue is full; no unload was accepted.                                                                                                                              |

Operation-failure bodies may also include an `instance` identifier for one
occurrence. The service-busy body has fixed `type`, `title`, `status`, and `detail`
fields and does not accept an `instance` field.
