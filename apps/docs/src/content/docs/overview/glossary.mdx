## Core runtime terms

- **Desktop**: the React user interface in `apps/desktop`.
- **Tauri host**: the native shell around the desktop app. It owns native
  commands such as backend start and stop.
- **Backend**: the Fastify process in `apps/backend` that serves HTTP routes,
  streams chat events, and persists conversations.
- **Protocol**: the shared HTTP and SSE contract exported by
  `packages/protocol`.
- **Share**: the shared domain-model package exported by `packages/share`.
- **Service**: a backend class named for its module, such as `AgentService`,
  `ChatService`, or `LlmService`, that the composition root creates once per
  backend and installs on Fastify (`app.agentService`, `app.chatService`) to
  own that module's operations.

## Conversation terms

- **Conversation**: the stored chat unit with metadata such as ID, title, the
  code of the agent that answers it, and timestamps. A new conversation names
  its agent; a continued one keeps it.
- **Built-in agent**: an agent that ships with the backend: Caliginia
  (`caliginia`), Lys's dark side, and Lysiptera (`lysiptera`), her light side.
  A built-in agent is never stored, changed, or deleted, and no stored agent
  can take its code. A new conversation starts with Caliginia unless another
  agent is selected.
- **Stored agent**: an agent the user created, kept in the backend database.
  It answers chats with the system prompt it has when each turn starts.
  Deleting it only marks it deleted, so its code is never free again.
- **Leader** and **member**: the role of an agent, fixed by its kind. The
  built-in agents are leaders, which can find every agent and read any
  agent's state; stored agents are members, which can read only their own.
- **Live agent**: the one instance of an agent that answers all of its
  turns while the backend runs and knows the requests it is working on.
- **Request slot**: one of the replies a live agent works on at once, two
  by default. A reply holds its slot from its start to its end; a reply
  that finds every slot held waits in line for one, and one that also finds
  the line full fails with an `error` event.
- **Agent state tools**: `read_my_state`, `find_agents`, and
  `read_agent_state`, which the backend adds to a turn of a model trained
  for tool use so an agent can tell what it and the other agents are
  doing.
- **User message**: a persisted message with role `user`, non-empty content,
  and the attachments sent with it.
- **Attachment**: a file sent with a user message and stored with the
  conversation under its own name, numbered once per conversation in sending
  order, as `[attachment 3] notes.md`. An image is seen by a model with
  vision; a text file is read by the model through `read_attachment`.
- **Assistant message**: a persisted message with role `assistant`, a model
  name, lifecycle status, an optional finish reason, and its parts.
- **Reply part**: one piece of a reply in the model round it belongs to:
  reasoning, text, or a tool call with its state and, once answered, its
  result.
- **Source**: a web page a tool call's result showed, numbered once per
  conversation; a reply cites it as `[n]`.
- **Finish reason**: the terminal model reason currently supported by the
  protocol: `stop` or `length`.
- **System prompt**: the instructions an agent sends first in the context of
  every reply. A built-in agent's comes from its backend prompt file
  (`caliginia.txt`, `lysiptera.txt`) and a stored agent's from its record; it
  is not stored with conversations.

## MCP terms

- **MCP**: the Model Context Protocol, an open protocol through which a
  separate program offers tools to an AI application. Lys uses the tools part
  of it.
- **MCP server**: a program that offers tools over MCP, listed in the `mcp`
  group of `settings.json`. Lys either starts it as a command and talks to it
  over its standard input and output (stdio), or reaches it at a URL over
  Streamable HTTP. The backend owns every connection.
- **MCP tool**: a tool of a connected MCP server. The model calls it as
  `mcp__<server>__<tool>`; the backend asks the person first, unless the tool
  is on Just run, and runs the call on the server. Its output is untrusted.

## Streaming terms

- **SSE**: Server-Sent Events. The chat endpoint responds as `text/event-stream`
  and emits typed lifecycle events.
- **Start event**: the first event in a chat turn, either
  `start-new-conversation-turn` or `start-existing-conversation-turn`.
- **Reply-part event**: a new reply part, or a tool call that changed state,
  as stored.
- **Reply-part-delta event**: a stored fragment appended to a reasoning or
  text part.
- **Done event**: the terminal assistant lifecycle event carrying the finish
  reason.
- **Title event**: the event that publishes a newly assigned or reconciled
  persisted conversation title.

## Handbook terms

- **ADR**: Architecture Decision Record, the reserved format for preserving a
  real decision and its historical context. No ADRs are published yet.
- **RFC**: Request for Comments, the reserved format for tracking a proposal
  before implementation. No RFCs are published yet.
- **docType**: the frontmatter field that tells the docs build whether a page is
  architecture, decision, proposal, runbook, or reference content.
