This page is intentionally conservative. It describes behavior visible in the
repository today; it is not a promise of unreleased work.

## Implemented now

- The desktop can start and stop the backend through the Tauri host.
- The backend exposes a health route, LLM inventory, load, and unload routes,
  LM Studio connection status and reconnect routes, chat, and conversation
  history routes.
- A chat turn creates or continues a conversation, inserts user and assistant
  rows in SQLite, and streams typed SSE events back to the desktop.
- A new conversation is answered by the agent chosen in the composer: a
  built-in agent, Caliginia unless another is chosen, or one of the user's
  own. A conversation keeps its agent for every turn, and one whose agent was
  deleted stays readable but accepts no new message.
- Conversation history supports search, cursor pagination, transcript retrieval,
  rename, and deletion. A reply's parts, its reasoning, text, and tool calls
  with their results, are each persisted before publication; continuation
  uses the current prompt of the conversation's agent and eligible stored
  history, without reasoning.
- The desktop's past-conversations dialog, opened from the composer or with
  Command+K or Control+K, searches, renames, and deletes stored conversations,
  and reopens one so its next message continues it.
- Assistant replies render as Markdown with KaTeX math and syntax-highlighted
  code blocks whose Copy button copies the plain code. A reply shows its
  reasoning and its tool steps, each call with its arguments and result,
  folded away, and its answer's `[n]` citations link to the web sources its
  tools numbered, which are listed under the answer.
- For a conversation without a stored title, the backend also attempts to
  generate a title asynchronously and emits the first assigned title as a stream
  event. When the conversation remains untitled, its next turn tries again; an
  existing titled turn resends the stored title to reconcile desktop metadata.
  A generated title is saved only if no rename has won the race. Only one
  title is generated at a time per conversation, and the composer accepts the
  next message as soon as the reply ends, without waiting for the title.
- Interrupted streaming rows are recovered on backend startup.
- Runtime, Model, Generation, Agents, Tools, and Secrets settings panes are
  available.
  The Runtime pane starts and stops the backend and vmo, shows whether each
  is ready, and saves whether each starts when Lys opens; Lys stops both when
  it quits. Model controls refresh inventory, load and unload weights, and check
  loaded-state health. The Agents pane lists the built-in agents, Caliginia
  and Lysiptera, which can be read and duplicated but not changed or deleted,
  and creates, edits, duplicates, and deletes the user's agents through the
  backend. The Tools pane lists the desktop's file tools and the backend's
  `read_page` and `web_search`; each tool's switch and its Ask me or Just run
  choice are saved, and the Tool calls switch lasts for the session only.
  `read_page` is
  off and cannot be switched on while vmo is not ready. The
  Secrets pane saves the Tavily API key `web_search` needs, and checks it.
- A chat offers the switched-on tools to a model trained for tool use and
  answers its tool calls: file tools run in the desktop, `read_page` asks vmo
  to read one public web page in headless Chromium inside a micro VM, running
  its scripts, following its redirects, and reading all of its text, hidden
  text included, and `web_search` searches the web through
  Tavily in the backend, unavailable until a Tavily API key is saved;
  `read_page` is likewise unavailable until vmo answers its health route. Each call
  asks the person first unless its tool is set to Just run, which the backend
  decides for every tool from the saved choices; both web tools start off. Lys's instructions do not
  give her today's date yet
  ([#148](https://github.com/w3lt/lys/issues/148)).
- A message can carry up to eight files. A model with vision sees an attached
  image with its message, on that turn and on every later one; every message
  lists its files for the model, and a model trained for tool use reads an
  attached text file on request through `read_attachment`, which never asks
  the person. The files are stored with the conversation under
  `$LYS_HOME/attachments` and shown on their message; see
  [attachments](/architecture/backend/#attachments).
- Generation controls apply to future chat requests and save automatically
  through Tauri to `$LYS_HOME/settings.json`, which contains runtime, model,
  generation, load configuration, secrets, and tools groups. The runtime
  group's two startup switches are saved when changed; the other runtime
  edits remain session-only.
- Every model load Lys starts sends that model's load configuration: context
  length, eval batch size, flash attention, KV cache placement, and active
  experts. The Model pane edits it for the selected default model and saves it
  automatically.
- The Composer label, send eligibility, and each chat request use the loaded
  runtime projection described in [desktop model settings](/architecture/desktop/#model-settings).
- On macOS, `build.sh` builds the desktop app from a source checkout, builds
  vmo in release, installs the backend runtime and vmo under
  `$LYS_HOME/runtime`, and copies `Lys.app` to `/Applications`. See
  [Packaging and releases](/operate/releases/). vmo boots its VMs only on a
  Mac with the kernel described in
  [Runtime dependencies](/operate/dependencies/#vmo)
  ([#200](https://github.com/w3lt/lys/issues/200)), and a vmo or backend whose
  Lys died without quitting keeps running
  ([#202](https://github.com/w3lt/lys/issues/202)).

## Coming soon

The current repository does not yet provide:

- a Conversation settings pane
- replay or reconnect semantics for chat streams
- a production desktop release workflow
- evidenced ADR and RFC records, and a canonical release log
