Lys currently uses shared loopback constants, one Lys home directory, backend
runtime composition, a Tauri-managed settings file, and one WebView theme
preference.

## Shared constants

| Constant        | Value       | Used by                                      |
| --------------- | ----------- | -------------------------------------------- |
| `API_PREFIX_V1` | `/api/v1`   | Route path composition                       |
| `BACKEND_HOST`  | `127.0.0.1` | Backend bind host and desktop backend URL    |
| `BACKEND_PORT`  | `12345`     | Backend bind port and desktop backend URL    |
| `LMSTUDIO_HOST` | `127.0.0.1` | Backend LM Studio HTTP and WebSocket clients |
| `LMSTUDIO_PORT` | `1234`      | Backend LM Studio HTTP and WebSocket clients |

## Lys home directory

The Lys home directory holds the desktop settings file, the conversation
database, and the runtime that release builds start. The handbook writes it as
`$LYS_HOME`. The desktop host resolves it once at startup from the `LYS_HOME`
environment variable:

| `LYS_HOME` value                             | Lys home                |
| -------------------------------------------- | ----------------------- |
| Unset or empty                               | `~/.lys`                |
| Absolute path                                | That path, used as-is   |
| Relative path, including an unexpanded `~/…` | Rejected at app startup |
| Not valid UTF-8                              | Rejected at app startup |

A rejected value stops the desktop app before any window opens and prints
`Lys cannot start: …` to standard error. The host does not create the directory
at startup; loading settings creates it when `settings.json` is missing.

| Path under `$LYS_HOME`        | Used by        | Contents                                                |
| ----------------------------- | -------------- | ------------------------------------------------------- |
| `settings.json`               | Tauri host     | [Persisted settings JSON](#persisted-settings-json)     |
| `lys_db.sqlite`               | Backend        | Conversation database                                   |
| `runtime/node/bin/node`       | Release builds | Node.js executable that runs the backend                |
| `runtime/backend/backend.mjs` | Release builds | Backend bundle that the release Node.js executable runs |

On macOS, `build.sh` installs the two `runtime/` entries under
`${LYS_HOME:-$HOME/.lys}`. It treats an empty value as unset but does not reject
a relative path.

The backend has no default of its own. It reads `LYS_HOME` once at startup and
uses an absolute path as given. It stops with `LYS_HOME is not set` when the
variable is unset or empty. A relative path, including an unexpanded `~/…`,
stops it with `LYS_HOME must be an absolute path, got "…"`, quoting the value.
The desktop host sets `LYS_HOME` to its resolved Lys home for the
backend it starts, in development and release builds. The root `backend:dev`
script sets `LYS_HOME` to `$HOME/.lys`.

:::caution[Apps opened from Finder or the Dock]
The desktop app reads `LYS_HOME` from its own process environment. An app
opened from Finder or the Dock does not inherit variables exported in a shell
profile, so it uses `~/.lys` even when your shell sets `LYS_HOME`. It also does
not find a runtime that `build.sh` installed under another directory.
:::

## Backend-composed values

| Value                          | Current source                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------- |
| Backend listen address         | `BACKEND_HOST` and `BACKEND_PORT`                                                     |
| LM Studio HTTP base URL        | `http://${LMSTUDIO_HOST}:${LMSTUDIO_PORT}/v1`                                         |
| LM Studio WebSocket base URL   | `ws://${LMSTUDIO_HOST}:${LMSTUDIO_PORT}`                                              |
| SQLite path                    | `$LYS_HOME/lys_db.sqlite`; see [Lys home directory](#lys-home-directory)              |
| Caliginia system prompt        | `src/utils/prompts/caliginia.txt`, as `caliginiaSystemPrompt`                         |
| Lysiptera system prompt        | `src/utils/prompts/lysiptera.txt`, as `lysipteraSystemPrompt`                         |
| Title-generation prompt        | `src/utils/prompts/title-generation.txt`, as `titleGenerationPrompt`                  |
| Title-generation attempt limit | `3`, from `titleGenerationMaxAttempts` in `src/config.ts`; must be a positive integer |
| Generated title length limit   | `100`, from `generatedTitleMaxLength` in `src/config.ts`; must be a positive integer  |

`loadBackendConfig()` builds these values once when the backend starts, so a
changed `LYS_HOME`, prompt file, or limit takes effect after a restart. The
attempt limit applies to each chat turn. The title length limit counts Unicode
code points before surrounding whitespace is trimmed.

### Backend configuration validation

The backend validates the complete configuration with `backendConfigSchema` in
`src/config.ts`. `loadBackendConfig()` validates the values it builds, and
`buildApp()` validates the configuration it receives before it creates the
application or any service. Every key is required, unknown keys are rejected,
and no defaults are applied.

| Key                                                                       | Accepted values                                                                               |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `backendHost`                                                             | An IPv4 loopback address (`127.x.x.x`); the backend does not authenticate non-browser callers |
| `backendPort`, `lmstudioPort`                                             | An integer from 1 to 65535                                                                    |
| `lmstudioHost`                                                            | A host name or IPv4 address, used unbracketed in the `http://` and `ws://` URLs               |
| `databaseFilePath`                                                        | An absolute path                                                                              |
| `caliginiaSystemPrompt`, `lysipteraSystemPrompt`, `titleGenerationPrompt` | Non-empty text without leading or trailing whitespace                                         |
| `titleGenerationMaxAttempts`, `generatedTitleMaxLength`                   | A positive integer                                                                            |

A value outside these rules stops the backend at startup with a `ZodError`
whose issues name each failing key. The shared constants, the `LYS_HOME`
database path, the trimmed prompt files, and the fixed limits above all satisfy
them.

## Persisted settings JSON

The Tauri host reads and writes `$LYS_HOME/settings.json`. A new file uses these
defaults:

```json
{
  "runtime": {
    "autoStartBackend": true,
    "defaultModel": null,
    "backendAddress": "http://127.0.0.1:12345"
  },
  "model": {
    "contextSize": 32768
  },
  "generation": {
    "temperature": 0.7,
    "replyCeiling": 2048
  },
  "loadConfiguration": {
    "default": {},
    "models": {}
  }
}
```

| Key                        | Type                    | Meaning                                                                                            |
| -------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------- |
| `runtime.autoStartBackend` | `boolean`               | Whether desktop initialization should ask Tauri to start the backend automatically                 |
| `runtime.defaultModel`     | `string \| null`        | Preferred model used when it is loaded; otherwise the first loaded inventory entry is the fallback |
| `runtime.backendAddress`   | `string`                | Backend address displayed in settings; HTTP clients still target the fixed loopback address        |
| `model.contextSize`        | unsigned 32-bit integer | Context-size estimate displayed in the Model pane; not forwarded by the load API                   |
| `generation.temperature`   | number in `[0, 1]`      | Sampling temperature sent with each new chat request                                               |
| `generation.replyCeiling`  | unsigned 32-bit integer | Maximum reply tokens; the desktop omits the request limit when this is `0`                         |
| `loadConfiguration`        | object                  | Settings sent with each model load; see [Load configuration](#load-configuration)                  |

A missing group, or a missing field in one of them, uses the host defaults;
for `loadConfiguration` that default is empty. Loading never rewrites an
existing file. Invalid JSON or invalid field values, including a temperature
outside `[0, 1]`, cause loading to fail, and the file is left as it is. Loading
a missing file creates the parent directory and writes the default document.

The file carries no version marker. The maintainer accepted that for
[PR #143](https://github.com/w3lt/lys/pull/143); see the
[settings file version exception](/reference/standard-application/#settings-file-version-exception).

### Load configuration

The `loadConfiguration` group holds the settings Lys sends when it loads a
model. The [load request](/reference/api/#model-load-request) defines each
setting.

| Key                         | Type                        | Meaning                                                                       |
| --------------------------- | --------------------------- | ----------------------------------------------------------------------------- |
| `loadConfiguration.default` | object                      | Settings for every model, used where a model has none of its own; starts `{}` |
| `loadConfiguration.models`  | object keyed by model key   | Settings each model has of its own; an entry holds only the changed values    |
| `contextLength`             | integer, 1 to 4,294,967,295 | Context window, in tokens                                                     |
| `evalBatchSize`             | integer, 1 to 4,294,967,295 | Prompt tokens evaluated in one batch                                          |
| `flashAttention`            | boolean                     | Whether flash attention is on                                                 |
| `offloadKVCacheToGpu`       | boolean                     | Whether the KV cache is kept in GPU memory                                    |
| `numExperts`                | integer, 1 to 4,294,967,295 | Experts active per token                                                      |

- Every setting is optional, in `default` and in a `models` entry.
- `default` holds only what you write into it by hand; the Model pane edits
  only `models` entries, and its saves leave `default` as it is in the file.
- Lys reads `settings.json` when it starts. A hand edit made while Lys runs
  takes effect the next time Lys starts. Until then a save from the Model pane
  keeps an edited `default`, and replaces `models` with the entries Lys holds.
- When Lys loads a model, each setting comes from the first of these that sets
  it: the model's own entry, then `default`, then the committed default below.
  `numExperts` is not sent when none of them sets it. The context length is
  lowered to the model's `maxContextLength` when the resolved value is larger.
- A missing group, `default`, or `models` is empty. An unknown setting or part,
  `null`, a fraction, or a value outside the range makes loading the settings
  fail.

The committed default is the file
`apps/desktop/src/lib/models/default_model_load_configuration.json`. It sets
`contextLength`, `evalBatchSize`, `flashAttention`, and `offloadKVCacheToGpu`,
and may set `numExperts`. The desktop bundle embeds it when it is built, so
editing it changes the default after the next build, for every settings file
that does not override a setting. Lys never copies it into `settings.json`. An
invalid committed file stops the desktop at startup.

An older Lys build does not know the group. It ignores it and removes it the
next time it saves settings, so going back to an older build loses the stored
load configurations.

## Settings updates

The settings view provides Runtime, Model, Generation, and Agents panes. Model
inventory, load, unload, and loaded-state health controls call the backend
through the application store. The user's agents are stored by the backend,
not in `settings.json`, and the built-in agents ship with the backend and are
not stored at all. The agent selected for a new conversation is kept only
until the app quits. There is no Conversation pane.

Generation edits apply to future messages immediately and are saved
automatically through Tauri. The save reloads the persisted document and replaces
only its `generation` group, preserving the other values already on disk.
Saves are serialized and newer edits are saved after the active write settles.
Save failure leaves the current values usable and exposes a retry action.

Load configuration edits in the Model pane are saved the same way, replacing
only the `models` part of the `loadConfiguration` group. The save keeps the
`default` that is in the file, because only a hand edit changes it. The edits
apply to the next load of the model they belong to. The desktop runs the two
kinds of save one at a time, so neither writes back an older copy of the other
group.

Runtime edits, including auto-start and default-model selection, remain in memory
for the current session. Edits to `model.contextSize` also remain session-only.
A generation or load configuration save does not persist those unsaved groups.

## Desktop theme preference

The active desktop theme is stored separately in WebView `localStorage` under
`lys.theme`. Valid values are `dark` and `light`; the fallback is `dark` when
the value is missing, invalid, or unavailable.

## Current caveats

- The React shell loads runtime settings from Tauri, but runtime and model edits,
  including `runtime.defaultModel`, are not persisted back through `save_settings`.
- `model.contextSize` is still a separate local estimate. The composer's
  context meter uses it and does not follow the context length a model is
  loaded with.
- LM Studio applies its own settings when it loads a model by itself, for
  example when a chat request names a model that is not loaded. The load
  configuration applies only to loads Lys starts.
