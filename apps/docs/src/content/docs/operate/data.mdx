## `~/.lys/settings.json`

The desktop host owns a JSON settings file at `~/.lys/settings.json`.

- created automatically when the file is missing
- currently stores `runtime.autoStartBackend` and `runtime.selectedModel`
- parsed as JSON on load and rewritten as pretty-printed JSON when the Tauri
  `save_settings` command is called

The current desktop UI loads this file, but the checked-in UI does not yet call
the Tauri save command after runtime-setting edits.

## `~/.lys/lys_db.sqlite`

The backend stores conversations in one SQLite database file at
`~/.lys/lys_db.sqlite`.

The checked-in schema currently creates:

- `conversations`
- `conversation_messages`
- one index on `(conversation_id, created_at, id)`
- triggers that keep `conversations.updated_at` in sync

SQLite `PRAGMA user_version` tracks the applied migration level. On startup the
backend applies any missing forward migrations and refuses to open a database
whose version is newer than the binary understands.

## Lifecycle notes

- The settings file is created by the Tauri host on first settings load.
- The SQLite file is opened by the backend when the conversation service starts.
- Both files live under the same `~/.lys/` directory, so user data and app
  settings currently share one root.

## WebView theme storage

The desktop theme is stored separately from `~/.lys/` under the `lys.theme`
WebView `localStorage` key. Its valid values are `dark` and `light`.

## What is not documented yet

The repository does not currently provide an evidenced contract for:

- exporting conversations to another format
- pruning or rotating stored conversation data
- relocating either file through supported configuration
- diagnostics bundles that package these files or projections of them

Retention, cleanup, and export procedures should be documented here once the
