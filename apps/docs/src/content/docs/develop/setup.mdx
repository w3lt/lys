## Required tools

- **Node 24.10 or later**: the root `.nvmrc` contains `24`, and the docs
  deployment workflow also builds with Node 24. The backend needs at least
  24.10, because its database owner uses `DatabaseSync.setAuthorizer`.
- **pnpm 11**: the root workspace pins `pnpm@11.17.0`.
- **Rust and Cargo**: required because the desktop app uses Tauri, the email
  MCP server Lys ships is a Rust crate in `mcps/email`, and the repository
  validation list includes Cargo-based checks for both.
- **Swift 6.3 or later** (Xcode or the Command Line Tools): required to build
  vmo, the page reader `read_page` uses, which the desktop starts with
  `apps/vmo/run.sh` and `build.sh` installs. vmo builds and runs only on
  macOS 26 on Apple silicon; see
  [Runtime dependencies](/operate/dependencies/#vmo).
- **A model provider**: one or several of LM Studio, a local Ollama server,
  Ollama Cloud, and Groq, turned on in Settings → Providers; required for the
  model inventory, chat, and title-generation paths, and LM Studio also for
  model loading. Lys starts without them and shows a provider that is on as
  not reachable until it answers.

## Install and bootstrap

```sh
pnpm install
```

That installs the workspace dependencies for:

- `apps/desktop`
- `apps/backend`
- `apps/docs`
- `packages/protocol`
- `packages/share`
- `scripts`

## First successful runs

From the repository root, run the path you need rather than starting all three
long-running processes at once:

```sh
pnpm docs:dev
pnpm backend:dev
pnpm dev
```

- `pnpm docs:dev` starts the Astro/Starlight handbook.
- `pnpm backend:dev` starts the Fastify backend in watch mode and shows its
  log lines as readable text.
- `pnpm dev` launches the Tauri desktop application.

Before standalone `pnpm backend:dev`, create its Lys home directory if needed.
The script sets `LYS_HOME` to `$HOME/.lys`:

```sh
mkdir -p "$HOME/.lys"
```

The email MCP server is not built by these commands. Build it once before
saving an email account in Settings → MCP, since Save signs in through it,
and again after changing it:

```sh
cargo build --manifest-path mcps/email/Cargo.toml --target-dir mcps/email/target
```

In development, the backend starts `mcps/email/target/debug/email`, where
`--target-dir` puts the build even when `CARGO_TARGET_DIR` or Cargo's
`build.target-dir` setting names another folder, unless a Cargo
configuration sets `build.target`, which adds the target's name to the path.

Desktop settings initialization creates the Lys home directory for the
desktop-managed path. Choose one backend launch path: desktop auto-start is
enabled by default, and starting another backend on the same port can conflict.
The same holds for vmo, which the desktop starts by default.
See [Running Lys locally](/develop/running/) for process ownership and
readiness.

## Local endpoints to expect

- The backend listens on `127.0.0.1:12345`.
- The backend reaches each provider turned on in Settings → Providers, at its
  saved address for LM Studio and a local Ollama server; with nothing saved,
  only LM Studio is on, on `127.0.0.1:1234`.
- vmo listens on `127.0.0.1:8080`.

Backend startup does not wait for the providers: the backend opens its HTTP
listener, then tries once to connect to each provider that is on. If a
provider starts later, press
**Refresh** on the Provider connections card in Settings → Runtime. A running desktop child
process alone does not establish that the HTTP endpoint is ready; the desktop
reports the backend as running only after `GET /api/v1/heath` answers.

## First validation checks

For a docs-only change, start with the docs app checks:

```sh
pnpm --filter @lys/docs run check
pnpm --filter @lys/docs run build
```

For broader work, follow the validation commands listed in `CONTRIBUTING.md`.
