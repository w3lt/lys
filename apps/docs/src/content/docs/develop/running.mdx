## Root commands

Choose the command you need and run it from the repository root:

```sh
pnpm docs:dev
pnpm backend:dev
pnpm dev
```

## What each command does

- `pnpm docs:dev`: starts the Astro/Starlight docs app.
- `pnpm backend:dev`: runs `tsx watch src/index.ts` in `apps/backend` with
  `LYS_HOME` set to `$HOME/.lys`.
- `pnpm dev`: runs `pnpm --filter @lys/desktop run tauri dev`, which starts the
  desktop Vite app and the Tauri shell.

For standalone backend development, create the Lys home directory before
starting the watcher:

```sh
mkdir -p "$HOME/.lys"
pnpm backend:dev
```

The root `backend:dev` script sets `LYS_HOME` to `$HOME/.lys`, so the
standalone backend opens `~/.lys/lys_db.sqlite`; it does not create that
directory. Running the backend package's `dev` script with `LYS_HOME` unset or
empty stops at startup with `LYS_HOME is not set`; a relative value stops it
with `LYS_HOME must be an absolute path`. The desktop-managed path creates its
[Lys home directory](/reference/configuration/#lys-home-directory) while
initializing missing settings. With `LYS_HOME` unset for the desktop, both paths
use the same database; they always use the same port, so choose one backend
launch path.

## Runtime behavior to expect

- The desktop app talks to the backend over HTTP at `http://127.0.0.1:12345`.
- The chat transport is a `POST /api/v1/chat` request that returns an SSE
  stream.
- The backend uses LM Studio for model inventory and load operations and an
  OpenAI-compatible endpoint for chat completions.
- The backend starts listening without LM Studio and then tries once to
  connect to `127.0.0.1:1234`. If LM Studio starts later, press **Refresh** on
  the LM Studio card in Settings → Runtime, or send
  `POST /api/v1/llm/runtime/connect`. `GET /api/v1/llm/runtime` reports
  `connecting`, `connected`, or `unreachable`.

## Backend lifecycle in the desktop app

The desktop starts and stops an owned `pnpm run dev` child through Tauri
commands. The command runs from the backend directory in the checkout recorded
when the host was compiled, so that checkout, installed dependencies, Node, and
`pnpm` must remain available. The host sets `LYS_HOME` on that child to the Lys
home it resolved at startup.

`runtime.autoStartBackend` defaults to `true`; initialization starts the child
when the loaded value is enabled. Runtime control edits remain session-only;
generation controls have separate autosave wiring.

Runtime status describes the owned child process. It does not discover a
backend started separately in a terminal or prove HTTP readiness. Use
`GET /api/v1/heath` to check the listener. Avoid launching a standalone watcher
alongside desktop auto-start because both attempt to use port `12345`.

## Using a scratch data directory

Set `LYS_HOME` to an absolute path to keep development settings and
conversations out of `~/.lys`. For the desktop app, the host creates that
directory while initializing settings and passes it to the backend it starts:

```sh
LYS_HOME="$HOME/lys-scratch" pnpm dev
```

For a standalone backend, create the directory and run the backend package
directly, because the root `backend:dev` script always sets `LYS_HOME` to
`$HOME/.lys`:

```sh
mkdir -p "$HOME/lys-scratch"
LYS_HOME="$HOME/lys-scratch" pnpm --filter @lys/backend run dev
```
