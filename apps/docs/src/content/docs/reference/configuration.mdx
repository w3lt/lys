Lys currently uses shared loopback constants, one Lys home directory, backend
runtime composition, a Tauri-managed settings file, and one WebView theme
preference.

## Shared constants

| Constant                | Value          | Used by                                                                 |
| ----------------------- | -------------- | ----------------------------------------------------------------------- |
| `API_PREFIX_V1`         | `/api/v1`      | Route path composition                                                  |
| `BACKEND_HOST`          | `127.0.0.1`    | Backend bind host and desktop backend URL                               |
| `BACKEND_PORT`          | `12345`        | Backend bind port and desktop backend URL                               |
| `LMSTUDIO_HOST`         | `127.0.0.1`    | LM Studio's default address, while `providers.lmStudio.address` is null |
| `LMSTUDIO_PORT`         | `1234`         | LM Studio's default address, while `providers.lmStudio.address` is null |
| `OLLAMA_HOST`           | `127.0.0.1`    | Ollama's default address, while `providers.ollama.address` is null      |
| `OLLAMA_PORT`           | `11434`        | Ollama's default address, while `providers.ollama.address` is null      |
| `OLLAMA_CLOUD_API_HOST` | `ollama.com`   | Host of Ollama Cloud's API, reached over HTTPS                          |
| `GROQ_API_HOST`         | `api.groq.com` | Host of Groq's API, reached over HTTPS                                  |
| `VMO_HOST`              | `127.0.0.1`    | Backend page reads and health checks, desktop vmo card                  |
| `VMO_PORT`              | `8080`         | Backend page reads and health checks, desktop vmo card                  |

The Tauri host's health check of vmo and vmo's own listener are Rust and
Swift, so they declare `127.0.0.1:8080` again. A desktop unit test fails when
either copy differs from `VMO_HOST` and `VMO_PORT`, so changing vmo's address
means changing all three; see the
[vmo address copy exception](/reference/standard-application/#vmo-address-copy-exception).

## Lys home directory

The Lys home directory holds the desktop settings file, the conversation
database, the attachment files, the runtime that release builds start, and the
backend's log files. The handbook writes it as
`$LYS_HOME`. The desktop host resolves it once at startup from the `LYS_HOME`
environment variable:

| `LYS_HOME` value                             | Lys home                |
| -------------------------------------------- | ----------------------- |
| Unset or empty                               | `~/.lys`                |
| Absolute path                                | That path, used as-is   |
| Relative path, including an unexpanded `~/…` | Rejected at app startup |
| Not valid UTF-8                              | Rejected at app startup |

A rejected value stops the desktop app before any window opens and prints
`Lys cannot start: …` to standard error. The host does not create the directory
at startup; loading settings creates it when `settings.json` is missing.

| Path under `$LYS_HOME`        | Used by        | Contents                                                                                                                                                         |
| ----------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `settings.json`               | Tauri host     | [Persisted settings JSON](#persisted-settings-json)                                                                                                              |
| `lys_db.sqlite`               | Backend        | Conversation database                                                                                                                                            |
| `attachments/`                | Backend        | One folder per conversation and one per message under it, holding the files sent with that message under their own names; created on the first attachment stored |
| `runtime/node/bin/node`       | Release builds | Node.js executable that runs the backend                                                                                                                         |
| `runtime/backend/backend.mjs` | Release builds | Backend bundle that the release Node.js executable runs                                                                                                          |
| `runtime/vmo/vmo`             | Release builds | vmo, the page reader the desktop starts, signed with the virtualization entitlement                                                                              |
| `logs/backend-YYYY-MM-DD.log` | Backend        | The backend's log lines of one UTC day, appended by every run that day and never deleted; see [the backend log files](/operate/logging/#the-backend-log-files)   |

On macOS, `build.sh` installs the three `runtime/` entries under
`${LYS_HOME:-$HOME/.lys}`. It treats an empty value as unset but does not reject
a relative path.

The backend has no default of its own. It reads `LYS_HOME` once at startup and
uses an absolute path as given. It stops with `LYS_HOME is not set` when the
variable is unset or empty. A relative path, including an unexpanded `~/…`,
stops it with `LYS_HOME must be an absolute path, got "…"`, quoting the value.
The desktop host sets `LYS_HOME` to its resolved Lys home for the
backend it starts, in development and release builds. vmo does not read it. The root `backend:dev`
script sets `LYS_HOME` to `$HOME/.lys`.

:::caution[Apps opened from Finder or the Dock]
The desktop app reads `LYS_HOME` from its own process environment. An app
opened from Finder or the Dock does not inherit variables exported in a shell
profile, so it uses `~/.lys` even when your shell sets `LYS_HOME`. It also does
not find a runtime that `build.sh` installed under another directory.
:::

## Backend-composed values

| Value                          | Current source                                                                                                                                                                                                    |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend listen address         | `BACKEND_HOST` and `BACKEND_PORT`                                                                                                                                                                                 |
| SQLite path                    | `$LYS_HOME/lys_db.sqlite`; see [Lys home directory](#lys-home-directory)                                                                                                                                          |
| Settings file path             | `$LYS_HOME/settings.json`, as `settingsFilePath`; read for the model provider, its address and key, and the Tavily API key                                                                                        |
| Attachments directory          | `$LYS_HOME/attachments`, as `attachmentsDirectoryPath`; created with its folders on the first attachment stored                                                                                                   |
| vmo endpoint                   | `127.0.0.1:8080`, as `vmoHost` and `vmoPort`, from `VMO_HOST` and `VMO_PORT` in `@lys/protocol`; where vmo listens. It reads every `read_page` page, and its `GET /health` decides whether `read_page` is offered |
| Caliginia system prompt        | `src/utils/prompts/caliginia.txt`, as `caliginiaSystemPrompt`                                                                                                                                                     |
| Lysiptera system prompt        | `src/utils/prompts/lysiptera.txt`, as `lysipteraSystemPrompt`                                                                                                                                                     |
| Title-generation prompt        | `src/utils/prompts/title-generation.txt`, as `titleGenerationPrompt`                                                                                                                                              |
| Title-generation attempt limit | `3`, from `titleGenerationMaxAttempts` in `src/config.ts`; must be a positive integer                                                                                                                             |
| Generated title length limit   | `100`, from `generatedTitleMaxLength` in `src/config.ts`; must be a positive integer                                                                                                                              |

`loadBackendConfig()` builds these values once when the backend starts, so a
changed `LYS_HOME`, prompt file, or limit takes effect after a restart. The
model provider is not among them: the backend reads it from the settings file
at each connection attempt, and builds its URLs from the
[provider settings](#providers). The
attempt limit applies to each chat turn. The title length limit counts Unicode
code points before surrounding whitespace is trimmed.

### Backend configuration validation

The backend validates the complete configuration with `backendConfigSchema` in
`src/config.ts`. `loadBackendConfig()` validates the values it builds, and
`buildApp()` validates the configuration it receives before it creates the
application or any service. Every key is required, unknown keys are rejected,
and no defaults are applied.

| Key                                                                       | Accepted values                                                                               |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `backendHost`                                                             | An IPv4 loopback address (`127.x.x.x`); the backend does not authenticate non-browser callers |
| `backendPort`, `vmoPort`                                                  | An integer from 1 to 65535                                                                    |
| `vmoHost`                                                                 | An IPv4 loopback address (`127.x.x.x`); vmo does not authenticate its callers                 |
| `databaseFilePath`, `settingsFilePath`, `attachmentsDirectoryPath`        | An absolute path                                                                              |
| `caliginiaSystemPrompt`, `lysipteraSystemPrompt`, `titleGenerationPrompt` | Non-empty text without leading or trailing whitespace                                         |
| `titleGenerationMaxAttempts`, `generatedTitleMaxLength`                   | A positive integer                                                                            |

A value outside these rules stops the backend at startup with a `ZodError`
whose issues name each failing key. The shared constants, the `LYS_HOME`
database path, the trimmed prompt files, and the fixed limits above all satisfy
them.

## Persisted settings JSON

The Tauri host reads and writes `$LYS_HOME/settings.json`. A new file uses these
defaults:

```json
{
  "runtime": {
    "autoStartBackend": true,
    "autoStartVmo": true,
    "defaultModel": null,
    "backendAddress": "http://127.0.0.1:12345"
  },
  "generation": {
    "temperature": 0.7,
    "replyCeiling": 2048
  },
  "loadConfiguration": {
    "default": {},
    "models": {}
  },
  "secrets": {
    "tavilyApiKey": null,
    "ollamaApiKey": null,
    "groqApiKey": null
  },
  "providers": {
    "active": "lmStudio",
    "lmStudio": { "address": null },
    "ollama": { "address": null }
  },
  "tools": {
    "justRun": [],
    "switches": {}
  },
  "location": {
    "city": null,
    "region": null,
    "country": null
  },
  "mcp": {
    "servers": []
  }
}
```

| Key                        | Type                    | Meaning                                                                                                              |
| -------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `runtime.autoStartBackend` | `boolean`               | Whether desktop initialization should ask Tauri to start the backend automatically                                   |
| `runtime.autoStartVmo`     | `boolean`               | Whether desktop initialization should ask Tauri to start vmo, the page reader `read_page` uses                       |
| `runtime.defaultModel`     | `string \| null`        | Preferred model used when it is loaded; otherwise the first loaded inventory entry is the fallback                   |
| `runtime.backendAddress`   | `string`                | Backend address displayed in settings; HTTP clients still target the fixed loopback address                          |
| `generation.temperature`   | number in `[0, 1]`      | Sampling temperature sent with each new chat request                                                                 |
| `generation.replyCeiling`  | unsigned 32-bit integer | Maximum reply tokens; the desktop omits the request limit when this is `0`                                           |
| `loadConfiguration`        | object                  | Settings sent with each model load; see [Load configuration](#load-configuration)                                    |
| `secrets.tavilyApiKey`     | `string \| null`        | Tavily API key of `web_search`, 1 to 256 visible ASCII characters, stored as plain text; see [Secrets](#secrets)     |
| `secrets.ollamaApiKey`     | `string \| null`        | API key of Ollama Cloud, under the same rule; see [Secrets](#secrets)                                                |
| `secrets.groqApiKey`       | `string \| null`        | Groq API key, under the same rule; see [Secrets](#secrets)                                                           |
| `providers`                | object                  | The model provider every request goes to, and where to find it; see [Providers](#providers)                          |
| `tools.justRun`            | array of tool names     | Tools that run without asking when a model calls them; every other tool asks; see [Tools](#tools)                    |
| `tools.switches`           | object of `boolean`     | Whether each tool the person switched is on, by tool name; any other tool starts at its default; see [Tools](#tools) |
| `location.city`            | `string \| null`        | City the person saved for `get_location`; see [Location](#location)                                                  |
| `location.region`          | `string \| null`        | State, province, or other region the person saved; see [Location](#location)                                         |
| `location.country`         | `string \| null`        | Country the person saved; see [Location](#location)                                                                  |
| `mcp.servers`              | array of server objects | MCP servers Lys connects to, in the order Settings → MCP lists them; see [MCP servers](#mcp-servers)                 |

A missing group, or a missing field in one of them, uses the host defaults;
for `loadConfiguration` that default is empty, for `secrets` it holds no
key, for `providers` it is LM Studio at its default address, for `tools` it
puts no tool on Just run and switches no tool, for `location` it saves no
location, and for `mcp` it lists no server. A `model` group, which
older files hold for a context-size estimate Lys no longer has, is ignored,
and the next save leaves it out. Loading never rewrites an
existing file. Invalid JSON or invalid field values, including a temperature
outside `[0, 1]`, cause loading to fail, and the file is left as it is. Loading
a missing file creates the parent directory and writes the default document.

Every save writes a temporary file beside `settings.json`, readable and
writable only by its owner on Unix, flushes it to disk, and renames it over the
file, so a reader sees the previous document or the whole new one, never part
of a write. The Tauri host is the file's only writer; the backend reads it for
the model provider and its key, the Tavily API key, the Just run choices, and
the MCP servers.

The file carries no version marker. The maintainer accepted that for
[PR #143](https://github.com/w3lt/lys/pull/143); see the
[settings file version exception](/reference/standard-application/#settings-file-version-exception).

### Load configuration

The `loadConfiguration` group holds the settings Lys sends when it loads a
model. The [load request](/reference/api/#model-load-request) defines each
setting.

| Key                         | Type                        | Meaning                                                                       |
| --------------------------- | --------------------------- | ----------------------------------------------------------------------------- |
| `loadConfiguration.default` | object                      | Settings for every model, used where a model has none of its own; starts `{}` |
| `loadConfiguration.models`  | object keyed by model key   | Settings each model has of its own; an entry holds only the changed values    |
| `contextLength`             | integer, 1 to 4,294,967,295 | Context window, in tokens                                                     |
| `evalBatchSize`             | integer, 1 to 4,294,967,295 | Prompt tokens evaluated in one batch                                          |
| `flashAttention`            | boolean                     | Whether flash attention is on                                                 |
| `offloadKVCacheToGpu`       | boolean                     | Whether the KV cache is kept in GPU memory                                    |
| `numExperts`                | integer, 1 to 4,294,967,295 | Experts active per token                                                      |

- Every setting is optional, in `default` and in a `models` entry.
- `default` holds only what you write into it by hand; the Model pane edits
  only `models` entries, and its saves leave `default` as it is in the file.
- Lys reads `settings.json` when it starts. A hand edit made while Lys runs
  takes effect the next time Lys starts. Until then a save from the Model pane
  keeps an edited `default`, and replaces `models` with the entries Lys holds.
- When Lys loads a model, each setting comes from the first of these that sets
  it: the model's own entry, then `default`, then the committed default below.
  `numExperts` is not sent when none of them sets it. The context length is
  lowered to the model's `maxContextLength` when the resolved value is larger.
- A missing group, `default`, or `models` is empty. An unknown setting or part,
  `null`, a fraction, or a value outside the range makes loading the settings
  fail.

The committed default is the file
`apps/desktop/src/lib/models/default_model_load_configuration.json`. It sets
`contextLength`, `evalBatchSize`, `flashAttention`, and `offloadKVCacheToGpu`,
and may set `numExperts`. The desktop bundle embeds it when it is built, so
editing it changes the default after the next build, for every settings file
that does not override a setting. Lys never copies it into `settings.json`. An
invalid committed file stops the desktop at startup.

An older Lys build does not know the group. It ignores it and removes it the
next time it saves settings, so going back to an older build loses the stored
load configurations.

### Secrets

The `secrets` group holds the keys of the services Lys calls on the person's
behalf: `tavilyApiKey`, the key `web_search` sends to Tavily; `ollamaApiKey`,
sent to Ollama Cloud; and `groqApiKey`, sent to Groq. Each key is opaque:
Lys never changes it, and Rust and the backend accept 1 to 256 visible ASCII
characters (`!` through `~`), so it cannot hold a space or a line break. An
invalid key makes the file fail to load, like an out-of-range temperature.
Each key goes only to its own service. The keys are plain text, protected by
the file's owner-only permissions; there is no keychain storage yet.

The desktop saves one key at a time: it reads the group on disk and replaces
only the key that changed, so saving one key never overwrites another.

The backend reads the Tavily key from this file when the desktop lists the
tools, when a chat request offers `web_search`, and when the person checks the
key, so a saved or removed key applies to the next of these without
restarting anything. A turn keeps the key it started with. It reads a
provider key at each connection attempt; see [Providers](#providers).

### Providers

The `providers` group holds the model provider every request goes to, chosen
in Settings → Providers, and where to find it.

| Key                          | Type                                                | Meaning                                                                                  |
| ---------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `providers.active`           | `"lmStudio" \| "ollama" \| "ollamaCloud" \| "groq"` | Provider every request goes to: LM Studio, a local Ollama server, Ollama Cloud, or Groq  |
| `providers.lmStudio.address` | `string \| null`                                    | LM Studio's server, or `null` for `LMSTUDIO_HOST:LMSTUDIO_PORT`                          |
| `providers.ollama.address`   | `string \| null`                                    | The local Ollama server, or `null` for `OLLAMA_HOST:OLLAMA_PORT`; unused by Ollama Cloud |

- An address is a host name or IPv4 address, a colon, and a port from 1 to
  65535, such as `127.0.0.1:1234`. A scheme, a path, a user name, or an IPv6
  address is not an address. It may name another machine; Lys reaches it over
  plain HTTP, without a key.
- A `null` address means the default, which only `@lys/protocol` declares, so
  changing a default moves every file that saved none.
- Ollama Cloud and Groq need their key in the `secrets` group.
  Without it the backend does not connect, and reports the provider as not
  reachable.
- A missing group or field means LM Studio at its default address, as before
  providers could be chosen. An unknown provider or field, or an
  invalid address, makes loading the settings fail.
- The backend reads the group, and the key it needs, at each connection
  attempt: when it starts, and each time the desktop asks it to reconnect.
  The desktop asks after every save from the Providers pane that changes
  where requests go. When it cannot read the file, or the group or the key is
  invalid, it does not connect. It never writes the file.

An older Lys build does not know the group or the two provider keys. It
ignores them and removes them the next time it saves settings, so it goes
back to LM Studio at its default address.

### Tools

The `tools` group holds the approval and the switch the person chose for each
tool in Settings → Tools. `justRun` lists the tools set to Just run; every
other tool, network tools included, is on Ask me and waits for the person
before each call. `switches` holds each tool the person switched on or off,
`true` for on and `false` for off. A tool without an entry starts on when it
only reads this machine and off when it sends requests off it (`network`), so
a tool a later build adds starts at its own default; a tool switched back to
its default keeps its entry. `read_attachment` and the agent state tools
(`read_my_state`, `find_agents`, `read_agent_state`), which the backend adds
to a turn itself, have neither entry: they never ask and cannot be switched
off.

- A name is 1 to 64 ASCII letters, digits, underscores, or hyphens, the rule
  every tool name follows. Any other name, `null` for the group, `justRun`, or
  `switches`, a switch that is not `true` or `false`, or an unknown field
  makes loading the settings fail.
- A name listed twice in `justRun` counts once, and a name given twice in
  `switches` keeps the last value. Lys writes both in ascending name order.
- A name Lys does not list, such as a tool from another build or a backend tool
  whose list could not be read, is kept and has no effect.
- The backend's tool approval service enforces the approval for the desktop's
  tools and the backend's alike. It reads `justRun` from this file when each
  round of tool calls arrives, so a saved change applies from the next round.
  It takes only `justRun`, ignoring every other field of the group, and never
  writes the file. When the file cannot be read, or `tools`, `justRun`, or a
  name in it is invalid, no tool is on Just run, every call asks, and the
  backend logs a warning.
- The backend never reads `switches`. The desktop applies them when it builds
  each chat request: it offers only the tools that are on and can run, names
  the ones that are off and the switched-on ones that cannot run now, or says
  tool calls are off, so the backend can tell the model (see the
  [chat request](/reference/api/#tools-the-turn-does-not-offer)).
- The desktop reads `settings.json` when it starts. A save from the Tools pane
  replaces `justRun` and `switches` with the choices the desktop holds, so a
  hand edit of `justRun` made while Lys runs takes effect at the next round of
  tool calls but is lost at the next save from the pane, and a hand edit of
  `switches` takes effect only at the next start and is likewise lost at the
  next save.

An older Lys build does not know the group. It ignores it and removes it the
next time it saves settings, so every tool asks again and every switch returns
to its default after going back to an older build.

### Location

The `location` group holds the location the person typed in Settings → Tools,
which the `get_location` client tool returns; Lys never detects it. Each part
is optional.

- A part is `null` or 1 to 100 characters, counted as Unicode code points,
  with no control character and no white space at either end. Any other
  value, `null` for the group, or an unknown field makes loading the settings
  fail; the error never quotes the value.
- A missing group or part, and a group whose parts are all `null`, mean no
  location is saved, and `get_location` fails with `locationNotSet`.
- The host's `get_location` command reads the group from this file at each
  call, without creating a missing file, so a saved change, or a hand edit,
  applies to the next call. The backend never reads it.
- The location is personal data stored as plain text, protected by the file's
  owner-only permissions. A call's result is stored with its reply; see
  [Data locations](/operate/data/).

An older Lys build does not know the group. It ignores it and removes it the
next time it saves settings, so the location must be saved again after going
back to an older build.

### MCP servers

The `mcp` group lists the [MCP](/overview/glossary/#mcp-terms) servers whose tools
Lys offers the model. Each server is a command Lys starts and talks to over
its standard input and output (`stdio`), or a URL Lys sends requests to over
Streamable HTTP (`http`):

```json
{
  "mcp": {
    "servers": [
      {
        "name": "files",
        "transport": "stdio",
        "command": "/opt/homebrew/bin/npx",
        "arguments": [
          "-y",
          "@modelcontextprotocol/server-filesystem",
          "/Users/me/Shared"
        ],
        "environment": [{ "name": "LOG_LEVEL", "value": "info" }]
      },
      {
        "name": "docs",
        "transport": "http",
        "url": "https://mcp.example.com/mcp",
        "headers": [{ "name": "Authorization", "value": "Bearer <token>" }]
      }
    ]
  }
}
```

| Field         | Server  | Rule                                                                                                                                                                                                                                                    |
| ------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | both    | 1 to 20 lowercase ASCII letters and digits, in runs joined by single hyphens; each name once in the group. The server's tools are named `mcp__<name>__<tool>`                                                                                           |
| `transport`   | both    | `stdio` or `http`                                                                                                                                                                                                                                       |
| `command`     | `stdio` | 1 to 1,024 characters, no control character or tab, no white space at either end. A bare name such as `npx` is found through the backend's `PATH`; see [Configuration](/operate/configuration/#mcp-servers)                                             |
| `arguments`   | `stdio` | Up to 64 arguments in order, each 1 to 1,024 characters without a line break or another control character but a tab; omitted means none. Passed as they are, without a shell                                                                            |
| `environment` | `stdio` | Up to 32 `{ name, value }` variables, each name once: a name is an ASCII letter or underscore, then up to 127 letters, digits, or underscores; a value is up to 4,096 characters without a control character but a tab, and may be empty                |
| `url`         | `http`  | Up to 2,048 characters without spaces: `https://`, or `http://` only for `localhost`, `127.0.0.1`, or `[::1]`; no user name, password, or `#`; no internationalized domain name, see below                                                              |
| `headers`     | `http`  | Up to 32 `{ name, value }` headers, each name once ignoring case: a name is an HTTP token of up to 128 characters, and not one Lys sets itself; a value is up to 8,192 visible ASCII characters, spaces, and tabs, without a space or tab at either end |

- The group holds at most 16 servers, which take at most 512 KiB together:
  the UTF-8 bytes of the group written as compact JSON, with every omitted
  list filled in. That is half of the 1 MiB of `settings.json` the backend
  reads, so the group, the indentation the host writes, and the other groups
  fit in the file. Characters are counted as Unicode code points, and a text
  with a lone surrogate, which only an escape such as `\ud800` can write, is
  refused. A server object with an unknown field, a field of the other
  transport, a broken rule, a larger group, or `null` for the group makes
  loading the settings fail; an error about a server names the broken rule
  and never quotes a value. An error about the group itself, such as a
  `servers` value that is not a list, can quote that value.
- A URL whose host has a part starting with `xn--` is refused, and so is one
  to a Unicode host such as `bücher.example`, which the URL parser writes in
  that form. The host's URL parser and the backend's convert such
  internationalized domain names differently, so one of them could accept a
  name the other refuses ([#285](https://github.com/w3lt/lys/issues/285)). A host whose characters map to ASCII, such as
  fullwidth letters, is accepted as its ASCII name.
- Lys sets these headers itself and refuses them in `headers`: `Accept`,
  `Content-Length`, `Content-Type`, `Host`, `Last-Event-ID`,
  `MCP-Protocol-Version`, and `Mcp-Session-Id`. It also refuses `Expect`,
  `Keep-Alive`, `Transfer-Encoding`, and `Upgrade`, which Node's fetch, the
  backend's HTTP client, refuses to send.
- A stdio server starts in the person's home folder, with `HOME`, `LOGNAME`,
  `PATH`, `SHELL`, `TERM`, and `USER` from the backend's environment, then the
  configured variables, which win over those. No other variable of the
  backend's environment reaches it.
- Environment values, header values, URLs, and arguments can hold secrets,
  such as an API key or a bearer token. They are stored as plain text,
  protected by the file's owner-only permissions, like the Tavily API key.
  The backend never sends them back: the server list carries only each
  server's name, transport, and state. No log line holds a setting, but a
  stdio server's standard error lines and the error messages a server sends
  are logged as the server wrote them, each cut to 2,000 characters, so a
  server that prints a secret puts it in the
  [backend log](/operate/logging/). An HTTP error answer is logged only by
  its status.
- The backend reads the group when it starts and whenever the desktop asks it
  to sync, which the MCP pane does after each save. It takes only `mcp`,
  ignoring every other group, and never writes the file. When the file
  cannot be read, or the group fails its rules, the backend keeps the servers
  it applied before and reports why; see
  [MCP servers](/reference/api/#mcp-servers).

An older Lys build does not know the group. It ignores it and removes it the
next time it saves settings, so the servers must be added again after going
back to an older build.

## Settings updates

The settings view provides Runtime, Model, Generation, Agents, Tools, MCP,
Providers, and Secrets panes. Model
inventory, load, unload, and loaded-state health controls call the backend
through the application store. The user's agents are stored by the backend,
not in `settings.json`, and the built-in agents ship with the backend and are
not stored at all. The agent selected for a new conversation is kept only
until the app quits. There is no Conversation pane.

Generation edits apply to future messages immediately and are saved
automatically through Tauri. The save reloads the persisted document and replaces
only its `generation` group, preserving the other values already on disk.
Saves are serialized and newer edits are saved after the active write settles.
Save failure leaves the current values usable and exposes a retry action.

Load configuration edits in the Model pane are saved the same way, replacing
only the `models` part of the `loadConfiguration` group. The save keeps the
`default` that is in the file, because only a hand edit changes it. The edits
apply to the next load of the model they belong to. The desktop runs the two
kinds of save one at a time, so neither writes back an older copy of the other
group.

The Secrets pane saves the Tavily API key only when the person presses Save or
Enter, replacing only that key of the `secrets` group in the same serialized
way; Remove saves `null`.

The Providers pane saves a picked provider, including Local or Cloud on the
Ollama card, or an address at
once, replacing only the `providers` group in the same serialized way; an
address is saved when the person presses Save or Enter, and an emptied field
saves `null`. A provider key is saved like the Tavily key, replacing only that
key. After a save that changes where requests go, including a key the active
provider uses, the desktop asks the backend to reconnect. After a failed save,
the backend keeps the provider last saved, and the pane says the save failed.

Choosing Ask me or Just run in the Tools pane, and switching a tool on or off,
is saved automatically the same way, replacing only the `tools` group. An
approval applies from the next round of tool calls once saved, because the
backend reads the file; a tool's switch applies to the next chat request at
once, because the desktop builds the request. After a failed save, approvals
keep following the choices last saved, each switch still applies until Lys
quits, and the pane exposes a retry action. The Tool calls switch remains
session-only and applies to the next chat request.

The Tools pane saves the location only when the person presses Save or
Enter, replacing only the `location` group in the same serialized way;
emptying every field and saving writes `null` for each part. After a failed
save, `get_location` keeps returning the location last saved, and the pane
says the save failed.

The Runtime pane's two startup switches, "Start it when Lys opens" for the
backend and "Start vmo when Lys opens", are saved automatically the same way
whenever either changes. The save writes both switches and keeps the rest of
the `runtime` group as it is in the file; the latest switches win. They apply
the next time Lys opens, or the window reloads, because both read them from
the file. After a failed save, that next launch follows the switches last
saved, the pane says so, and changing a switch tries the save again. A file
saved before `autoStartVmo` existed loads with it on.

The MCP pane saves the servers only when the person saves a server in its
editor or confirms removing one, replacing only the `mcp` group in the same
serialized way, and then asks the running backend to apply them. After a
failed save, the pane says the save failed, an open editor keeps the server
as typed, and the backend keeps the servers it applied before. Its tool chips
and a server's Ask me or Just run choice save the `tools` group the way the
Tools pane does.

The other runtime edits, such as default-model selection, remain in memory for
the current session. A save of another group does not persist those unsaved
edits.

## Desktop theme preference

The active desktop theme is stored separately in WebView `localStorage` under
`lys.theme`. Valid values are `dark` and `light`; the fallback is `dark` when
the value is missing, invalid, or unavailable.

## Current caveats

- The React shell loads runtime settings from Tauri, but runtime edits other
  than the two startup switches, including `runtime.defaultModel`, are not
  persisted back through `save_settings`.
- LM Studio applies its own settings when it loads a model by itself, for
  example when a chat request names a model that is not loaded. The load
  configuration applies only to loads Lys starts. The backend checks that the
  model is loaded before each reply round and each title request, so this
  happens only when the model is unloaded between that check and the request.
