## Summary

Truncating a session removes every message after a chosen point and emits one
event describing the new tail, rather than deleting rows and leaving subscribers
to infer what happened.

## Motivation

Editing a message mid-conversation requires discarding everything that followed
it. Without a defined truncation operation, each caller invented its own
sequence of deletions, and a subscriber could observe a session in a state that
never existed.

## Proposed design

Truncation takes a session and a message identifier. Inside one write
transaction the backend removes every message after it and emits
`session.truncated` carrying the surviving tail identifier. Nothing else in the
session is modified; provider budget accounting is unchanged.

## Alternatives

Soft-deleting truncated messages was rejected: it doubles the states every
consumer must handle in order to support an undo feature that was not requested.

## Consequences

Truncation became a single command with a single event, so replay and live
delivery show the same sequence. Implemented in the same change as
[ADR-0005](/decisions/adr-0005-single-session-writer/).
