`CONTRIBUTING.md` is the canonical source for validation expectations. The
short version is: run the smallest relevant checks first, widen only when your
change affects shared contracts or multiple packages, and never claim a check
passed without current output.

## Current canonical validation commands

```sh
pnpm exec prettier . --check
pnpm exec eslint .
pnpm --filter @lys/desktop test
pnpm --filter @lys/desktop build
pnpm --filter @lys/backend exec tsc --noEmit
pnpm --filter @lys/backend test
cargo fmt --manifest-path apps/desktop/src-tauri/Cargo.toml -- --check
cargo clippy --manifest-path apps/desktop/src-tauri/Cargo.toml --all-targets --all-features -- -D warnings
cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml
```

## Docs-only work

For changes confined to `apps/docs`, start with:

```sh
pnpm --filter @lys/docs run check
pnpm --filter @lys/docs run build
```

Then use broader workspace checks only if the docs change depends on shared
contracts, schemas, or behavior that crosses package boundaries.

## Current test shape

- `apps/backend/test/unit` contains a Vitest unit suite. Run it once with
  `pnpm --filter @lys/backend test`, or rerun it on every change with
  `pnpm --filter @lys/backend run test:watch`. It needs no LM Studio server,
  network access, or `LYS_HOME`.
- `apps/desktop/test/unit` contains a Vitest unit suite for the renderer: the
  HTTP and Tauri API wrappers, the stores and their pure logic, and the
  components, renderer hooks, and views, rendered with Testing Library in
  jsdom. Run it once with `pnpm --filter @lys/desktop test`, or rerun
  it on every change with `pnpm --filter @lys/desktop run test:watch`.
  `pnpm --filter @lys/desktop exec tsc` typechecks the renderer and the suite.
  The suite needs no LM Studio server, running backend, Tauri runtime, or
  personal settings: it substitutes the backend behind `fetch` and the native
  host behind Tauri's `mockIPC`. Known defects stay in the suite as expected
  failures that name the defect and fail the run once it is fixed. Its
  [coverage inventory](https://github.com/w3lt/lys/blob/main/apps/desktop/test/unit/COVERAGE.md)
  lists what each test file covers and what it cannot prove.
- The `Desktop unit tests` workflow runs that typecheck and the desktop suite on
  every pull request and on every push to `main`.
- The shared packages have no package-level test scripts or tracked test suites.
- `apps/backend` also exposes a TypeScript validation path through
  `pnpm --filter @lys/backend exec tsc --noEmit`.
- `apps/docs` exposes `check` and `build` scripts that are appropriate for
  docs-only changes.

## Coming soon

Backend coverage is unit-level only: the backend integration and end-to-end
suites are tracked in [issue #44](https://github.com/w3lt/lys/issues/44) and
[issue #45](https://github.com/w3lt/lys/issues/45), and no CI workflow runs the
backend unit suite yet. The desktop unit suite runs in jsdom, so layout,
scrolling, real pointer and drag behavior, and assistive-technology output
belong to the end-to-end suite. Native Tauri tests and
end-to-end desktop tests are tracked in
[issue #133](https://github.com/w3lt/lys/issues/133) and
[issue #134](https://github.com/w3lt/lys/issues/134). Shared-package automated
test coverage is currently absent. A command that exits successfully without
executing tests does not establish coverage. If you are changing behavior, be explicit in your handoff
about which paths you verified and which still lack dedicated automation.
