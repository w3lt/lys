This page connects the current Lys implementation to the canonical construction
standards. Its observations identify boundaries to review and test; they do not
certify compliance. Generic rules remain in the
[canonical standards](https://github.com/w3lt/lys/blob/main/docs/CODE_STANDARDS.md).
Implementation mappings, compliance findings, and exception evidence belong in
this handbook rather than source comments or the canonical rule chapters.

## Project-specific protocol policy

This policy applies the schema/type authority rule in
[TYPE-009](https://github.com/w3lt/lys/blob/main/docs/code_standards/TYPE.md)
and the construction exception in
[OBJECT-006](https://github.com/w3lt/lys/blob/main/docs/code_standards/OBJECT.md)
to the [protocol API directory](https://github.com/w3lt/lys/tree/main/packages/protocol/src/apis).
It retains the existing project requirements and allowances.

In `packages/protocol/src/apis/`, primary payload contracts such as request bodies, path or query parameters, individual responses, and stream events MUST use Zod schemas, with their payload types inferred from those schemas. Types imported from outside this directory may be used directly.

Endpoint descriptors, status-to-schema maps, reply maps, and framework route wrappers MAY use ordinary objects and TypeScript types that compose the primary contracts. They do not require Zod schemas solely for type derivation. Avoid handwritten mirrors of an inferable schema-map or descriptor shape. Use `z.infer`, `z.input`, or `z.output` only with an actual Zod schema, never with a plain descriptor or schema map.

## LLM runtime surface and unresolved review

The current runtime surface maps to
[IFACE-006 and IFACE-026](https://github.com/w3lt/lys/blob/main/docs/code_standards/INTERFACE.md)
and [CLASS-006](https://github.com/w3lt/lys/blob/main/docs/code_standards/CLASS.md).
The interface default is at most five effective operations; the class default is
at most seven public operations. Inherited operations count, as do public getters,
disposal, and the class's public static factory.

| Declaration                    | Effective surface                                                                                  | Count |
| ------------------------------ | -------------------------------------------------------------------------------------------------- | ----: |
| `LlmEngine`                    | Downloaded inventory, loaded-instance inventory, load, and stop                                    |     4 |
| `LlmRuntimeLifecycle`          | `lifecycleStatus`, `getRuntimeAvailability()`, and `[Symbol.asyncDispose]()`                       |     3 |
| `LlmRuntime`                   | All inherited `LlmEngine` and `LlmRuntimeLifecycle` operations; no additional declarations         |     7 |
| `LmStudioRuntime`              | The seven runtime operations plus public static `create()`; its private constructor does not count |     8 |
| `LlmEngineOperationQueue`      | `handleLlmEngineOperationRequest()`                                                                |     1 |
| `LlmRuntimeConnectionObserver` | `llmRuntimeConnectionStatus`                                                                       |     1 |
| `LlmRuntimeConnector`          | `connectLlmRuntime()`                                                                              |     1 |

The declarations are in [engine capability](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmEngine.ts),
[lifecycle capability](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntimeLifecycle.ts),
[composite runtime](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntime.ts),
[LM Studio adapter](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/runtimes/lmStudioRuntime.ts),
[service consumer contract](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmService.ts),
[runtime capabilities](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntimeCapabilities.ts),
and [runtime service](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntimeService.ts).

`LlmRuntimeService` consumes the full `LlmRuntime`: the four engine operations
on behalf of `LlmService`, `getRuntimeAvailability()` for probes, and disposal.
[Singleton composition](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/singleton.ts)
supplies `create()` as the runtime service's acquisition capability; each
acquired instance transfers to the runtime service, which releases it when it
drops the connection or cleans up. Source inspection found no production calls
to `lifecycleStatus`. The factory's readiness check calls the SDK directly, so
it does not establish a consumer of the public availability method.

The seven-operation composite and eight-operation class exceed their default
limits. Shared resource identity alone does not satisfy the exception criteria:
the inspected production owner uses six of the seven operations, and no actual
consumer or approved public contract was established for `lifecycleStatus`.
No valid exception approval was established in the inspected repository and PR
review evidence. [Issue #37](https://github.com/w3lt/lys/issues/37) remains unresolved;
recording these facts does not approve an exception or change the implementation.

Historically, [review finding I-8 on PR #23](https://github.com/w3lt/lys/pull/23#issuecomment-5633082465)
identified a missing design record and approval behind source-level exception
claims. Those claims were subsequently removed from source documentation. The
missing record was not present in the inspected repository or its path history,
and the inspected PR review list was empty; this describes the inspected evidence,
not proof that no discussion could have occurred elsewhere. Moving the review
mapping here does not close the finding's underlying surface-compliance issue.

A separate implementation decision can reduce the surface or provide the evidence
and explicit reviewer approval required by the
[exception process](https://github.com/w3lt/lys/blob/main/CONTRIBUTING.md).
Removing both currently unused observations would leave five interface operations
and six public class operations including `create()`. That is a proposed change,
not an implemented compatibility decision. Behavioral coverage remains separate
work tracked in [issue #25](https://github.com/w3lt/lys/issues/25).

## Agent editor error discovery exception

The Agents pane editor has an approved exception to the multiple-control
clause of
[COMP-130](https://github.com/w3lt/lys/blob/main/docs/code_standards/COMPONENT.md):
when a rejected save leaves more than one field invalid, focus does not move to
an error summary. The exception was approved by the maintainer on 2026-10-04
for [PR #116](https://github.com/w3lt/lys/pull/116), following review finding
I-6.

- **Scope:** only the rejected-save path of the
  [agent editor](https://github.com/w3lt/lys/blob/main/apps/desktop/src/components/SettingsViewComponents/AgentEditor.tsx)
  when a draft has more than one problem.
  [`findAgentDraftProblem`](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/store/agents/agent-draft.ts)
  reports the first problem in field order. The single-control clause still
  applies and is met: the field is marked invalid, described by the problem,
  and focused, and the entered text stays intact.
- **Constraint:** the approved pane design shows one problem line. A summary
  needs design decisions that the design does not make: its placement, its
  look in both themes, and whether each problem also appears under its field.
- **Alternatives considered:**
  - Building a summary without a design was rejected, because it would invent
    those decisions.
  - Holding #116 until the summary exists was rejected by the maintainer.
- **Risk and control:** a draft with several problems shows one of them per
  save attempt. Nothing is sent while any problem remains, and each problem is
  announced through its focused field.
- **Removal condition:** [issue #117](https://github.com/w3lt/lys/issues/117)
  delivers the summary, and this exception is removed with it.

## File tool path exception

The `read_text_file` and `find_files` desktop commands have an approved
exception to
[API-018](https://github.com/w3lt/lys/blob/main/docs/code_standards/API.md):
they accept any absolute path that the desktop process can read, instead of
constraining it to the resources Lys may use. The exception was approved by
the maintainer on 2026-10-07 for
[PR #115](https://github.com/w3lt/lys/pull/115), following review finding I-1.

- **Scope:** only the
  [read-text-file](https://github.com/w3lt/lys/blob/main/apps/desktop/src-tauri/src/tools/read_text_file.rs)
  and
  [search-files](https://github.com/w3lt/lys/blob/main/apps/desktop/src-tauri/src/tools/search_files.rs)
  commands. Every other path-taking API still follows API-018.
- **Constraint:** the commands are tools, not the permission gateway, and Lys
  has no path policy yet for them to check against. The paths they can reach
  are bounded only by the operating-system user that runs Lys, which today is
  the person who launched it.
- **Alternatives considered:**
  - A fixed restriction inside the commands, such as the home directory only
    or no hidden files, was rejected when the tools were designed: it would be
    a second path policy, separate from the gateway's.
  - A path check in the permission gateway that
    [issue #110](https://github.com/w3lt/lys/issues/110) introduces needs that
    gateway, and it would still run with the full access of the person's
    account.
- **Risk and control:** any renderer code can read or list every file that the
  operating-system user running Lys can read. No part of the app invokes the
  commands yet, and the renderer's Markdown pipeline does not render raw HTML,
  so review found no path for injected script to reach them. The window has no
  content security policy, so this control depends on the renderer running
  only its own code. The commands must not be offered to a model before the
  gateway exists.
- **Removal condition:** [issue #122](https://github.com/w3lt/lys/issues/122)
  runs Lys's file access as a dedicated, less-privileged operating-system user,
  so the operating system limits the commands to the paths that user is
  granted, on the provider side as
  [API-015](https://github.com/w3lt/lys/blob/main/docs/code_standards/API.md)
  requires. This exception is removed with that change.

### Example of scoped stream completion

| Observation in the current chat exchange | What it establishes                                                   | What it does not establish                                               |
| ---------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Successful response establishment        | The consumer can begin reading the declared representation            | Generation and persistence have completed successfully                   |
| Conversation start event                 | Identifiers for this exchange are available according to the protocol | All later tasks have succeeded                                           |
| Assistant `done` event                   | The assistant generation has reached its documented outcome           | No title or other task event can follow                                  |
| Stream closure                           | No more bytes arrive on that connection                               | Every required application outcome occurred or every effect was reversed |

The [SSE reference](/reference/sse-events/) explains the current task ordering. A complete API contract identifies which remaining outcomes each consumer requires before it reports success.

## Asynchronous work

Canonical rules: [ASYNC-001, ASYNC-002, ASYNC-003](https://github.com/w3lt/lys/blob/main/docs/code_standards/ASYNC.md).

These examples identify useful review boundaries in the current repository. They do not certify that existing implementations satisfy every rule in the linked standard.

| Situation                                                                                         | Contract distinction                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The LLM runtime service serializes accepted operations through a private completion tail          | Accepted model operations and connection attempts use an application-owned completion-only contract. Keeping the queue usable after failure is separate from preserving each caller's original failure and establishing bounded admission. |
| Service disposal closes admission before awaiting accepted work                                   | Joining accepted operations before dependency release demonstrates one shutdown boundary; it does not by itself establish every cancellation or deadline requirement.                                                                      |
| Service construction registers each acquired service for asynchronous cleanup                     | A later acquisition failure still requires release of earlier services and preservation of both creation and cleanup failures.                                                                                                             |
| A reply generation starts its reply and title tasks and joins them with an all-settled collection | Joining both lifetimes does not handle rejected results; each rejected outcome still has to reach the generation's failure reporter before its followers close.                                                                            |
| The generation registry records a conversation's running title task when it admits the generation | The record exists before the task can start, so a later turn of the same conversation cannot start a second title task. It must end when that task settles, whether it succeeds or fails, or later turns never retry.                      |
| The desktop chat adapter returns an async generator                                               | Calling the generator supplies an iterator; consuming it begins the fetch. Never iterating and exiting early are different lifetime paths.                                                                                                 |
| The desktop stops a request and revokes its publication token                                     | Old output can lose authority immediately while the underlying transport remains pending. Publication safety and termination are separate obligations.                                                                                     |
| Assistant completion arrives before the generated title                                           | One domain task can finish while the enclosing stream still has valid work and messages to deliver.                                                                                                                                        |
| An early stream exit cancels a reader and releases its lock                                       | Cancelling the source, releasing the reader, and preserving a failure during cleanup require distinct protocol handling.                                                                                                                   |
| A hook owns an uptime interval while the application store owns model requests                    | The hook releases its interval on unmount. Model requests survive view unmounts; invalidating local publication and aborting transport do not cancel accepted backend work.                                                                |

The relevant sources are the [LLM service](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmService.ts), [LLM runtime service](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntimeService.ts), [service lifetime](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/singleton.ts), [reply generation](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/chat/replyGeneration.ts), [generation registry](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/chat/replyGenerationRegistry.ts), [desktop chat adapter](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/apis/http/chat.ts), [chat-view owner](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/store/chat-view/index.ts), [uptime hook](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/hooks/backendRuntime.ts), and [model request owner](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/store/model-actions.ts).

No backend service-lifetime tests are currently tracked. These source examples identify boundaries that need controlled-schedule tests; they are not evidence of executed coverage. See the [testing guide](/develop/testing/) for the current gap.

## Resource ownership

Canonical rules: [RESOURCE-025 through RESOURCE-031](https://github.com/w3lt/lys/blob/main/docs/code_standards/RESOURCE.md).

These examples identify useful review boundaries in the current repository. They do not certify that existing implementations satisfy every rule in the linked standard.

| Situation                                                                             | Contract distinction                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A service bundle exposes operation capabilities and a module-private close capability | Using a service and owning the bundle's complete cleanup are different responsibilities. A frozen outer record does not by itself establish compliant lifecycle ownership.                                                                |
| Each service acquisition is registered before acquiring the next service              | The next acquisition can fail without removing responsibility for the services already acquired. Installation into the final application host is another ownership boundary.                                                              |
| The LLM runtime service owns a runtime adapter that retains one SDK client            | The runtime protects the client with its disposal stack; the runtime service waits for accepted work before disposing the runtime and disposes a runtime that stopped answering. Closing the client does not unload remote model weights. |
| The database owner keeps one compiled statement per SQL text for every operation      | The statements' use depends on the connection remaining valid; returning a statement to an operation does not give that operation ownership of it.                                                                                        |
| A model inventory operation returns immutable instance identities                     | The snapshot is data. It does not establish exclusive ownership of models that other clients can change.                                                                                                                                  |
| A chat sender captures a borrowed reply connection                                    | The sender can use the connection within its permitted lifetime without owning the connection's release.                                                                                                                                  |
| An effect registers pointer and keyboard listeners on the document                    | The effect owns its two registrations and borrows the document and DOM references.                                                                                                                                                        |
| A view observes application-owned model requests                                      | Removing the view does not end request ownership. The application store invalidates observations and aborts local transport when the runtime is released; accepted backend work may continue.                                             |
| A stream adapter cancels early consumption and then releases its reader lock          | Upstream cancellation and lock release are separate obligations; cleanup failures still need their proper outcome.                                                                                                                        |
| Native shutdown observes the direct child process                                     | Direct-child exit, descendant lifetime, process-group termination, and handle release are separate facts.                                                                                                                                 |

The relevant sources are the [service bundle and runtime acquisition](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/singleton.ts), [application lifetime registration](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/fastify.ts), [database owner](https://github.com/w3lt/lys/blob/main/apps/backend/src/infrastructure/database/sqliteDatabase.ts), [LLM service](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmService.ts), [LLM runtime service](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntimeService.ts), [LM Studio runtime owner](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/runtimes/lmStudioRuntime.ts), [remote model reconciliation](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/stopLlmModelsByKey.ts), [borrowed reply sender](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/chat/routes/share.ts), [listener registrations](https://github.com/w3lt/lys/blob/main/apps/desktop/src/components/ComposerComponents/ComposerContextMeter.tsx), [model request owner](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/store/model-actions.ts), [stream reader](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/apis/http/chat.ts), and [native process owner](https://github.com/w3lt/lys/blob/main/apps/desktop/src-tauri/src/backend.rs).

The backend unit suite has cases for the backend owners above, with substituted services, SDK clients, and in-memory databases, except the application lifetime registration, whose composition cases belong to the integration suite in [issue #44](https://github.com/w3lt/lys/issues/44). The desktop and native owners have no tracked lifetime tests. These examples identify ownership boundaries to test, not verified cleanup coverage; see the [testing guide](/develop/testing/).

## Persisted schemas

Canonical rules: [SCHEMA-001, SCHEMA-002, SCHEMA-003](https://github.com/w3lt/lys/blob/main/docs/code_standards/SCHEMA.md).

These examples identify boundaries in the current source; they do not certify those implementations as compliant with the linked standard or every active standard. Existing limitations are not exceptions for new or modified code.

| Observed boundary                                                                                                                                                                                                                                               | Schema and migration distinction                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Conversation storage keeps an ordered array of SQL migrations and uses its position as the version                                                                                                                                                              | Array order is persistent history; changing an applied entry can make fresh and upgraded stores disagree.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| The migration runner acquires a write transaction before reading the version, applies pending changes, updates the marker, and commits                                                                                                                          | Coordination, schema changes, and version recording have a concrete boundary; this does not prove general application writes or external effects are atomic.                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| The database owner rejects a newer version before publishing borrowed transactions                                                                                                                                                                              | Supported opening versions and dependent access are explicit concerns; the open factory owns acquisition and failure cleanup.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Conversation tables define role checks, correlated assistant status and finish reason, indexes, and timestamp triggers                                                                                                                                          | A storage schema contains behavioral invariants beyond its column names. Copying rows alone would not preserve the complete contract.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| The `agents` table checks only that each column is present and the code, name, bio, and system prompt are non-empty, while the agent schemas check code format, lengths, trimmed and well-formed text, and timestamps on every row the backend writes and reads | The storage constraint is deliberately narrower than the domain contract, so a format change needs no table rebuild; a writer that bypasses the schemas can store a row that then fails to read.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Shared conversation schemas constrain UUIDs and timestamps, while SQL enforces an assistant-state relationship not fully encoded in the runtime shape                                                                                                           | Similar representations do not prove identical enforcement; each invariant needs a deliberate owner and consistent affected mappings.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Conversation metadata reads alias stored column names and validate the returned value                                                                                                                                                                           | A query result and its static type are separate from the trusted internal representation. Missing rows and invalid rows have different outcomes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Conversation-list cursors carry a version and query binding                                                                                                                                                                                                     | Versioned representation contracts extend beyond databases. The current decoder validates its shape before rejecting unsupported versions; its existence does not waive version-selection rules.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| The chat route installs a shared request schema and the desktop validates decoded stream events                                                                                                                                                                 | Schema changes affect real producers and consumers, including coercion, required fields, discriminants, and strict unknown-field handling.                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Native settings initialize defaults when absent and deserialize existing JSON, but have no explicit format migration path                                                                                                                                       | Defaults and current field names do not establish historical version identity or a failure-safe document migration. Configuration rules remain applicable.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| The database owner opens SQLite and runs migrations, while the recovery runbook declares no supported repair procedure                                                                                                                                          | Backend unit cases run the migrations against in-memory databases for fresh creation, a repeated run, a newer-version refusal, and rollback of a failed migration. A conversation-turns case covers restart recovery of replies left streaming. A database-owner case reopens a current-version file and keeps its stored data. One case upgrades a version-5 store holding a conversation to version 6; its fixture is the current schema without the `agents` table, which equals version 5 because migration 6 only adds that table. No tracked test establishes upgrades from earlier versions or operator repair. |

The relevant sources are the [conversation services](https://github.com/w3lt/lys/tree/main/apps/backend/src/modules/conversation), [conversation records](https://github.com/w3lt/lys/tree/main/apps/backend/src/infrastructure/database/conversations), [database owner](https://github.com/w3lt/lys/blob/main/apps/backend/src/infrastructure/database/sqliteDatabase.ts), [migration runner](https://github.com/w3lt/lys/blob/main/apps/backend/src/infrastructure/database/migrations.ts), [shared conversation schemas](https://github.com/w3lt/lys/blob/main/packages/share/src/models/conversation.ts), [agent records](https://github.com/w3lt/lys/tree/main/apps/backend/src/infrastructure/database/agents), [agent schemas](https://github.com/w3lt/lys/blob/main/packages/share/src/models/agent.ts), [cursor encoding and decoding](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/conversation/listOptions.ts), [chat protocol schemas](https://github.com/w3lt/lys/blob/main/packages/protocol/src/apis/chat/chatRoute.ts), [backend chat registration](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/chat/routes/chatRoute.ts), [desktop stream validation](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/apis/http/chat.ts), [native settings persistence](https://github.com/w3lt/lys/blob/main/apps/desktop/src-tauri/src/settings.rs), and [current recovery-support statement](/operate/runbooks/recover-session-database/).

## Test boundaries and current gaps

Canonical rules: [TEST-001, TEST-002, TEST-003](https://github.com/w3lt/lys/blob/main/docs/code_standards/TEST.md).

These examples identify production boundaries and validation tooling present in the repository. They do not claim that automated tests cover those boundaries or that the implementation complies with every active requirement. Existing limitations are not exceptions for new or modified code.

| Observed boundary                                                                                                                                                                   | Test and fixture distinction                                                                                                                                                        |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend routes use shared protocol descriptors and delegate to application capabilities                                                                                             | A future route test must exercise real request validation and response mapping; sharing a descriptor alone does not independently protect its historical external path.             |
| The stop operation distinguishes canonical model keys from loaded instance identifiers and reconciles state after unload                                                            | Meaningful fixtures must distinguish multiple instances and unrelated models; command outcomes and final inventory require separate assertions.                                     |
| The LLM runtime service owns queued operations, connection attempts, and asynchronous shutdown                                                                                      | Concurrency coverage requires controlled admission and settlement boundaries; reading the lifecycle implementation is not execution evidence.                                       |
| Singleton composition acquires services and owns their reverse-order release                                                                                                        | Ownership tests need to observe partial acquisition and compound failures. Such tests would not by themselves prove file durability or historical migrations.                       |
| The backend manifest declares only development and bundle-build scripts, and its TypeScript project includes source, the build script, the unit tests, and the Vitest configuration | The backend has a tracked Vitest unit suite but no supported `test` script, so the suite runs only through `vitest` directly. Type checking does not establish behavioral coverage. |
| The desktop manifest includes a test runner, but no desktop cases are tracked                                                                                                       | A dependency or command is not evidence of exercised behavior.                                                                                                                      |

The relevant sources are the [load route](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/routes/loadModelRoute.ts), [unload route](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/routes/unloadModelRoute.ts), [stop operation](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/stopLlmModelsByKey.ts), [LLM service](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmService.ts), [LLM runtime service](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntimeService.ts), [singleton composition](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/singleton.ts), [backend package manifest](https://github.com/w3lt/lys/blob/main/apps/backend/package.json), [backend TypeScript project](https://github.com/w3lt/lys/blob/main/apps/backend/tsconfig.json), [desktop package manifest](https://github.com/w3lt/lys/blob/main/apps/desktop/package.json), and [current testing guide](/develop/testing/).

The backend has a tracked unit suite only; desktop and shared-package test suites are currently absent from the tracked repository. The boundaries above identify where evidence is needed; they are not a passing run, measured coverage, or a supported production-service integration suite.
