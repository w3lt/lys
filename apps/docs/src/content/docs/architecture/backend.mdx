The backend is a TypeScript Fastify application in `apps/backend`. It owns the
SQLite conversation store and the HTTP and SSE surface consumed by the desktop
application.

## Current backend shape

| Layer              | Implementation                 | Responsibility                                                                                        |
| ------------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| App bootstrap      | `src/app.ts`                   | Registers CORS, SSE support, singleton services, and all routes.                                      |
| Runtime config     | `src/config.ts`                | Loads loopback host and port values, the SQLite path, the system and title prompts, and title limits. |
| Singleton services | `src/di/singleton.ts`          | Creates the chat and conversation services, and selects the runtime owned by the LLM service.         |
| Chat routes        | `src/modules/chat`             | Accepts chat requests, persists turn data, streams SSE responses, and updates conversation titles.    |
| LLM routes         | `src/modules/llm/routes`       | Lists LM Studio models, checks loaded-model health, and loads or unloads a model on demand.           |
| Health route       | `src/modules/health/routes.ts` | Returns a simple `{ ok: true }` response.                                                             |

## Chat request flow

1. `POST /api/v1/chat` validates the request body with the shared Zod schema.
2. `ConversationTurn` creates or looks up the conversation, inserts the user
   message, and inserts an empty streaming assistant message.
3. The route immediately emits either `start-new-conversation-turn` or
   `start-existing-conversation-turn`.
4. For an existing conversation with a stored title, the route emits that title
   to reconcile desktop metadata from an earlier missed delivery.
5. `createChatTask` opens an OpenAI-compatible streaming completion against LM
   Studio and converts model chunks into `delta` and `done` events.
6. When the conversation has no stored title, `createTitleGenerationTask` runs
   in parallel and emits a `title` event after it wins the first assignment.
7. Chat generation errors become `error` events when the client is still
   connected; title-generation failures are logged instead.

Each completion receives the default system prompt and the current user message.
Continuing an existing conversation appends a turn in SQLite but does not send
earlier messages or the stored conversation-specific system prompt to the model.
The required `generationOptions` controls supply sampling temperature and an
optional completion-token ceiling; the [API reference](/reference/api/#chat-request-body)
defines their limits.

The Lys system prompt and the title-generation prompt are read once, when
`loadBackendConfig()` builds the backend configuration at startup.

A new conversation is stored without a title (`null`). Title generation runs
for every turn whose conversation has no stored title and uses that turn's user
message, so a conversation that remains untitled after an earlier failed or
interrupted task gets another try on its next turn. It uses a separate chat
completion request with a JSON-schema response format that limits the title to
`generatedTitleMaxLength` Unicode code points (100 by default), then validates the
reply; JSON wrapped in one Markdown code fence is accepted. Only a reply that
cannot be used as a title leads to another attempt, up to
`titleGenerationMaxAttempts` attempts per turn (three by default). An HTTP,
connection, or cancellation failure ends title generation for the turn, after
the OpenAI SDK has retried a connection failure, timeout, or 408, 409, 429, or
5xx response up to two more times within the attempt. Concurrent title tasks
use a conditional first assignment, and only the winning task publishes its
candidate. Existing titled turns send the stored title after their start event,
which repairs desktop metadata after a prior title event was lost.

The current chat task updates the stored assistant status and finish reason, but
does not append streamed delta text to the stored assistant content. The full
reply shown by the desktop therefore exists only in current-window state.

## Persistence

The backend stores conversations in SQLite at `~/.lys/lys_db.sqlite`.

| Table                   | Purpose                                                                                      |
| ----------------------- | -------------------------------------------------------------------------------------------- |
| `conversations`         | Stores conversation metadata, title, system prompt, and timestamps.                          |
| `conversation_messages` | Stores ordered user and assistant messages, assistant status, finish reason, and timestamps. |

The database schema is applied by inline migrations using `PRAGMA user_version`.
Two triggers keep `conversations.updated_at` in sync with message inserts and
message updates.

## LM Studio integration

Chat generation and model management use separate integration boundaries:

| Service           | Backend dependency  | Current use                                                                                                       |
| ----------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `ChatService`     | `openai` SDK        | Streams chat completions and generates titles through LM Studio's OpenAI-compatible HTTP interface.               |
| `LlmService`      | `LlmServiceRuntime` | Coordinates inventory, loaded-model health, model loading, and stopping instances matching a canonical model key. |
| `LmStudioRuntime` | `@lmstudio/sdk`     | Verifies engine availability, implements model operations and lifecycle inspection, and owns SDK client cleanup.  |

Fastify exposes the application-scoped `llmService` as `LlmService`. Each LLM
route uses its required provider-neutral capability for inventory, health,
loading, or stopping. The ownership path is
`routes -> LlmService -> LlmRuntime -> LmStudioRuntime -> SDK`. The composition
root constructs the runtime, protects it during acquisition, and transfers it to
the service. If service publication fails, cleanup runs through the current
owner. The service drains accepted operations before disposing its runtime;
runtime disposal releases the client without unloading models or stopping the
external engine. Consumers do not select or depend on the concrete runtime.

`LlmRuntime` combines `LlmEngine` and `LlmRuntimeLifecycle`. The service receives
a narrower view containing the four engine operations and disposal. The full
runtime additionally exposes a synchronous lifecycle snapshot and a fresh SDK
availability query. Runtime creation waits for LM Studio to answer its version
query; connection, authentication, and query errors reported by the SDK reject
startup and release acquired resources. An empty model inventory does not
prevent startup.

The installed SDK cannot cancel a pending version query. Acquisition and
availability checks therefore have no completion deadline; a nonresponding
dependency or a malformed response ignored by the SDK can keep startup or
shutdown pending.

The backend currently assumes a local LM Studio runtime on loopback.

`GET /api/v1/llm/:modelId/health` uses the same service queue and makes one fresh
loaded-inventory query. It reports `ready` when the validated snapshot contains
the requested canonical key. An absent key reports `model-not-loaded`; a query
that cannot establish loaded state reports `runtime-unavailable`. The check
does not generate text or change which models are loaded, and does not involve
`ChatService`. It establishes current availability, not future inference success.
See the [health response contract](/reference/api/#model-health-responses).

## Failure behavior

| Condition                                          | Current behavior                                                                                                           |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Chat SSE connection closes                         | The close handler aborts the signal used by chat and title generation; no further title request is made.                   |
| Model operation or health-check client disconnects | Accepted work continues until success or failure; user cancellation is unavailable.                                        |
| LLM service already has nine accepted operations   | New inventory/health/load/unload requests receive `503` with `urn:lys:problem:llm:service-busy` before acceptance.         |
| Model stream ends without a finish reason          | The route treats it as an error and may emit `error`.                                                                      |
| Assistant state update fails                       | The backend throws because the persisted assistant row is missing.                                                         |
| Unknown finish reason                              | The backend throws instead of silently coercing it.                                                                        |
| Title generation produces no usable title          | The task logs a warning and sends no `error` or `title` event; a later turn retries if the conversation is still untitled. |
| A generated title cannot be saved                  | The task logs an error and sends no `title` event; a later turn retries if the conversation is still untitled.             |
| A stored title cannot be sent after turn start     | The backend logs at debug level and continues chat generation; a later turn attempts reconciliation again.                 |
| Starting a turn fails for another reason           | The route rethrows; Fastify logs it and responds `500` if no event was sent. Written rows stay.                            |

See the [provider cancellation policy](/architecture/providers/#cancellation-policy)
for the separate inference and model-management lifetimes.

## What is not implemented here

- No Rust backend service
- No replayable shared event bus
- No public conversation listing or history-retrieval API; continuing a turn
  requires a conversation identifier the caller already knows
- No credential-management layer
- No provider fallback or budget-accounting logic
