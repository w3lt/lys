## The desktop shows the backend as stopped

The desktop runtime pane controls the backend child owned by Tauri. It does not
discover a backend launched separately in a terminal. Choose one launch path
before starting another process on the same port.

For the desktop-managed path:

- confirm the runtime pane reports `stopped` rather than `starting`
- start the backend from that pane
- the pane switches to `running` only after `GET /api/v1/heath` answers; if
  the process stays up without answering for 30 seconds, it shows **Backend
  not responding**. Press **Stop**, then **Start**
- verify `GET /api/v1/heath` responds at `http://127.0.0.1:12345`

If the listener is unavailable, inspect the backend's log: the day's file
`logs/backend-YYYY-MM-DD.log` in the Lys home, named by the UTC date, or the
terminal of a development build (see
[the backend log files](/operate/logging/#the-backend-log-files)). A backend
that stopped on a failure, such as a prompt file it cannot read or a port
already in use, logs it there at level `fatal`; only a missing or relative
`LYS_HOME` stops it before it can log, with the reason on standard error.
LM Studio is not required for the backend to listen. For standalone startup,
also ensure `LYS_HOME` is set to an absolute path and its directory exists as
described in [Running Lys locally](/develop/running/).

## LM Studio is not reachable

The Runtime pane's LM Studio card shows **LM Studio not reachable** when the
backend cannot connect to `127.0.0.1:1234`, and the model list stays empty.
Start LM Studio and its local server, then press **Refresh** on that card. The
backend does not retry on its own.

## The backend starts but model operations fail

The backend is wired to LM Studio at `127.0.0.1:1234`. If model listing,
loading, or chat requests fail after HTTP readiness was established, verify
that LM Studio is still reachable. When LM Studio stops while connected, the
next failing model request marks it not reachable; press **Refresh** after
restarting it. The
[model health endpoint](/operate/logging/#model-health-observation) can report
loaded state; it does not test inference success.

## vmo is not ready, so `read_page` is unavailable

The backend offers `read_page` only while vmo answers `GET /health` at
`127.0.0.1:8080`. Until then, the Tools pane shows `read_page` off and
disabled, with "vmo, Lys's page reader, isn't ready. See Settings → Runtime."
The vmo card in Settings → Runtime says why:

- **vmo starting**: every start fetches the `lys-readpage` image's `latest`
  tag from `ghcr.io`, and the first start, or the first after a new reader
  image, downloads the `vminit` or `lys-readpage` image, which can take a few
  minutes. A development build compiles vmo first. Lys waits up to ten
  minutes.
- **vmo not responding**: the process stayed up for ten minutes without
  answering, or a start or stop failed while vmo still ran or its status could
  not be read; the card then shows that failure. Press **Stop**, then
  **Start**. Check network access to `ghcr.io`, and that the Mac meets
  [vmo's requirements](/operate/dependencies/#vmo); vmo does not boot its VMs
  without the kernel described there
  ([#200](https://github.com/w3lt/lys/issues/200)).
- **vmo stopped** right after Start: the process exited before it answered,
  for example because it could not reach `ghcr.io` for its images; could not
  read which `vminit` [its image store](/operate/data/#vmos-image-store)
  holds unpacked, delete that unpack, or unpack and save the new one; could
  not delete the images it no longer uses from the store; or, in a
  development build, did not compile. In development, vmo's build and error
  output appear in the terminal that runs `pnpm dev`. When every start stops
  this way although `ghcr.io` is reachable and the disk has room for vmo's
  images, delete `~/Library/Application Support/com.w3lt.lys-vmo` while vmo
  is stopped; the next start downloads its images again.
- **Lys couldn't start vmo: Failed to run …/vmo: No such file or directory**:
  vmo is not installed. Run `build.sh`; see
  [Packaging and releases](/operate/releases/).

## vmo was killed

Stopping vmo sends it `SIGTERM` and waits up to 60 seconds while it deletes its
VMs. When it has not exited by then, Lys kills it, and the vmo card says "vmo
didn't stop in time and was killed. It may have left VMs running."
Lys cannot remove those VMs yet; a restart of the Mac ends them. Quitting Lys
waits for vmo the same way, so quitting can take up to a minute.

## A vmo or backend keeps running after Lys died

Lys stops vmo and the backend when it quits. When it dies without quitting,
after a crash, Force Quit, or `kill -9`, or when a development rebuild restarts
the desktop host, both keep running
([#202](https://github.com/w3lt/lys/issues/202)). The next Lys cannot start its
own: the vmo and backend it starts cannot listen and exit. Its cards still show
**vmo running** and **Backend running**, because the old processes answer their
health routes, and `read_page` works through the old vmo. Stop and quitting Lys
do not reach either old process.

To end them, find each process by its port and send it `SIGTERM`:

```sh
lsof -nP -iTCP:8080 -sTCP:LISTEN    # vmo
lsof -nP -iTCP:12345 -sTCP:LISTEN   # backend
kill <pid>
```

Never use `kill -9` on vmo: only `SIGTERM` lets it delete its VMs before it
exits, which can take up to a minute. Once `lsof` shows nothing on a port,
press **Stop** and then **Start** on that process's card, or quit and reopen
Lys. The cards still show the old processes as running, so **Start** stays
unavailable until **Stop**.

## An MCP server shows Failed

A server tagged `failed` in Settings → MCP says in its details why the
backend could not connect to it, or why its connection ended. The backend log has an
`MCP server could not be connected` entry with the same `reason` and what Lys
saw in `failure`, or an `MCP server connection ended` entry; a command
server's own error output is logged as `MCP server log line` entries (see
[MCP server entries](/operate/logging/#mcp-server-entries)). Nothing
reconnects by itself: fix the cause, then press **Retry** in the server's
details. A save that changes the server also tries again.

| `reason`         | Cause and what to do                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `start-failed`   | The command could not be started, usually because it was not found. Lys starts it without a shell and with the short `PATH` of an app opened from Finder or the Dock; see [the command works in a terminal](#an-mcp-command-works-in-a-terminal-but-not-in-lys).                                                                                                                                                                                                                       |
| `closed`         | The process exited, or the connection ended, while connecting or later. Read the server's log lines: a wrong argument, a missing variable such as an API key, or a crash. Running the same command in a terminal shows its output too. A URL server that no longer knows its session, such as after it restarted, answers a call with HTTP `404`, which also ends the connection; press **Retry**. An answer larger than 16 MiB once the server is connected also ends the connection. |
| `timed-out`      | The server did not connect and list its tools within two minutes. A first `npx -y` downloads the package and can take that long; press **Retry** once it is done. A command that waits for input, such as a sign-in prompt, never answers.                                                                                                                                                                                                                                             |
| `unauthorized`   | The server answered HTTP `401` or `403`. Check the token under Sign-in and the headers. A server that needs an OAuth sign-in cannot be used yet ([#253](https://github.com/w3lt/lys/issues/253)).                                                                                                                                                                                                                                                                                      |
| `unreachable`    | No connection could be made: the host or port is wrong, the name does not resolve, or the server is not running. A server on `localhost` must be started before Lys connects.                                                                                                                                                                                                                                                                                                          |
| `http-error`     | The server answered another HTTP error, or a redirect, which Lys does not follow. Check the URL's path, such as a missing `/mcp`, and use the address a redirect points to.                                                                                                                                                                                                                                                                                                            |
| `protocol-error` | The server's answers are not valid MCP, or an answer is larger than 16 MiB while connecting, or it refused to connect or to list its tools; a `refused` failure in the log carries its message. Check that the URL is the server's MCP endpoint, not a web page, and that it speaks Streamable HTTP.                                                                                                                                                                                   |

Lys speaks only Streamable HTTP to a URL server. A server that offers only the
older HTTP+SSE transport cannot be used yet
([#254](https://github.com/w3lt/lys/issues/254)).

A server tagged `not applied` is a saved server the backend does not list,
such as one saved while the backend could not apply the settings. **Start**,
or **Connect** for a remote server, in its details applies the saved servers.

## An MCP command works in a terminal but not in Lys

The backend starts a command server with `HOME`, `LOGNAME`, `PATH`, `SHELL`,
`TERM`, and `USER` from its own environment, and no shell. An app opened from
Finder or the Dock gets the short `PATH` macOS gives apps, without the folders
a shell profile adds, such as Homebrew's `/opt/homebrew/bin` or a version
manager's, so a bare `npx`, `uvx`, or `node` is often not found
([#258](https://github.com/w3lt/lys/issues/258)). Enter the command's full
path, which `command -v npx` prints in a terminal. A command that is a script,
such as `npx`, also needs its interpreter: when the server then fails as
`closed` because `node` is not found, add a `PATH` variable in Environment
whose value holds the interpreter's folder, followed by `:/usr/bin:/bin`.

Shell syntax does not work either: quotes in Arguments only group an argument
that holds a space, and `~`, `$VARIABLE`, pipes, and `&&` reach the command
unchanged.

## An MCP server's tools are missing or skipped

- The backend lists a server's tools only while the server is connected, so
  the Tools pane has an `MCP · <server>` group only then.
- The backend reads a server's tool list once, when it connects. A server
  that adds tools later needs **Restart** or **Reconnect**
  ([#256](https://github.com/w3lt/lys/issues/256)).
- A connected server's details say `· N skipped` when the backend left
  tools out; **Skipped tools** lists each with why. A tool is named
  `mcp__<server>__<tool>` in at most 64 characters, so a tool name that is
  too long can fit under a shorter server name. Two tools whose names become
  the same once their unsupported characters are replaced keep only the first;
  a tool whose input schema Lys cannot offer, or one larger than 64 KiB,
  cannot be used through Lys, and neither can one whose name or input schema
  holds a character a person cannot see, such as a zero-width space.
- Lys reads a server's first 128 tools, and its details say so when it lists
  more. It reads the tool list across at most 16 pages: a server whose 16th
  page names a next one fails to connect, unless its list passed 128 tools
  before that page.
- A tool whose input schema nests deeper than 32 levels is skipped, however
  deep it nests; the server's other tools stay usable.

## A message fails because an MCP server is not connected

The chat shows "`<tool>` is unavailable: its MCP server isn't connected. See
Settings → MCP, or switch `<tool>` off." The backend refused the message
because the message offered a tool of a server that is not connected now, such
as one whose connection ended after the tool list was read. Lys reads the tool
list again, so the next message leaves that server's tools out; press
**Restart** or **Reconnect** in the server's details to bring them back. The MCP pane can still
show the server as connected, because it does not read the states again then.

A call whose server stops being connected during a reply fails instead: the
model reads that the server is not connected, and the call is stored as
failed.

## The MCP pane says Lys keeps the servers it applied last

The pane says "The mcp group in settings.json isn't valid." or "Lys couldn't
read settings.json." when the backend's last read of the settings file failed,
which happens after a hand edit of the file. The backend keeps the servers it
applied before. The backend log has a matching entry; for an invalid group,
its `problems` name each broken rule (see
[MCP servers](/reference/configuration/#mcp-servers) for the rules). Fix the
file, then quit and reopen Lys: the desktop host also refuses a settings file
whose `mcp` group breaks the rules.

## Lys forgets runtime settings

The Runtime pane saves its two startup switches, "Start it when Lys opens" for
the backend and "Start vmo when Lys opens", to `$LYS_HOME/settings.json`
whenever either changes. When that save fails, the pane says "Lys couldn't save
the startup switches. The next launch follows the switches last saved; changing
a switch tries again." Then:

- check whether `$LYS_HOME/settings.json` exists
- if it exists, verify that it contains valid JSON
- if it does not exist, the host should recreate it the next time settings are
  loaded

The default-model selection is not saved and lasts for the session only.
Generation controls and load configurations autosave separately and expose a
save failure with a retry action; those saves preserve the runtime and model
values already on disk.

## Startup fails after a schema change

The backend's database owner reads SQLite `PRAGMA user_version` when it opens
the database on startup and refuses to open a database newer than the running
binary supports. If a startup failure mentions an unsupported database version,
use a matching or newer build rather than editing the database by hand.

## The desktop app exits at startup or uses another data directory

The desktop host resolves `LYS_HOME` once at startup. A relative path,
including an unexpanded `~/…`, or a value that is not valid UTF-8 stops the app
before any window opens and prints `Lys cannot start: …` to standard error. That
message is visible only when the app is started from a terminal. Set `LYS_HOME`
to an absolute path, or unset it to use `~/.lys`.

An app opened from Finder or the Dock does not see a `LYS_HOME` exported in a
shell profile, so it uses `~/.lys`. See the
[Lys home directory](/reference/configuration/#lys-home-directory) reference.

## Known gaps

The repository does not currently include evidenced support for:

- automated store repair commands
- diagnostics bundles
- vmo log files in the release app
  ([#229](https://github.com/w3lt/lys/issues/229))
- a published operator escalation path

Those workflows should be documented here only after the product ships them.
