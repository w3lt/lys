The repository policy is explicit: documentation changes belong in the same
change as the behavior or contract they describe.

## Put facts at their canonical source

- Put workflow and contributor policy in `CONTRIBUTING.md`.
- Put construction rules in `docs/CODE_STANDARDS.md` and its active chapters.
- Put JS and TS documentation rules in `docs/JSDOC.md`.
- Put durable decision history in ADRs.
- Put proposed future changes in RFCs.
- Put shared runtime and transport contracts in reference pages or the package
  code they describe.

When a page depends on an existing decision or standard, prefer linking to that
source over restating it in slightly different words.

## Keep code and construction rules independent

Source comments and JSDoc describe the code's contract, constraints, and
reasoning. They do not cite construction-rule IDs or carry compliance findings
or exception-approval records. Record standards-category labels in the
[implementation classifications](/reference/implementation-classifications/),
while keeping the actual ownership and behavior contracts beside declarations.

Canonical standards define general requirements and may use illustrative
examples. They do not depend on concrete Lys declarations, source paths, or
the current implementation's compliance status.

Document relationships between an implementation and a rule in this handbook
under `apps/docs`. Link to both sources there, distinguish observations from
verified guarantees, and keep findings and exception status with their
supporting evidence. The [implementation mappings](/reference/standard-application/)
collect the current examples; they do not redefine rules or grant exceptions.

## Handbook validation

The docs app validates handbook frontmatter at build time. The content model
currently recognizes these `docType` values:

- `architecture`
- `decision`
- `proposal`
- `runbook`
- `reference`

Decision and proposal pages also have required metadata such as identifiers,
status, dates, and affected areas.

## Record integrity

Generated handbook indexes fail closed when required record metadata is missing
or two records claim the same identifier. That is deliberate: a broken index is
better than publishing misleading decision or RFC listings.

## Practical writing rules

- Remove filler and stale claims instead of decorating them.
- Say when a capability does not exist yet.
- Avoid inventing policy not grounded in the repo.
- Keep docs close to the code and contracts they describe.
