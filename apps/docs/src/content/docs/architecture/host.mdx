The Tauri layer is a small native host. It does not implement the backend API
itself; it starts the backend and vmo, the page reader `read_page` uses, and
exposes a few native commands to the React UI.

## Registered commands

| Command              | Purpose                                                                                       |
| -------------------- | --------------------------------------------------------------------------------------------- |
| `start_backend`      | Starts the backend for the current build mode with the Lys home and stores the child handle.  |
| `stop_backend`       | Kills the backend process group and waits for shutdown.                                       |
| `get_backend_status` | Reports whether the stored child process is still running.                                    |
| `start_vmo`          | Starts vmo for the current build mode unless the owned vmo runs, and reports its status.      |
| `stop_vmo`           | Sends vmo `SIGTERM`, waits up to 60 seconds for it to exit, then kills it, and reports which. |
| `get_vmo_status`     | Reports whether the owned vmo is stopped, running, or stopping.                               |
| `get_vmo_health`     | Asks vmo's `GET /health` at `127.0.0.1:8080` whether it can read pages, within one second.    |
| `load_settings`      | Reads `$LYS_HOME/settings.json`, creating a default file if needed.                           |
| `save_settings`      | Replaces `$LYS_HOME/settings.json` atomically, owner-only, with a new settings JSON document. |
| `read_text_file`     | Returns the complete text of one UTF-8 file of at most 1 MiB.                                 |
| `find_files`         | Searches a directory tree for regular files by name or by text content.                       |
| `list_tools`         | Returns the definition of every client tool, for the Tools settings pane.                     |

## File tools

`read_text_file` and `find_files` are the desktop side of the client tools that
let Lys work with files on the user's machine. The desktop's tool-call store
runs them for the calls the backend sends to run: calls the person allowed, or
calls of a tool set to Just run in the Tools pane. The backend's tool approval
service decides which; see [Desktop](/architecture/desktop/#tool-calls). The renderer reaches them through `readTextFile` and `findFiles` in
`apps/desktop/src/lib/apis/tauri/tools.ts`, which validate arguments, results,
and declared failures with the schemas exported by `@lys/protocol`.

Both commands accept any absolute path that the desktop process can read. They
are tools, not a permission gateway: deciding whether Lys may use a tool or a
path belongs to the caller that runs tool requests. Relative paths are rejected
rather than resolved against the process's working directory. Each call runs on
Tauri's blocking-task pool, so the window stays responsive, and cannot be
cancelled.

- `read_text_file` follows symbolic links and returns the whole file. It
  rejects directories, FIFOs, sockets, and devices without blocking on them,
  files over 1 MiB, and content that is not UTF-8. It never truncates.
- `find_files` walks the tree breadth-first, lists each directory in byte order
  of entry names, and never follows symbolic links below the root. It compares
  file names, lines of UTF-8 files up to 1 MiB, or both, case-insensitively
  after Unicode lowercasing. A search stops after the requested number of
  matches (50 by default, at most 200), 20,000 examined entries, or 64 MiB of
  read content, and its report says whether the result limit or a scan budget
  ended it.

Expected failures reject with a JSON object whose `code` names the failure,
such as `{ "code": "fileNotFound" }`. Any other rejection, such as an
unregistered command, is thrown by the TypeScript wrappers as an error.

## Client tool list

`list_tools` returns `CLIENT_TOOLS` from `src-tauri/src/tools/client_tools.rs`:
the definition of every client tool, in the order Settings lists them. A
definition holds what a model is offered for the tool, its name, description,
and arguments, plus the `group` and `access` that Settings shows and the
`runner`, which is `client` for every tool here. It mirrors
`toolDefinitionSchema` in `@lys/share`, which the backend's `AgentTool` also
uses, and the renderer's `listTools` validates the list with
`listToolsResultSchema` from `@lys/protocol`, which also requires every
`runner` to be `client`. A list that does not match is rejected with the
caller-safe message "The app returned an invalid tool list.", and the
decoding failure is kept as its cause.

Each tool builds its own definition next to the limits it enforces, so a
description states the current limits. The tools are named `read_text_file`
and `search_files`; the search-files tool keeps its name although its command
is `find_files`. Its arguments are the exact keys of the `find_files` filter,
and `target` is an enum of `name`, `content`, and `nameAndContent`. The command
reads nothing and never fails.

## Lys home

Before building the application, the host resolves the
[Lys home directory](/reference/configuration/#lys-home-directory) once from the
`LYS_HOME` environment variable and manages it as application state. The
settings, backend, and vmo commands receive that value instead of reading the
environment again. An invalid `LYS_HOME` stops the app before any window opens.

## Backend process ownership

The host owns a `Backend` state object containing `Mutex<Option<Child>>`. The
child process is started only when the UI asks for it or when auto-start logic
requests it during desktop initialization.

The child depends on the build mode:

- Development builds run `pnpm run dev` from `apps/backend` in the checkout
  recorded at compile time.
- Release builds run `$LYS_HOME/runtime/node/bin/node` with
  `$LYS_HOME/runtime/backend/backend.mjs`.

```rust
Command::new("pnpm")
    .args(["run", "dev"])
    .current_dir(backend_dir)
    .env("LYS_HOME", lys_home.as_path())
    .process_group(0)
    .spawn()
```

Both children run in their own process group, with `LYS_HOME` set to the Lys
home the host resolved, so the backend uses the same directory as the host.

When the direct child is still running, stopping the backend sends `SIGKILL`
to its whole process group and waits for that child. If the direct child has
already exited, the host clears its handle without killing any surviving
descendants. On app exit, the host stops the backend while it stops vmo; see
[vmo process ownership](#vmo-process-ownership).

The checked-in process supervisor currently uses Unix process-group APIs and
the `nix` crate. The repository does not yet demonstrate equivalent lifecycle
behavior on Windows.

## vmo process ownership

The host owns one `Vmo` state object (`src/vmo.rs`). vmo starts when the
desktop's initialization or the Runtime pane asks for it, never on its own.
The child depends on the build mode:

- Development builds run `bash run.sh` in `apps/vmo` of the checkout recorded
  at compile time. `run.sh` builds vmo, signs it, and replaces itself with it
  through `exec`, so the child the host owns is vmo itself.
- Release builds run `$LYS_HOME/runtime/vmo/vmo`, which `build.sh` installs.

vmo runs in a process group of its own. The host does not set `LYS_HOME`
for vmo, which does not read it.
`start_vmo` checks and spawns under one lock, so two starts never spawn two
children; it leaves a running vmo alone and refuses while a stop still waits
for the previous one, which holds vmo's port. A spawn failure names the
program it tried to run.

vmo deletes its VMs when it receives `SIGTERM`, and a second `SIGTERM` would
end it before it finishes. A stop therefore sends `SIGTERM` to vmo's process
group once and checks every 100 ms whether vmo has exited. A stop that arrives
meanwhile joins it and gets the same result, without another signal. When vmo
still runs after 60 seconds, the stop sends `SIGKILL` and reports `killed`:
vmo may then have left VMs running. When `SIGTERM` or a check fails, the stop
sends `SIGKILL` at once and reports the failure. It sends `SIGKILL` at most
once and does not repeat a failed one, because by then the group's identifier
may name another group. `stop_vmo` and `get_vmo_health` run off the main
thread, so a stop never blocks the window.

`get_vmo_health` sends `GET /health` over a plain TCP connection to
`127.0.0.1:8080` and answers `ready` only for a `HTTP/1.1 200` status line
within one second. It runs in the host because vmo sends no CORS headers. It
asks whatever listens on vmo's port, so the renderer reads `get_vmo_status`
first, which keeps a vmo that has exited from counting as ready.

On app exit, the host stops vmo and the backend together and waits for both,
so quitting can take up to 60 seconds while vmo deletes its VMs. A failure or
a killed vmo is written to standard error and does not stop the exit. When the
app dies without running its exit handler, after a crash, Force Quit, or
`kill -9`, vmo and the backend keep running
([#202](https://github.com/w3lt/lys/issues/202)); see
[troubleshooting](/operate/troubleshooting/#a-vmo-or-backend-keeps-running-after-lys-died).

## Settings file

The host creates the following defaults when the settings file is missing:

```json
{
  "runtime": {
    "autoStartBackend": true,
    "autoStartVmo": true,
    "defaultModel": null,
    "backendAddress": "http://127.0.0.1:12345"
  },
  "model": {
    "contextSize": 32768
  },
  "generation": {
    "temperature": 0.7,
    "replyCeiling": 2048
  },
  "loadConfiguration": {
    "default": {},
    "models": {}
  },
  "secrets": {
    "tavilyApiKey": null
  },
  "tools": {
    "justRun": []
  }
}
```

Only the Rust host writes this file. The React UI reaches it through Tauri
`invoke` calls, and the backend reads it for the Tavily API key of
`web_search`. Every write, including the defaults of a missing file, goes to a
new temporary file beside it, created with mode `0600` on Unix and flushed to
disk, which is then renamed over the file. The temporary file's name holds the
process id and a per-process number, so no two saves share one, and creating
it never opens, truncates, or follows anything already at that name. A reader
therefore sees the previous document or a complete new one, also while the
installed app and a development build save at the same moment (the one
renamed last is kept), and other OS users cannot read the key. A failed save
removes its temporary file; a host that stops in the middle of a save leaves
it, owner-only. The rename itself is not synced to the directory, so it is not
promised to survive a power loss. When `settings.json` is a symbolic link, the rename replaces the
link with a regular file, and the file it pointed to stops receiving saves.

The `secrets` group holds the Tavily API key as plain text, validated on load
(1 to 256 visible ASCII characters); an invalid key makes loading fail. Its
`Debug` output never shows the key.

The host only stores the `loadConfiguration` group. A settings file written
before load configurations existed has no such group; `load_settings` reads it
as empty and does not rewrite the file. The committed default load
configuration belongs to the renderer, which applies it when it resolves a load
(see the [configuration reference](/reference/configuration/#load-configuration)).

The desktop automatically saves generation edits by reading this document,
replacing its generation group, and saving the complete document. Load
configuration edits are saved the same way, and so are each tool's Ask me or
Just run choice and the Tavily API key when the person saves or removes it in
the Secrets pane. A change of either startup switch in the Runtime pane saves
`autoStartBackend` and `autoStartVmo` and keeps the rest of the `runtime`
group as stored; a file without `autoStartVmo` loads it as `true`. The other
runtime edits and `model.contextSize` edits in the UI remain session-only; the
automatic saves preserve those values as already stored on disk. The local context size
supports the generation controls and the agent editor's prompt measure, and is
separate from the context length a model is loaded with, which the composer's
context meter shows.

## What the host does not currently do

- It does not manage provider credentials.
- It does not read the operating-system keychain.
- It does not proxy HTTP requests to LM Studio.
- It does not replay prior conversations into the window.
- It does not stop vmo or the backend when it dies without running its exit
  handler ([#202](https://github.com/w3lt/lys/issues/202)).
