## Context

Provider credentials were read by the backend directly from the
operating-system keychain. That put secret material in the same process as
provider HTTP clients, adapter parsing code, and the session store, so any
parsing bug in an adapter had a plausible path to a credential.

It also made the trust boundary hard to describe. Reviewers could not answer
"what has access to a key" without reading three crates.

## Decision

The Tauri host is the only component that reads the keychain. It issues
short-lived, scoped credential handles to the backend, and the backend
exchanges a handle for an authorised request at call time. Handles are never
persisted and never appear in logs, diagnostics bundles, or events.

- The host owns keychain access and handle issuance.
- The backend holds handles in memory for the duration of a call.
- Provider adapters receive an authorised client, never a secret.

## Alternatives considered

- Keep direct keychain access in the backend, and rely on review discipline.
  Rejected: the boundary was not enforceable.
- Run a separate credential process. Rejected: a third process for one
  responsibility, with no benefit over the host that already exists.
- Encrypt credentials at rest inside the session store. Rejected: moves the
  secret closer to the data most likely to be exported in a diagnostics bundle.

## Consequences

The trust boundary is now one sentence long, and a compromised adapter cannot
exfiltrate a key. Cost: every provider call crosses the process boundary once
more, and offline development needs a stub handle issuer.

[ADR-0003](/decisions/adr-0003-single-event-bus/) is superseded because the
single-bus assumption depended on the backend being the only credentialed
component.
