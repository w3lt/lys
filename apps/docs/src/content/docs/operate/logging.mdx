## Backend health check

The backend registers a single health endpoint that returns `{ ok: true }` when
the Fastify app is running:

- route: `/api/v1/heath`
- method: `GET`

This confirms that the HTTP listener responds. The desktop's runtime status
instead observes its owned backend child process and does not perform this
health request.

## Model health observation

`GET /api/v1/llm/:modelId/health` observes whether a canonical model key is
currently loaded. Encode the key as one path parameter. An accepted query
returns `200` with `modelId`, `latencyMs`, and either:

- `status: "ready"`
- `status: "not-ready"` with reason `model-not-loaded` or `runtime-unavailable`

Queue admission rejection returns `503` Problem Details. Responses use
`Cache-Control: no-store`. Loaded state is a fresh inventory observation and
does not prove that a later inference request will succeed.

## Process logging

The backend logs requests, the failures it reports, Node's warnings, and the
LM Studio SDK's messages through one pino logger, which it creates before it
loads the rest of its configuration and which Fastify uses for requests. The
logger writes level `info` and above, so the `debug` calls in the chat path
are not written. Each line is one JSON object whose `level` is the level name
and whose `time` is a UTC ISO-8601 time. The log keeps everything: a
request's lines carry its full URL, query string included, so a history
search is written too, and a request for a route that does not exist gets a
line of its own. A line, shown here across several lines:

```json
{
  "level": "info",
  "time": "2026-10-21T08:15:02.123Z",
  "pid": 4242,
  "hostname": "mac",
  "reqId": "req-1",
  "req": {
    "method": "GET",
    "url": "/api/v1/heath",
    "host": "127.0.0.1:12345",
    "remoteAddress": "127.0.0.1",
    "remotePort": 52538
  },
  "msg": "incoming request"
}
```

The backend writes each line to two places, whatever started it: it appends
the line to its log file for the day, `$LYS_HOME/logs/backend-YYYY-MM-DD.log`
(see [the backend log files](#the-backend-log-files)), and writes it to its
standard output, which shows the line where the backend was started:

| Started by                          | Where the standard output goes                                                                                                           |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm backend:dev`                  | The terminal, through `pino-pretty`: `[10:15:02.123] INFO (4242): incoming request` in local time, with the other fields indented below. |
| `pnpm dev`, the development desktop | The terminal that runs `pnpm dev`, the same way, because the host runs the backend's `dev` script.                                       |
| The release app                     | The app's own standard output, which only an app started from a terminal shows.                                                          |

When writing to its standard output or standard error fails, such as on a
full disk or once `pino-pretty` has exited, the backend keeps running. The
lines it cannot write are lost, and it writes again once the stream works,
such as after space has been freed. The first failure of each stream is
reported on the other stream; later failures of that stream are not.

The Tauri host does not keep the backend's output. It writes its own failures,
such as a backend it could not stop at exit, to its standard error, which only
an app started from a terminal shows.

### The backend log files

- The backend appends each line to the file of the UTC day on which it writes
  the line, so each day has one file, which every run of that day adds to. A
  running backend moves to the next day's file with its first line after
  midnight UTC.
- Lys never deletes or rewrites a log file, so the files add up over time;
  delete old ones yourself when you no longer need them.
- The backend creates `$LYS_HOME/logs/` whenever it is missing, but never a
  missing Lys home, and each day's file with that day's first line; a new
  file is readable and writable by its owner only. Development runs and
  standalone `pnpm backend:dev` write their files too, in the Lys home they
  run with.
- When a line cannot be appended, such as on a full disk, it is lost from the
  file, or only its start is kept when the disk fills partway through it, but
  it is still written to standard output. The backend keeps running, reports
  the first such failure on its standard error, and appends again once writing
  works.
- When the backend stops on a failure nothing caught, it logs the failure at
  level `fatal`, with Node's `origin` of it, before Node ends it. This
  includes a prompt file it cannot read, a database that cannot be opened,
  and a port already in use.
- Each warning Node reports, such as a deprecation, is logged at level `warn`
  as `Node reported a warning`, with the warning's type, code, and text in
  `err`.
- Each message of the LM Studio SDK, such as why it could not connect to LM
  Studio, is logged at the level the SDK gave it, with the text the SDK would
  have printed in `msg`, its `[LMStudioClient]…` prefix first, an error with
  its stack, and no terminal colors. Its `debug` messages are left out like
  the backend's own. When the model provider cannot be reached, the backend
  also logs its own `Model provider runtime acquisition failed` line, for
  every provider. Its error names neither the provider's answer nor a key.
- Some output never reaches the files, only the backend's standard error:
  a failure before the backend has created its logger, which only `LYS_HOME`
  not set or not an absolute path causes; Node's messages before the
  backend's code runs, such as a missing backend bundle; and the few messages
  the LM Studio SDK prints itself instead of through its logger, such as
  `writeUpstream called when not subscribed`. Node also still prints each
  warning, and the failure that stops the backend, on standard error. The
  release app opened from Finder or the Dock does not keep its standard
  error.
- The files hold request lines (method, full URL with its query string,
  host, remote address and port, status, response time), so they keep the
  text of history searches, and the failures the backend reports, whose
  messages and stacks can name models, files, or page URLs. Nothing is
  redacted
  ([request log exception](/reference/standard-application/#request-log-exception)),
  so read a log before you share it.

To follow today's log while Lys runs:

```sh
tail -f ~/.lys/logs/backend-$(date -u +%F).log
```

From a checkout, `pino-pretty` shows a file the way the development terminal
does:

```sh
pnpm --filter @lys/backend exec pino-pretty < ~/.lys/logs/backend-$(date -u +%F).log
```

vmo's output is not kept in a release build
([#229](https://github.com/w3lt/lys/issues/229)).

## Desktop runtime status

The desktop runtime settings pane exposes a small amount of process state:

- whether the backend is `running`, `starting`, `stopping`, or `stopped`
- the persisted `runtime.backendAddress`, defaulting to
  `http://127.0.0.1:12345`, as status copy
- a derived uptime label while the backend is running

The same pane also exposes `Start` and `Stop` actions that call Tauri commands
to manage the backend child process.

## What is not implemented yet

The repository does not currently prove support for:

- vmo log files ([#229](https://github.com/w3lt/lys/issues/229))
- removing old backend log files
- diagnostics bundles
- redaction policies for exported diagnostics artifacts
- a documented incident-sharing workflow

:::note[Coming soon]
Removing old log files, diagnostics bundles, and export and redaction rules
should be added to this page only after the repository ships them as supported
behavior.
:::
