This page connects the current Lys implementation to the canonical construction
standards. Its observations identify boundaries to review and test; they do not
certify compliance. Generic rules remain in the
[canonical standards](https://github.com/w3lt/lys/blob/main/docs/CODE_STANDARDS.md).
Implementation mappings, compliance findings, and exception evidence belong in
this handbook rather than source comments or the canonical rule chapters.

## Project-specific protocol policy

This policy applies the schema/type authority rule in
[TYPE-009](https://github.com/w3lt/lys/blob/main/docs/code_standards/TYPE.md)
and the construction exception in
[OBJECT-006](https://github.com/w3lt/lys/blob/main/docs/code_standards/OBJECT.md)
to the [protocol API directory](https://github.com/w3lt/lys/tree/main/packages/protocol/src/apis).
It retains the existing project requirements and allowances.

In `packages/protocol/src/apis/`, primary payload contracts such as request bodies, path or query parameters, individual responses, and stream events MUST use Zod schemas, with their payload types inferred from those schemas. Types imported from outside this directory may be used directly.

Endpoint descriptors, status-to-schema maps, reply maps, and framework route wrappers MAY use ordinary objects and TypeScript types that compose the primary contracts. They do not require Zod schemas solely for type derivation. Avoid handwritten mirrors of an inferable schema-map or descriptor shape. Use `z.infer`, `z.input`, or `z.output` only with an actual Zod schema, never with a plain descriptor or schema map.

## LLM runtime surface and unresolved review

The current runtime surface maps to
[IFACE-006 and IFACE-026](https://github.com/w3lt/lys/blob/main/docs/code_standards/INTERFACE.md)
and [CLASS-006](https://github.com/w3lt/lys/blob/main/docs/code_standards/CLASS.md).
The interface default is at most five effective operations; the class default is
at most seven public operations. Inherited operations count, as do public getters,
disposal, and the class's public static factory.

| Declaration           | Effective surface                                                                                  | Count |
| --------------------- | -------------------------------------------------------------------------------------------------- | ----: |
| `LlmEngine`           | Downloaded inventory, loaded-instance inventory, load, and stop                                    |     4 |
| `LlmRuntimeLifecycle` | `lifecycleStatus`, `getRuntimeAvailability()`, and `[Symbol.asyncDispose]()`                       |     3 |
| `LlmRuntime`          | All inherited `LlmEngine` and `LlmRuntimeLifecycle` operations; no additional declarations         |     7 |
| `LmStudioRuntime`     | The seven runtime operations plus public static `create()`; its private constructor does not count |     8 |
| `LlmServiceRuntime`   | `LlmEngine` plus `AsyncDisposable`                                                                 |     5 |

The declarations are in [engine capability](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmEngine.ts),
[lifecycle capability](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntimeLifecycle.ts),
[composite runtime](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/llmRuntime.ts),
[LM Studio adapter](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/runtimes/lmStudioRuntime.ts),
and [service consumer contract](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/services/llmService.ts).

Production service calls use the four engine operations and disposal.
[Singleton composition](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/singleton.ts)
uses `create()` for acquisition and retains cleanup responsibility until the
instance transfers to the service. The service consumes the same runtime instance
through its five-operation contract. Source inspection found no production calls
to `lifecycleStatus` or `getRuntimeAvailability()`. The factory's readiness check
calls the SDK directly, so it does not establish a consumer of the public
availability method.

The seven-operation composite and eight-operation class exceed their default
limits. Shared resource identity alone does not satisfy the exception criteria:
the inspected production owner already uses a smaller contract, and no actual
consumer or approved public contract was established for the two observations.
No valid exception approval was established in the inspected repository and PR
review evidence. [Issue #37](https://github.com/w3lt/lys/issues/37) remains unresolved;
recording these facts does not approve an exception or change the implementation.

Historically, [review finding I-8 on PR #23](https://github.com/w3lt/lys/pull/23#issuecomment-5633082465)
identified a missing design record and approval behind source-level exception
claims. Those claims were subsequently removed from source documentation. The
missing record was not present in the inspected repository or its path history,
and the inspected PR review list was empty; this describes the inspected evidence,
not proof that no discussion could have occurred elsewhere. Moving the review
mapping here does not close the finding's underlying surface-compliance issue.

A separate implementation decision can reduce the surface or provide the evidence
and explicit reviewer approval required by the
[exception process](https://github.com/w3lt/lys/blob/main/CONTRIBUTING.md).
Removing both currently unused observations would leave five interface operations
and six public class operations including `create()`. That is a proposed change,
not an implemented compatibility decision. Behavioral coverage remains separate
work tracked in [issue #25](https://github.com/w3lt/lys/issues/25).

### Example of scoped stream completion

| Observation in the current chat exchange | What it establishes                                                   | What it does not establish                                               |
| ---------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Successful response establishment        | The consumer can begin reading the declared representation            | Generation and persistence have completed successfully                   |
| Conversation start event                 | Identifiers for this exchange are available according to the protocol | All later tasks have succeeded                                           |
| Assistant `done` event                   | The assistant generation has reached its documented outcome           | No title or other task event can follow                                  |
| Stream closure                           | No more bytes arrive on that connection                               | Every required application outcome occurred or every effect was reversed |

The [SSE reference](/reference/sse-events/) explains the current task ordering. A complete API contract identifies which remaining outcomes each consumer requires before it reports success.

## Asynchronous work

Canonical rules: [ASYNC-001, ASYNC-002, ASYNC-003](https://github.com/w3lt/lys/blob/main/docs/code_standards/ASYNC.md).

These examples identify useful review boundaries in the current repository. They do not certify that existing implementations satisfy every rule in the linked standard.

| Situation                                                                        | Contract distinction                                                                                                                                                                                               |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The LLM service serializes accepted operations through a private completion tail | Accepted model operations use an application-owned completion-only contract. Keeping the queue usable after failure is separate from preserving each caller's original failure and establishing bounded admission. |
| Service disposal closes admission before awaiting accepted work                  | Joining accepted operations before dependency release demonstrates one shutdown boundary; it does not by itself establish every cancellation or deadline requirement.                                              |
| Service construction registers each acquired service for asynchronous cleanup    | A later acquisition failure still requires release of earlier services and preservation of both creation and cleanup failures.                                                                                     |
| The chat route starts assistant and title tasks and awaits all settlements       | Joining both lifetimes does not handle rejected results if the result collection is discarded.                                                                                                                     |
| The desktop chat adapter returns an async generator                              | Calling the generator supplies an iterator; consuming it begins the fetch. Never iterating and exiting early are different lifetime paths.                                                                         |
| The desktop stops a request and revokes its publication token                    | Old output can lose authority immediately while the underlying transport remains pending. Publication safety and termination are separate obligations.                                                             |
| Assistant completion arrives before the generated title                          | One domain task can finish while the enclosing stream still has valid work and messages to deliver.                                                                                                                |
| An early stream exit cancels a reader and releases its lock                      | Cancelling the source, releasing the reader, and preserving a failure during cleanup require distinct protocol handling.                                                                                           |
| A hook owns an uptime interval while the application store owns model requests   | The hook releases its interval on unmount. Model requests survive view unmounts; invalidating local publication and aborting transport do not cancel accepted backend work.                                        |

The relevant sources are the [LLM service](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/services/llmService.ts), [service lifetime](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/singleton.ts), [chat task group](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/chat/chat/index.ts), [desktop chat adapter](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/apis/http/chat.ts), [chat-view owner](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/store/chat-view/index.ts), [uptime hook](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/hooks/backendRuntime.ts), and [model request owner](https://github.com/w3lt/lys/blob/main/apps/desktop/src/lib/store/model-actions.ts).

## Persisted schemas

Canonical rules: [SCHEMA-001, SCHEMA-002, SCHEMA-003](https://github.com/w3lt/lys/blob/main/docs/code_standards/SCHEMA.md).

These examples identify boundaries in the current source; they do not certify those implementations as compliant with the linked standard or every active standard. Existing limitations are not exceptions for new or modified code.

| Observed boundary                                                                                                                                     | Schema and migration distinction                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Conversation storage keeps an ordered array of SQL migrations and uses its position as the version                                                    | Array order is persistent history; changing an applied entry can make fresh and upgraded stores disagree.                                                                                        |
| The migration runner acquires a write transaction before reading the version, applies pending changes, updates the marker, and commits                | Coordination, schema changes, and version recording have a concrete boundary; this does not prove general application writes or external effects are atomic.                                     |
| The store rejects a newer version before publishing borrowed access                                                                                   | Supported opening versions and dependent access are explicit concerns; the open factory owns acquisition and failure cleanup.                                                                    |
| Conversation tables define role checks, correlated assistant status and finish reason, indexes, and timestamp triggers                                | A storage schema contains behavioral invariants beyond its column names. Copying rows alone would not preserve the complete contract.                                                            |
| Shared conversation schemas constrain UUIDs and timestamps, while SQL enforces an assistant-state relationship not fully encoded in the runtime shape | Similar representations do not prove identical enforcement; each invariant needs a deliberate owner and consistent affected mappings.                                                            |
| Conversation metadata reads alias stored column names and validate the returned value                                                                 | A query result and its static type are separate from the trusted internal representation. Missing rows and invalid rows have different outcomes.                                                 |
| Conversation-list cursors carry a version and query binding                                                                                           | Versioned representation contracts extend beyond databases. The current decoder validates its shape before rejecting unsupported versions; its existence does not waive version-selection rules. |
| The chat route installs a shared request schema and the desktop validates decoded stream events                                                       | Schema changes affect real producers and consumers, including coercion, required fields, discriminants, and strict unknown-field handling.                                                       |
| Native settings initialize defaults when absent and deserialize existing JSON, but have no explicit format migration path                             | Defaults and current field names do not establish historical version identity or a failure-safe document migration. Configuration rules remain applicable.                                       |
| The conversation store opens SQLite and runs migrations, while the recovery runbook declares no supported repair procedure                            | Backend tests cover fresh creation, historical upgrades, rollback, and streaming-state recovery. They do not establish an operator repair procedure.                                             |

## Test boundaries and current gaps

Canonical rules: [TEST-001, TEST-002, TEST-003](https://github.com/w3lt/lys/blob/main/docs/code_standards/TEST.md).

These examples identify production boundaries and validation tooling present in the repository. They do not claim that automated tests cover those boundaries or that the implementation complies with every active requirement. Existing limitations are not exceptions for new or modified code.

| Observed boundary                                                                                                        | Test and fixture distinction                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend routes use shared protocol descriptors and delegate to application capabilities                                  | Route tests exercise real request validation and response mapping; sharing a descriptor alone does not independently protect its historical external path.    |
| The stop operation distinguishes canonical model keys from loaded instance identifiers and reconciles state after unload | Meaningful fixtures must distinguish multiple instances and unrelated models; command outcomes and final inventory require separate assertions.               |
| The LLM service owns queued operations and asynchronous shutdown                                                         | Concurrency coverage requires controlled admission and settlement boundaries; reading the lifecycle implementation is not execution evidence.                 |
| Singleton composition acquires services and owns their reverse-order release                                             | Ownership tests need to observe partial acquisition and compound failures. Such tests would not by themselves prove file durability or historical migrations. |
| The backend manifest runs Node tests through tsx, and TypeScript includes both implementation and tests                  | History and chat tests exercise SQLite and HTTP/SSE boundaries. Type checking alone does not establish behavioral coverage.                                   |
| The desktop manifest includes a test runner, but no desktop cases are tracked                                            | A dependency or command is not evidence of exercised behavior.                                                                                                |

The relevant sources are the [load route](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/routes/loadModelRoute.ts), [unload route](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/routes/unloadModelRoute.ts), [stop operation](https://github.com/w3lt/lys/blob/main/apps/backend/src/modules/llm/stopLlmModelsByKey.ts), [LLM service](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/services/llmService.ts), [singleton composition](https://github.com/w3lt/lys/blob/main/apps/backend/src/di/singleton.ts), [backend package manifest](https://github.com/w3lt/lys/blob/main/apps/backend/package.json), [backend TypeScript project](https://github.com/w3lt/lys/blob/main/apps/backend/tsconfig.json), [desktop package manifest](https://github.com/w3lt/lys/blob/main/apps/desktop/package.json), and [current testing guide](/develop/testing/).

Backend history and chat tests are tracked; desktop and shared-package suites remain absent. The boundaries above are not a passing run, measured coverage, or evidence of live LM Studio integration.
