## Docs deployment

The docs publication workflow runs independently of desktop releases:

- workflow: `.github/workflows/deploy-docs.yml`
- trigger: pushes to `main` and manual dispatch
- build command: `pnpm --filter @lys/docs run build`
- artifact directory: `apps/docs/dist`
- deploy target: GitHub Pages

## Desktop builds

The repository has no desktop build or release workflow under
`.github/workflows`, and the Tauri configuration sets up no code signing or
notarization. Desktop builds are made locally with `build.sh`.

## Local macOS install with `build.sh`

On macOS, `build.sh` at the repository root builds the desktop app from a
source checkout and installs it on the same machine. On any other operating
system it prints a message and exits without building. A checkout of `stable`
builds the latest release; a checkout of `main` builds the development version.
Run it from the repository root:

```sh
./build.sh
```

The script stops at the first failing step. In order, it:

1. Runs `pnpm install --frozen-lockfile`.
2. Builds vmo, the page reader `read_page` uses, in release with
   `swift build -c release --package-path apps/vmo`. It stops first when the
   Swift toolchain is missing. Nothing is installed yet, so a machine that
   cannot build vmo keeps its current install.
3. Runs `pnpm run backend:build`, which bundles the backend into
   `apps/backend/dist/backend.mjs` and copies its prompt files beside it.
4. Creates `$LYS_HOME/runtime`, using `${LYS_HOME:-$HOME/.lys}`.
5. Downloads the newest Node.js release in the major version named by
   `.nvmrc`, or the latest LTS release when `.nvmrc` is absent, verifies it
   against that release's `SHASUMS256.txt`, and installs it at
   `$LYS_HOME/runtime/node`. A matching installed version is reused.
6. Moves `apps/backend/dist` to `$LYS_HOME/runtime/backend`, replacing the
   previously installed backend.
7. Replaces `$LYS_HOME/runtime/vmo` with a directory holding only the new
   `vmo` executable, and signs it ad hoc with the virtualization entitlement
   in `apps/vmo/vmo.entitlements`.
8. Runs `pnpm run desktop:build:ci` and `pnpm run desktop:bundle:ci`, which
   build the Tauri app without bundling and then bundle only `Lys.app`.
9. Removes any previously installed `/Applications/Lys.app`, then copies the
   new `Lys.app` there with `ditto`. Without the removal, files from the old
   bundle would remain inside the new one.

The script needs the toolchain from [Environment setup](/develop/setup/),
including the Swift toolchain, plus `curl`, `jq`, and network access to
`nodejs.org`, and to `github.com` for vmo's Swift packages until
`apps/vmo/.build` holds them. vmo builds and runs only on Apple silicon with
macOS 26; see [Runtime dependencies](/operate/dependencies/#vmo).

:::caution[Desktop runtime is still under development]
Release builds of the desktop app start the backend and vmo from a runtime
installed in the [Lys home directory](/reference/configuration/#lys-home-directory):
`$LYS_HOME/runtime/node/bin/node` running
`$LYS_HOME/runtime/backend/backend.mjs`, and `$LYS_HOME/runtime/vmo/vmo`. Only
`build.sh` installs that runtime, and only on the machine that runs it, so a
copied `Lys.app` cannot start its backend or vmo on a machine without it. The same reference explains why an app opened
from Finder or the Dock looks for the runtime under `~/.lys`.
:::

## Versioning

The root `VERSION` file holds the release version, currently `0.4.0`. The
`@lys/scripts` package writes it into the manifests or checks them:

```sh
pnpm --filter @lys/scripts run version:sync
pnpm --filter @lys/scripts run version:check
```

All checked-in workspace manifests, `apps/desktop/src-tauri/Cargo.toml`, and
`apps/desktop/src-tauri/tauri.conf.json` are currently versioned `0.4.0`.
`version:sync` does not rewrite `apps/desktop/src-tauri/Cargo.lock`; update its
`lys-desktop` entry in the same change. Each release is tagged `v<version>` in
Git, and the changelog's compare links rely on those tags. See the
[package reference](/reference/packages/#lysscripts) for what the scripts
rewrite, and the [changelog](/changelog/) for the recorded releases.

## Patch releases

`stable` holds the latest release and `main` holds development toward the next
one; the
[Branches section of `CONTRIBUTING.md`](https://github.com/w3lt/lys/blob/main/CONTRIBUTING.md#branches)
says which branch a pull request targets. A patch release ships one day's fixes
for issues with the `Patch Fix` label to `stable`. A day without such a fix has
no patch release. For a patch from `0.4.0` to `0.4.1`:

1. At 00:00 UTC, the [patch branch workflow](#patch-branch-workflow) creates
   `patch/v0.4.1` from `stable`.
2. Each fix reaches the patch branch through its own pull request.
3. At 20:00 UTC, the workflow deletes the branch when it holds no fix, and that
   day has no patch release. Otherwise it opens a pull request from the branch
   into `stable`.
4. Before merging, the maintainer adds one commit to that pull request that
   sets the version to `0.4.1` as [Versioning](#versioning) describes, and
   records the release as
   [Recording a release](/changelog/#recording-a-release) describes.
5. The maintainer merges the pull request into `stable` and tags the result
   `v0.4.1`.
6. At the next 00:00 UTC, the
   [stable into main workflow](#stable-into-main-workflow) opens a pull request
   from `stable` into `main`. The maintainer squashes it, so that `main` keeps
   every fix.

### Patch branch workflow

`.github/workflows/patch-branch.yml` runs at 00:00 and 20:00 UTC. GitHub runs
scheduled workflows only from `main`, and may start a run late. The workflow
can also be run by hand with the task `open` or `close`.

- It names the branch from `VERSION` on `stable`, and fails when that file does
  not hold a `major.minor.patch` version.
- `open` creates the branch from `stable`, unless it already exists. A pull
  request that is not merged by 00:00 leaves `stable`'s version unchanged, so
  the same branch, with its open pull request, carries over to the next day.
- `close` deletes the branch when `stable` already has every commit on it.
  Otherwise it opens a pull request into `stable`, unless one is already open.
  The pull request lists the fixes and the steps above, and the workflow never
  merges it.
- The workflow creates and deletes branches with its own token, and opens the
  pull request with the `PATCH_PR_TOKEN` repository secret. GitHub starts no
  workflow for a pull request opened with the workflow's own token, so the CI
  checks would not run on it. The secret is a fine-grained personal access
  token for `w3lt/lys` with read and write access to pull requests and
  read-only access to contents. Without it, `close` fails and opens no pull
  request.
- Merged patch branches are not deleted.

### Stable into main workflow

`.github/workflows/stable-into-main.yml` runs at 00:00 UTC from `main`, and can
also be run by hand.

- It reads `VERSION` on `stable` and on `main`, and fails, naming the branch,
  when either does not hold a `major.minor.patch` version.
- It compares the two as numbers, major first, then minor, then patch. When
  `stable`'s version is newer and no pull request from `stable` into `main` is
  open, it opens one. Otherwise it does nothing, and it never merges.
- It opens the pull request with the same `PATCH_PR_TOKEN` secret as the patch
  branch workflow, and fails without it.
- The maintainer squashes that pull request, because `main` requires a linear
  history. The squash brings `stable`'s `VERSION` to `main`, so the versions
  match and the workflow stays quiet until the next patch release.
- It relies on `main`'s `VERSION` staying at the released version until the
  next release is prepared. If `main` is raised to the next version earlier,
  `stable`'s patch versions are older than `main`'s, and no pull request
  opens.
