The Tauri layer is a small native host. It does not implement the backend API
itself; it starts the backend process and exposes a few native commands to the
React UI.

## Registered commands

| Command              | Purpose                                                                                      |
| -------------------- | -------------------------------------------------------------------------------------------- |
| `start_backend`      | Starts the backend for the current build mode with the Lys home and stores the child handle. |
| `stop_backend`       | Kills the backend process group and waits for shutdown.                                      |
| `get_backend_status` | Reports whether the stored child process is still running.                                   |
| `load_settings`      | Reads `$LYS_HOME/settings.json`, creating a default file if needed.                          |
| `save_settings`      | Writes a new settings JSON document to `$LYS_HOME/settings.json`.                            |
| `read_text_file`     | Returns the complete text of one UTF-8 file of at most 1 MiB.                                |
| `find_files`         | Searches a directory tree for regular files by name or by text content.                      |

## File tools

`read_text_file` and `find_files` are the desktop side of the client tools that
let Lys work with files on the user's machine. No part of the app invokes them
yet. The renderer reaches them through `readTextFile` and `findFiles` in
`apps/desktop/src/lib/apis/tauri/tools.ts`, which validate arguments, results,
and declared failures with the schemas exported by `@lys/protocol`.

Both commands accept any absolute path that the desktop process can read. They
are tools, not a permission gateway: deciding whether Lys may use a tool or a
path belongs to the caller that runs tool requests. Relative paths are rejected
rather than resolved against the process's working directory. Each call runs on
Tauri's blocking-task pool, so the window stays responsive, and cannot be
cancelled.

- `read_text_file` follows symbolic links and returns the whole file. It
  rejects directories, FIFOs, sockets, and devices without blocking on them,
  files over 1 MiB, and content that is not UTF-8. It never truncates.
- `find_files` walks the tree breadth-first, lists each directory in byte order
  of entry names, and never follows symbolic links below the root. It compares
  file names, lines of UTF-8 files up to 1 MiB, or both, case-insensitively
  after Unicode lowercasing. A search stops after the requested number of
  matches (50 by default, at most 200), 20,000 examined entries, or 64 MiB of
  read content, and its report says which of these ended it.

Expected failures reject with a JSON object whose `code` names the failure,
such as `{ "code": "fileNotFound" }`. Any other rejection, such as an
unregistered command, is thrown by the TypeScript wrappers as an error.

## Lys home

Before building the application, the host resolves the
[Lys home directory](/reference/configuration/#lys-home-directory) once from the
`LYS_HOME` environment variable and manages it as application state. The
settings and backend commands receive that value instead of reading the
environment again. An invalid `LYS_HOME` stops the app before any window opens.

## Backend process ownership

The host owns a `Backend` state object containing `Mutex<Option<Child>>`. The
child process is started only when the UI asks for it or when auto-start logic
requests it during desktop initialization.

The child depends on the build mode:

- Development builds run `pnpm run dev` from `apps/backend` in the checkout
  recorded at compile time.
- Release builds run `$LYS_HOME/runtime/node/bin/node` with
  `$LYS_HOME/runtime/backend/backend.mjs`.

```rust
Command::new("pnpm")
    .args(["run", "dev"])
    .current_dir(backend_dir)
    .env("LYS_HOME", lys_home.as_path())
    .process_group(0)
    .spawn()
```

Both children run in their own process group, with `LYS_HOME` set to the Lys
home the host resolved, so the backend uses the same directory as the host.

When the direct child is still running, stopping the backend sends `SIGKILL`
to its whole process group and waits for that child. If the direct child has
already exited, the host clears its handle without killing any surviving
descendants. Tauri attempts this same cleanup on app exit.

The checked-in process supervisor currently uses Unix process-group APIs and
the `nix` crate. The repository does not yet demonstrate equivalent lifecycle
behavior on Windows.

## Settings file

The host creates the following defaults when the settings file is missing:

```json
{
  "runtime": {
    "autoStartBackend": true,
    "defaultModel": null,
    "backendAddress": "http://127.0.0.1:12345"
  },
  "model": {
    "contextSize": 32768
  },
  "generation": {
    "temperature": 0.7,
    "replyCeiling": 2048
  }
}
```

Only the Rust host reads and writes this file directly. The React UI reaches it
through Tauri `invoke` calls.

The desktop automatically saves generation edits by reading this document,
replacing its generation group, and saving the complete document. Runtime and
model edits in the UI remain session-only; generation saves preserve those
groups as already stored on disk. The local context size supports composer
estimates and does not configure LM Studio's load-time context.

## What the host does not currently do

- It does not manage provider credentials.
- It does not read the operating-system keychain.
- It does not proxy HTTP requests to LM Studio.
- It does not replay prior conversations into the window.
