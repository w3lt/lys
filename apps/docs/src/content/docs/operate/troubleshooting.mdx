## The desktop shows the backend as stopped

The desktop runtime pane controls the backend child owned by Tauri. It does not
discover a backend launched separately in a terminal. Choose one launch path
before starting another process on the same port.

For the desktop-managed path:

- confirm the runtime pane reports `stopped` rather than `starting`
- start the backend from that pane
- the pane switches to `running` only after `GET /api/v1/heath` answers; if
  the process stays up without answering for 30 seconds, it shows **Backend
  not responding**. Press **Stop**, then **Start**
- verify `GET /api/v1/heath` responds at `http://127.0.0.1:12345`

If the listener is unavailable, inspect the backend output. LM Studio is not
required for the backend to listen. For standalone startup, also ensure
`LYS_HOME` is set to an absolute path and its directory exists as described in
[Running Lys locally](/develop/running/).

## LM Studio is not reachable

The Runtime pane's LM Studio card shows **LM Studio not reachable** when the
backend cannot connect to `127.0.0.1:1234`, and the model list stays empty.
Start LM Studio and its local server, then press **Refresh** on that card. The
backend does not retry on its own.

## The backend starts but model operations fail

The backend is wired to LM Studio at `127.0.0.1:1234`. If model listing,
loading, or chat requests fail after HTTP readiness was established, verify
that LM Studio is still reachable. When LM Studio stops while connected, the
next failing model request marks it not reachable; press **Refresh** after
restarting it. The
[model health endpoint](/operate/logging/#model-health-observation) can report
loaded state; it does not test inference success.

## vmo is not ready, so `read_page` is unavailable

The backend offers `read_page` only while vmo answers `GET /health` at
`127.0.0.1:8080`. Until then, the Tools pane shows `read_page` off and
disabled, with "vmo, Lys's page reader, isn't ready. See Settings → Runtime."
The vmo card in Settings → Runtime says why:

- **vmo starting**: every start fetches the `lys-readpage` image's `latest`
  tag from `ghcr.io`, and the first start, or the first after a new reader
  image, downloads the `vminit` or `lys-readpage` image, which can take a few
  minutes. A development build compiles vmo first. Lys waits up to ten
  minutes.
- **vmo not responding**: the process stayed up for ten minutes without
  answering, or a start or stop failed while vmo still ran or its status could
  not be read; the card then shows that failure. Press **Stop**, then
  **Start**. Check network access to `ghcr.io`, and that the Mac meets
  [vmo's requirements](/operate/dependencies/#vmo); vmo does not boot its VMs
  without the kernel described there
  ([#200](https://github.com/w3lt/lys/issues/200)).
- **vmo stopped** right after Start: the process exited before it answered,
  for example because it could not reach `ghcr.io` for its images; could not
  read which `vminit` [its image store](/operate/data/#vmos-image-store)
  holds unpacked, delete that unpack, or unpack and save the new one; could
  not delete the images it no longer uses from the store; or, in a
  development build, did not compile. In development, vmo's build and error
  output appear in the terminal that runs `pnpm dev`. When every start stops
  this way although `ghcr.io` is reachable and the disk has room for vmo's
  images, delete `~/Library/Application Support/com.w3lt.lys-vmo` while vmo
  is stopped; the next start downloads its images again.
- **Lys couldn't start vmo: Failed to run …/vmo: No such file or directory**:
  vmo is not installed. Run `build.sh`; see
  [Packaging and releases](/operate/releases/).

## vmo was killed

Stopping vmo sends it `SIGTERM` and waits up to 60 seconds while it deletes its
VMs. When it has not exited by then, Lys kills it, and the vmo card says "vmo
didn't stop in time and was killed. It may have left VMs running."
Lys cannot remove those VMs yet; a restart of the Mac ends them. Quitting Lys
waits for vmo the same way, so quitting can take up to a minute.

## A vmo or backend keeps running after Lys died

Lys stops vmo and the backend when it quits. When it dies without quitting,
after a crash, Force Quit, or `kill -9`, or when a development rebuild restarts
the desktop host, both keep running
([#202](https://github.com/w3lt/lys/issues/202)). The next Lys cannot start its
own: the vmo and backend it starts cannot listen and exit. Its cards still show
**vmo running** and **Backend running**, because the old processes answer their
health routes, and `read_page` works through the old vmo. Stop and quitting Lys
do not reach either old process.

To end them, find each process by its port and send it `SIGTERM`:

```sh
lsof -nP -iTCP:8080 -sTCP:LISTEN    # vmo
lsof -nP -iTCP:12345 -sTCP:LISTEN   # backend
kill <pid>
```

Never use `kill -9` on vmo: only `SIGTERM` lets it delete its VMs before it
exits, which can take up to a minute. Once `lsof` shows nothing on a port,
press **Stop** and then **Start** on that process's card, or quit and reopen
Lys. The cards still show the old processes as running, so **Start** stays
unavailable until **Stop**.

## Lys forgets runtime settings

The Runtime pane saves its two startup switches, "Start it when Lys opens" for
the backend and "Start vmo when Lys opens", to `$LYS_HOME/settings.json`
whenever either changes. When that save fails, the pane says "Lys couldn't save
the startup switches. The next launch follows the switches last saved; changing
a switch tries again." Then:

- check whether `$LYS_HOME/settings.json` exists
- if it exists, verify that it contains valid JSON
- if it does not exist, the host should recreate it the next time settings are
  loaded

The default-model selection is not saved and lasts for the session only.
Generation controls and load configurations autosave separately and expose a
save failure with a retry action; those saves preserve the runtime and model
values already on disk.

## Startup fails after a schema change

The backend's database owner reads SQLite `PRAGMA user_version` when it opens
the database on startup and refuses to open a database newer than the running
binary supports. If a startup failure mentions an unsupported database version,
use a matching or newer build rather than editing the database by hand.

## The desktop app exits at startup or uses another data directory

The desktop host resolves `LYS_HOME` once at startup. A relative path,
including an unexpanded `~/…`, or a value that is not valid UTF-8 stops the app
before any window opens and prints `Lys cannot start: …` to standard error. That
message is visible only when the app is started from a terminal. Set `LYS_HOME`
to an absolute path, or unset it to use `~/.lys`.

An app opened from Finder or the Dock does not see a `LYS_HOME` exported in a
shell profile, so it uses `~/.lys`. See the
[Lys home directory](/reference/configuration/#lys-home-directory) reference.

## Known gaps

The repository does not currently include evidenced support for:

- automated store repair commands
- diagnostics bundles
- packaged log collection and rotation
- a published operator escalation path

Those workflows should be documented here only after the product ships them.
