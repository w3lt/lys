The backend is a TypeScript Fastify application in `apps/backend`. It owns the
SQLite conversation store, the HTTP and SSE surface consumed by the desktop
application, and the connections to the MCP servers the settings file names.

## Current backend shape

Each module in `src/modules/` keeps its HTTP routes in `routes/` and its
services, contracts, and domain logic at the module root. `src/di/` only wires
the services together.

## Chat request flow

1. `POST /api/v1/chat` validates the request body with the shared Zod schema,
   whose attachment rules it applies within its 32 MiB body limit, decodes
   each attachment and reads what it is from its bytes, then finds each
   backend tool the request names in `backendToolNames`: a built-in tool, or
   a tool of an MCP server. An attachment that is neither UTF-8 text nor a
   PNG, JPEG, or WebP image answers `400` with the attachment-unsupported
   problem, and a name that is neither a built-in tool nor a tool an applied
   MCP server lists answers `400`, before anything is stored. An offered
   built-in tool that cannot run now, and then a tool whose MCP server is
   applied but not connected, answers `409` with the
   backend-tool-unavailable problem, storing nothing either.
2. The route finds the agent that answers before it stores anything. For a
   new conversation it asks the agent runtime service
   (`app.agentRuntimeService`) for the requested agent, built-in or stored
   and not deleted; if no such agent has that code, it answers
   `404` with the agent-not-found problem. For an existing conversation it
   reads the conversation's agent code through the history reader, answers
   `404` with the conversation-not-found problem when the conversation is not
   stored, and answers `409` with the conversation agent missing problem when
   no agent has that code any more, as after the agent was deleted. In each
   of those cases nothing is stored.
   The route then reads whether the model sees images and is trained for
   tool use through the capability lookup the chat and chat-context routes
   share (`createModelCapabilitiesLookup`), which lists the connected
   provider's inventory until it has seen the model and then remembers what
   the model can do while the backend stays connected to that provider,
   because a model's capabilities come from its files; it forgets all of it
   when another provider connects. A model the inventory does not list is not remembered,
   and its turn sees no image and is offered none of the tools the backend
   adds. While the lookup lists, a full model-operation queue or a missing
   runtime answers its `503` problem, and an image attached for a model
   without vision, or for one the inventory does not list, answers `409`
   with the image-needs-vision problem, nothing stored either way. The
   route makes the identities of a new conversation and of the user message
   and writes the attachment files under them, so they are in place when the
   turn commits; see [attachments](#attachments). Once the files are written,
   the route looks the agent up again and `StoredConversationTurns` creates
   the conversation with that agent or loads the existing one, interrupts a
   reply still streaming in it, and stores the user message with its numbered
   attachments and the empty streaming assistant message, all in one write
   transaction of the SQLite turn records. That lookup and the write run in
   one synchronous step, so the agent that answers is the conversation's
   agent when the turn is stored; a conversation or agent deleted while the
   files were written or the inventory was read gets its `404` or `409`
   problem instead, and the written files are deleted again.
3. The route immediately emits either `start-new-conversation-turn` or
   `start-existing-conversation-turn`.
4. For an existing conversation with a stored title, the route emits that title
   to reconcile desktop metadata from an earlier missed delivery.
5. The agent found when the turn is stored answers with the system prompt it
   has then: a built-in agent's shipped prompt, or a stored agent's current
   one. The agent's `createReply` opens an
   OpenAI-compatible streaming completion against the connected provider through
   `OpenAiReplyModel`, offers the turn's tools (the attachment reader first
   when the conversation holds a text file and the model is trained for tool
   use, then client tools, then built-in tools, then MCP tools, then, when
   the model is trained for tool use, the
   [agent state tools](#agent-state-tools) the agent's role gives; when the
   model is trained for tool use, the request's tools are
   [routed](#tool-routing): the first round offers `find_tools` in their
   place, and each tool Armitage finds is offered from the next round), and
   runs rounds while
   the model calls them: each call is
   checked by `AgentTool`, then decided by the
   [tool call policy](#tool-call-policy), then passes the round's
   [approval gate](#tool-approval). A call of a backend tool is first parsed by
   the tool, so arguments it can never run are answered without asking. An
   allowed client tool's call is sent to the desktop as a `tool-call` event
   and answered through the tool-result route; an allowed backend tool runs in
   the backend under the reply's cancellation, and an allowed MCP tool's call
   runs on its server, which is told when the reply is stopped. Every call
   has an answer before the next round. [Reply parts](#reply-parts-and-sources) describes how each
   part is stored before it is sent to every stream following the reply; the
   agent stores completion before emitting `done`.
6. When the conversation has no stored title, `createTitleGenerationTask` runs
   in parallel and emits a `title` event only after a conditional write wins the
   first assignment.
7. Chat generation errors become `error` events for every follower; a reply
   that ends early becomes `interrupted`; title-generation failures are logged
   instead.

### Context window check

Before each round, the agent measures the round's context and offered tools
against the model the turn names. `LlmReplyContextMeter` gives `LlmService`
the text the model reads for each message (its content, and the name and
argument text of each tool call it carries) and each offered tool's JSON;
`LlmService` counts them with the loaded model's tokenizer through the model
operation queue and reports the context length the model is loaded with. The
meter adds a fixed allowance for the chat template's markup: 8 tokens per
message, 16 per tool call of an earlier round, and 160 once when tools are
offered. Each image a user message sends, which the tokenizer cannot count,
is counted as `⌈width ÷ 28⌉ × ⌈height ÷ 28⌉` tokens up to 1,280
(`calculateImageTokens` in `@lys/share`). A file staged in the composer is
measured only once its message is stored: the desktop adds the image
estimate for a staged image, while the listing lines of staged files and the
reader's definition, when a staged text file would make the turn offer it,
are not counted until then.

A round is sent only when its tokens and the reply ceiling (or zero without
one) together stay within that context length. Otherwise the round is not
sent: the reply is stored `failed`, keeping the parts earlier rounds stored,
and its `error` event names the tokens needed and the context length. A model
that is not loaded is never loaded for the round; the reply fails with an
`error` that asks to load it. A measurement that fails, because no provider
is connected or the queue is full, also fails the reply, with the general
sentence. Without this check, LM Studio's context overflow setting could keep
the start of the conversation, drop its middle, and let the model answer an
earlier message. With the reply ceiling off, nothing is held back for the
reply, so a reply that grows past the window is still handled by that
setting.

`POST /api/v1/chat/context` makes the same measurement for the composer's
context meter. It resolves the agent and the conversation as the chat route
does, through the same lookups, reads a continued conversation once, and
asks the agent's `findContextMeasurement` for the system prompt, with the
notes about the tools the request does not offer when it names any or
switches tool calls off, the tools, and
stored messages a turn's first round would send, with an empty new message
that measures the markup around the text. It reads the model's capabilities
through the chat route's lookup, so the images a model with vision sees are
counted, and the tools are measured as a turn's first round would offer
them: `read_attachment` first when a turn would offer it, then the request's
tools, or, for a routed turn, `find_tools` in their place with the routing
note at the end of the system prompt, then the agent state tools. An offered
MCP tool is measured, or counted among a routed turn's tools, only while its
server is connected, because its definition is known only then; one whose
server is not connected is left out, and a name no applied server lists
answers `400`. It never reads an image's
bytes: `getAgentContextImageSides` asks the attachment file store whether
each file is still there, and the measured context carries a stored image's
sides, or a missing one's placeholder, where a turn sends the image. See the
[route contract](/reference/api/#chat-context-measurement).

Each completion receives the system prompt of the conversation's agent, prior
user messages, the rounds of completed or interrupted replies, and the current
user message once. When the request names
[tools the turn does not offer](/reference/api/#tools-the-turn-does-not-offer)
or switches tool calls off, `findUnofferedTools` in
`src/modules/chat/routes/turnRequest.ts` turns those fields into one
`UnofferedTools` value, checking that every tool named as unable to run is one
the backend runs, and `formatSystemPrompt` adds the notes
`src/modules/agent/unofferedTools.ts` writes after the system prompt, in every
round: that tool calls are off, or which tools are switched off and which
switched-on tools cannot run now, why, and what fixes it. Each note tells the
model to say why a needed tool cannot be used instead of guessing what it
would return. Each user message sends its text followed by the list of
its attachments and, for a model with vision, its images; see
[attachments](#attachments). `buildAgentContext` sends each stored round as one
assistant message with the round's text and its tool calls that have a
result, followed by one tool message per result. Reasoning is never sent
back, nor are calls without a result; a round with neither text nor such a
call is left out. Failed replies are excluded from model context. A reply
still streaming when the next turn is created becomes interrupted first, so its
partial rounds are included. Within one turn, a round's reasoning is not sent
to the next round either ([#185](https://github.com/w3lt/lys/issues/185)).
The required `generationOptions` controls supply sampling temperature and an
optional completion-token ceiling; the [API reference](/reference/api/#chat-request-body)
defines their limits. Partial reply parts remain available in history
after cancellation or failure.

### Reply parts and sources

A reply is a list of parts: reasoning, text, and tool calls with their
results, each in the model round it belongs to. `OpenAiReplyModel` yields a
round's reasoning from the stream's `delta.reasoning` field, which LM Studio
0.4 sends, or else from `delta.reasoning_content`, before the chunk's text.
Reasoning a model writes between `<think>` tags in its text stays text
([#183](https://github.com/w3lt/lys/issues/183)).

`ReplyPartSequence` (`src/modules/agent/replyPartSequence.ts`) owns the
reply's open part. A reasoning or text fragment extends the last part when it
is of the same kind and round; otherwise it starts a new part. Every part,
fragment, and tool call change is stored first, through the turn's
`ReplyPartWriter` capabilities, and sent as a `reply-part` or
`reply-part-delta` event in the same synchronous step, so a follower that
reads a snapshot sees both or neither. A refused write means the reply was
superseded, deleted, or finalized, and ends it as interrupted.

The tool-call round stores each call as a part in the model's order, under
the UUIDv7 it sends: a call of an unknown tool, or with arguments that do not
match, as `failed` with the message the model reads, which for a tool the
request names as switched off or unable to run, or for any tool while tool
calls are off, says why it did not run; a turn that offers no tool answers
such calls the same way when the request names any tool or switches tool
calls off, and otherwise fails the reply; a checked call as
`running` when the gate allows it at once, or otherwise as
`awaiting-approval` before its prompt is sent, in the same step. A call the
store refuses because its reply has ended is never prompted. An allowed call
becomes `running`, a rejected one
`rejected` with the rejection the model reads, and a call that ran
`succeeded` or `failed` with its result. A network tool's result is cleaned
before it is stored, so the stored result is what the model read.

`SourceCatalog` (`src/modules/agent/sourceCatalog.ts`) numbers the web
sources of one conversation during a turn, seeded with the sources the
conversation stored. A backend tool's run receives `addWebSources`, which
gives each candidate URL the number it already has, or the next one. A
title in which a person sees nothing, only whitespace and default-ignorable
code points such as Hangul fillers, is replaced by the URL's host, both in
the result the model reads and in the source. Any other title becomes the
source's title cleaned of the characters a person cannot see, as a network
tool's result is, and trimmed, so a citation never shows an empty or
disguised title.
`web_search` labels each result `Source [n]`, and `read_page` adds a
`Source number: [n]` line; the citation rule tells the model to cite those
numbers in square brackets and to write no list of sources. A succeeded call
stores the numbers its result shows with the sources themselves, then a
`sources` event precedes its `reply-part` event. A number given to a call
whose result is never stored, because the reply ended first, is not kept:
the next turn gives the numbers above every stored number again, so a gap is
left only below the highest stored number. Only web pages are sources today;
files a tool reads are not ([#184](https://github.com/w3lt/lys/issues/184)).

`StoredReplyParts` (`src/modules/conversation/replyParts.ts`) implements
`ReplyPartWriter` over `SqliteReplyPartRecordWriter`, reading the clock once
per operation; reasoning and text parts get a new UUIDv7. Each write is one
transaction guarded by the reply still streaming. Ending a reply, a newer
turn superseding it, and startup recovery mark its `awaiting-approval` and
`running` calls `interrupted` in the same transaction as the reply.

The Lys system prompt and the title-generation prompt are read once, when
`loadBackendConfig()` builds the backend configuration at startup.

A new conversation is stored without a title (`null`). Title generation runs
for a turn whose conversation has no stored title, unless an earlier turn of
that conversation is still generating one, and uses that turn's user message.
A conversation that remains untitled after an earlier task failed or was
cancelled gets another try on its next turn after that task ended. It uses a
separate chat completion request with a JSON-schema response format that limits
the title to `generatedTitleMaxLength` Unicode code points (100 by default),
then validates the reply; JSON wrapped in one Markdown code fence is accepted.
Only a reply that cannot be used as a title leads to another attempt, up to
`titleGenerationMaxAttempts` attempts per turn (three by default). Before each
attempt, the task asks the model-operation queue whether the model is loaded,
without loading it. When it is not, the turn requests no title, logs
`model-not-loaded` at debug level, and the next turn tries again, so a title
request does not make the provider load the model with its own settings. An HTTP,
connection, or cancellation failure ends title generation for the turn, after
the OpenAI SDK has retried a connection failure, timeout, or 408, 409, 429, or
5xx response up to two more times within the attempt. A generated title is
saved with a conditional first assignment and published only when that
assignment succeeds, so generation cannot overwrite a manual rename. Existing titled turns
send the stored title after their start event, which repairs desktop metadata
after a prior title event was lost.

`ReplyGenerationRegistry` owns every running generation and runs at most one
title task per conversation: a turn sent while an earlier turn's title task is
still running gets none, so its streams close when its reply ends. A
`ReplyGeneration` owns one turn's reply task and optional title task, their
cancellation, and the SSE streams following them; no HTTP connection owns it. It
also lists what its reply waits on (`PendingToolCalls`): calls sent to the
desktop to run and approval prompts, which the reply-events snapshot reports
and the tool-result and tool-approval routes answer. Each stream is
a `ReplyEventSubscription`, an ordered queue that never makes the generation
wait and closes a follower that falls 4,096 events behind. Only the reply-stop
route (reply task only) and shutdown (both tasks) cancel work. A newer turn or a
deletion also ends a reply, but only when the model sends its next content: that
write is refused, which ends the upstream request. A reply waiting for a tool
result or an approval is not ended this way
([#137](https://github.com/w3lt/lys/issues/137)).
The title task of a deleted conversation still runs to its end. The registry is
disposed in Fastify's `preClose` hook, while streams are still open: it closes
admission, cancels every generation, and waits until each has stored its final
state before singleton disposal closes SQLite. Task failures are logged by the
generation that owns them.

### Attachments

A chat request can carry up to 8 files, 10 MiB each and 20 MiB together, as
base64 `attachments`; the limits are constants of `@lys/share`
(`packages/share/src/models/attachment.ts`), which the desktop applies too.
`parseChatAttachments` (`src/modules/attachment/chatAttachments.ts`) reads
what each file is from its bytes, never from its name: a PNG, JPEG, or WebP
header makes an image with its media type and sides; bytes that decode as
UTF-8 without a NUL character make a text file; anything else is refused
with `400` before anything is stored.

`AttachmentFileStore` (`src/modules/attachment/attachmentFileStore.ts`) owns
the attachments directory, `$LYS_HOME/attachments`, and writes a message's
files at `<conversation id>/<message id>/<name>` before the turn is stored.
Every path it touches is built only from a validated UUIDv7 and a validated
name, so no request can name a path, and the message's folder and each file
in it are created exclusively, so nothing on disk is overwritten. A file that
cannot be written deletes what was written for the message and fails the
request, which stores nothing. A turn that cannot be stored after its files
were written deletes the message's folder again and fails the request; when
that deletion fails too, the request fails with both failures and the folder
stays, under a message the conversation never stores. Deleting a
conversation deletes its rows, then its folder; a folder that cannot be
removed is logged at `error` with its cause, and the delete still answers
`204`.

The turn stores each attachment's number, name, kind, size, and an image's
media type and sides in `conversation_attachments`. Numbers start at 1 and
count up across the conversation in sending order, so the model knows each
file as `[attachment 3] notes.md` whatever message it belongs to. Loading a
conversation never reads the disk.

`buildAgentContext` sends each user message as its text, a blank line, and
`Attached files:` with one line per attachment giving its label, `text` or
the image's media type and sides, and its size; a message without
attachments sends its text alone. For a model with vision, each image follows
its message's text as an `image_url` part carrying the file as a data URL, on
the turn it was sent and on every later turn; `readAgentContextImages` reads
the files once per turn, in conversation order. An image the model does not
get is one more line of the text instead: "is an image that this model
cannot see." for a model without vision, which reads no file, or "is an
image whose file is missing from this machine, so it cannot be shown." when
the file is gone. The context meter counts each image sent as its estimate
from the image's stored sides, so it needs no bytes.

A text file is never sent whole. When the conversation holds one and the
model is trained for tool use, the turn offers
[`read_attachment`](#read_attachment) before the request's tools, in every
round, and the model reads the file in parts when it needs it. The
reader's results stay in
the reply's stored parts, so later turns resend them like every other tool
result.

Whether the model sees images and is trained for tool use is read from the
connected provider's inventory (`src/modules/chat/routes/modelCapabilities.ts`) for
every turn and every context measurement, as it decides the images the model
sees and the tools the backend offers it. A listed model's capabilities are
remembered while the backend stays connected to that provider, and forgotten
when another one connects, so only requests made before a listing
had the model wait for the model-operation queue; a failed listing and a
model it does not list are not remembered. The read lists the downloaded
models only (`LlmService.listDownloadedLlmModels()`), without the loaded
state and context lengths the model list adds. A model the inventory does
not list has neither capability: an image attached for it is refused, and no
reader is offered.

## Tool call policy

Every checked call of every turn passes one gateway step, `startToolCall` in
`src/modules/agent/toolCallRound.ts`, before it runs or the person is asked.
For each call, in order:

1. A call of a tool its round did not offer, such as a routed turn's tool
   Armitage has not found, is stored as failed with a result the model reads.
2. `AgentTool` checks the arguments against the tool's definition, only
   their shape for an MCP tool, and a backend tool's `parseToolCall` checks
   them for what it can run; a call either refuses is stored as failed.
3. `decideToolCall` (`src/modules/toolApproval/toolCallPolicy.ts`) decides
   the call by fixed rules, whatever the tool.
4. An allowed call of a backend tool that runs without approval starts at
   once; every other allowed call passes the round's
   [approval gate](#tool-approval).

A denied call is stored as failed with a sentence the model reads
(`formatToolCallDenial`), naming the rule it broke and telling the model not
to reach the target another way: it never runs, and the person is never
asked, even for a tool saved as Just run. The rules are code and have no
settings. Their one input from the machine, the settings file path, comes
from the configuration: `app.ts` hands it to the chat route, every turn
carries it, and `find_tools` hands it to Armitage's search turn, so
Armitage's own `search_tools` and `recommend_tool` calls are decided too.

The policy reads every text of the call's arguments: the argument names,
every string value at any depth, and the keys of nested objects; numbers,
booleans, and `null` are not read. Each text is trimmed, and the first rule
is asked over every text before the second:

- **Credential file.** The text is split into parts at `/` and `\`, without
  empty and `.` parts, and compared in lowercase. The call is denied when a
  part is a credential folder (`.ssh`, `.gnupg`, `.aws`, `.azure`, `.kube`,
  `.docker`, or `Keychains`), a credential file name (`id_rsa`, `id_dsa`,
  `id_ecdsa`, `id_ed25519`, `id_ecdsa_sk`, `id_ed25519_sk`, `.netrc`,
  `_netrc`, `.pgpass`, `.git-credentials`, `.npmrc`, `.pypirc`, `.htpasswd`,
  or `.env`), a name that starts with `.env.`, or a name that ends with
  `.pem`, `.key`, `.p8`, `.p12`, `.pfx`, `.ppk`, `.jks`, `.keystore`, or
  `.kdbx`. It is also denied when the parts hold the settings file's folder
  and name side by side, `.lys/settings.json` with the default Lys home: the
  file holds the provider and Tavily API keys and the email password. A
  `file:` URL is read by its decoded path; a URL of any other scheme with a
  host names a file on another machine and is left to the next rule.
- **Blocked address.** A text without whitespace that is a URL with a host,
  or a bare host with an optional port and path, is denied when the host is
  `localhost`, a name under `.localhost`, or an IP address in a range Lys
  never connects to: the ranges of `webAddresses.ts`, which `read_page` and
  `web_search` also refuse. A URL's host is normalized as an `http` host
  first, so `postgres://0x7f.1/db` names `127.0.0.1`; a bare address counts
  only in standard notation, so a text `2130706433` is a number, not an
  address.

The rules read text only. They resolve no host name: an MCP server resolves
the names it reaches, and `read_page` checks every resolved address when it
runs. They follow no symbolic link and read no command, and a text with
whitespace, such as a sentence or a shell command, is never read as an
address, so a tool that runs commands or searches file contents can still
reach a credential file or a local address;
[#339](https://github.com/w3lt/lys/issues/339) proposes checking the
resolved paths of the desktop's file tools on the host. A sentence that holds a credential
path, such as a web search query, is denied like a path.

## Tool approval

`ToolApprovalService` (`src/modules/toolApproval/toolApprovalService.ts`) is the
approval gate for every tool call of every turn that the
[tool call policy](#tool-call-policy) allows, client, backend, and MCP tools
alike, except a call of a backend tool that runs without approval:
`read_attachment` reads only what the person attached to the conversation,
the [agent state tools](#agent-state-tools) only read what agents are
doing, and [`find_tools`](#tool-routing) and Armitage's search tools only
read the turn's tool definitions and name tools, running none, so their
calls are stored as `running` at once and never pass the gate. A call of a
tool its round did not offer, such as a routed turn's tool Armitage has not
found, is stored as failed with a result the model reads and never reaches
the gate. When a
round with a call to gate arrives, `createToolCallGate` reads
`tools.justRun` from the desktop's settings file with `readJustRunToolNames`
(`src/infrastructure/settings/justRunToolsFile.ts`) and returns a
`ToolCallGate` for that round. The reader shares the bounded settings-file
read (`settingsFile.ts`) with the Tavily key reader: at most 1 MiB, UTF-8,
parse failures dropped unread. A missing file, `tools` group, or `justRun`
list means no tool is on Just run. A round whose calls all run without
approval or name no offered tool creates no gate and does not read the file.

For each allowed call that passes the gate, in the model's order, the gate's
`startToolCall` stores the call and decides how it goes on. A call of a tool on Just run is
stored as `running` and goes on at once. Any other call is stored as
`awaiting-approval` first; the gate then sends a `tool-approval` event, and
the round waits for the person's answer through the tool-approval route,
with no timer. A call the store refuses is never prompted. Storing and
prompting happen in the same synchronous step, so a follower that sees the
prompt can read the call, and a round's prompts and the run requests of
calls allowed at once keep the model's order. When the settings
file cannot be read, or `tools`, `justRun`, or a name in it is invalid, no
tool is on Just run, every call of the round asks, and the chat route logs a
warning with the request's logger. A choice the desktop saves applies from
the next round. The desktop is the file's only writer; the backend never
writes it.

The Tools pane's switches are not part of the gateway: they decide only which
tools a chat request offers, so switching a tool or tool calls off applies
from the next message.

## Built-in tools

A built-in tool implements `BuiltInTool` (`src/modules/tool/builtIn/builtInTool.ts`):
`parseToolCall` checks a call's arguments before the person is asked and
returns either an explanation the model reads or a run function. The run
receives the reply's Stop signal and `addWebSources`, which numbers the web
sources it is about to show. It returns the text the model reads, with the
numbered sources a succeeded result shows, or rejects only with the Stop
reason or a defect.

Each entry of the registry pairs a definition with a `BuiltInToolProvider`,
whose `findTurnTool()` gives the tool for one turn or says why it cannot run
now (`page-reader-not-ready`, `api-key-missing`, `api-key-invalid`, or
`settings-unreadable`). `createBuiltInTools()` builds the list once at
startup: `read_page`, found by `ReadPageToolProvider`, then `web_search`,
found by `WebSearchToolProvider`. The attachment reader, `read_attachment`,
the agent state tools, and `find_tools` are in neither the registry nor the
tool list: the chat route builds the reader for each turn whose conversation
holds a text attachment, the agent adds its state tools to each turn and
`find_tools` to each routed turn, and their calls run without asking; see
[`read_attachment`](#read_attachment),
[agent state tools](#agent-state-tools), and [tool routing](#tool-routing).
`ReadPageToolProvider` sends vmo one
`GET /health` per lookup (`web/vmoHealth.ts`), on a connection of its own, and
gives the tool only for a `200` within one second. Any other status, a refused
or broken connection, an answer that is not HTTP, or no answer in time is
`page-reader-not-ready`, so a lookup waits at most one second for vmo. Any
other failure, such as a vmo address that is not a URL, is a defect and
rejects the lookup. The backend never starts vmo, which
the desktop owns. `GET /api/v1/tools` returns every definition, followed by
the tools of the MCP servers connected at that moment, and looks up every
built-in tool again to list the ones that cannot run now; the desktop offers
the switched-on, available ones by name. The chat route looks up every
offered backend tool before it looks up the agent and stores the turn, and
answers 409 `backend-tool-unavailable`, storing nothing, when one cannot run.
The turn keeps the tools it found then.

The address-checked connection (`web/webConnection.ts`: the checked lookup
and the connected-socket check) and the formatting of untrusted web text
(`web/untrustedText.ts`: delimiter-free text, single-line fields without
control characters, excerpts, and the citation rule) are shared by both web
tools.

Every result of a tool whose definition has `access: "network"`, client or
backend, succeeded or failed, passes `formatNetworkToolResult()`
(`src/modules/tool/networkToolResult.ts`) in the tool-call round before the
model reads it, so a new network tool is cleaned without code of its own. It
removes Unicode format and control characters (zero-width, direction
controls, tag characters, `BEL`, `ESC`, and the like) except tabs and line
breaks, keeps a zero-width joiner or non-joiner only between two visible
characters, where emoji, Persian, and Indic text need it, and removes every
variation selector except one text-style (U+FE0E) or emoji-style (U+FE0F)
selector right after a visible character, as in `❤️` or `1️⃣`. A run of
variation selectors can spell a message one byte per selector, and the other
selectors only pick a rare alternate shape of the character before them.
When it removed anything, it adds a last line saying how many characters, so
the model can tell the person the source hid text. The format characters it
removes include a few visible signs, such as the Arabic number signs
(U+0600–U+0605) and the end-of-ayah sign (U+06DD), and the tag characters of
the England, Scotland, and Wales flags, which then show as a plain black
flag; a character picked by a variation selector keeps its default shape.

### `read_page`

Its arguments are `url` and an
optional `focus`. A URL longer than 2,048 characters, as given or once
normalized and percent-encoded, not absolute `http` or `https`, carrying a
username or password, or naming this machine or a blocked IP address is
answered at once. Once allowed, a read goes through vmo
(`web/pageRendering.ts`), the page reader in `apps/vmo` that runs on the same
machine:

1. it looks up the URL's host name through the operating system and refuses
   the read, without asking vmo, when the name has no address or any of its
   addresses is blocked by the rule in `webAddresses.ts`. A host that is an IP
   address is not looked up: the URL rules already checked it. The check
   covers only the URL given: the page's redirects, what the page loads, and a
   name that resolves differently inside vmo's micro VM are not checked;
2. it sends `GET /web/read-page` to vmo at `127.0.0.1:8080`, with the URL
   form-encoded as the `url` query parameter, on a connection of its own. vmo
   checks that the URL is absolute `http` or `https` with a host, and passes
   it to the reader as given. It creates a micro VM from the
   `ghcr.io/w3lt/lys-readpage` image, built from `sandboxes/readpage`, whose
   `latest` tag the image workflow moves to each build on `main` and vmo
   fetches at each start. The reader loads the page in headless Chromium,
   with the page's scripts running and its redirects followed, for up to 10
   seconds of virtual time, in which the page's timers run without waiting.
   It dismisses each dialog the page opens, as Cancel would, so an
   `alert()`, `confirm()`, or `prompt()` does not hold the read up. It
   writes the HTML of the DOM it ended on as the page renders it, built by a
   script of the reader's own that the page's scripts cannot reach: a web
   component's open shadow root stands in place of the component's children,
   and light content slotted into the component stands at its `<slot>`, so
   it is read once, where it shows. A closed shadow root cannot be read, so a
   component that has one keeps its own children. On a page with an open
   shadow root, light content that no slot shows is left out, and a
   `<template>` is written empty; a page without one is written as
   Chromium's own `--dump-dom` writes it, because building the rendered copy
   takes about four times the memory. It leaves out scripts, styles,
   `<noscript>`, `<link>`, `<meta>`, and `class` and `style` attributes.
   With no stylesheet left, text a stylesheet hides is read like
   any other text. Without `<meta>`, Readability finds no site or publication
   date, and without `class` it cannot use class names to drop boilerplate
   such as share bars and comment threads
   ([#208](https://github.com/w3lt/lys/issues/208)). vmo deletes the VM
   before it answers and gives the read 30 seconds;
3. it reads vmo's answer. Only a `200` body is read: JSON
   `{ html, isTruncated }` of at most 16 MiB, whose HTML is cut to 4 Mi UTF-16
   code units without splitting a character. A `400` or `431`, for a URL vmo
   refuses, a `502`, for a page the reader could not load or that was empty,
   and a `504`, for a read past vmo's 30 seconds, fail the read with that
   reason. Any other status, or an answer that is not that JSON, fails it as
   a failure of the page reader. A plain-text page arrives as the HTML
   Chromium shows it in, its text inside a `<pre>`, and is read as one block
   that keeps its line breaks;
4. it extracts the main text with Mozilla Readability over a linkedom
   document, after removing `<template>`, `<script>`, `<noscript>`, `<style>`,
   and `<svg>` elements, whose text is not page text, and dropping the
   `hidden` and `aria-hidden` attributes so the text they hide is read like
   any other text. It refuses markup with more
   than 40,000 start tags before parsing it, and a parsed page with more than
   40,000 elements or a nesting depth sum above 400,000. A `<br>` or a nested
   block keeps the words around it apart;
5. it splits the text into passages of at most 1,200 characters and keeps at
   most 12,000 characters: the whole page, the passages that best match
   `focus` by BM25, or the beginning;
6. it frames the page's title, its site and date when the page's metadata
   gives them, which vmo's reader does not pass on yet
   ([#208](https://github.com/w3lt/lys/issues/208)), and the passages between
   `<<<page content>>>` delimiters, with the URL Lys was asked to read, a
   notice that the content is untrusted, the page's source number, and an
   instruction to cite it by that number, and notes a page
   with less than 200 characters of main text, which may ask the reader to
   sign in or check for automated readers. Every run of three or more `<` or
   `>` in page text is shortened to two, so no page can write a delimiter.
   Characters that show nothing (Unicode default-ignorable code points, and
   every format and control character except tabs and line breaks) belong to
   a run when they sit between its brackets, and are dropped with it, so they
   cannot hide a delimiter either.

The whole read, the host lookup and vmo's answer included, must finish within
60 seconds, which leaves time for vmo to create, boot, and delete the VM
around its own 30 seconds. Stop and the time limit end only Lys's request:
vmo does not notice, and the VM runs until vmo's own limit ends it. vmo does
not say where the page's redirects led, its HTTP status, or its media type,
so the page is cited under the URL Lys was asked to read, and an error page
is read like any other page. Failures the model can act on, such as a blocked
address, a page that did not load, a page too large to read, or a page
without any main text, become the call's result. A turn offers `read_page`
only while vmo answers its health route, but vmo can stop during the turn: a
vmo that is not running, fails, answers outside its contract, or does not
answer in time fails the read with whom to contact, and its cause goes to the backend log; vmo's own
error output is never read. Lys reads what a signed-out visitor sees; it
never signs in.

### `web_search`

`web_search(query)` searches the web through the Tavily Search API with the
person's API key. The query is trimmed and must have 1 to 400 characters, none
of which is a Unicode default-ignorable code point (such as a zero-width,
direction, tag, or variation selector character, or a Hangul filler), a
control, format, surrogate, private-use, or unassigned code point, or a line
or paragraph separator; otherwise the call is answered at once. Such
characters show nothing or can reorder text, so they are refused rather than
removed, and the approval card shows exactly the query sent. An emoji written
with a variation selector, such as `❤️`, is refused too. The rule is
`hasHiddenWebSearchQueryCharacter` in `@lys/protocol`, which the desktop
applies too.

- **Key.** `WebSearchToolProvider` reads `secrets.tavilyApiKey` from the
  desktop's settings file (`settingsFilePath`, `$LYS_HOME/settings.json`) with
  `readTavilyApiKey` (`src/infrastructure/settings/tavilyApiKeyFile.ts`),
  once per tool list request, chat request, and key check. The desktop host is
  the file's only writer. The reader reads at most 1 MiB, takes only that
  field, and drops every parse failure without logging it, because JSON parse
  messages quote the text. A missing file, group, or `null` means no key; a
  value that fails the key format is invalid; anything else unreadable is
  `settings-unreadable`. A turn's tool holds the key read when the turn
  started.
- **Request** (`web/tavilyRequest.ts`, `web/tavilyApi.ts`). Once allowed, one
  `POST https://api.tavily.com/search` asks for a basic search (one credit) of
  at most 5 results, without Tavily's generated answer, raw page text, or
  images. The client uses `node:https` with certificate verification forced on
  and TLS 1.2 at least, the same address rule as `read_page` on every resolved
  address and the connected socket, one connection per request, no cookies or
  proxy, and the key only in the `authorization` header. No redirect is
  followed. The whole request must finish within 15 seconds, and a body larger
  than 1 MiB, not `application/json` in UTF-8, or compressed is refused.
- **Evidence** (`web/searchEvidence.ts`). A result is kept only when its URL
  passes `read_page`'s URL rules, once per URL; titles are cut to 300
  characters and snippets to 500, flattened onto one line. The query line,
  the result count, and an untrusted-content notice precede the results,
  which sit between `<<<search results>>>` delimiters, each labelled with its
  source number; a closing note says a
  snippet is only an excerpt to read before relying on it and repeats the
  citation rule. No results produce a plain statement that nothing was found.
- **Failures.** A rejected key (401/403), rate limiting (429, with its
  `Retry-After` seconds), used-up credits (432/433), other HTTP errors, a
  redirect, a timeout, an unreachable host, an address refused by the rule,
  and an unreadable or oversized answer each become the call's result in
  Lys's own words; Tavily's error text is never passed on.

`POST /api/v1/tools/web_search/key-check`, whose body must be the empty JSON
object `{}`, reads the key and asks Tavily's `GET /usage` about it, through the
same client and limits, and answers
`accepted` (with the plan's credits when reported, a fraction rounded up to a
whole credit), `rejected`,
`unavailable`, or `failed`. Tavily charges two credits for each `GET /usage`,
although its documentation lists no cost for it; the check still uses it
because only that answer reports the plan's credits, which Test shows. Each
check sends the key to Tavily, so it is a
`POST` with a JSON body, which a page on another site cannot send without a
CORS preflight that the backend refuses; another body is answered with 400, or
415 for a media type Fastify cannot parse, before the key is read.

### `read_attachment`

`read_attachment(number, start_line?, line_count?)` returns lines of a text
file the person attached to a message of the conversation. Its definition
(`buildReadAttachmentDefinition`, `src/modules/attachment/readAttachmentTool.ts`)
has group `files`, access `reads`, and runner `backend`, and tells the model
to read a file by the number its message lists it under. A turn offers it
first, as a direct tool in every round, routed or not, when the
conversation, the new message included, holds a text attachment and the
model is trained for tool use. Its calls run without approval, as they
read only what the person attached to
this conversation; it has no Tools pane row and no saved choice.

`ReadAttachmentTool` holds the conversation's attachments by number and a
reader lent by the file store, so a call reaches a file only through its
stored row, never through a path of the model's. A number no attachment has
is answered with the list of the conversation's attachments; an image's
number, with a reminder that images are seen with their message; a line
argument that is not a whole number of at least 1, with the rule. A call
returns at most 200 lines, lowering a larger `line_count` to that, and at
most 16,000 characters, cut before the line that would pass the limit, or
within a first line longer than it, without splitting a character: a header
naming the attachment, the lines returned, the file's total lines and size,
how the limit cut them, which for a line cut within says the rest of it
cannot be read, and how to continue when lines follow; then the lines. Line
breaks of
either kind end lines; an empty file is reported empty, and a start line past
the end fails with the file's line count. A file missing from this machine
fails the call with a result the model reads; a file that cannot be read for
another reason rejects the call with the reader's failure, as a defect, and
Stop ends a read in progress.

### Agent state tools

The agent state tools let an agent say what it and the other agents are
doing in its own voice. `buildAgentStateTools`
(`src/modules/agent/agentStateTools.ts`) builds them for each turn of a model
trained for tool use, also while tool calls are switched off, after every
other tool of the turn. Their definitions have group `agents`, access
`reads`, and runner `backend`; they have no Tools pane row and no saved
choice, and their calls run without approval. Which ones an agent gets
follows its role (see [roles](#roles)):

| Tool               | Offered to               | Arguments                    | Result                                                                                                                                                                    |
| ------------------ | ------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `read_my_state`    | every agent but Armitage | none                         | Who the agent is, its role, how many of its request slots are in use, and each request it is working on or that waits for a slot, the reply that calls the tool included. |
| `find_agents`      | the built-in agents      | `query`, 1 to 100 characters | Up to 20 agents whose code, name, or bio contains the query, deleted ones included, and how many match.                                                                   |
| `read_agent_state` | the built-in agents      | `code`, an agent code        | Another agent's name, role, when it was deleted if it was, how many of its request slots are in use, and the requests it is working on or that wait for a slot.           |

A state names each request's conversation by its title, read when the tool
runs (`This reply, in this conversation` for the calling reply, otherwise
`In "<title>"`, `In an untitled conversation`, or
`In a conversation that was deleted`), the model, when it
started and how long ago, and its step: waiting for a free request slot,
with its place in line, getting ready to answer, reading tool results,
thinking, writing the reply, or using tools, with each call of the round and
its status, `running in the app` for a client tool. A state also gives the
time it was read and how many of the agent's request slots are in use, with
how many requests wait for one. A query is trimmed first; a query that is
then empty or longer than 100 characters, and a code that is not an agent
code, fail the call with a result that says the rule. A code no agent has
fails with a hint to use `find_agents`. A member that calls a leader's tool
gets the failed result of a tool the turn does not offer, and the runtime
service refuses such a search or read before it reads anything. Names, bios,
and titles are put on one line, as they may hold line breaks. Results are
stored with the reply like every tool result.

## Live agents

`AgentRuntimeService` (`src/modules/agent/agentRuntimeService.ts`) keeps one
live `Agent` per agent that a turn or a context measurement has loaded
(`loadChatAgent`), created on that first load and kept until the backend
stops, so every turn of an agent, overlapping or not, runs on one instance
that knows all of them. Each load gives the live agent the system prompt the
built-in or
stored agent has then; a reply already running keeps the prompt it started
with. A deleted agent answers no new turn, but its live instance stays, so
the replies it was writing when it was deleted run to their end and stay
listed in its state. Nothing of it is stored: a restart starts with no live
agent and no request.

While a reply runs, its agent follows the request in `AgentActivity`
(`src/modules/agent/agentActivity.ts`): the conversation, the model, the
start time, and the step of its current round, from the parts the reply
stores. A request is added when `createReply` starts, unless it is refused
because the agent's slots and line are full (see
[request slots](#request-slots)), and removed when it ends, whether the reply
completed, failed, or was stopped. A newer turn in the
conversation or a deletion ends a running reply only once its next write is
refused, so a reply waiting for an approval or a tool result stays listed
until the call is answered, the reply is stopped, or the backend stops
([#137](https://github.com/w3lt/lys/issues/137)). A reply waiting for a
request slot stays listed until it gets one, then ends at once (see
[request slots](#request-slots)).

### Request slots

`AgentActivity` also keeps the agent's request slots. A live agent works on
at most `agentRequestSlotCount` replies at once (2, from `src/config.ts`),
and each live agent has its own slots, so a busy agent never holds back
another. A reply takes a slot when `createReply` starts and keeps it until
the reply ends, also while it waits on the person for an approval or a
client tool's result. A reply that finds every slot held waits in line,
listed with the step `waiting` after the replies that hold slots; when a
reply of the agent ends, whatever its outcome, the reply that has waited
longest takes the slot at once and starts its first round. A waiting reply
has measured and sent nothing: Stop or shutdown ends it as `interrupted` and
frees its place in line, and it answers with the system prompt its agent had
when its turn was stored. The desktop shows it like a reply whose model has
not written yet. A newer turn in its conversation or a deletion does not
take it out of line, so it still counts toward the limit below; once it gets
its slot, the reply reads its stored state first, and when it is no longer
streaming, it ends as `interrupted` without reading, measuring, or sending
anything of its conversation, and frees the slot for the next reply.

At most `agentWaitingRequestLimit` replies wait per agent (8). A reply that
finds every slot held and the line full is refused: it is stored as
`failed` without reaching the model, its stream ends with an `error` event
that says how many requests the agent has and to send the message again once
it finishes one, and the chat route logs a warning. A reply is admitted, made
to wait, or refused synchronously when `createReply` starts, so two replies
can never take the same slot. Context measurements and title generation are
not requests and take no slot. Nothing of the slots is stored: a restart
frees them all.

### Roles

Roles are fixed in code (`src/modules/agent/agentRoles.ts`), from the
agent's code and kind:

| Role          | Agents                                  | Permissions                                     |
| ------------- | --------------------------------------- | ----------------------------------------------- |
| `leader`      | the built-in agents other than Armitage | read its own state, find agents, read any state |
| `member`      | the stored agents                       | read its own state                              |
| `tool-keeper` | Armitage                                | none                                            |

The tools an agent is offered and every check follow these permissions.
The runtime service answers each state read and search
(`AgentStateReader`): it checks the asking agent's permission before it
reads anything, reads agents through the agent service, deleted ones
included, and reads the requests of the agent's live instance; an agent with
no live instance is working on no request, and a read never creates one.

## Tool routing

When the model is trained for tool use and a turn offers client, built-in,
or MCP tools, the turn routes them through Armitage, the tool keeper, so the
model's context does not hold every tool definition while it decides which
one it needs ([#330](https://github.com/w3lt/lys/issues/330)).
`buildReplyTools` (`src/modules/agent/toolRouting.ts`) keeps every tool of
the turn in its toolset, but the reply's `ReplyToolOffer` offers its first
round only the direct tools (the attachment reader), `find_tools`, and the
agent state tools, and every round's system prompt ends with a note that
says how many tools Armitage keeps and to call `find_tools` before using
one. A model not trained for tool use, and a turn without such a tool, get
every tool from the first round, as before.

`find_tools(task)` (`src/modules/agent/findToolsTool.ts`) takes what the
model needs a tool for, 1 to 500 characters after trimming. Its definition
has group `agents`, access `reads`, and runner `backend`; it has no Tools
pane row and no saved choice, and its calls run without approval. A call
asks the `ToolKeeper` for the turn's tools that fit the task and answers
with their names, and each one is offered from the reply's next round to its
end. Discovery is not authorization: each call of a found tool passes the
argument check, the [tool call policy](#tool-call-policy), and the
[approval gate](#tool-approval) as any other, and a
call of a tool its round did not offer is stored as failed and never runs,
with a result that lists the tools the model can call and points to
`find_tools`, without saying whether the turn has that tool. When Armitage
cannot search, the call fails with a result saying so, no tool is offered
for it, the reply goes on, and the chat route logs a warning with the
request's logger.

`AgentRuntimeService` is the `ToolKeeper`. `runToolKeeperSearch`
(`src/modules/agent/toolKeeperSearch.ts`) runs each search on Armitage's
[live agent](#live-agents), as one of its requests on the asking
conversation, so it takes one of Armitage's request slots and a leader's
`read_agent_state` lists it while it runs. Armitage answers with its own
system prompt, the asking turn's model and generation controls, a user
message holding the task, no history or images, and two tools of its own,
which run at once without approval:

| Tool             | Arguments                                                                                                         | Result                                                                                                                                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `search_tools`   | `query`, 1 to 200 characters, with a word                                                                         | Up to 8 of the asking turn's tools whose name, group, and description best match the query, ranked with BM25 (`ToolCatalog`, `toolCatalog.ts`), each with its description on one line cut to 200 characters, and how many more match. |
| `recommend_tool` | `name`, the exact name of one of the asking turn's tools, as `search_tools` lists them; any other name is refused | Records the tool as fitting the task, at most 5 per search.                                                                                                                                                                           |

Armitage reads only the asking turn's definitions and runs none of its
tools. `MemoryReply` (`memoryReply.ts`) keeps Armitage's reply in memory;
it is never stored or sent, and the asking reply shows the search only as
its `find_tools` call. A search ends with the tools Armitage recommended
when its reply completes or reaches its limit of 6 rounds of tool calls. It
fails when Armitage's reply is refused, because its request slots and line
are full, a round does not fit the model's context window, or the model is
not loaded, when the reply fails, or when the model reports it cancelled.
Stop ends a search with the asking reply. Nothing of a search is stored.

## MCP servers

The backend is the Model Context Protocol client of Lys: it connects to the
servers the `mcp` group of `settings.json` names and switches on, and to the
servers Lys ships, today the [email server](#the-email-server), once the
person switches one on; it offers their tools to the model and runs each
allowed call on the tool's server. It speaks MCP through
the official TypeScript SDK, `@modelcontextprotocol/client`, over stdio or
Streamable HTTP. The routes are in the
[API reference](/reference/api/#mcp-servers), and the group's rules in the
[configuration reference](/reference/configuration/#mcp-servers).

### Registry and sessions

`McpServerRegistry` (`src/modules/mcp/mcpServerRegistry.ts`) owns the applied
servers, the servers Lys ships first and then the group's in its order, with
one `McpServerSession` for each server that is switched on and can start; a
server that is switched off, or a built-in server that cannot start, has no
session and is listed as `off` or `failed`. The composition
root creates it without reading the file or starting anything, and an
`onReady` hook in `src/di/fastify.ts` applies the group before the backend
listens, so the first request already sees every configured server,
connecting. The servers connect in the background and never delay
listening.

`updateServers()` reads the group with `readMcpSettings`
(`src/infrastructure/settings/mcpSettingsFile.ts`), which shares the bounded
settings-file read (at most 1 MiB, UTF-8) and takes only the `mcp` group, and
applies what it read in one synchronous step. Reads run one after another in
call order. A group that passes its rules is applied server by server: a new
server, or one whose settings changed, gets a new session while it is
switched on; an unchanged one keeps its session, with its connection or its
failure; a removed or switched-off one's session is stopped, and the list
reports a switched-off server as `off`. The servers Lys ships come first, in
their fixed order: while one is switched on, each apply reads what it needs,
for the email server the saved account and its password, and starts it in a
session, or lists it as `failed` with `account-missing` or `account-invalid`
and logs a warning once per reason; an added server with a built-in server's
name takes its place, and the built-in server is not applied until the added
one is renamed or removed, which is logged as a warning once. A missing file
or group means no added server and every built-in server off. A group that
fails its rules, or a file that cannot be read as a JSON object, keeps the
servers applied before; the list reports `invalid` or `unreadable`, and a
warning is logged. The warning names each failed rule by its path and the
rule, never a value, and a JSON parse error, which can quote the file, is
dropped unread. `POST /api/v1/mcp/servers/sync` applies the group again;
nothing else reads it after startup.

`openServerAgain(name)` stops the server's session and starts a new one with the
settings applied before, without reading the file; the new session opens once
the old one, and every other stopped session, released its server. A server
that is switched off, or a built-in server that cannot start, has no session
to open again: the reconnect route answers `409` instead. Nothing
reconnects by itself: a server whose connection ended stays failed until Reconnect or a
changed setting. The registry also lists the servers and their states, lists
the tools of every connected server, and finds one tool by its model-facing
name: the server name sits between `mcp__` and the next `__`, which is exact
because server names hold no `_`. `close()` stops every session and waits for
every settings read, opening, and close it started; the singleton bundle's
cleanup closes the email account checker first and the registry right after
it, before every other service.

An `McpServerSession` (`mcpServerSession.ts`) is one attempt to open a server
and the connection it leads to. It is `connecting` until the opening ends,
then `connected` with its tools or `failed` with a reason. A connection that
ends by itself, such as a process that exits or a URL server that answers a
call with HTTP 404 because it no longer knows the session, fails the session
as `closed`.
Stopping a session cancels its opening or closes its connection, and a
connection an opening returns after the stop is closed at once. A call that
is running when its session is stopped fails with a sentence that says why,
which the model reads: the settings just applied switched the server off,
changed it, or no longer name it; the person restarted or reconnected it;
or Lys was shutting down. Closes run in
the background, and the registry keeps each until it settles. Stopping also
returns the session's release, which settles once its opening ended and every
connection it led to closed, a command server's whole process group
included; for a group that does not end when its input closes, that takes
up to about four seconds, and asking a URL server to end its session up to
two more. The registry keeps the release of every session it stopped until it
settles, and every new session, after Reconnect or a new, changed, renamed,
or re-added server, opens only once all of them settled, whatever names
their servers had; applying the group stops every session it does not keep
before it starts any. So every process of a command's process group has
ended before the next one starts, a server a launcher such as `npx` or `uvx`
runs included, and a session stopped while it waits opens nothing. A process
that leaves the group, such as one that starts a session of its own, is not
covered. Every state change happens in one synchronous step, so a lookup sees
one consistent state.

The desktop host's stop of the backend's process group does not reach the
stdio servers' process groups, so the backend ends them itself when its own
process ends. `McpServerProcessGroups` (`mcpServerProcessGroups.ts`) holds
each group from the start of its command until no process of it is left, or
until its stop gave up after `SIGKILL`, and `registerBackendStopHandlers`
(`processStop.ts`) sends `SIGKILL` at once to every group it still holds: on
`SIGTERM`, which the desktop host sends first, on `SIGINT`, and on `SIGHUP`,
after each of which the backend exits with 128 plus the signal's number, and
on any other exit Node runs `exit` listeners for.

A backend killed with `SIGKILL`, or one that hangs until the host kills it,
runs none of that, so the holder also saves the groups it holds to
`$LYS_HOME/mcp-process-groups` (the `mcpProcessGroupsFilePath` setting) on
every change: each identifier in decimal followed by a line feed, written to
`mcp-process-groups.tmp` beside it and renamed over it, so a reader sees a
whole list; ending every group saves it empty. Once the host's stop has killed
and waited for the backend, it sends `SIGKILL` to every group the file still
names and deletes it; see
[backend process ownership](/architecture/host/#backend-process-ownership). A
save that fails is logged as an error and changes no group the holder holds;
the file then keeps the list of the save before. A backend that dies without
the host stopping it leaves its servers running until they notice their
closed standard input, and the next start deletes the file. A URL server's
session is not ended when the backend stops; the server ends it at its own
time limit.

### Opening a server

`openMcpServer` (`mcpServerOpening.ts`) starts or reaches the server, finishes
the MCP handshake, and reads the tool list, all within two minutes, which also
bound each request, and under the session's cancellation. It returns the
connection with its tools, a failure reason, or that it was cancelled; on
anything but a connection it closes what it started first. Two minutes leave
room for a command such as `npx` that downloads the server before it starts.

`McpServerConnection` (`mcpServerConnection.ts`) owns the SDK's `Client` and
its transport. Lys introduces itself as `lys` with the backend's version and
declares no client capabilities.

- **stdio.** `McpServerProcess` (`mcpServerProcess.ts`) starts the command
  with its arguments, without a shell, in the person's home folder, in a new
  session and process group of its own, which every process it starts joins
  unless it leaves it. The process gets
  `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, and `USER` from the backend's
  own environment, plus the configured variables, which win over them; it
  inherits nothing else. A command is looked up on that `PATH`, which for an
  app opened from the Finder is not the login shell's
  ([#258](https://github.com/w3lt/lys/issues/258)). The server's standard
  error is read line by line by `McpServerLogLines` (`mcpServerLogLines.ts`):
  each line without its line break, cut to 2,000 characters, blank lines left
  out, goes to the backend log. `McpServerMessageLines`
  (`mcpServerMessageLines.ts`) reads its standard output as one JSON-RPC
  message per line, as the SDK's own stdio transport does. A line longer than
  16 MiB is reported as soon as its bytes show it, and the rest of it is
  dropped; it fails the request it answers as too large and ends the
  connection; the calls in flight then fail as too large once the process
  group ended. Closing the connection ends the whole process group: Lys closes
  the command's standard input, sends `SIGTERM` to the group when a process of
  it is still left two seconds later, then `SIGKILL` after two more. A close
  settles once no process of the group is left, reaped included, and the
  three pipes are closed; the command's own exit does not count, because the
  processes it started may still run. Once the pipes are closed, what a
  process that left the group but kept one of the command's standard streams
  writes reaches nobody. A group still left two seconds after `SIGKILL` fails the close
  and is no longer held: every process of it the backend may signal already
  received `SIGKILL`, and sending it again at the backend's exit could reach
  another group that took the identifier once this one ended.
  `McpStdioTransport`
  (`mcpStdioTransport.ts`) makes every close share that one stop, whoever
  starts it: the SDK client, the connection at a message line past 16 MiB, or
  the transport itself once the command's process exited by itself, which
  ends the rest of its group too. It tells the client that the transport
  closed only once that stop settled.
- **Streamable HTTP.** The SDK's `StreamableHTTPClientTransport` sends each
  request to the configured URL with the configured headers, and
  `redirect: "manual"`, so a redirect is an HTTP error and is never
  followed. `sendMcpHttpRequest` (`mcpResponseLimit.ts`) reads at most 16 MiB of
  each answer's body. An event stream the SDK reads one event at a time, a
  success other than `202` whose media type is `text/event-stream`, is counted
  per event instead: an event's lines with their line ends, the count starting
  again after each blank line. A stream that stays open, such as the one the
  SDK opens for the server's own messages, can so send any number of events
  within the limit. Every other answer the SDK reads whole, an error answer
  included, and is counted whole. An answer or event past the limit ends the
  connection, as a long stdio message line does: `McpServerConnection` closes
  the client at once, so every request in flight fails as too large. The SDK
  alone would leave a request whose event stream breaks waiting for its time
  limit. A call answered with HTTP 404 ends the connection, because the server
  no longer knows the session. `McpHttpTransport` (`mcpHttpTransport.ts`)
  wraps the SDK's transport. A failure the SDK both reports on the connection
  and throws from a send reaches Lys once, as the failure of that request; a
  failure it reports while a send is pending is passed on once the send
  settles; and an HTTP error a send throws carries the status but never the
  answer's body. Closing the connection aborts its open requests, which fail
  without being reported as connection errors: an abort failure the SDK
  reports once the close started is dropped, because the SDK reports the
  aborted request for the server's event stream although it was asked to
  abort it. The close then asks the server to end its session, as the MCP
  specification asks of a client:
  `closeMcpHttpSession` (`mcpHttpSessionEnd.ts`) sends `DELETE` to the URL with
  the configured headers, `Mcp-Session-Id`, and `Mcp-Protocol-Version`,
  following no redirect, and gives up after two seconds. An answer of `2xx`,
  `404`, which says the server no longer knows the session, or `405`, which
  says it does not let clients end sessions, is fine. Any other answer, a
  request that fails, or the time limit passing is logged as a warning, with
  only the status of an answer, and the close still succeeds. An opening
  whose handshake fails after the server gave a session ends that session
  too. The SDK's own `terminateSession` is not used: after the close, it
  would send under the transport's aborted signal and report its failure as
  a connection error.

The tool list is read past the SDK's response cache, so the SDK holds no
tool's output schema and never checks a result against one: it would compile
the schema and run a `pattern` the server chose on the backend's event loop.
A result's structured content is read as untrusted JSON within Lys's own
limits instead.

`getMcpToolCatalog` (`mcpToolList.ts`) asks for the tool list one page at a
time and turns each page's tools into catalog entries before it asks for the
next page, so the read holds one page, at most 16 MiB, the names of the page
before, and the catalog, never the server's whole list or its objects.
Reading stops at the end of the list; at the 129th tool, which marks the list
as cut, so later pages are never asked for; or at a page that names the cursor
it was asked with and holds as many tools with the same names as the page
before, whose tools are left out as the server repeating itself. The SDK's own
list read stops at such a page too, but compares the whole tools; Lys compares
only their names, so that it never walks two untrusted pages. A 16th page that
names a next one fails the opening as an answer that is not valid MCP, unless
the list passed 128 tools by the end of that page.
`calculateMcpRequestFailure`
(`mcpError.ts`) tells failures apart by the SDK's error types and their
causes: a time limit that passed, a process that exited or a connection that
ended, an HTTP status (403 also when the SDK reports a missing scope), no
connection at all,
a command that could not be started, a JSON-RPC error the server answered
with, an answer that is not valid MCP, an answer longer than 16 MiB, or none
of these. An opening reports them as `timed-out`, `closed`,
`unauthorized` (HTTP 401 or 403), `http-error` (any other status),
`unreachable`, `start-failed`, or `protocol-error` (an error answer, an answer
that is not MCP or is too long, or a failure Lys cannot tell apart).

### Tools of a server

`McpToolCatalogBuilder` (`mcpToolCatalog.ts`) takes a server's tools one at a
time, keeps the first 128, and marks the list as cut at the next one. It
checks each tool against the SDK's MCP tool schema first; a tool that schema
refuses fails the opening as an answer that is not valid MCP. That schema
checks no more of a tool's output schema than that it is an object; Lys never
reads output schemas. Each tool is offered to the model
as `mcp__<server>__<tool>`, with every character of the server's name for it
other than an ASCII letter, a digit, `_`, or `-` replaced by `_`. A tool is
skipped, with its reason, when the server's name for it is empty, longer
than 128 characters, or holds a character a person cannot see, or its
`mcp__` name would pass 64 characters (`unsupported-name`);
when a tool listed before it gets the same name (`duplicate-name`); when its
input schema is not an object schema, names an argument outside the argument
name rule, nests deeper than 32 levels, holds a `__proto__` key, or holds a
character a person cannot see in any key or text
(`unsupported-input-schema`); or when that schema is larger than 64 KiB as
JSON (`input-schema-too-large`). The SDK's tool schema checks the properties
of an input schema recursively, so an input schema nested deeper than 32
levels, or holding a `__proto__` key, is checked as an empty object schema
instead, and its tool is then skipped as `unsupported-input-schema`: a schema
nested thousands of levels deep costs only its own tool. The SDK's tool
schema checks no other part of a tool recursively. A listed tool's
description is the server's
description, else its title, else its annotations' title, cleaned of
invisible characters and cut to 4,096 characters, or else a sentence naming
the tool and its server. Its name and input schema are kept as the server
gave them, the schema as the function's parameters for the model; because
Lys does not change them, a tool is listed only when both hold text a person
can see, so the approval prompt and Settings show what the model reads. Every
MCP tool has group `mcp`, access `unknown`, and runner `mcp`: what it does
depends on its server, which Lys cannot tell. The catalog is read once, when
the server connects ([#256](https://github.com/w3lt/lys/issues/256)).

### Calls of MCP tools

`findRequestedBackendTools` (`src/modules/chat/routes/turnRequest.ts`) sorts
the names in `backendToolNames`: a built-in tool's name, or a name starting
with `mcp__`, which the registry looks up. It throws for every name that is
neither, which the chat and context routes answer with `400`. The chat route
checks the built-in tools' availability first, then answers `409`
`backend-tool-unavailable` with the reason `mcp-server-not-connected` for the
first offered tool whose server is applied but not connected. The tool list
names only the tools of connected servers, so a desktop offers such a tool
only when the server stopped being connected after the list was read.

The turn keeps each tool's definition and a call function, and `Agent` adds
MCP tools to the toolset after the reader, the client tools, and the
built-in tools, and before the [agent state tools](#agent-state-tools); a
[routed](#tool-routing) turn offers each one once `find_tools` finds it.
`AgentTool.parseCallArguments` checks only the shape of an MCP call's
arguments before the person is asked: argument text of at most 256 KiB, a
JSON object whose keys follow the argument name rule, every name the input
schema requires, at most 32 levels of nesting, and no `__proto__` key. The
server checks the values.

`handleMcpToolCall` (`src/modules/agent/toolCallRound.ts`) sends every call
the [tool call policy](#tool-call-policy) allows through the round's
[approval gate](#tool-approval), which asks the person
unless they saved the tool as Just run. An allowed call runs on its server as
the server is connected when the call runs, with five minutes to answer, and
the reply's Stop signal tells the server that the call was cancelled. A call
whose server is no longer connected, or no longer lists the tool, fails with a
sentence the model reads and is logged as a call that was not sent. Because an MCP tool's access is `unknown`, its
result, failure, or rejection is cleaned of invisible characters like a
network tool's before it is stored and read.

`formatMcpToolResult` (`mcpToolResult.ts`) frames the server's result as
untrusted: a sentence naming the server and the tool, by the
`mcp__<server>__<tool>` name the model called, then the output between
`<<<mcp result>>>` and `<<<end of mcp result>>>`, in which every run of three
or more `<` or `>` is shortened to two, cut at 20,000 characters with a note.
Text blocks and embedded text resources are kept; an image, audio, or a binary
resource is named but not passed on
([#257](https://github.com/w3lt/lys/issues/257)); a resource link shows its
name and address. A result without content shows its structured content as
JSON. A result the server marks as an error is stored as a failed call, with a
sentence saying the server reported the tool failed. A call that fails before
the server returns a result is stored as failed with a sentence saying why
(`formatMcpToolCallFailure`), and is logged; a failure Lys cannot tell apart is
logged at `error` with what was thrown, and the reply goes on.

### MCP log entries

`handleMcpServerEvent` (`mcpServerEventLog.ts`) writes what the servers do that no
caller observes to the backend log, through the reporter the composition root
passes; each entry names the server as `mcpServer`. A settings group that
fails its rules or cannot be read, a connection that ended, a connection error
the SDK reports outside a request, a URL server's session that its close did
not end, and an opening or call failure Lys can tell apart are warnings, and
so are a built-in server that is switched on without a usable account and a
built-in server's name an added server took; a session stopped because the
settings switched its server off, changed it, or no longer name it is
information, with the reason. A connection, with its tool and skipped-tool counts, and
each standard-error line of a stdio server are information. A failure Lys
cannot tell apart and a failed close are errors, with what was thrown. Lys
builds no entry from a command, an argument, an environment variable, a URL,
or a header. An error is logged as it was thrown, though, so its message can
carry part of what the server answered, such as a piece of an answer that is
not JSON; an HTTP error is logged only by its code and status, never its
body. A stdio server's line is logged as the server wrote it; see
[process logging](/operate/logging/#process-logging). The email account checks
are logged by `handleEmailAccountCheckEvent`
(`builtIn/email/emailAccountCheckLog.ts`): a report is information, with both
outcomes and the server's own error lines; a missing email server, a check
refused while another ran, and a check the closing backend ended or did not
run are warnings; and every other failure to report is an error, with Node's
error for a start that failed, which can name the command, and otherwise
with the server's own error lines and, when it exited, its exit code or
signal. No entry holds the account or the password. See
[email account check entries](/operate/logging/#email-account-check-entries).

### The email server

Lys ships one MCP server of its own, `email`, which reads, searches, sends,
and files the person's mail over one IMAP and SMTP account. It is a Rust
program at `mcps/email`, installed by `build.sh` as
`$LYS_HOME/runtime/email/email` and named to the backend as `emailServerPath`,
from `LYS_EMAIL_SERVER_PATH`, which the desktop host sets to the workspace
build in development; see the
[configuration reference](/reference/configuration/#lys-home-directory).
`createEmailMcpServer` (`src/modules/mcp/builtIn/email/emailServer.ts`)
describes it to the registry as a built-in stdio server. At each apply while
its switch, `mcp.builtIn.email.enabled`, is on, the registry reads the saved
account and its password with `readEmailAccount`
(`src/infrastructure/settings/emailAccountFile.ts`), which takes only the
`email` and `secrets` groups of `settings.json` and reports `read`,
`missing`, `invalid`, or `unreadable`, and builds the server's settings: the
executable as the command, no argument, and one environment variable,
`LYS_EMAIL_ACCOUNT`, holding the account and the password as one line of
JSON. Those settings pass the shared server rules like any command the
backend starts, so the server runs through the same session, process group,
log line, message line, and stop code as an added stdio server, and a
changed account or password is a changed setting that restarts it. A
missing account, or an account or password that fails its rules or cannot
be read, lists the server as `failed` with `account-missing` or
`account-invalid`, and nothing is started; a missing executable fails the
start as `start-failed`.

The server reads the variable back under the same rules, because anyone on the
machine can start the binary with a variable of their own, then serves MCP
over stdio with ten tools: `search_emails`, `read_email`, `read_conversation`,
`read_attachment`, `list_folders`, `manage_folder`, `send_email`,
`save_draft`, `send_draft`, and `delete_draft`; the [API
reference](/reference/api/#the-email-servers-tools) says what each does. Every
call opens at most one IMAP and one SMTP connection of its own and closes them
before answering. A reply, a forward, and `send_draft` keep their IMAP
connection open while they send; any other send that files a copy in Sent
opens IMAP only after the send. Nothing stays open between calls, and
stopping the process closes every connection. A connection is protected as
the account says: TLS from the first byte, STARTTLS before any credential,
or none, which the rules allow only to `localhost`, `127.0.0.1`, or `[::1]`;
a certificate is verified by the operating system's store through
`rustls-platform-verifier`. A whole call takes at most 240 seconds, the one
deadline, within the five minutes the backend gives every MCP call; inside it,
the TCP connection and each TLS handshake but SMTP's after STARTTLS take at
most 15 seconds each, each IMAP command and each SMTP step, such as the
greeting with EHLO, STARTTLS with its handshake and second EHLO, the sign-in,
MAIL, each recipient, DATA, or QUIT, at most 30, and a message's content with
the SMTP server's answer at most 120. A longer successful result is cut so
that, with its note, it holds at most 20,000 UTF-16 code units, the length the
backend keeps of every MCP result, error or not. The server's standard error
lines, which the backend keeps as `MCP server log line` entries, name an
operation, counts, and the class of a failure, never the password, an
address, a subject, or a body.

### Email account check

`EmailAccountChecker` (`src/modules/mcp/builtIn/email/emailAccountCheck.ts`)
answers `POST /api/v1/mcp/email/account-check`, which the desktop sends before
it saves an account: it runs the email server's `check` subcommand in the
person's home folder, with the candidate account and password in
`LYS_EMAIL_ACCOUNT`, as the server itself is started, and the subcommand signs
in to the IMAP and the SMTP server at the same time, within 20 seconds each
with the logout, and prints one JSON line with both outcomes; a sign-in whose
closing LOGOUT or QUIT fails or goes unanswered still counts as accepted, and
the server writes an error line about it. The checker reads at most 65,536
characters of that output, keeps the first 32 of the server's error lines,
which the log writes with the outcomes or with the failure, runs one check at
a time without a queue, and kills a check that has not ended after one minute.
It answers `checked` with each server's outcome, `accepted` or `failed` with a
reason, or `unavailable` with `busy` at once, without running and without
keeping the account or the password, when another check is running,
`server-missing` when the executable is not where the configuration names it, or
`server-failed` when it could not be started, ended without a report, did not
end in time, or the checker is closing. Nothing is saved: the desktop saves the
account and its password only after both servers accepted the sign-in. The
checker owns the run of the check running now, an `EmailServerCheckRun` that
owns its process; the singleton bundle's cleanup closes the checker before the
registry, which kills a running check.

## Persistence

The backend stores conversations and agent definitions in SQLite at
`$LYS_HOME/lys_db.sqlite`, in the
[Lys home directory](/reference/configuration/#lys-home-directory).

| Table                      | Purpose                                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `conversations`            | Stores conversation metadata: title, agent code, and timestamps.                                              |
| `conversation_messages`    | Stores ordered user messages and replies with status, finish reason, and timestamps, and each reply's parts.  |
| `conversation_sources`     | Stores each conversation's numbered web sources.                                                              |
| `conversation_attachments` | Stores each attachment of a user message: number, name, kind, size, and an image's media type and sides.      |
| `agents`                   | Stores agent definitions: code, name, bio, system prompt, timestamps, and the time a deleted one was deleted. |

The backend's database owner, `SqliteDatabase` in `src/infrastructure/database/`,
opens the file once, applies the schema from `migrations.ts` using
`PRAGMA user_version`, and is the only owner that closes it. Stores borrow read
and write transactions that expose neither connection closing nor transaction
control; the SQLite conversation records in `conversations/` are built on them
and hold every conversation query. The history-reading, history-editing,
turn, and reply-part services wrap those records, and each is its own
application service. The attachment files themselves live outside SQLite,
under `$LYS_HOME/attachments`, owned by `AttachmentFileStore`; see
[attachments](#attachments).
The agent service `AgentService` (`src/modules/agent/agentService.ts`) owns
agent management. It uses the SQLite agent records in `agents/` for stored
agents, but it is not one of the database services: it also owns the built-in
agents, Caliginia (`caliginia`), Lysiptera (`lysiptera`), and Armitage
(`armitage`), the tool keeper, which `buildBuiltInAgents`
(`src/modules/agent/builtInAgents.ts`) builds from the three configured
system prompts. Armitage answers other agents through
[`find_tools`](#tool-routing), never a chat. A built-in agent is never
stored: the service
lists it with every page, reads it with `kind: "built-in"`, refuses to change
or delete it, and refuses to store another agent under its code. Deleting a
stored agent marks its row deleted at the time of the deletion and keeps the
rest: listings, counts, `GET`, and changes skip it, but its code stays taken,
a lookup or search still finds it, and a code derived from a name skips it.
The composition root creates the service after the conversation services,
over the agent records, and the agent runtime service over it, the chat
service, the LLM service, and the history reader, which gives the titles of
the requests' conversations.

`Agent` (`src/modules/agent/agent.ts`) answers turns with its own system prompt
through a `ReplyModel`. `AgentRuntimeService.loadChatAgent` returns the
[live agent](#live-agents) that answers chats under a code, built-in or
stored and not deleted, holding the agent's current system prompt, so an
edited prompt is sent from the conversation's next turn. The chat module's `OpenAiReplyModel` implements `ReplyModel`
over `ChatService`'s streaming completion, using only choice 0 and refusing
finish reasons other than `stop` and `length`. The chat route passes the agent
the turn's history, its reply writes, its event sender, its Stop signal, and
four reporters that log with the request's logger: a cancelled reply and a
round that was not sent, because it did not fit or its model was not loaded,
at debug level, a tool search Armitage could not finish at warning level,
and any other failed reply at error level. A new
conversation must name a built-in or stored agent other than Armitage, or
the chat route answers `404` before storing anything. When a stored
conversation's agent is deleted
or no longer exists, the chat route answers `409` and stores nothing, so the
conversation stays readable. A deleted agent's code is never free again;
only an agent removed before version 11 left its code free, and its
conversations accept messages again once an agent has that code.
Version 4 preserves activity
timestamps on rename, version 5 preserves them on status-only message updates,
version 6 adds the `agents` table, version 7 replaces the stored system prompt
with the conversation's agent code, version 8 moves every conversation stored
under the former built-in code `lys` to `caliginia`, version 9 stores each
reply's parts as rows of their own and adds the conversation sources,
version 10 adds the attachment rows, version 11 adds `agents.deleted_at`, so
deleting an agent only marks it, version 12 moves a stored agent coded
`armitage`, deleted or not, and every conversation stored under `armitage`
to the first `armitage-<n>` code no agent or conversation holds, so the code
is Armitage's, and
turn persistence's startup recovers streaming assistants and their open tool
calls without reordering history.
Two triggers keep `conversations.updated_at` in sync with message and part
inserts and `content` updates.

## Model provider integration

Chat generation and model management use separate integration boundaries:

| Service             | Backend dependency        | Current use                                                                                                                  |
| ------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `ChatService`       | `openai` SDK              | Streams chat completions and generates titles through the connected provider's OpenAI-compatible HTTP interface.             |
| `LlmService`        | `LlmEngineOperationQueue` | Runs inventory, health, load, stop-by-key, and context measurement through the serialized queue.                             |
| `LlmRuntimeService` | `LlmRuntime`              | Owns the runtime of the saved provider, its connection status, and the serialized model-operation queue; connects on demand. |
| `LmStudioRuntime`   | `@lmstudio/sdk`           | Verifies engine availability, lists, loads, stops, and measures models, and owns SDK client cleanup.                         |
| `OllamaRuntime`     | `fetch`                   | Lists, describes, and measures Ollama's chat models over its native API, on a local server or in Ollama Cloud.               |
| `GroqRuntime`       | `fetch`                   | Lists and measures Groq's models over its OpenAI-compatible API.                                                             |

The [provider integration](/architecture/providers/) describes each provider.

Every runtime implements `LlmRuntime`: the `LlmEngine` queries, which list the
downloaded models and the instances that answer a request now and measure a
context, and the `LlmRuntimeLifecycle` probe and disposal. Loading a model and
stopping an instance is the separate `LlmModelInstanceController` capability,
which only `LmStudioRuntime` implements. Acquiring a runtime reports who loads
the provider's models: `lys` for LM Studio, with the runtime as its controller,
and `provider` for Ollama, Ollama Cloud, and Groq, which decide which models
are in memory: every model of Ollama Cloud and Groq counts as loaded, and so
does every model a local Ollama server is running. Each queued operation receives
the connected engine with that report, and the controller only when Lys loads
the models. `LlmService` refuses a load or an unload for a provider that loads
its own models without a runtime call, and the list response carries the
report as `modelLoading`.

Fastify exposes the application-scoped `llmService` and `llmRuntimeService`.
Model routes use provider-neutral capabilities of `LlmService`; the runtime
status and connect routes use `LlmRuntimeConnectionObserver` and
`LlmRuntimeConnector`, implemented by `LlmRuntimeService`. The ownership path
is `routes -> LlmService -> LlmRuntimeService queue -> LlmRuntime ->
LmStudioRuntime | OllamaRuntime | GroqRuntime`. The composition root creates
the database, then `LlmRuntimeService` without contacting the provider, then
`ChatService`, which reads the connected provider from it; cleanup runs in
the reverse order. After the HTTP listener opens, an `onListen` hook makes
one connection attempt; later attempts happen only through
`POST /api/v1/llm/runtime/connect`. Each attempt reads the saved provider
from `settings.json` again, and a held runtime for another provider, address,
or key is released before a new one is acquired. The runtime service drains
accepted operations before releasing its runtime; releasing LM Studio's
closes the SDK client without unloading models or stopping LM Studio.

Each SDK client logs through `PinoLmStudioSdkLogger`, which the composition
root creates over the application's logger, so the SDK's messages, such as
why it could not connect, are lines of the backend's log; see
[process logging](/operate/logging/#process-logging).

The connection status is `connecting` until the first attempt settles,
`connected` while a runtime is held, and `unreachable` after a failed attempt
or after a held runtime stops answering. Model operations are refused with
`503` `urn:lys:problem:llm:runtime-unavailable` unless the status is
`connected`. When a runtime call fails during a model operation, the service
probes the runtime before the queue moves on and releases it if the provider
no longer answers. Refresh keeps a runtime that still answers and otherwise
acquires a new one. Refreshes share a queued attempt. A refresh made while an
attempt runs reads the saved provider and shares that attempt when it read the
same provider, so a provider that does not answer is not tried twice;
otherwise the refresh queues one of its own, so a provider picked while an
attempt runs is the one connected. The queue and its `ready`, `closing`, and
`closed` lifecycle belong to `LlmRuntimeOperationQueue`, which
`LlmRuntimeService` owns.

`LmStudioRuntime.create()` still waits for LM Studio to answer its version
query, so a held runtime was always available when acquired. The installed SDK
cannot cancel a pending version query, so an attempt and the queue behind it
have no completion deadline; a nonresponding LM Studio can keep an attempt or
shutdown pending. A refused loopback port fails immediately. SDK messages
queued during an outage can be sent after a reconnect; see
[issue #81](https://github.com/w3lt/lys/issues/81).

`GET /api/v1/llm/:modelId/health` uses the same service queue and makes one fresh
loaded-inventory query. It reports `ready` when the validated snapshot contains
the requested canonical key. An absent key reports `model-not-loaded`; a query
that cannot establish loaded state reports `runtime-unavailable`. The check
does not generate text or change which models are loaded, and does not involve
`ChatService`. It establishes current availability, not future inference success.
See the [health response contract](/reference/api/#model-health-responses).

## Failure behavior

| Condition                                                                                                                                                              | Current behavior                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Chat SSE connection closes                                                                                                                                             | Only that follower ends; the reply and its title keep generating and are stored.                                                                                                                                                                                   |
| Reply-stop request                                                                                                                                                     | The reply's upstream request is aborted, the reply is stored interrupted, and followers receive `interrupted`; the title task continues.                                                                                                                           |
| Model operation or health-check client disconnects                                                                                                                     | Accepted work continues until success or failure; user cancellation is unavailable.                                                                                                                                                                                |
| LLM runtime queue already has nine accepted operations (including connection attempts)                                                                                 | New inventory/health/load/unload requests receive `503` with `urn:lys:problem:llm:service-busy` before acceptance.                                                                                                                                                 |
| The provider is not connected                                                                                                                                          | List, load, unload, and health requests receive `503` with `urn:lys:problem:llm:runtime-unavailable` before acceptance.                                                                                                                                            |
| A runtime call fails and the provider stopped answering                                                                                                                | The runtime is released, the status becomes `unreachable`, and a rejected request receives the runtime-unavailable `503`.                                                                                                                                          |
| The saved provider needs a key and none is saved, or `settings.json` cannot be read                                                                                    | The connection attempt fails without contacting a provider, the status becomes `unreachable`, and the backend logs why without a key.                                                                                                                              |
| Load or unload is asked of a provider that loads its own models (Ollama, Groq)                                                                                         | `409` with `urn:lys:problem:llm:provider-loads-models` before any runtime call. The desktop offers neither when the list says so.                                                                                                                                  |
| A request resolves after a failed runtime call; the probe or release then fails                                                                                        | The response keeps its result; the backend logs the probe or release failure at `error`.                                                                                                                                                                           |
| A reply round does not fit the loaded model, or its model is not loaded                                                                                                | The round is not sent; the reply is stored failed and followers receive an `error` that says why.                                                                                                                                                                  |
| A reply round cannot be measured (provider not connected, queue full)                                                                                                  | The round is not sent; the reply is stored failed and followers receive the general `error`.                                                                                                                                                                       |
| Model stream ends without a finish reason                                                                                                                              | The route treats it as an error and may emit `error`.                                                                                                                                                                                                              |
| Assistant row was deleted or already finalized                                                                                                                         | Late writes return false without recreating data.                                                                                                                                                                                                                  |
| Assistant terminal state cannot be persisted                                                                                                                           | The task aggregates the original and storage failures, plus a failed fallback's, and rejects; the generation logs it. No final event.                                                                                                                              |
| Unknown finish reason                                                                                                                                                  | The backend throws instead of silently coercing it.                                                                                                                                                                                                                |
| Title generation produces no usable title                                                                                                                              | The task logs a warning and sends no `error` or `title` event; a later turn retries if the conversation is still untitled.                                                                                                                                         |
| A generated title cannot be saved                                                                                                                                      | The task logs an error and sends no `title` event; a later turn retries if the conversation is still untitled.                                                                                                                                                     |
| A stored title cannot be sent after turn start                                                                                                                         | That follower ends silently while generation continues; a later turn attempts reconciliation again.                                                                                                                                                                |
| A follower falls 4,096 events behind                                                                                                                                   | That follower closes without a final event while generation continues; following the reply again returns its stored state.                                                                                                                                         |
| A chat request's attachment is neither UTF-8 text nor a PNG, JPEG, or WebP image                                                                                       | The route answers `400` with `urn:lys:problem:chat:attachment-unsupported`; nothing is stored or written.                                                                                                                                                          |
| An image is attached for a model without vision, or for one the inventory does not list                                                                                | The route answers `409` with `urn:lys:problem:chat:image-needs-vision`; nothing is stored or written.                                                                                                                                                              |
| The provider is not connected, or the queue is full, while a chat or context request reads a model's capabilities for the first time                                   | The route answers the runtime-unavailable or service-busy `503` problem; nothing is stored or written.                                                                                                                                                             |
| An attachment file cannot be written                                                                                                                                   | The message's folder and the files written into it are deleted, and the route rethrows; nothing is stored.                                                                                                                                                         |
| A turn cannot be stored after its attachment files were written                                                                                                        | The message's folder is deleted again and the route answers `500`; a folder that cannot be deleted fails the request with both failures.                                                                                                                           |
| A stored attachment's file is missing from disk                                                                                                                        | An image becomes a placeholder sentence in its message; a read of a text file fails with a result the model reads. The turn goes on.                                                                                                                               |
| A deleted conversation's attachment folder cannot be removed                                                                                                           | The delete still answers `204`; the backend logs the failure with its cause at `error`, and the folder stays.                                                                                                                                                      |
| A request offers a backend tool that is neither a built-in tool nor a tool an applied MCP server lists                                                                 | The route answers `400`, naming every such name; nothing is stored.                                                                                                                                                                                                |
| A request offers a tool whose MCP server is applied but not connected                                                                                                  | The route answers `409` with `urn:lys:problem:chat:backend-tool-unavailable` and `mcp-server-not-connected`; nothing is stored.                                                                                                                                    |
| An MCP server cannot be started or reached, refuses Lys, or does not finish opening within two minutes                                                                 | The server is `failed` with its reason and its tools are not listed; the backend logs a warning, or an error with what was thrown for a failure it cannot tell apart. Reconnect or a changed setting tries again.                                                  |
| A connected MCP server's process exits, its connection ends, or it answers a call with HTTP 404                                                                        | The server becomes `failed` with `closed`, its tools are no longer listed, and the backend logs a warning; a call that then runs fails with a result the model reads.                                                                                              |
| An MCP tool call fails before the server returns a result (five minutes passed, the connection ended, an HTTP error, a refusal)                                        | The call is stored `failed` with the reason the model reads, and the backend logs it; the reply goes on.                                                                                                                                                           |
| The `mcp` settings group fails its rules, or the settings file cannot be read, when it is applied                                                                      | The servers applied before are kept, the server list reports `invalid` or `unreadable`, and the backend logs a warning without any value.                                                                                                                          |
| An MCP server is switched off in Settings → MCP                                                                                                                        | Its session is stopped and its tools are no longer listed; a call running on it fails with a sentence saying the server was stopped, and the list reports `off`. Reconnect answers `409` with `urn:lys:problem:mcp:server-off`.                                    |
| The built-in email server is switched on while no usable account is saved                                                                                              | The server is `failed` with `account-missing` or `account-invalid`, nothing is started, and the backend logs a warning once per reason; Reconnect answers `409` with `urn:lys:problem:mcp:server-off`, and saving an account applies the group again.              |
| An added MCP server has the built-in email server's name                                                                                                               | The added server is applied and listed; the built-in server is not, and the backend logs a warning until the added server is renamed or removed.                                                                                                                   |
| The email server's executable is missing, or an account check does not report                                                                                          | The server fails as `start-failed`; a check answers `unavailable` with `server-missing` or `server-failed`, and the backend logs a warning for a missing server, or an error with the server's error lines; a check that has not ended after one minute is killed. |
| An account check arrives while another runs                                                                                                                            | It is answered `unavailable` with `busy` at once, without running and without keeping the account or the password, and the backend logs a warning.                                                                                                                 |
| A chat names Armitage, the tool keeper                                                                                                                                 | The route answers `404` with the agent-not-found problem; nothing is stored.                                                                                                                                                                                       |
| Armitage cannot finish a tool search (its request slots and line are full, a round does not fit or its model is not loaded, its model fails or reports a cancellation) | The `find_tools` call is stored failed with a result saying Armitage could not search, no tool is offered for it, the reply goes on, and the chat route logs a warning.                                                                                            |
| Starting a turn fails for another reason                                                                                                                               | The route rethrows; Fastify logs it and responds `500` if no event was sent. Written rows stay.                                                                                                                                                                    |

See the [provider cancellation policy](/architecture/providers/#cancellation-policy)
for the separate inference and model-management lifetimes.

## What is not implemented here

- No Rust backend service
- No replayable shared event bus
- No credential-management layer
- No OAuth sign-in to a mail provider: the email server signs in with a
  password or an app password only
- No OAuth sign-in for remote MCP servers
  ([#253](https://github.com/w3lt/lys/issues/253)), no HTTP+SSE transport for
  older MCP servers ([#254](https://github.com/w3lt/lys/issues/254)), and no
  MCP resources, prompts, sampling, elicitation, or roots
  ([#255](https://github.com/w3lt/lys/issues/255))
- No provider fallback or budget-accounting logic
- No attribute-based policy engine: the
  [tool call policy](#tool-call-policy) applies fixed rules to argument
  text, and answers allow or deny, never a request for approval of its own
- No approval bound to one exact call
  ([#336](https://github.com/w3lt/lys/issues/336)) and no stored audit
  record of tool decisions ([#337](https://github.com/w3lt/lys/issues/337)),
  parts of #330's tool authorization spec
