Lys answers every request through one model provider at a time, chosen in
the desktop's Providers pane:

| Provider  | Where it runs                                                       | How Lys reaches it                                        |
| --------- | ------------------------------------------------------------------- | --------------------------------------------------------- |
| LM Studio | A server at an address the person sets, `127.0.0.1:1234` by default | The LM Studio SDK, and its OpenAI-compatible `/v1`        |
| Ollama    | A local server, `127.0.0.1:11434` by default, or Ollama's cloud     | Ollama's native `/api/*`, and its OpenAI-compatible `/v1` |
| Groq      | Groq's hosted API at `api.groq.com`                                 | Groq's OpenAI-compatible `/openai/v1`                     |

LM Studio and a local Ollama server are reached over plain HTTP, without a
key. Ollama's cloud and Groq are reached over HTTPS with the API key the
person saved for them, and receive the conversations they answer. The
choice, the addresses, and the keys live in the
[settings file](/reference/configuration/#persisted-settings-json).

## Current stack

| Concern          | Current implementation                                                                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model inventory  | `LlmService.listLlmModels()` lists the provider's models, annotates which model keys have loaded instances, and the context length each is loaded with.  |
| Model health     | `LlmService.getLlmModelHealth()` checks one fresh loaded-inventory snapshot for the requested key without generating text.                               |
| Model loading    | `POST /api/v1/llm/load` uses the application service to load one model with the request's load settings and return its metadata.                         |
| Model unloading  | `PATCH /api/v1/llm/unload` stops every observed loaded instance matching one key, then reconciles the loaded-instance inventory.                         |
| Chat generation  | `ChatService.completeChatStream()` uses the `openai` SDK against the connected provider's OpenAI-compatible endpoint.                                    |
| Title generation | `ChatService.generateTitle()` calls the same endpoint with a separate prompt and a length-limited JSON-schema response format, then validates the reply. |

Loading and unloading apply to LM Studio only: its runtime alone implements
`LlmModelInstanceController`. Ollama and Groq decide which models are in
memory, so the model list reports `modelLoading: "provider"` for them, and
the load and unload routes refuse with `409` before any runtime call. A load
request may carry a `configuration`: context length, eval batch size,
flash attention, KV cache placement, and active experts. The service hands it to
the runtime adapter unchanged, and `LmStudioRuntime` gives the SDK's load call a
`config` that holds only the settings the request set, so LM Studio decides the
rest. One setting has a further effect: when the config sets a context length,
`@lmstudio/sdk` 2.0.0 also sends LM Studio's auto-fit as off, so LM Studio does
not choose the context length and the model placement automatically for that
load. This has not been checked against a running LM Studio. The backend keeps
no load settings; the desktop stores them and sends them with each load. See the [load request](/reference/api/#model-load-request)
for the fields.

Before each round of a reply, and for the composer's context meter, the
backend measures a context against the loaded model with
`LlmService.findLlmContextMeasurement()`, which runs through the same model
operation queue. `LmStudioRuntime` finds the instances `client.llm.listLoaded()`
reports for the model a chat request names, matching an instance identifier
or a model key, reports the smallest of their `getContextLength()` answers,
and counts each text with the first instance's `countTokens()`, one SDK
query per text, all at once. It never loads a model: when none is loaded
there is no measurement. The counts cover each
message's text and each tool's JSON; the backend adds a fixed allowance for
the chat template's markup instead of rendering the template. The model list
measures each loaded model key with no text in the same queued operation, one
key after another because the runtime refuses overlapping operations, to
report the context length as `loadedContextLength`. This has not been checked
against a running LM Studio.

Ollama and Groq offer no tokenizer, so their runtimes estimate each count
as the text's UTF-8 length divided by three, rounded up. Most English text
counts higher than a real tokenizer would, so a context that fits by the
estimate rarely overflows the window. The window is the context length a
local Ollama server reports for a running model, otherwise the model's own
window from Ollama's `/api/show`, or Groq's `context_window`. A local Ollama
server that has not loaded the model yet can load it with a smaller window.

Generation temperature and reply-ceiling edits are saved automatically and
applied to future chat requests. The [API reference](/reference/api/#chat-request-body)
defines how those controls reach chat completion; title generation uses its own
request.

## Request path

```text
Desktop chat store -> Fastify /api/v1/chat -> ChatService -> connected provider's OpenAI-compatible endpoint
Fastify /api/v1/llm/* -> LlmService -> LlmRuntimeService -> LlmRuntime -> LmStudioRuntime | OllamaRuntime | GroqRuntime
Agent (each round), Fastify /api/v1/chat/context -> LlmReplyContextMeter -> LlmService -> ... -> LlmRuntime
```

The desktop settings view supplies the shared context for its Runtime, Model,
and Generation panes; the Agents pane reads the agent store instead. Model controls call the inventory, health, load, and
unload routes through the application store only while the provider is
connected; the Runtime pane's provider card reads and refreshes the
connection. The model routes use the application-scoped `llmService` through
provider-neutral capabilities, and `LlmService` sends each operation through
the queue owned by `llmRuntimeService`.

Each connection attempt reads the saved provider from the settings file
again. `LlmRuntimeService` keeps a held runtime while the saved provider,
address, and key are unchanged; otherwise it releases it before acquiring a
runtime for the saved provider through `acquireLlmProviderRuntime()`. A
saved provider that needs a key without one, or a settings file that cannot
be read, fails the attempt, and the status becomes `unreachable`. The
service owns the runtime until it releases it, and consumes the full
`LlmRuntime`: the three engine queries, the availability probe, and
disposal, with the model-loading capability of a runtime whose models Lys
loads. Concrete runtime selection belongs in composition.

`ChatService` sends chat and title requests to the provider the runtime
service is connected to, keeping one `openai` client per endpoint, so chat
reaches the same provider as the model operations. While no provider is
connected, a chat request fails as runtime-unavailable.

`LmStudioRuntime` owns SDK calls, vendor-data validation, immutable runtime
snapshots, and client cleanup. `LlmService` owns canonical metadata lookup after
loading, loaded-state annotation and sorting, loaded-model health, and stop-by-key reconciliation.
Runtime snapshots contain no SDK handles or application `loaded` flag.

Every runtime allows one active call and rejects overlapping operational
calls before reaching the provider, through the shared
`LlmRuntimeAdmission`. It adds no waiting queue. Disposal closes runtime
admission, waits for its active call, and releases the SDK client once. Repeated
disposal observes the same outcome, including failure. Client cleanup neither
unloads every model nor terminates the external LM Studio engine.

## Ollama and Groq runtimes

`OllamaRuntime` uses Ollama's native API: `/api/tags` lists the models,
`/api/show` describes each, and `/api/ps` reports a local server's running
models. A model whose capabilities lack `completion`, such as an embedding
model, is left out of every listing and measurement; a model is kept when
Ollama reports no capabilities for it. `GroqRuntime` lists Groq's models
from `/openai/v1/models` and hides one Groq marks inactive. Both report every
listed model as one loaded instance whose identifier is its key, because the
provider loads a model when a request names it, and neither offers model
loading.
Neither caches an answer nor holds a connection, so disposal only closes
admission.

Their HTTP requests share `requestProviderJson()`: each has a 15-second
deadline and a 4 MiB limit on the answer, and a failure message names
neither the answer's body nor the key. Acquisition succeeds once the
provider lists its models, and the availability probe lists them again.
Groq reports no capabilities: every Groq model is treated as accepting
tools and not images. These runtimes have not been checked against a
running Ollama server, Ollama's cloud, or Groq.

## Runtime readiness and inspection

`LmStudioRuntime.create()` waits for a successful
`client.system.getLMStudioVersion()` response before returning. This opens a
real SDK connection and verifies a query response without loading a model.
Connection, authentication, and query errors reported by the SDK reject
acquisition with a retained diagnostic cause; acquired resources are released
before rejection. Empty downloaded and loaded inventories are valid. The
runtime service calls it for the startup attempt and for each refresh that needs
a new runtime, never before the backend listens.

The runtime keeps its admission and cleanup state (`ready`, `active`,
`closing`, or `closed`) private; callers observe it only through which
operations it admits. Admission alone does not establish current engine
availability.

`getRuntimeAvailability()` performs a fresh SDK query and returns `available` or
`unavailable`. It shares the runtime's single-operation guard: overlapping calls
reject as busy, and checks after disposal begins reject as closed. A failed
availability query releases admission so a later check can succeed. Its result
is an observation, not a guarantee that the next model operation will succeed.
The runtime service uses it to verify a held runtime on refresh and after a
failed runtime call. The resulting connection status, not the raw observation,
is exposed through `GET /api/v1/llm/runtime` and the desktop's provider card.

The model-specific `GET /api/v1/llm/:modelId/health` endpoint uses the existing
`listLoadedLlmModelInstances()` operation. A successful query establishes that
the engine answered, and a matching canonical key establishes observed loaded
presence. It needs no additional availability request or runtime capability.
`ready` does not verify generation or guarantee that the model remains loaded
after the snapshot. Responses are not cached. The
[API reference](/reference/api/#model-health-responses) defines the result and
latency fields.

Acquisition and accepted availability checks are owned until settlement. SDK
2.0.0 has no public RPC cancellation or forced client shutdown; its cleanup
waits for pending communication. These queries therefore have no completion
deadline, and a nonresponding engine can keep a connection attempt, a check, or
shutdown pending. The SDK also ignores invalid version payloads without settling
the request, so a malformed response can leave acquisition or a check pending
until a valid response or transport failure arrives. A timeout race would not
cancel the underlying SDK request. HTTP greeting checks do not establish SDK
WebSocket authentication and are not used as a substitute.

## Model operation queue

The `LlmRuntimeService` queue accepts one active operation and up to eight
waiting operations across inventory, health, loading, unloading, context
measurement, and connection attempts together. A reply round's measurement
therefore waits behind a load in progress. Accepted operations run in arrival
order. A full queue rejects a new request immediately with HTTP `503` and the
Problem Details type `urn:lys:problem:llm:service-busy`; rejected work never
reaches the runtime. Finishing an operation releases its capacity on either
success or failure.

The first accepted operation reserves the active position before execution starts,
so a burst arriving in the same event-loop turn cannot exceed nine accepted
operations. There is no second waiting queue behind this limit. Shutdown closes
admission and drains accepted work before releasing the runtime resources.

## Cancellation policy

Users cannot cancel model loading or unloading. Once the runtime queue accepts
either operation, it owns the work until success or failure, including any time
spent waiting in its queue. Closing the requesting client connection does not
cancel that accepted work. During shutdown, the runtime service stops accepting
new operations and waits for accepted work before releasing its runtime
resources.

Inventory queries and model health checks use the same service-owned completion policy. This is the
application-owned completion-only case defined by `IFACE-018` in
`docs/code_standards/INTERFACE.md`. The service enforces no completion deadline;
if a runtime operation never settles, shutdown also keeps waiting for it.

Inference has a separate cancellation lifetime. `ChatService` passes an abort
signal to the OpenAI SDK for chat and title generation. The reply-stop route
aborts the reply's signal; backend shutdown aborts both. Closing a chat SSE
connection aborts neither. Cancelling inference does not unload the model or
cancel an accepted model-management operation.

The LM Studio SDK supports cancellation of model loading, but Lys deliberately
does not expose it for that operation. Its current inventory and unload methods
do not expose per-call cancellation. These SDK details do not change the product
policy.

## What the backend assumes today

- The saved provider, when running, answers at its saved or default
  address; the backend starts without it.
- Chat requests can be satisfied by an OpenAI-compatible HTTP endpoint.
- Load and unload are available through the LM Studio SDK only.
- Ollama's cloud and Groq accept the saved key as a bearer token; no other
  credential exchange is required.

## Limitations

- There is no provider registry or adapter plugin system; the three
  providers are fixed.
- One provider answers at a time; switching reconnects the backend.
- There is no retry or request-time fallback after a provider and model are
  sampled for an admitted request.
- There is no request budgeting, quota tracking, or provider-specific telemetry.
- Default-model selection lasts for the current session and does not load weights.
  The [desktop model settings](/architecture/desktop/#model-settings) describe how
  the observed loaded model reaches chat requests.
- The backend does not report the settings a loaded model runs with. SDK
  2.0.0 exposes them through `LLMDynamicHandle.getLoadConfig()`, which Lys
  does not call yet ([#145](https://github.com/w3lt/lys/issues/145)). The
  desktop knows them only for loads it started in the current session.
