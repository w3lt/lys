## Summary

Define exactly which fields are stripped before a bundle can leave a machine.

## Motivation

A diagnostics bundle is the one artifact a user is routinely asked to send
elsewhere. Before this proposal its contents were decided field by field as the
bundle writer grew, and a bundle was found to carry provider account
identifiers that nobody had intended to include.

## Proposed design

Bundle contents are an allowlist. A field reaches a bundle only when it has
been explicitly classified as safe to disclose; anything unclassified is
omitted and the omission is recorded in the bundle's manifest.

- Message content is never included.
- Provider identifiers, account metadata, and credential handles are never
  included.
- Store paths are reduced to a placeholder root.

## Alternatives

A denylist was rejected: it is safe only while it is exhaustive, and it stops
being exhaustive the moment a new field is added anywhere upstream.

## Risks and trade-offs

An allowlist omits genuinely useful fields until someone classifies them, which
makes some first-report bundles thinner than a maintainer would like.
