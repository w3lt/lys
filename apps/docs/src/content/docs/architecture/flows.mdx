This page documents only the flows implemented in the current codebase.

## Start the backend

1. The React app calls `initialize`.
2. The desktop loads host-managed settings through `load_settings` and shows
   the shell.
3. If `autoStartBackend` is enabled, or a backend process already runs, the
   store starts or checks the backend in the background. vmo starts at the
   same time; see [Start vmo](#start-vmo).
4. For a stopped backend, the store sets `starting` and calls `start_backend`.
   The Tauri host starts the backend with `LYS_HOME` set to the Lys home it
   resolved at startup: `pnpm run dev` in `apps/backend` for development builds,
   or the installed runtime under `$LYS_HOME/runtime` for release builds.
5. The backend opens its HTTP listener without contacting LM Studio, then makes
   one LM Studio connection attempt.
6. The store checks `GET /api/v1/heath` until it answers (`running`), the
   process exits (`stopped`), or 30 seconds pass (`unresponsive`).
7. Once running, the store reads the LM Studio status, joining the startup
   attempt if it is still `connecting`.
8. If LM Studio is connected, the store requests model inventory; otherwise
   the model list stays empty.

A manual Start follows steps 4–8.

## Start vmo

1. During `initialize`, if `autoStartVmo` is enabled, or the host already owns
   a vmo, the store starts or checks vmo in the background, without waiting
   for the backend. When the host is still stopping vmo, as after a window
   reload during Stop, the store joins that stop instead, and vmo stays
   stopped.
2. The store sets `starting` and reads `get_vmo_status`. For a stopped vmo it
   calls `start_vmo`, and the Tauri host runs `bash run.sh` in `apps/vmo` for
   development builds, or `$LYS_HOME/runtime/vmo/vmo` for release builds.
3. vmo pulls `vminit` when it does not have it yet and unpacks it unless its
   image store holds it unpacked from that `vminit` already. It fetches the
   reader image's `latest` tag, pulls the reader image when it does not have
   it yet, and deletes every other image in
   [its image store](/operate/data/#vmos-image-store). On a first start, this
   can take minutes. vmo then listens at `127.0.0.1:8080`. It exits instead
   when a pull fails; when it cannot read which `vminit` the store holds
   unpacked, delete that unpack, or unpack and save the new one; or when it
   cannot delete the other images.
4. Every second, for up to ten minutes, the store reads `get_vmo_status` and,
   while vmo runs, `get_vmo_health`. vmo becomes `running` once it answers,
   `stopped` when its process exits first, and `unresponsive` after ten
   minutes.
5. When vmo becomes `running`, `stopped`, or `unresponsive` while the backend
   runs, or the backend starts running, a tool list already read is read
   again from `GET /api/v1/tools`. The backend asks
   vmo's `GET /health` on that lookup and lists `read_page` as unavailable
   with `page-reader-not-ready` unless vmo answered.

A manual Start follows steps 2–5. A stop sends vmo `SIGTERM` through
`stop_vmo`, shows `stopping` while vmo deletes its VMs, and kills it after 60
seconds. Quitting Lys stops vmo and the backend together.

## Reconnect to LM Studio

1. The user starts LM Studio and presses **Refresh** on the Runtime pane's LM
   Studio card.
2. The store shows `connecting` and sends `POST /api/v1/llm/runtime/connect`.
3. The backend queues one attempt behind accepted model work. It keeps a held
   runtime that still answers and otherwise acquires a new one. Concurrent
   requests share the attempt.
4. The response carries `connected` or `unreachable`, and the store publishes
   it.
5. On `connected`, the store requests model inventory.

## Send one chat message

1. The composer asks the chat store to `sendMessage`.
2. The desktop creates a request token and an `AbortController` that ends
   only its own observation of the stream.
3. The desktop sends `POST /api/v1/chat` with `conversation`, `message`,
   `model`, required `generationOptions`, and `attachments` when the tray
   holds files, each with its name and base64 content. `conversation` is
   `{ kind: "new", agentCode }` for a new conversation, naming the agent
   selected in the composer (`caliginia` until another is selected), and
   `{ kind: "existing", id }` to continue one, which keeps its agent. Generation options contain
   the current temperature and an optional reply ceiling; a local zero ceiling
   is omitted from the request.
4. The backend reads what each attachment is from its bytes and finds the
   agent that answers. When the request or the conversation holds an
   attachment, it reads from LM Studio whether the model sees images and is
   trained for tool use. It then writes the attachment files under
   `$LYS_HOME/attachments/<conversation id>/<message id>/`, creates or reuses
   the conversation, inserts the user message with its numbered attachments,
   and inserts an empty streaming assistant message. When an attachment is
   neither text nor an image Lys sends, no agent has the requested code, the
   conversation is not stored, its agent was deleted, an image is attached
   for a model without vision, or LM Studio cannot answer about the model, the
   backend answers with a problem instead and stores nothing.
5. The backend emits a `start-new-conversation-turn` or
   `start-existing-conversation-turn` event.
6. Before each round of the reply, the backend builds the round's context,
   in which each user message carries its text, the list of its attachments,
   and the images a model with vision sees, and measures it with the loaded
   model's tokenizer, counting each image as its estimate. A round that does not fit the context
   length the model is loaded with, together with the reply ceiling, or whose
   model is not loaded, is not sent: the reply is stored failed and the
   backend emits `error` with the reason. Otherwise the backend stores each
   reasoning or text part of the reply, and each fragment that extends one,
   then streams it as a `reply-part` or `reply-part-delta` event, and ends
   with a `done` event when the model finishes successfully.
7. For an existing conversation with a stored title, the backend emits that
   title immediately after the turn-start event to reconcile desktop metadata.
   When the conversation has no stored title, a parallel title task requests a
   title after the turn-start event. The first usable title assigned is emitted
   before, during, or after the reply's parts and completion. An untitled
   turn whose title task neither generates nor assigns a title sends no title
   event; a turn started after that task ended requests a title again while
   the conversation remains untitled. A turn sent while an earlier turn's title
   task is still running requests no title, so its stream ends with its reply.
8. The desktop applies each event to immutable local conversation state.
9. Once the reply is final, the composer shows Send again, even while the
   stream stays open for a title. Sending the next message then stops following
   that stream; the backend still saves the title, and the desktop receives it
   with the next turn or when it reads the conversation again
   ([issue #96](https://github.com/w3lt/lys/issues/96)).

## Measure the next message

1. While the composer could send, it builds the measurement request that
   sending would make: `conversation` (`{ kind: "existing", id }` for the
   shown conversation, `{ kind: "new", agentCode }` otherwise), the loaded
   `model`, and the `tools` the Tools pane would offer.
2. The desktop sends `POST /api/v1/chat/context`. A newer request abandons an
   older one.
3. The backend finds the agent and the conversation as the chat route does,
   builds the system prompt, offered tools, and stored messages a turn's first
   round would send, their attachment lists and, for a model with vision,
   their images included, and `read_attachment` among the tools when the
   conversation holds a text file and the model is trained for tool use, with
   an empty new message for the markup around the text, and measures them
   with the loaded model's tokenizer through the model operation queue.
4. The backend answers with the context length and the tokens of each part,
   or with a `503` problem when the model is not loaded, LM Studio is not
   connected, or the queue is full.
5. The composer adds an estimate of the draft's text, the staged images'
   estimates, and the reply ceiling,
   shows the result in its context meter, and disables Send while the request
   would not fit.

## Stop an in-flight reply

1. The user presses Stop in the composer.
2. The desktop sends
   `POST /api/v1/chat/:conversationId/replies/:assistantMessageId/stop`. A
   Stop pressed before the turn-start event is sent as soon as that event
   names the reply, unless the user opens another conversation or starts a new
   one first; the reply then generates to its end.
3. The backend aborts the reply's upstream LM Studio request. Title generation
   continues.
4. The reply task stores the reply as `interrupted` and sends `interrupted` to
   every stream following it; the stop request then answers `204`.
5. The desktop marks the assistant message `interrupted` when that event
   arrives and shows Send again. A title may still arrive before the stream
   closes.

Switching to another conversation or starting a new one only stops the
desktop from following the stream; the backend keeps generating and storing
the reply and its title.

If the next message reaches the backend before the stopped reply is finalized,
creating the new turn interrupts that reply first, so the text and answered
calls it stored are part of the new turn's context.

## Answer a tool call

1. The desktop sends `POST /api/v1/chat` with `tools`: the definitions of the
   switched-on client tools and the names of the switched-on backend tools
   that can run now, offered only to a model trained for tool use. It names
   the tools that are switched off in `switchedOffToolNames`, which the
   backend notes after the system prompt.
2. Before it stores the turn, the backend looks up every offered backend tool;
   `web_search` reads the Tavily API key from the settings file and keeps it
   for the turn. When an offered tool cannot run, the backend answers `409`
   with the `backend-tool-unavailable` problem and stores nothing; the desktop
   shows the error and reads the tool list again.
3. The backend offers the tools to the model in every round. Each round's
   reasoning and text are stored as parts of that round and streamed. When a
   round ends with tool calls,
   the backend checks each call's arguments against its definition, and a
   backend tool also checks them by its own rules, such as `read_page`'s URL
   rules. A call to an unknown tool, such as one the request names as
   switched off, or with invalid arguments is answered by the backend itself
   and stored as a `failed` call. Every other call is
   stored as a part too, `running` or `awaiting-approval`, and each later
   change of it is stored and sent as a `reply-part` event.
4. The backend's tool approval service reads the Just run choices from the
   settings file once for the round. For each valid call, in the model's order:
   a tool saved as Just run goes on at once; any other tool's call is stored
   as `awaiting-approval` and then shown to the person with a `tool-approval`
   event, in the same step. A call the store refuses, because the reply has
   ended, is never shown. If the settings file cannot be read, every call is
   shown and the backend logs a warning.
5. The desktop's tool-call store, which follows the reply on its own
   connection, shows each prompt above the composer, or answers it
   `showFailed` at once when it cannot describe the call. Allow once and
   Reject send the answer to
   `POST /api/v1/chat/:conversationId/replies/:assistantMessageId/tool-approvals/:callId`.
6. An allowed client tool's call goes to the desktop as a `tool-call` event
   under the same `id`; the store runs the Tauri command at once and sends
   its result to
   `POST /api/v1/chat/:conversationId/replies/:assistantMessageId/tool-results/:callId`.
   Both routes answer `204`, or `409` when the call no longer waits for that
   answer.
7. An allowed backend tool runs in the backend under the reply's
   cancellation, whether or not a desktop follows the reply, and its result
   goes to the model and is stored with the call, cleaned of invisible
   characters when the tool reaches the network, as every network tool's
   result is. A web tool numbers each source it shows after the
   conversation's earlier sources, keeping a URL's number; the sources are
   stored and sent as a `sources` event before the call's `reply-part`. An allowed
   `read_page` call asks vmo to read the page in headless Chromium in a fresh
   micro VM, which follows its redirects. An allowed `web_search` call sends one query to
   `https://api.tavily.com` and gives the model the results framed as
   untrusted text; the model may then call `read_page` for a result's URL,
   which is shown again on Ask me. A rejected call runs nothing; the model
   reads the rejection, which is stored as the call's result. Once every call of the round has an answer, the
   backend asks the model again with the results. The loop ends with the
   first round that makes no tool calls, even one that writes no text, then
   `done`. The desktop shows the rounds that called tools as the reply's
   steps, the last round's text as the answer with its `[n]` citations
   linked, and the sources the answer cites under it.

The backend sets no time limit on a prompt or a pending call. It waits until
the call is answered, the reply is stopped, or the backend shuts down; a newer
turn or a deletion does not end it yet
([#137](https://github.com/w3lt/lys/issues/137)). A client that was not
following when a prompt or call was sent finds it in the next
`reply-snapshot`'s `pendingToolApprovals` or `pendingToolCalls`.

## Open a past conversation

1. The user opens history from the composer or with Command+K or Control+K.
2. The history store reads `GET /api/v1/conversations` for the current search
   query.
3. Choosing a row closes history and asks the chat store to `openConversation`.
4. The chat store stops following any active reply (the backend keeps
   generating it), then reads `GET /api/v1/conversations/:conversationId`.
5. When the read succeeds, the stored transcript replaces the shown
   conversation. A missing conversation or failed read keeps the previous
   conversation and records an inline error.
6. When the conversation then shown, opened or kept, ends with a reply that is
   still `streaming`, the chat store follows it with
   `GET /api/v1/chat/:conversationId/replies/:assistantMessageId/events`: the
   `reply-snapshot` replaces the stored content, then live events apply as for
   a new message.
7. The next message sends that conversation as `{ kind: "existing", id }`, so
   the backend continues it.

## Error path

If opening the stream, reading SSE frames, validating payloads, or finishing the
model response fails, the desktop records a chat lifecycle error and may mark
the assistant message as `failed`.
