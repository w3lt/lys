Paths on this page use `$LYS_HOME` for the
[Lys home directory](/reference/configuration/#lys-home-directory): `~/.lys`
unless the `LYS_HOME` environment variable selects another directory.

## `$LYS_HOME/settings.json`

The desktop host owns a JSON settings file at `$LYS_HOME/settings.json`.

- created automatically when the file is missing
- stores the `runtime`, `model`, `generation`, `loadConfiguration`,
  `secrets`, and `tools` groups described in
  [Configuration](/operate/configuration/)
- parsed as JSON on load and rewritten as pretty-printed JSON when the Tauri
  `save_settings` command is called
- read, never written, by the backend for the Tavily API key and the Just run
  list

The desktop loads this file at initialization and autosaves generation, load
configuration, tool approval, and runtime startup switch edits. Each save
replaces only its own part and preserves the rest already on disk, including a
`loadConfiguration.default` written by hand; the other runtime edits and
`model.contextSize` edits in the UI remain session-only.

## `$LYS_HOME/lys_db.sqlite`

The backend stores conversations and agent definitions in a SQLite database at
`$LYS_HOME/lys_db.sqlite`. A conversation holds its messages, the record of
each file sent with a message (the file itself is under `attachments/`,
below), each reply's reasoning, text, and tool calls, and every web source a succeeded
`web_search` or `read_page` call showed, whether a reply cites it or not.
Each tool call is stored with its arguments and its full result, such as the
text of a file `read_text_file` read. All of it is kept until the
conversation is deleted.

The database runs in write-ahead-log mode, so `lys_db.sqlite-wal` and
`lys_db.sqlite-shm` sit beside it. They usually remain after the app quits,
because the desktop stops the backend without a clean close, and
`lys_db.sqlite-wal` can then hold recent changes that are not yet in
`lys_db.sqlite`. They are part of the database: copy, move, or delete all three
together, and only while the backend is stopped. A power loss or operating-system crash can lose the
last few writes; an application crash cannot.

The checked-in schema currently creates:

- `conversations`
- `conversation_messages`, which also holds each reply's parts
- `conversation_sources`
- `conversation_attachments`
- `agents`
- one index on `(conversation_id, created_at, id)`, and one unique index on
  each reply's part positions
- triggers that keep `conversations.updated_at` in sync

SQLite `PRAGMA user_version` tracks the applied migration level. On startup the
backend applies any missing forward migrations and refuses to open a database
whose version is newer than the binary understands.

## `$LYS_HOME/attachments/`

The backend keeps every file sent with a message under
`$LYS_HOME/attachments/<conversation id>/<message id>/<file name>`, with the
name the person gave it. It creates the directory and the folders under it on
the first attachment it stores, so a Lys that never received one has no
`attachments/` directory. A message's folder is written before the message is
stored and never written again, and the database row of each file records its
number, name, kind, and size, so opening a conversation reads nothing from the
directory.

- Deleting a conversation deletes its rows first, then its folder; a folder
  that cannot be removed is logged and left, and the delete still succeeds.
- A turn whose files were written but whose database transaction failed
  deletes its folder again. A folder left by a crash between the two, or
  whose deletion failed, belongs to a message the database does not hold;
  nothing reads it, and you can delete it by hand.
- A file removed by hand after its row was written is not noticed until the
  model needs it: an image becomes a placeholder sentence in its message, and
  a read of a text file fails with a message the model reads. A file changed
  by hand is sent or read as it now is; its stored size and sides are not
  checked against it.
- The directory belongs with the database: copy, move, or delete the two
  together, while the backend is stopped.

## vmo's image store

vmo, the page reader `read_page` uses, keeps its images and the files of its
VMs in `~/Library/Application Support/com.w3lt.lys-vmo`, outside the Lys home,
because vmo does not read `LYS_HOME`. Containerization creates and lays out
the directory at vmo's first start, and only vmo writes it.

- it holds the `vminit` image; `initfs.ext4`, the filesystem vmo's VMs boot
  from, unpacked from that `vminit`; `initfs.ext4.vminit-digest`, which names
  the `vminit` that `initfs.ext4` was unpacked from; the reader image that
  `ghcr.io/w3lt/lys-readpage:latest` named at vmo's last start; and, while a
  read runs, that read's VM under `containers/`
- at each start, vmo reuses `initfs.ext4` only when
  `initfs.ext4.vminit-digest` names the `vminit` it pins. Otherwise it deletes
  both files and unpacks `vminit` again: after an update that pins another
  `vminit`, when a vmo from before
  [#218](https://github.com/w3lt/lys/issues/218) left `initfs.ext4` without
  it, or when an unpack did not finish, even because of a power loss. vmo
  writes `initfs.ext4.vminit-digest` only once `initfs.ext4` is on disk.
  When vmo cannot check `initfs.ext4`, or `initfs.ext4.vminit-digest` exists
  but cannot be read, the start stops without deleting either. When it cannot
  delete them, the start stops too
- at each start, after it fetches `latest`, vmo deletes every other image in
  the store and the files that only those images used, so a reader image that
  `latest` no longer names does not stay
- deleting the directory while vmo is stopped loses nothing else; the next
  start downloads both images again

Before [#213](https://github.com/w3lt/lys/issues/213), vmo kept its images in
Containerization's default image store,
`~/Library/Application Support/com.apple.containerization`, which other tools
built on Containerization can share. vmo no longer uses that directory and
does not delete what it left there. If no other tool uses it, deleting it frees
that space.

## Lifecycle notes

- The settings file is created by the Tauri host on first settings load.
- The SQLite file is opened once by the backend's database owner when the
  backend's services start, before the conversation services and the agent
  service are created.
- The backend does not create the Lys home directory. A standalone backend
  started with `pnpm backend:dev` uses `~/.lys`, which must already exist; the
  desktop creates the Lys home when initializing a missing settings file. See
  [Running Lys locally](/develop/running/).
- The settings file, the database, and the attachments directory live in the
  same Lys home directory, so user data and app settings currently share one
  root. Release builds also start their backend and vmo
  from the `runtime/` directory there.

## WebView theme storage

The desktop theme is stored separately from the Lys home directory under the
`lys.theme` WebView `localStorage` key. Its valid values are `dark` and `light`.

## What is not documented yet

The repository does not currently provide an evidenced contract for:

- exporting conversations to another format
- pruning or rotating stored conversation data
- relocating either file on its own; `LYS_HOME` moves both together
- moving existing files when `LYS_HOME` changes; Lys does not copy them, so an
  empty new directory starts with default settings and an empty database
- diagnostics bundles that package these files or projections of them

Retention, cleanup, and export procedures should be documented here once the
repository ships them as supported behavior.
:::
