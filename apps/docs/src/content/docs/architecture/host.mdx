The Tauri layer is a small native host. It does not implement the backend API
itself; it starts the backend and vmo, the page reader `read_page` uses, and
exposes a few native commands to the React UI.

## Registered commands

| Command              | Purpose                                                                                                                                                         |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `start_backend`      | Starts the backend for the current build mode with the Lys home and stores the child handle.                                                                    |
| `stop_backend`       | Sends the backend process group `SIGTERM`, then `SIGKILL` after at most 2 seconds, waits for shutdown, and ends the MCP server groups the backend still listed. |
| `get_backend_status` | Reports whether the stored child process is still running.                                                                                                      |
| `start_vmo`          | Starts vmo for the current build mode unless the owned vmo runs, and reports its status.                                                                        |
| `stop_vmo`           | Sends vmo `SIGTERM`, waits up to 60 seconds for it to exit, then kills it, and reports which.                                                                   |
| `get_vmo_status`     | Reports whether the owned vmo is stopped, running, or stopping.                                                                                                 |
| `get_vmo_health`     | Asks vmo's `GET /health` at `127.0.0.1:8080` whether it can read pages, within one second.                                                                      |
| `load_settings`      | Reads `$LYS_HOME/settings.json`, creating a default file if needed.                                                                                             |
| `save_settings`      | Replaces `$LYS_HOME/settings.json` atomically, owner-only, with a new settings JSON document.                                                                   |
| `read_text_file`     | Returns the complete text of one UTF-8 file of at most 1 MiB, unless it is a credential file or the settings file.                                              |
| `find_files`         | Searches a directory tree for regular files by name or by text content, leaving credential files and the settings file out.                                     |
| `get_current_time`   | Returns the machine's local date and time, UTC offset, weekday, and time zone.                                                                                  |
| `get_location`       | Returns the location the person saved in Settings → Tools, read from the settings file.                                                                         |
| `list_tools`         | Returns the definition of every client tool, for the Tools settings pane.                                                                                       |

## File tools

`read_text_file` and `find_files` are the desktop side of the client tools that
let Lys work with files on the user's machine. The desktop's tool-call store
runs them for the calls the backend sends to run: calls the person allowed, or
calls of a tool set to Just run in the Tools pane. The backend's tool call
policy and tool approval service decide which; see [Desktop](/architecture/desktop/#tool-calls). The renderer reaches them through `readTextFile` and `findFiles` in
`apps/desktop/src/lib/apis/tauri/tools.ts`, which validate arguments, results,
and declared failures with the schemas exported by `@lys/protocol`.

Both commands accept any absolute path that the desktop process can read,
except a private key or credential file and Lys's settings file. They are
tools, not a permission gateway: whether Lys may use a tool or any other path
is decided by the caller that runs tool requests. Relative paths are rejected
rather than resolved against the process's working directory. Each call runs on
Tauri's blocking-task pool, so the window stays responsive, and cannot be
cancelled.

- `read_text_file` follows symbolic links and returns the whole file. It
  rejects directories, FIFOs, sockets, and devices without blocking on them,
  credential files, files over 1 MiB, and content that is not UTF-8. It never
  truncates.
- `find_files` walks the tree breadth-first, lists each directory in byte order
  of entry names, and never follows symbolic links below the root. It compares
  file names, lines of UTF-8 files up to 1 MiB, or both, case-insensitively
  after Unicode lowercasing. A search stops after the requested number of
  matches (50 by default, at most 200), 20,000 examined entries, or 64 MiB of
  read content, and its report says whether the result limit or a scan budget
  ended it.

The credential names are those the backend's
[tool call policy](/architecture/backend/#tool-call-policy) denies:
`packages/protocol/src/tools/credentialFiles.json` lists the folders, file
names, starts, and ends, the backend imports it as `CREDENTIAL_FILE_LIST`, and
`src-tauri/src/tools/credential_files.rs` embeds it when the host is built.
The host parses it once at startup and does not start if it cannot. Both
commands decide by a file's real path, with every symbolic link resolved, and
compare each of its parts in lowercase with the list. Lys's settings file,
`settings.json` in the Lys home, holds the API keys and the email password; it
is recognized by its device and inode numbers, so a link or a hard link to it
is refused too.

- `read_text_file` opens the file, resolves its real path, and checks that the
  path still names the opened file before it reads a byte. A credential file
  fails with `{ "code": "credentialFile" }`, also when it is over 1 MiB.
- `find_files` fails with `{ "code": "rootInCredentialFolder" }` when the
  root's real path is inside a credential folder. Its walk never enters a
  credential folder and leaves credential files and the settings file out, as
  it leaves links out, so a search lists none of them and returns no line of
  one, whatever folder it starts in. Reported paths keep the root as it was
  given.

A hard link to a key under another name, in a folder with another name, is not
recognized: only the settings file is compared by identity. A temporary copy
that a stopped save left beside `settings.json` is not recognized either
([#345](https://github.com/w3lt/lys/issues/345)).

Expected failures reject with a JSON object whose `code` names the failure,
such as `{ "code": "fileNotFound" }`. Any other rejection, such as an
unregistered command, is thrown by the TypeScript wrappers as an error.

## Time and location tools

`get_current_time` and `get_location` take no arguments and run synchronously
on Tauri's main thread, like `load_settings`, since each reads a few bytes. The renderer reaches them
through `getCurrentTime` and `getLocation` in
`apps/desktop/src/lib/apis/tauri/tools.ts`, which validate results and
declared failures with the schemas exported by `@lys/protocol`. Neither
command reaches the network.

- `get_current_time` reads the system clock and the machine's time zone at
  each call, so a change of zone applies to the next call. The zone is the
  one `TZ` sets when it is set, read through the `jiff` crate, which keeps it
  for up to 5 minutes; that matters only when `TZ` names a file whose zone
  changes. Otherwise it is the zone `/etc/localtime` sets, read without a
  cache: a link into a `zoneinfo` directory names its zone, and any other file
  is read as TZif data. It returns `dateTime` (local time to the second with
  its offset, such as `2026-10-22T21:30:05+02:00`; fractions of a second are
  dropped), `weekday` (English name), `utcOffset` (`+HH:MM`, or `+HH:MM:SS`
  for a historical offset with seconds), and `timeZone`, the IANA name, or
  `null` for a zone without one, such as one a POSIX `TZ` rule or a TZif file
  that is not a `zoneinfo` link sets. When the time zone cannot be determined
  it rejects with `{ "code": "timeZoneUnknown" }` rather than assume UTC.
- `get_location` reads the `location` group of the settings file, without
  creating the file when it is missing, so a saved change applies to the next
  call. It returns `city`, `region`, and `country`, each a string or `null`,
  at least one a string. It rejects with `{ "code": "locationNotSet" }` when
  there is no file or no part is saved, and with
  `{ "code": "settingsUnreadable" }` when the file cannot be read or parsed;
  neither failure carries the path or the operating system's message. Lys
  never detects the location: no Location Services, no network lookup, no
  guess from the time zone.

## Client tool list

`list_tools` returns `CLIENT_TOOLS` from `src-tauri/src/tools/client_tools.rs`:
the definition of every client tool, in the order Settings lists them. A
definition holds what a model is offered for the tool, its name, description,
and arguments, plus the `group` and `access` that Settings shows and the
`runner`, which is `client` for every tool here. It mirrors
`toolDefinitionSchema` in `@lys/share`, which the backend's `AgentTool` also
uses, and the renderer's `listTools` validates the list with
`listToolsResultSchema` from `@lys/protocol`, which also requires every
`runner` to be `client`. A list that does not match is rejected with the
caller-safe message "The app returned an invalid tool list.", and the
decoding failure is kept as its cause.

Each tool builds its own definition next to the limits it enforces, so a
description states the current limits. The tools are named `read_text_file`,
`search_files`, `get_current_time`, and `get_location`; the search-files tool
keeps its name although its command is `find_files`, and the last two, in
the `timeAndPlace` group, take no arguments. The search-files tool's
arguments are the exact keys of the `find_files` filter, and `target` is an
enum of `name`, `content`, and `nameAndContent`. The command reads nothing and
never fails.

## Lys home

Before building the application, the host resolves the
[Lys home directory](/reference/configuration/#lys-home-directory) once from the
`LYS_HOME` environment variable and manages it as application state. The
settings, backend, and vmo commands receive that value instead of reading the
environment again. An invalid `LYS_HOME` stops the app before any window opens.

## Backend process ownership

The host owns a `Backend` state object containing `Mutex<Option<Child>>`. The
child process is started only when the UI asks for it or when auto-start logic
requests it during desktop initialization.

The child depends on the build mode:

- Development builds run `pnpm run dev` from `apps/backend` in the checkout
  recorded at compile time.
- Release builds run `$LYS_HOME/runtime/node/bin/node` with
  `$LYS_HOME/runtime/backend/backend.mjs`.

```rust
Command::new("pnpm")
    .args(["run", "dev"])
    .current_dir(backend_dir)
    .env("LYS_HOME", lys_home.as_path())
    .process_group(0)
    .spawn()
```

Both children run in their own process group, with `LYS_HOME` set to the Lys
home the host resolved, so the backend uses the same directory as the host.
Both also receive `LYS_EMAIL_SERVER_PATH`, the email MCP server the backend
starts once the person switches it on and runs for each account check: the
workspace build `mcps/email/target/debug/email` in the checkout recorded at
compile time for a development build, and `$LYS_HOME/runtime/email/email`
for a release build. The host never starts that server itself and does not
check that the file exists; the backend reports a missing server when it
needs it.

The host does not redirect either child's output: a development child writes
to the terminal that runs the app, and a release child's standard output and
standard error are the app's own. The backend keeps its own log files under
`$LYS_HOME/logs/`; see
[the backend log files](/operate/logging/#the-backend-log-files).

When the direct child is still running, stopping the backend sends `SIGTERM`
to its whole process group and waits up to 2 seconds until no process of that
group is left, the child's own exit not counting: in development the child is
the `pnpm` script, which can exit before the backend it runs. On `SIGTERM`, the
backend ends the process groups of its stdio MCP servers, which its own group
does not hold, and exits; see
[the MCP server lifecycle](/architecture/backend/#mcp-servers). The host then
sends `SIGKILL` to the group in every case, because a process that ignores
`SIGTERM` can still be in it, and waits for the child. `SIGKILL` follows the
check that saw the group end without a pause. A group that is already gone, or
whose processes all exited but were not yet reaped, which macOS reports as
`EPERM`, counts as ended and as signalled.

The backend lists the process groups of its stdio MCP servers in
`$LYS_HOME/mcp-process-groups`, one decimal identifier per line, and replaces
the file whole each time a group starts or ends. Once the backend's group
received `SIGKILL` and the child was waited on, so the backend can no longer
change the list, the stop sends `SIGKILL` to every group the list still names
and deletes it. This ends the servers of a backend that hung or was killed
before it could end them itself. A line that is not a decimal identifier
greater than 1, or that names the host's own group, is skipped and reported,
so a damaged list can never signal the host or every process it may signal. A
start deletes a list an earlier backend left before it spawns the child, under
the same lock, so a stop never reads it; when that deletion fails, the start
fails and starts nothing.

If the direct child has already exited when the stop starts, the host clears
its handle without killing any surviving descendants and without reading the
list. `stop_backend` runs off the main thread, as `stop_vmo` does, so a stop
that waits for the backend never blocks the window. On app exit, the host
stops the backend while it stops vmo; see
[vmo process ownership](#vmo-process-ownership).

The checked-in process supervisor currently uses Unix process-group APIs and
the `nix` crate. The repository does not yet demonstrate equivalent lifecycle
behavior on Windows.

## vmo process ownership

The host owns one `Vmo` state object (`src/vmo.rs`). vmo starts when the
desktop's initialization or the Runtime pane asks for it, never on its own.
The child depends on the build mode:

- Development builds run `bash run.sh` in `apps/vmo` of the checkout recorded
  at compile time. `run.sh` builds vmo, signs it, and replaces itself with it
  through `exec`, so the child the host owns is vmo itself.
- Release builds run `$LYS_HOME/runtime/vmo/vmo`, which `build.sh` installs.

vmo runs in a process group of its own. The host does not set `LYS_HOME`
for vmo, which does not read it.
`start_vmo` checks and spawns under one lock, so two starts never spawn two
children; it leaves a running vmo alone and refuses while a stop still waits
for the previous one, which holds vmo's port. A spawn failure names the
program it tried to run.

vmo deletes its VMs when it receives `SIGTERM`, and a second `SIGTERM` would
end it before it finishes. A stop therefore sends `SIGTERM` to vmo's process
group once and checks every 100 ms whether vmo has exited. A stop that arrives
meanwhile joins it and gets the same result, without another signal. When vmo
still runs after 60 seconds, the stop sends `SIGKILL` and reports `killed`:
vmo may then have left VMs running. When `SIGTERM` or a check fails, the stop
sends `SIGKILL` at once and reports the failure. It sends `SIGKILL` at most
once and does not repeat a failed one, because by then the group's identifier
may name another group. `stop_vmo` and `get_vmo_health` run off the main
thread, so a stop never blocks the window.

`get_vmo_health` sends `GET /health` over a plain TCP connection to
`127.0.0.1:8080` and answers `ready` only for a `HTTP/1.1 200` status line
within one second. It runs in the host because vmo sends no CORS headers. It
asks whatever listens on vmo's port, so the renderer reads `get_vmo_status`
first, which keeps a vmo that has exited from counting as ready.

On app exit, the host stops vmo and the backend together and waits for both,
so quitting can take up to 60 seconds while vmo deletes its VMs. A failure or
a killed vmo is written to standard error and does not stop the exit. When the
app dies without running its exit handler, after a crash, Force Quit, or
`kill -9`, vmo and the backend keep running
([#202](https://github.com/w3lt/lys/issues/202)); see
[troubleshooting](/operate/troubleshooting/#a-vmo-or-backend-keeps-running-after-lys-died).

## Settings file

The host creates the following defaults when the settings file is missing:

```json
{
  "runtime": {
    "autoStartBackend": true,
    "autoStartVmo": true,
    "defaultModel": null,
    "backendAddress": "http://127.0.0.1:12345"
  },
  "generation": {
    "temperature": 0.7,
    "replyCeiling": 2048
  },
  "loadConfiguration": {
    "default": {},
    "models": {}
  },
  "secrets": {
    "tavilyApiKey": null,
    "ollamaApiKey": null,
    "groqApiKey": null,
    "emailPassword": null
  },
  "providers": {
    "active": "lmStudio",
    "lmStudio": { "address": null },
    "ollama": { "address": null }
  },
  "tools": {
    "justRun": [],
    "switches": {}
  },
  "location": {
    "city": null,
    "region": null,
    "country": null
  },
  "mcp": {
    "servers": [],
    "builtIn": {
      "email": { "enabled": false }
    }
  },
  "email": {
    "account": null
  }
}
```

Only the Rust host writes this file. The React UI reaches it through Tauri
`invoke` calls, and the backend reads it for the Tavily API key of
`web_search`, the tools on Just run, the MCP servers with their switches, and
the email account with its password. Every write, including the defaults of a missing file, goes to a
new temporary file beside it, created with mode `0600` on Unix and flushed to
disk, which is then renamed over the file. The temporary file's name holds the
process id and a per-process number, so no two saves share one, and creating
it never opens, truncates, or follows anything already at that name. A reader
therefore sees the previous document or a complete new one, also while the
installed app and a development build save at the same moment (the one
renamed last is kept), and other OS users cannot read the key. A failed save
removes its temporary file; a host that stops in the middle of a save leaves
it, owner-only. The rename itself is not synced to the directory, so it is not
promised to survive a power loss. When `settings.json` is a symbolic link, the rename replaces the
link with a regular file, and the file it pointed to stops receiving saves.

The document, each of its groups, and each object inside a group, such as a
provider's server or a model's load settings, are read from a JSON object
only (`src/settings/json.rs`): an array in their place makes loading fail, as
it does in the `@lys/share` schemas the backend reads the file with, so both
sides judge a file the same way. The objects are read as the JSON reader
reads them, so a load error still names the line and column where reading
stopped. A missing group takes its defaults.

The `secrets` group holds the Tavily, Ollama, and Groq API keys as plain
text, validated on load (1 to 256 visible ASCII characters), and
`emailPassword`, the password of the saved email account, 1 to 1,024
characters without a control character, spaces kept; an invalid key or
password makes loading fail. Its `Debug` output never shows a key or the
password.

The `location` group holds the location the person typed, validated on load:
each part is `null` or 1 to 100 characters with no control character and no
white space at either end. An invalid part, an unknown field, or a `null`
group makes loading fail, and the error never quotes the value. Its `Debug`
output never shows the location.

The `mcp` group holds the MCP servers the person saved in the MCP pane
(`src/settings/mcp.rs`), validated on load with the rules of
`mcpSettingsSchema` in `@lys/share`, which the renderer and the backend also
check; the [configuration reference](/reference/configuration/#mcp-servers)
lists them. A missing group or a missing `servers` list means no server. Each
server has a switch, `enabled`, on when the file omits it, and the group's
`builtIn` object holds the switch of each server Lys ships, today `email`,
off when the file omits it; a `null` object or switch, a built-in name the
build does not know, or a switch that is not `true` or `false` makes loading
fail. A
`null` group, an unknown field, a field of the other transport, more than 16
servers, two servers with one name, or a broken rule makes loading fail, and
an error about a server names the rule without quoting a value; an error
about the group itself, such as a `servers` value that is not a list, can
quote that value. Environment values and
header values can be secrets, such as tokens, and are stored as plain text,
like the Tavily API key. `Debug` output shows a command server's name, its
command, how many arguments it has, its variables' names, and its switch; a
URL server's name, its URL without the query, its headers' names, and its
switch; and the built-in switches. It never shows an argument, a value, or a
query. The host only stores the group; the backend starts or reaches the
servers.

The `email` group holds the one email account the person saved on the MCP
pane's email server (`src/settings/email.rs`), or `null`, validated on load
with the rules of `emailSettingsSchema` in `@lys/share`, which the renderer
and the backend also check; the
[configuration reference](/reference/configuration/#email-account) lists
them. A missing group or a missing `account` field means no account. A
`null` group, an unknown field, or a broken rule makes loading fail, and an
error about the account names the rule without quoting a value; an error
about the group itself can quote the value. The account is personal data:
`Debug` output shows placeholders for the address, the names, and the mail
servers' hosts. The password is not in this group but in `secrets`, and the
host only stores both; the backend starts the email server with them.

The host only stores the `loadConfiguration` group. A settings file written
before load configurations existed has no such group; `load_settings` reads it
as empty and does not rewrite the file. The committed default load
configuration belongs to the renderer, which applies it when it resolves a load
(see the [configuration reference](/reference/configuration/#load-configuration)).

The desktop automatically saves generation edits by reading this document,
replacing its generation group, and saving the complete document. Load
configuration edits are saved the same way, and so are each tool's switch and
its Ask me or Just run choice, the Tavily API key when the person saves or
removes it in the Secrets pane, the location when the person saves it in
the Tools pane, the MCP servers when the person saves or removes one in the
MCP pane, each server's switch when the person flips it there, and the email
account with its password, in one write of both groups, when the person
saves or removes it on the email server's card. A change of either startup switch in the Runtime pane saves
`autoStartBackend` and `autoStartVmo` and keeps the rest of the `runtime`
group as stored; a file without `autoStartVmo` loads it as `true`. The other
runtime edits in the UI remain session-only; the automatic saves preserve
those values as already stored on disk. An older file's `model` group, which
held a local context-size estimate, is ignored when loading and left out of
the next save.

## What the host does not currently do

- It does not manage provider credentials.
- It does not read the operating-system keychain.
- It does not start MCP servers or connect to them; the backend does.
- It does not proxy HTTP requests to LM Studio.
- It does not replay prior conversations into the window.
- It does not stop vmo or the backend when it dies without running its exit
  handler ([#202](https://github.com/w3lt/lys/issues/202)).
