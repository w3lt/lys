The desktop application is a React app rendered inside a Tauri window. It owns
presentation state, not durable conversation storage.

## Main responsibilities

| Area                | Current implementation                                                                                                                          |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| App shell           | `App.tsx` swaps between chat and settings views and runs startup initialization.                                                                |
| Chat UI             | `ChatView` renders the transcript, composer, jump-to-latest controls, and the past-conversations dialog.                                        |
| Message rendering   | `MarkdownMessage` renders assistant replies as Markdown with KaTeX math and highlighted, copyable code blocks.                                  |
| Chat state          | `src/lib/store/chat-view` owns the active conversation, request lifecycle, conversation opening, and error presentation.                        |
| History state       | `src/lib/store/conversation-history` owns the past-conversations dialog, its search and pages, and rename and delete calls.                     |
| Agent state         | `src/lib/store/agents` owns the Agents pane's list, its editor and draft, and the agent create, update, and delete calls.                       |
| Tool state          | `src/lib/store/tools.ts` owns the Tools pane's list of client tools and the session-only choices that gate tool calls.                          |
| Tool calls          | `src/lib/store/tool-calls` follows each running reply's tool calls, decides each by the Tools pane, runs client tools, and sends their answers. |
| Shell/runtime state | `src/lib/store/index.ts` tracks which view is open, whether the backend is running, and settings loaded from Tauri.                             |
| Model lifecycle     | `src/lib/store/model-actions.ts` owns real inventory, load, unload, and health requests shared by settings and the composer.                    |
| SSE consumption     | `src/lib/apis/http/chat.ts` opens chat and reply-events SSE streams, validates events with Zod, and sends reply stops and tool results.         |
| Theme               | `src/app/theme.ts` applies light or dark mode and stores the choice as `lys.theme` in WebView `localStorage`.                                   |

## Chat state split

The desktop currently has six separate state systems:

| Store                   | Owns                                                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Chat Zustand store      | Active conversation, request and open tokens, local abort controllers, streamed assistant deltas, inline error text            |
| History Zustand store   | Dialog visibility, search query, displayed conversation pages, the row being renamed or confirmed, pending renames and deletes |
| Agent Zustand store     | Every listed agent, the open editor and its draft, the save attempt, the pending save or delete, the most recently saved agent |
| Tool Zustand store      | The client tool list read from the desktop, tool calls on or off, each tool's switch and approval                              |
| Tool-call Zustand store | Every tool call held until the backend takes its answer, and the reply follows that deliver them                               |
| Shell Zustand store     | Active top-level view, loaded runtime settings, backend process status, startup progress                                       |

The transcript shown in the window is built from backend events for the current
request, or from the stored transcript read when a past conversation is opened.
Shell state such as backend status is managed independently.

## Streaming path

1. The composer calls `sendMessage`.
2. The chat store opens `POST /api/v1/chat`. The request offers the
   switched-on tools when tool calls are on and the loaded model was trained
   for tool use.
3. The desktop parses SSE frames with `EventSourceParserStream`.
4. Each payload is validated against `chatApiStreamEventSchema`.
5. The store applies `start-*`, `delta`, `done`, `interrupted`, `title`, or
   `error` events to local immutable conversation state, and hands the reply
   to the tool-call store, which answers its `tool-call` events.

The composer shows Stop while the turn is awaited or the reply streams, and
Send otherwise. After `done`, `interrupted`, or `error`, the stream can stay
open for a title; sending the next message then stops following it, and the
backend still saves the title. The desktop then learns that title only from
the next turn's start event, from reopening the conversation, or from the
history dialog; delivering it live is tracked in
[issue #96](https://github.com/w3lt/lys/issues/96).

The desktop keeps no replay log and does not reconnect a dropped stream on its
own. Showing a conversation whose reply is still generating, after an open or a
failed open, follows that reply again from a stored `reply-snapshot`. Quitting
the app also ends the backend; a reply still generating then keeps its
persisted text and is marked interrupted when the backend next starts.

## Assistant message rendering

`MarkdownMessage` renders each assistant reply with `react-markdown`. Links
open in a new tab without a referrer. `remark-math` and `rehype-katex` render
`$…$` inline math and `$$…$$` display math with KaTeX, whose stylesheet
`src/index.css` imports.

Each fenced code block shows its language and a Copy button. Shiki
(`@shikijs/rehype`) highlights a block whose language it bundles, loading that
language's grammar the first time a reply uses it. Token colors are CSS
`light-dark()` pairs from the GitHub Light and GitHub Dark themes, so they
follow the app's `color-scheme` and change with the theme without highlighting
again. A block without a language, or in one Shiki does not bundle (names are
case-sensitive, so `TS` is not `ts`), is labelled `Text` and shown without
highlighting. Copy writes the block's plain text without its final newline,
never the highlighting markup.

Rendering is asynchronous. Until a message's first pass finishes, it shows
plain Markdown without the link, math, and code-block handling; the first
reply in a session also waits for Shiki to start. While a reply streams, the
previous rendering stays visible until the new text is processed.

## Conversation history

The Past conversations button in the composer, or Command+K or Control+K,
toggles a history dialog above the composer. Opening it reads the first page
of `GET /api/v1/conversations`, 30 entries at a time. Typing in the search
field reads again with the trimmed query after a 200 ms pause in typing, so
the backend receives one list request per pause rather than per keystroke.
Enter in the search field reads a search still waiting for that pause at once
and then opens its first row. Older pages load on request.
Rows can be renamed in place or deleted after confirmation through the
conversation `PATCH` and `DELETE` routes. While the backend is not running,
these actions fail inline without sending a request.

Closing the dialog cancels a pending list read and saves a changed title that
is still being edited. Renames and deletions already sent continue after the
dialog closes and record their outcome.

Choosing a row closes the dialog and opens that conversation. The chat store
first stops following any active reply, which keeps generating on the backend,
then reads `GET /api/v1/conversations/:conversationId`. The previous
conversation stays visible until the read succeeds, and no message can be sent
while it is pending. A missing conversation or failed read keeps the previous
conversation and shows an inline error. When the conversation then shown,
opened or kept, ends with a reply that is still generating, the chat store
follows it from a stored snapshot. The next message sends the opened
conversation as `{ kind: "existing", id }`, so the backend continues it. Deleting the conversation the
chat view presents, or learning that it no longer exists, resets the view to a
new conversation.

## Backend and LM Studio status

The shell store tracks three facts separately. The Tauri host reports whether
the backend process exists. The store reports the backend as `running` only
after `GET /api/v1/heath` answers: it checks every 250 ms, each check bounded
to one second, for up to 30 seconds, and shows **Backend not responding**
(`unresponsive`) when the process stays alive without answering. Once the
backend runs, the store reads `GET /api/v1/llm/runtime`, joining the backend's
startup attempt through `POST /api/v1/llm/runtime/connect` while it is still
`connecting`.

The Runtime pane's LM Studio card shows `unknown`, `connecting`, `connected`,
or `unreachable` with the address `127.0.0.1:1234`. Its **Refresh** button is
the only control that asks the backend to reconnect. A failed model request
re-reads the status, so a lost LM Studio appears as not reachable without
polling. The composer banner names the first missing prerequisite—the
backend, LM Studio, or model weights—and opens the settings pane that fixes
it. `initialize` shows the shell as soon as settings load; the backend starts
in the background.

## Model settings

The shell store refreshes `GET /api/v1/llm/list` when LM Studio becomes
connected and on entry into settings while it stays connected. While LM Studio
is not connected, the model list is empty, model actions are disabled, and the
pane explains how to recover. A manual Refresh action picks up changes made in
LM Studio. Inventory metadata and each model's `loaded` flag drive the model
rows and composer menu; several models may be loaded at once.

Load sends `{ modelId, configuration }` to `POST /api/v1/llm/load`. Unload sends
`{ modelId }` to `PATCH /api/v1/llm/unload` and accepts its bodyless `204`
response. Both operations reconcile the inventory afterward, including when the
command fails, because a lost acknowledgement does not establish whether weights
changed. Requests are serialized locally and mutations are never retried
automatically.

### Load configuration

Every load the desktop starts, from the Runtime pane or from a model row, sends
that model's load configuration. The store builds it when the load is admitted:
each setting is the model's own stored value when it has one, then the stored
default's, then the committed default's, and the context length is lowered to
the model's `maxContextLength` from the inventory. Edits made while the load is in flight
do not change what it sent. The composer's "Load model" action opens the Model
pane and starts no load.

The Model pane's "load configuration" section edits the configuration of the
selected default model. With no default model selected it edits nothing, even
while a model is loaded, and asks to choose one; the selection lasts for the
session, so after a restart the section waits for a choice. It has five rows: context length, eval batch size, flash attention, KV cache on
GPU, and active experts. An edit is stored for that model only, applies to its
next load, and is saved automatically to the `models` part of the
`loadConfiguration` group of `settings.json`; the save keeps the `default` that
is in the file. Active experts reads "auto" until it is set, because LM Studio
reports no expert counts ([#144](https://github.com/w3lt/lys/issues/144)).

The backend does not report the settings a loaded model runs with
([#145](https://github.com/w3lt/lys/issues/145)), so the store keeps its own
record for each model it observes as loaded:

- For a model Lys loaded in this session, the record is the configuration that
  load sent. When the stored settings differ from it, each changed row shows
  the loaded value, and a line under the rows lists what a reload would apply.
- For a model found already loaded, the record is the configuration stored
  when it was first observed. It only shows whether the settings changed since.
  The pane then says that changes apply on the next load.

"Reload now" unloads the model and loads it again with its stored configuration,
as one operation. If the unload fails, no load starts. If the load fails after
the unload, the model stays unloaded and the failure is shown. Stopping the
backend or losing LM Studio discards the records.

Test calls `GET /api/v1/llm/:modelId/health` with the canonical key encoded as
one path segment. Its result reports a fresh loaded-state observation and query
latency, not inference success. The frontend validates responses against the
shared protocol and exposes request failures inline.

The application store owns requests across pane changes. Stopping the backend
invalidates pending observations before aborting their local HTTP transport;
a late response cannot restore obsolete residency. LM Studio owns weights
separately from the backend process, so a reconnect queries their actual state.

The Composer label, send eligibility, and chat request use that same compact
runtime projection. The [default-model setting](/reference/configuration/#persisted-settings-json)
defines the preference and fallback selection. A send is admitted only while
the backend is running and the projection is loaded. A submission rejected
because no model is eligible produces an inline chat error without discarding the draft or conversation;
Model settings provide inventory refresh and load controls for recovery. The
chat store samples that model key once at submission, so a later selection
change applies only to a later request.

## Generation settings

Generation edits apply to the next chat request. Temperature uses the API's
inclusive `0`–`1` range. The optional reply ceiling uses an on/off switch and
a token slider. Switching it off stores zero and omits `replyCeiling`
from the request, so the backend does not receive a zero-token limit.
Switching it back on restores the application default. The local context estimate
sets the usual slider range, which expands to include an existing saved ceiling
rather than silently clamping it.
The model's actual context capacity and stopping behavior still apply.

Generation edits automatically persist only the generation group through Tauri.
The store reads the existing settings document and preserves its runtime and
model groups before invoking `save_settings` with `{ newSettings }`. Saves
are serialized in the application store and continue across pane changes;
edits made during a write are coalesced into the latest settings and saved next.
Failures remain visible and can be retried or replaced by a newer edit; a
completion cannot overwrite newer edits or label those edits as saved. Future
messages use the latest settings, including after restart once the save completes;
already submitted requests keep their original settings. The read-modify-write operation
does not coordinate with external editors of the settings file.

## Agent settings

The Agents pane manages the agents stored by the backend through the
[agent API](/reference/api/#agents). It reads every stored agent when it
appears and whenever the backend starts running, one page of 50 after another,
because names are checked for uniqueness against all of them; a read stops
with a failure past 1,000 agents. A displayed list stays on screen while it is
read again. A status line above the agents says why they are not shown: the
backend is not running, or a read failed, which offers Retry. When the status
appears because the control holding focus disappeared with the list or an
editor, focus moves to Retry or to the status line.

The pane lists the user's agents oldest first with their name, code, and bio.
Built-in agents are not available yet, so the pane has no section for them.
Opening an agent reads it with its system prompt into an editor; New agent opens
an empty one. The editor edits the name, bio, and system prompt, and for a new
agent an optional code. The name, bio, and prompt are marked required, and the
code field states the format it accepts. Typed codes keep only lowercase
letters, digits, and single hyphens; `use name` fills the code from the name,
and an empty code lets the backend derive one. Limits come from `@lys/share`,
and the counters measure the trimmed text, as it is saved. Saving checks the
draft first: a blank name, bio, or prompt, a name or bio over its limit once
trimmed, a name another agent has (ignoring case), or a malformed or listed
code is shown and nothing is sent. Once the field is marked invalid, focus moves
to it. Names need not be unique to the backend, so a stored agent that keeps
its own name can be saved even when another agent shares it. The backend still
refuses a code taken since the list was read. Duplicate opens a copy as a new
agent under a free name, and Delete asks for confirmation.

The agent store owns the editor and every change, so a draft survives leaving
and returning to the pane, and a save or delete continues across pane changes.
Settled changes are applied to the displayed list; a list read still pending
is replaced, since it may answer from before the change. The same holds when an
agent being opened or saved turns out to be gone. A creation whose response is
lost may still have stored the agent, so the editor says the save could not be
confirmed and the list is read again; an agent that was stored then appears,
and its name and code count as taken. Saving is unavailable while the list is
read again, so a draft is never checked against a list that read may change.
Agents are not used by chats yet.

## Tool settings

The Tools pane lists Lys's client tools: the tools that run in the desktop app
and work with files on the user's machine. The tool store reads them from the
[`list_tools` command](/architecture/host/#client-tool-list) when the pane first
appears; they do not depend on the backend. A failed read shows the failure
above the pane with Retry. Tools are grouped by their `group`, and each group
says how many of its tools are on.

Each row shows the tool's name, what it does with the machine (`reads`), that it
runs in Lys, its description, an estimate of the tokens it adds to each request,
and a switch. The estimate measures the function tool a model receives, built
by `buildToolFunctionFormat` from `@lys/share`, with the composer's text
estimator, so it varies with the model's tokenizer. Expanding a row, one at a
time, shows the tool's arguments with their type and whether they are required;
an enum argument shows `enum · N` and its accepted values. It also shows where
the tool runs and whether Lys asks before it runs.

The tool-calls card holds the master switch and a status line. The status line
names the loaded model and how many tools are offered with their summed
estimate. When the loaded model's `trainedForToolUse` is false, Lys offers it
no tools: a card says the model isn't trained for tool calls, and every control
below it recedes and is disabled. An expanded row closes while the controls are
locked and opens again when they unlock.

Every choice on the pane applies to the next chat request or tool call: tool
calls on or off, each tool's switch, and Ask me or Just run. Every tool starts
on Ask me. The choices last for the session only; nothing is saved.

## Tool calls

A chat request offers the switched-on tools when tool calls are on and the
loaded model's `trainedForToolUse` is true. If the tool list cannot be read, the
request fails with an inline error and nothing is sent.

The tool-call store follows every reply the chat store starts or follows on
its own reply-events connection, so tool calls keep moving while another
conversation is shown. It takes each call from a `tool-call` event or from the
snapshot's `pendingToolCalls`, once, and decides it by the Tools pane at that
moment. An answered call stays held while the store follows its reply, so a
snapshot built before the answer arrived does not bring the call back:

1. A tool the desktop does not list, or arguments that do not match its
   command, is answered as `runFailed`.
2. With tool calls off, or the tool switched off, the call is answered as
   `declined`.
3. On Just run, the tool runs at once and nothing is shown.
4. On Ask me, the call waits for the person.

A waiting call shows a card above the composer field: the tool, what it does
with the machine, that it runs in Lys, a plain sentence such as "Read
/Users/me/notes/todo.md. Nothing is changed.", and its arguments on request.
Reject sends the composer's text as the reason; Allow once runs the call, and
Allow anyway does too while keeping the text. In the field, Escape rejects,
Enter with an empty draft allows, and Enter with text rejects with that text.
Several calls wait in the model's order, one card at a time.

A read sends the file's text, a search sends its report as JSON, and a
declared tool failure sends the failure as JSON. Each answer goes to the
[tool-result route](/reference/api/#tool-results). When an answer cannot be
sent, the card says so and Try again sends the same answer without running the
tool again. When the reply ends, by finishing, Stop, or backend shutdown, its
waiting calls disappear. A newer turn in the conversation or deleting the
conversation does not end a waiting reply yet
([#137](https://github.com/w3lt/lys/issues/137)). After a renderer reload, a
call still waiting is found again through the reply's snapshot when its
conversation is shown. Quitting the app stops the backend, so its waiting calls
are gone and the reply is marked interrupted when the backend next starts.

## Current limitations

- Runtime edits and `model.contextSize` edits remain session-only. Generation
  settings and load configurations save automatically; a failed save leaves the
  edits available for the current session.
- The retained local context budget, `model.contextSize`, is still used for
  composer estimates. It is separate from the context length in a model's load
  configuration and does not follow it.
- The KV cache load setting has no effect with the installed LM Studio SDK; see
  the [load request](/reference/api/#model-load-request).
- Model observations refresh on LM Studio connection, entry into settings,
  manual refresh, and model operations. The LM Studio status changes only on
  backend start, Refresh, and failed model requests; it is not polled. Changes
  made by another LM Studio client between observations are not pushed to the
  desktop.
- The composer's attachment tray stages files and long pastes for its local
  context estimate only. The chat protocol has no attachment field, so staged
  attachments are never sent.
- The Tools pane's choices last for the session only; every tool starts on Ask
  me again after a restart.
- There is no "Allow for this chat": each call on Ask me is asked about.
- Tool calls leave no trace in the transcript: a call on Just run shows
  nothing, and an answered call's card disappears. Streamed and stored reply
  parts are planned next.
