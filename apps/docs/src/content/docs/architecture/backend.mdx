The backend is a TypeScript Fastify application in `apps/backend`. It owns the
SQLite conversation store and the HTTP and SSE surface consumed by the desktop
application.

## Current backend shape

Each module in `src/modules/` keeps its HTTP routes in `routes/` and its
services, contracts, and domain logic at the module root. `src/di/` only wires
the services together.

| Layer                 | Implementation                    | Responsibility                                                                                                                                                                                                                                                                                            |
| --------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| App bootstrap         | `src/app.ts`                      | Registers CORS, SSE support, singleton services, and all routes, and sets up the logger from `src/log.ts`, writing to the destination the entry point passes, which `src/index.ts` makes standard output.                                                                                                 |
| Logging               | `src/log.ts`                      | Builds the logger options (level names, UTC ISO-8601 times, full request URLs) and keeps the backend running when writing to standard output or standard error fails; `src/index.ts` registers that first.                                                                                                |
| Runtime config        | `src/config.ts`                   | Loads loopback host and port values, the SQLite path and the attachments directory under `LYS_HOME`, the system and title prompts, and title limits.                                                                                                                                                      |

| Conversation services | `src/modules/conversation`        | Keep the conversation decisions (identities, timestamps, validation, superseding, cursors) over records declared in `records.ts`; contain no SQL.                                                                                                                                                         |
| Agent service         | `src/modules/agent`               | Owns the built-in agents, lists them with each page of stored agents, validates agent definitions and changes, derives a code from the name when none is given, stamps each change with the current time over records declared in `records.ts`, and finds the agent that answers a chat; contains no SQL. |

| Attachments           | `src/modules/attachment`          | Decodes a chat request's attachments and reads what each is from its bytes, keeps the files under the attachments directory by conversation and message, and runs `read_attachment`, the reader the backend adds to a turn itself; its calls run without approval.                                        |

## Chat request flow

1. `POST /api/v1/chat` validates the request body with the shared Zod schema,
   whose attachment rules it applies within its 32 MiB body limit, decodes
   each attachment and reads what it is from its bytes, then finds each
   backend tool the request names in `backendToolNames`. An attachment that
   is neither UTF-8 text nor a PNG, JPEG, or WebP image answers `400` with the
   attachment-unsupported problem, and a name no built-in tool has answers
   `400`, before anything is stored.
2. The route finds the agent that answers before it stores anything. For a
   new conversation it asks the agent service (`app.agentService`) for the
   requested agent, built-in or stored; if no agent has that code, it answers
   `404` with the agent-not-found problem. For an existing conversation it
   reads the conversation's agent code through the history reader, answers
   `404` with the conversation-not-found problem when the conversation is not
   stored, and answers `409` with the conversation agent missing problem when
   no agent has that code any more, as after the agent was deleted. In each
   of those cases nothing is stored.
   When the request or the conversation holds an attachment, the route then
   reads from LM Studio's inventory whether the model sees images and is
   trained for tool use: a full model-operation queue or a missing runtime
   answers its `503` problem, and an image attached for a model without
   vision, or for one the inventory does not list, answers `409` with the
   image-needs-vision problem, nothing stored either way. A request without
   attachments in a conversation without any never reads the inventory. The
   route makes the identities of a new conversation and of the user message
   and writes the attachment files under them, so they are in place when the
   turn commits; see [attachments](#attachments). Once the files are written,
   the route looks the agent up again and `StoredConversationTurns` creates
   the conversation with that agent or loads the existing one, interrupts a
   reply still streaming in it, and stores the user message with its numbered
   attachments and the empty streaming assistant message, all in one write
   transaction of the SQLite turn records. That lookup and the write run in
   one synchronous step, so the agent that answers is the conversation's
   agent when the turn is stored; a conversation or agent deleted while the
   files were written or the inventory was read gets its `404` or `409`
   problem instead, and the written files are deleted again.
3. The route immediately emits either `start-new-conversation-turn` or
   `start-existing-conversation-turn`.
4. For an existing conversation with a stored title, the route emits that title
   to reconcile desktop metadata from an earlier missed delivery.
5. The agent found when the turn is stored answers with the system prompt it
   has then: a built-in agent's shipped prompt, or a stored agent's current
   one. The agent's `createReply` opens an
   OpenAI-compatible streaming completion against LM Studio through
   `OpenAiReplyModel`, offers the request's tools (client tools first, then
   backend tools, then the attachment reader when the conversation holds a
   text file and the model is trained for tool use), and runs rounds while
   the model calls them: each call is
   checked by `AgentTool`, then passes the round's
   [approval gate](#tool-approval). A call of a backend tool is first parsed by
   the tool, so arguments it can never run are answered without asking. An
   allowed client tool's call is sent to the desktop as a `tool-call` event
   and answered through the tool-result route; an allowed backend tool runs in
   the backend under the reply's cancellation. Every call has an answer before
   the next round. [Reply parts](#reply-parts-and-sources) describes how each
   part is stored before it is sent to every stream following the reply; the
   agent stores completion before emitting `done`.
6. When the conversation has no stored title, `createTitleGenerationTask` runs
   in parallel and emits a `title` event only after a conditional write wins the
   first assignment.
7. Chat generation errors become `error` events for every follower; a reply
   that ends early becomes `interrupted`; title-generation failures are logged
   instead.

### Context window check

Before each round, the agent measures the round's context and offered tools
against the model the turn names. `LlmReplyContextMeter` gives `LlmService`
the text the model reads for each message (its content, and the name and
argument text of each tool call it carries) and each offered tool's JSON;
`LlmService` counts them with the loaded model's tokenizer through the model
operation queue and reports the context length the model is loaded with. The
meter adds a fixed allowance for the chat template's markup: 8 tokens per
message, 16 per tool call of an earlier round, and 160 once when tools are
offered. Each image a user message sends, which the tokenizer cannot count,
is counted as `⌈width ÷ 28⌉ × ⌈height ÷ 28⌉` tokens up to 1,280
(`calculateImageTokens` in `@lys/share`). A file staged in the composer is
measured only once its message is stored: the desktop adds the image
estimate for a staged image, while the listing lines of staged files and the
reader's definition, when a staged text file would make the turn offer it,
are not counted until then.

A round is sent only when its tokens and the reply ceiling (or zero without
one) together stay within that context length. Otherwise the round is not
sent: the reply is stored `failed`, keeping the parts earlier rounds stored,
and its `error` event names the tokens needed and the context length. A model
that is not loaded is never loaded for the round; the reply fails with an
`error` that asks to load it. A measurement that fails, because LM Studio is
not connected or the queue is full, also fails the reply, with the general
sentence. Without this check, LM Studio's context overflow setting could keep
the start of the conversation, drop its middle, and let the model answer an
earlier message. With the reply ceiling off, nothing is held back for the
reply, so a reply that grows past the window is still handled by that
setting.

`POST /api/v1/chat/context` makes the same measurement for the composer's
context meter. It resolves the agent and the conversation as the chat route
does, through the same lookups, reads a continued conversation once, and
asks the agent's `findContextMeasurement` for the system prompt, tools, and
stored messages a turn's first round would send, with an empty new message
that measures the markup around the text. When a stored message holds an
attachment, it reads the model's capabilities as the chat route does, so the
images a model with vision sees are counted and `read_attachment` is among
the measured tools when a turn would offer it. See the
[route contract](/reference/api/#chat-context-measurement).

Each completion receives the system prompt of the conversation's agent, prior
user messages, the rounds of completed or interrupted replies, and the current
user message once. Each user message sends its text followed by the list of
its attachments and, for a model with vision, its images; see
[attachments](#attachments). `buildAgentContext` sends each stored round as one
assistant message with the round's text and its tool calls that have a
result, followed by one tool message per result. Reasoning is never sent
back, nor are calls without a result; a round with neither text nor such a
call is left out. Failed replies are excluded from model context. A reply
still streaming when the next turn is created becomes interrupted first, so its
partial rounds are included. Within one turn, a round's reasoning is not sent
to the next round either ([#185](https://github.com/w3lt/lys/issues/185)).
The required `generationOptions` controls supply sampling temperature and an
optional completion-token ceiling; the [API reference](/reference/api/#chat-request-body)
defines their limits. Partial reply parts remain available in history
after cancellation or failure.

### Reply parts and sources

A reply is a list of parts: reasoning, text, and tool calls with their
results, each in the model round it belongs to. `OpenAiReplyModel` yields a
round's reasoning from the stream's `delta.reasoning` field, which LM Studio
0.4 sends, or else from `delta.reasoning_content`, before the chunk's text.
Reasoning a model writes between `<think>` tags in its text stays text
([#183](https://github.com/w3lt/lys/issues/183)).

`ReplyPartSequence` (`src/modules/agent/replyPartSequence.ts`) owns the
reply's open part. A reasoning or text fragment extends the last part when it
is of the same kind and round; otherwise it starts a new part. Every part,
fragment, and tool call change is stored first, through the turn's
`ReplyPartWriter` capabilities, and sent as a `reply-part` or
`reply-part-delta` event in the same synchronous step, so a follower that
reads a snapshot sees both or neither. A refused write means the reply was
superseded, deleted, or finalized, and ends it as interrupted.

The tool-call round stores each call as a part in the model's order, under
the UUIDv7 it sends: a call of an unknown tool, or with arguments that do not
match, as `failed` with the message the model reads; a checked call as
`running` when the gate allows it at once, or otherwise as
`awaiting-approval` before its prompt is sent, in the same step. A call the
store refuses because its reply has ended is never prompted. An allowed call
becomes `running`, a rejected one
`rejected` with the rejection the model reads, and a call that ran
`succeeded` or `failed` with its result. A network tool's result is cleaned
before it is stored, so the stored result is what the model read.

`SourceCatalog` (`src/modules/agent/sourceCatalog.ts`) numbers the web
sources of one conversation during a turn, seeded with the sources the
conversation stored. A backend tool's run receives `addWebSources`, which
gives each candidate URL the number it already has, or the next one. A
title in which a person sees nothing, only whitespace and default-ignorable
code points such as Hangul fillers, is replaced by the URL's host, both in
the result the model reads and in the source. Any other title becomes the
source's title cleaned of the characters a person cannot see, as a network
tool's result is, and trimmed, so a citation never shows an empty or
disguised title.
`web_search` labels each result `Source [n]`, and `read_page` adds a
`Source number: [n]` line; the citation rule tells the model to cite those
numbers in square brackets and to write no list of sources. A succeeded call
stores the numbers its result shows with the sources themselves, then a
`sources` event precedes its `reply-part` event. A number given to a call
whose result is never stored, because the reply ended first, is not kept:
the next turn gives the numbers above every stored number again, so a gap is
left only below the highest stored number. Only web pages are sources today;
files a tool reads are not ([#184](https://github.com/w3lt/lys/issues/184)).

`StoredReplyParts` (`src/modules/conversation/replyParts.ts`) implements
`ReplyPartWriter` over `SqliteReplyPartRecordWriter`, reading the clock once
per operation; reasoning and text parts get a new UUIDv7. Each write is one
transaction guarded by the reply still streaming. Ending a reply, a newer
turn superseding it, and startup recovery mark its `awaiting-approval` and
`running` calls `interrupted` in the same transaction as the reply.

The Lys system prompt and the title-generation prompt are read once, when
`loadBackendConfig()` builds the backend configuration at startup.

A new conversation is stored without a title (`null`). Title generation runs
for a turn whose conversation has no stored title, unless an earlier turn of
that conversation is still generating one, and uses that turn's user message.
A conversation that remains untitled after an earlier task failed or was
cancelled gets another try on its next turn after that task ended. It uses a
separate chat completion request with a JSON-schema response format that limits
the title to `generatedTitleMaxLength` Unicode code points (100 by default),
then validates the reply; JSON wrapped in one Markdown code fence is accepted.
Only a reply that cannot be used as a title leads to another attempt, up to
`titleGenerationMaxAttempts` attempts per turn (three by default). Before each
attempt, the task asks the model-operation queue whether the model is loaded,
without loading it. When it is not, the turn requests no title, logs
`model-not-loaded` at debug level, and the next turn tries again, so a title
request does not make LM Studio load the model with its own settings. An HTTP,
connection, or cancellation failure ends title generation for the turn, after
the OpenAI SDK has retried a connection failure, timeout, or 408, 409, 429, or
5xx response up to two more times within the attempt. A generated title is
saved with a conditional first assignment and published only when that
assignment succeeds, so generation cannot overwrite a manual rename. Existing titled turns
send the stored title after their start event, which repairs desktop metadata
after a prior title event was lost.

`ReplyGenerationRegistry` owns every running generation and runs at most one
title task per conversation: a turn sent while an earlier turn's title task is
still running gets none, so its streams close when its reply ends. A
`ReplyGeneration` owns one turn's reply task and optional title task, their
cancellation, and the SSE streams following them; no HTTP connection owns it. It
also lists what its reply waits on (`PendingToolCalls`): calls sent to the
desktop to run and approval prompts, which the reply-events snapshot reports
and the tool-result and tool-approval routes answer. Each stream is
a `ReplyEventSubscription`, an ordered queue that never makes the generation
wait and closes a follower that falls 4,096 events behind. Only the reply-stop
route (reply task only) and shutdown (both tasks) cancel work. A newer turn or a
deletion also ends a reply, but only when the model sends its next content: that
write is refused, which ends the upstream request. A reply waiting for a tool
result or an approval is not ended this way
([#137](https://github.com/w3lt/lys/issues/137)).
The title task of a deleted conversation still runs to its end. The registry is
disposed in Fastify's `preClose` hook, while streams are still open: it closes
admission, cancels every generation, and waits until each has stored its final
state before singleton disposal closes SQLite. Task failures are logged by the
generation that owns them.

### Attachments

A chat request can carry up to 8 files, 10 MiB each and 20 MiB together, as
base64 `attachments`; the limits are constants of `@lys/share`
(`packages/share/src/models/attachment.ts`), which the desktop applies too.
`parseChatAttachments` (`src/modules/attachment/chatAttachments.ts`) reads
what each file is from its bytes, never from its name: a PNG, JPEG, or WebP
header makes an image with its media type and sides; bytes that decode as
UTF-8 without a NUL character make a text file; anything else is refused
with `400` before anything is stored.

`AttachmentFileStore` (`src/modules/attachment/attachmentFileStore.ts`) owns
the attachments directory, `$LYS_HOME/attachments`, and writes a message's
files at `<conversation id>/<message id>/<name>` before the turn is stored.
Every path it touches is built only from a validated UUIDv7 and a validated
name, so no request can name a path, and the message's folder and each file
in it are created exclusively, so nothing on disk is overwritten. A file that
cannot be written deletes what was written for the message and fails the
request, which stores nothing. A turn that cannot be stored after its files
were written deletes the message's folder again and fails the request; when
that deletion fails too, the request fails with both failures and the folder
stays, under a message the conversation never stores. Deleting a
conversation deletes its rows, then its folder; a folder that cannot be
removed is logged at `error` with its cause, and the delete still answers
`204`.

The turn stores each attachment's number, name, kind, size, and an image's
media type and sides in `conversation_attachments`. Numbers start at 1 and
count up across the conversation in sending order, so the model knows each
file as `[attachment 3] notes.md` whatever message it belongs to. Loading a
conversation never reads the disk.

`buildAgentContext` sends each user message as its text, a blank line, and
`Attached files:` with one line per attachment giving its label, `text` or
the image's media type and sides, and its size; a message without
attachments sends its text alone. For a model with vision, each image follows
its message's text as an `image_url` part carrying the file as a data URL, on
the turn it was sent and on every later turn; `loadAgentContextImages` reads
the files once per turn, in conversation order. An image the model does not
get is one more line of the text instead: "is an image that this model
cannot see." for a model without vision, which reads no file, or "is an
image whose file is missing from this machine, so it cannot be shown." when
the file is gone. The context meter counts each image sent as its estimate.

A text file is never sent whole. When the conversation holds one and the
model is trained for tool use, the turn offers
[`read_attachment`](#read_attachment) after the request's tools, and the
model reads the file in parts when it needs it. The reader's results stay in
the reply's stored parts, so later turns resend them like every other tool
result.

Whether the model sees images and is trained for tool use is read from LM
Studio's inventory (`src/modules/chat/routes/modelCapabilities.ts`) only for
a turn that involves an attachment, so a turn without any never waits for
the model-operation queue. A model the inventory does not list has neither
capability: an image attached for it is refused, and no reader is offered.

## Tool approval

`ToolApprovalService` (`src/modules/toolApproval/toolApprovalService.ts`) is the
approval gateway for every tool call of every turn, client and backend tools
alike, except a call of a backend tool that runs without approval:
`read_attachment` reads only what the person attached to the conversation,
so its calls are stored as `running` at once and never pass the gate. When a
round with a call to gate arrives, `createToolCallGate` reads
`tools.justRun` from the desktop's settings file with `readJustRunToolNames`
(`src/infrastructure/settings/justRunToolsFile.ts`) and returns a
`ToolCallGate` for that round. The reader shares the bounded settings-file
read (`settingsFile.ts`) with the Tavily key reader: at most 1 MiB, UTF-8,
parse failures dropped unread. A missing file, `tools` group, or `justRun`
list means no tool is on Just run. A round whose calls all run without
approval or name no offered tool creates no gate and does not read the file.

For each checked call that passes the gate, in the model's order, the gate's
`startToolCall` stores the call and decides how it goes on. A call of a tool on Just run is
stored as `running` and goes on at once. Any other call is stored as
`awaiting-approval` first; the gate then sends a `tool-approval` event, and
the round waits for the person's answer through the tool-approval route,
with no timer. A call the store refuses is never prompted. Storing and
prompting happen in the same synchronous step, so a follower that sees the
prompt can read the call, and a round's prompts and the run requests of
calls allowed at once keep the model's order. When the settings
file cannot be read, or `tools`, `justRun`, or a name in it is invalid, no
tool is on Just run, every call of the round asks, and the chat route logs a
warning with the request's logger. A choice the desktop saves applies from
the next round. The desktop is the file's only writer; the backend never
writes it.

The Tools pane's switches are not part of the gateway: they decide only which
tools a chat request offers, so switching a tool or tool calls off applies
from the next message.

## Built-in tools

A built-in tool implements `BuiltInTool` (`src/modules/tool/builtIn/builtInTool.ts`):
`parseToolCall` checks a call's arguments before the person is asked and
returns either an explanation the model reads or a run function. The run
receives the reply's Stop signal and `addWebSources`, which numbers the web
sources it is about to show. It returns the text the model reads, with the
numbered sources a succeeded result shows, or rejects only with the Stop
reason or a defect.

Each entry of the registry pairs a definition with a `BuiltInToolProvider`,
whose `findTurnTool()` gives the tool for one turn or says why it cannot run
now (`page-reader-not-ready`, `api-key-missing`, `api-key-invalid`, or
`settings-unreadable`). `createBuiltInTools()` builds the list once at
startup: `read_page`, found by `ReadPageToolProvider`, then `web_search`,
found by `WebSearchToolProvider`. The attachment reader, `read_attachment`,
is in neither the registry nor the tool list: the chat route builds it for
each turn whose conversation holds a text attachment, and its calls run
without asking; see [`read_attachment`](#read_attachment). `ReadPageToolProvider` sends vmo one
`GET /health` per lookup (`web/vmoHealth.ts`), on a connection of its own, and
gives the tool only for a `200` within one second. Any other status, a refused
or broken connection, an answer that is not HTTP, or no answer in time is
`page-reader-not-ready`, so a lookup waits at most one second for vmo. Any
other failure, such as a vmo address that is not a URL, is a defect and
rejects the lookup. The backend never starts vmo, which
the desktop owns. `GET /api/v1/tools` returns every definition and
looks up every tool again to list the ones that cannot run now; the desktop
offers the switched-on, available ones by name. The chat route looks up every
offered backend tool before it looks up the agent and stores the turn, and
answers 409 `backend-tool-unavailable`, storing nothing, when one cannot run.
The turn keeps the tools it found then.

The address-checked connection (`web/webConnection.ts`: the checked lookup
and the connected-socket check) and the formatting of untrusted web text
(`web/untrustedText.ts`: delimiter-free text, single-line fields without
control characters, excerpts, and the citation rule) are shared by both web
tools.

Every result of a tool whose definition has `access: "network"`, client or
backend, succeeded or failed, passes `formatNetworkToolResult()`
(`src/modules/tool/networkToolResult.ts`) in the tool-call round before the
model reads it, so a new network tool is cleaned without code of its own. It
removes Unicode format and control characters (zero-width, direction
controls, tag characters, `BEL`, `ESC`, and the like) except tabs and line
breaks, keeps a zero-width joiner or non-joiner only between two visible
characters, where emoji, Persian, and Indic text need it, and removes every
variation selector except one text-style (U+FE0E) or emoji-style (U+FE0F)
selector right after a visible character, as in `❤️` or `1️⃣`. A run of
variation selectors can spell a message one byte per selector, and the other
selectors only pick a rare alternate shape of the character before them.
When it removed anything, it adds a last line saying how many characters, so
the model can tell the person the source hid text. The format characters it
removes include a few visible signs, such as the Arabic number signs
(U+0600–U+0605) and the end-of-ayah sign (U+06DD), and the tag characters of
the England, Scotland, and Wales flags, which then show as a plain black
flag; a character picked by a variation selector keeps its default shape.

### `read_page`

Its arguments are `url` and an
optional `focus`. A URL longer than 2,048 characters, as given or once
normalized and percent-encoded, not absolute `http` or `https`, carrying a
username or password, or naming this machine or a blocked IP address is
answered at once. Once allowed, a read goes through vmo
(`web/pageRendering.ts`), the page reader in `apps/vmo` that runs on the same
machine:

1. it looks up the URL's host name through the operating system and refuses
   the read, without asking vmo, when the name has no address or any of its
   addresses is blocked by the rule in `webAddresses.ts`. A host that is an IP
   address is not looked up: the URL rules already checked it. The check
   covers only the URL given: the page's redirects, what the page loads, and a
   name that resolves differently inside vmo's micro VM are not checked;
2. it sends `GET /web/read-page` to vmo at `127.0.0.1:8080`, with the URL
   form-encoded as the `url` query parameter, on a connection of its own. vmo
   checks that the URL is absolute `http` or `https` with a host, and passes
   it to the reader as given. It creates a micro VM from the
   `ghcr.io/w3lt/lys-readpage` image, built from `sandboxes/readpage`, whose
   `latest` tag the image workflow moves to each build on `main` and vmo
   fetches at each start. The reader loads the page in headless Chromium,
   with the page's scripts running and its redirects followed, for up to 10
   seconds of virtual time, in which the page's timers run without waiting.
   It writes the HTML of the DOM it ended on, without shadow trees, so text
   inside a web component's shadow root is not read
   ([#209](https://github.com/w3lt/lys/issues/209)). It leaves out scripts,
   styles, `<noscript>`, `<link>`, `<meta>`, and `class` and `style`
   attributes. With no stylesheet left, text a stylesheet hides is read like
   any other text. Without `<meta>`, Readability finds no site or publication
   date, and without `class` it cannot use class names to drop boilerplate
   such as share bars and comment threads
   ([#208](https://github.com/w3lt/lys/issues/208)). vmo deletes the VM
   before it answers and gives the read 30 seconds;
3. it reads vmo's answer. Only a `200` body is read: JSON
   `{ html, isTruncated }` of at most 16 MiB, whose HTML is cut to 4 Mi UTF-16
   code units without splitting a character. A `400` or `431`, for a URL vmo
   refuses, a `502`, for a page the reader could not load or that was empty,
   and a `504`, for a read past vmo's 30 seconds, fail the read with that
   reason. Any other status, or an answer that is not that JSON, fails it as
   a failure of the page reader. A plain-text page arrives as the HTML
   Chromium shows it in, its text inside a `<pre>`, and is read as one block
   that keeps its line breaks;
4. it extracts the main text with Mozilla Readability over a linkedom
   document, after removing `<template>`, `<script>`, `<noscript>`, `<style>`,
   and `<svg>` elements, whose text is not page text, and dropping the
   `hidden` and `aria-hidden` attributes so the text they hide is read like
   any other text. It refuses markup with more
   than 40,000 start tags before parsing it, and a parsed page with more than
   40,000 elements or a nesting depth sum above 400,000. A `<br>` or a nested
   block keeps the words around it apart;
5. it splits the text into passages of at most 1,200 characters and keeps at
   most 12,000 characters: the whole page, the passages that best match
   `focus` by BM25, or the beginning;
6. it frames the page's title, its site and date when the page's metadata
   gives them, which vmo's reader does not pass on yet
   ([#208](https://github.com/w3lt/lys/issues/208)), and the passages between
   `<<<page content>>>` delimiters, with the URL Lys was asked to read, a
   notice that the content is untrusted, the page's source number, and an
   instruction to cite it by that number, and notes a page
   with less than 200 characters of main text, which may ask the reader to
   sign in or check for automated readers. Every run of three or more `<` or
   `>` in page text is shortened to two, so no page can write a delimiter.
   Characters that show nothing (Unicode default-ignorable code points, and
   every format and control character except tabs and line breaks) belong to
   a run when they sit between its brackets, and are dropped with it, so they
   cannot hide a delimiter either.

The whole read, the host lookup and vmo's answer included, must finish within
60 seconds, which leaves time for vmo to create, boot, and delete the VM
around its own 30 seconds. Stop and the time limit end only Lys's request:
vmo does not notice, and the VM runs until vmo's own limit ends it. vmo does
not say where the page's redirects led, its HTTP status, or its media type,
so the page is cited under the URL Lys was asked to read, and an error page
is read like any other page. Failures the model can act on, such as a blocked
address, a page that did not load, a page too large to read, or a page
without any main text, become the call's result. A turn offers `read_page`
only while vmo answers its health route, but vmo can stop during the turn: a
vmo that is not running, fails, answers outside its contract, or does not
answer in time fails the read with whom to contact, and its cause goes to the backend log; vmo's own
error output is never read. Lys reads what a signed-out visitor sees; it
never signs in.

### `web_search`

`web_search(query)` searches the web through the Tavily Search API with the
person's API key. The query is trimmed and must have 1 to 400 characters, none
of which is a Unicode default-ignorable code point (such as a zero-width,
direction, tag, or variation selector character, or a Hangul filler), a
control, format, surrogate, private-use, or unassigned code point, or a line
or paragraph separator; otherwise the call is answered at once. Such
characters show nothing or can reorder text, so they are refused rather than
removed, and the approval card shows exactly the query sent. An emoji written
with a variation selector, such as `❤️`, is refused too. The rule is
`hasHiddenWebSearchQueryCharacter` in `@lys/protocol`, which the desktop
applies too.

- **Key.** `WebSearchToolProvider` reads `secrets.tavilyApiKey` from the
  desktop's settings file (`settingsFilePath`, `$LYS_HOME/settings.json`) with
  `readTavilyApiKey` (`src/infrastructure/settings/tavilyApiKeyFile.ts`),
  once per tool list request, chat request, and key check. The desktop host is
  the file's only writer. The reader reads at most 1 MiB, takes only that
  field, and drops every parse failure without logging it, because JSON parse
  messages quote the text. A missing file, group, or `null` means no key; a
  value that fails the key format is invalid; anything else unreadable is
  `settings-unreadable`. A turn's tool holds the key read when the turn
  started.
- **Request** (`web/tavilyRequest.ts`, `web/tavilyApi.ts`). Once allowed, one
  `POST https://api.tavily.com/search` asks for a basic search (one credit) of
  at most 5 results, without Tavily's generated answer, raw page text, or
  images. The client uses `node:https` with certificate verification forced on
  and TLS 1.2 at least, the same address rule as `read_page` on every resolved
  address and the connected socket, one connection per request, no cookies or
  proxy, and the key only in the `authorization` header. No redirect is
  followed. The whole request must finish within 15 seconds, and a body larger
  than 1 MiB, not `application/json` in UTF-8, or compressed is refused.
- **Evidence** (`web/searchEvidence.ts`). A result is kept only when its URL
  passes `read_page`'s URL rules, once per URL; titles are cut to 300
  characters and snippets to 500, flattened onto one line. The query line,
  the result count, and an untrusted-content notice precede the results,
  which sit between `<<<search results>>>` delimiters, each labelled with its
  source number; a closing note says a
  snippet is only an excerpt to read before relying on it and repeats the
  citation rule. No results produce a plain statement that nothing was found.
- **Failures.** A rejected key (401/403), rate limiting (429, with its
  `Retry-After` seconds), used-up credits (432/433), other HTTP errors, a
  redirect, a timeout, an unreachable host, an address refused by the rule,
  and an unreadable or oversized answer each become the call's result in
  Lys's own words; Tavily's error text is never passed on.

`POST /api/v1/tools/web_search/key-check`, whose body must be the empty JSON
object `{}`, reads the key and asks Tavily's `GET /usage` about it, through the
same client and limits, and answers
`accepted` (with the plan's credits when reported, a fraction rounded up to a
whole credit), `rejected`,
`unavailable`, or `failed`. Tavily charges two credits for each `GET /usage`,
although its documentation lists no cost for it; the check still uses it
because only that answer reports the plan's credits, which Test shows. Each
check sends the key to Tavily, so it is a
`POST` with a JSON body, which a page on another site cannot send without a
CORS preflight that the backend refuses; another body is answered with 400, or
415 for a media type Fastify cannot parse, before the key is read.

### `read_attachment`

`read_attachment(number, start_line?, line_count?)` returns lines of a text
file the person attached to a message of the conversation. Its definition
(`buildReadAttachmentDefinition`, `src/modules/attachment/readAttachmentTool.ts`)
has group `files`, access `reads`, and runner `backend`, and tells the model
to read a file by the number its message lists it under. A turn offers it
after the request's backend tools when the conversation, the new message
included, holds a text attachment and the model is trained for tool use. Its
calls run without approval, as they read only what the person attached to
this conversation; it has no Tools pane row and no saved choice.

`ReadAttachmentTool` holds the conversation's attachments by number and a
reader lent by the file store, so a call reaches a file only through its
stored row, never through a path of the model's. A number no attachment has
is answered with the list of the conversation's attachments; an image's
number, with a reminder that images are seen with their message; a line
argument that is not a whole number of at least 1, with the rule. A call
returns at most 200 lines, lowering a larger `line_count` to that, and at
most 16,000 characters, cut before the line that would pass the limit, or
within a first line longer than it, without splitting a character: a header
naming the attachment, the lines returned, the file's total lines and size,
how the limit cut them, which for a line cut within says the rest of it
cannot be read, and how to continue when lines follow; then the lines. Line
breaks of
either kind end lines; an empty file is reported empty, and a start line past
the end fails with the file's line count. A file missing from this machine
fails the call with a result the model reads; a file that cannot be read for
another reason rejects the call with the reader's failure, as a defect, and
Stop ends a read in progress.

## Persistence

The backend stores conversations and agent definitions in SQLite at
`$LYS_HOME/lys_db.sqlite`, in the
[Lys home directory](/reference/configuration/#lys-home-directory).

| Table                      | Purpose                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `conversations`            | Stores conversation metadata: title, agent code, and timestamps.                                             |
| `conversation_messages`    | Stores ordered user messages and replies with status, finish reason, and timestamps, and each reply's parts. |
| `conversation_sources`     | Stores each conversation's numbered web sources.                                                             |
| `conversation_attachments` | Stores each attachment of a user message: number, name, kind, size, and an image's media type and sides.     |
| `agents`                   | Stores agent definitions: code, name, bio, system prompt, and timestamps.                                    |

The backend's database owner, `SqliteDatabase` in `src/infrastructure/database/`,
opens the file once, applies the schema from `migrations.ts` using
`PRAGMA user_version`, and is the only owner that closes it. Stores borrow read
and write transactions that expose neither connection closing nor transaction
control; the SQLite conversation records in `conversations/` are built on them
and hold every conversation query. The history-reading, history-editing,
turn, and reply-part services wrap those records, and each is its own
application service. The attachment files themselves live outside SQLite,
under `$LYS_HOME/attachments`, owned by `AttachmentFileStore`; see
[attachments](#attachments).
The agent service `AgentService` (`src/modules/agent/agentService.ts`) owns
agent management. It uses the SQLite agent records in `agents/` for stored
agents, but it is not one of the database services: it also owns the built-in
agents, Caliginia (`caliginia`) and Lysiptera (`lysiptera`), which
`buildBuiltInAgents` (`src/modules/agent/builtInAgents.ts`) builds from the
two configured system prompts. A built-in agent is never stored: the service
lists it with every page, reads it with `kind: "built-in"`, refuses to change
or delete it, and refuses to store another agent under its code. The
composition root creates the service after the conversation services, over
the agent records and the chat service.

`Agent` (`src/modules/agent/agent.ts`) answers turns with its own system prompt
through a `ReplyModel`. `AgentService.findChatAgent` returns the agent that
answers chats under a code: a built-in agent, or a new `Agent` built from the
stored agent's current record, so an edited prompt is sent from the
conversation's next turn. The chat module's `OpenAiReplyModel` implements `ReplyModel`
over `ChatService`'s streaming completion, using only choice 0 and refusing
finish reasons other than `stop` and `length`. The chat route passes the agent
the turn's history, its reply writes, its event sender, its Stop signal, and
three reporters that log with the request's logger: a cancelled reply and a
round that was not sent, because it did not fit or its model was not loaded,
at debug level, and any other failed reply at error level. A new
conversation must name a built-in or stored agent, or the chat route answers
`404` before storing anything. When a stored conversation's agent no longer
exists, the chat route answers `409` and stores nothing, so the conversation
stays readable and accepts messages again once an agent has that code.
Version 4 preserves activity
timestamps on rename, version 5 preserves them on status-only message updates,
version 6 adds the `agents` table, version 7 replaces the stored system prompt
with the conversation's agent code, version 8 moves every conversation stored
under the former built-in code `lys` to `caliginia`, version 9 stores each
reply's parts as rows of their own and adds the conversation sources,
version 10 adds the attachment rows, and
turn persistence's startup recovers streaming assistants and their open tool
calls without reordering history.
Two triggers keep `conversations.updated_at` in sync with message and part
inserts and `content` updates.

## LM Studio integration

Chat generation and model management use separate integration boundaries:

| Service             | Backend dependency        | Current use                                                                                                      |
| ------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `ChatService`       | `openai` SDK              | Streams chat completions and generates titles through LM Studio's OpenAI-compatible HTTP interface.              |
| `LlmService`        | `LlmEngineOperationQueue` | Runs inventory, health, load, stop-by-key, and context measurement through the serialized queue.                 |
| `LlmRuntimeService` | `LlmRuntime`              | Owns the LM Studio runtime, its connection status, and the serialized model-operation queue; connects on demand. |
| `LmStudioRuntime`   | `@lmstudio/sdk`           | Verifies engine availability, implements model operations and lifecycle inspection, and owns SDK client cleanup. |

Fastify exposes the application-scoped `llmService` and `llmRuntimeService`.
Model routes use provider-neutral capabilities of `LlmService`; the runtime
status and connect routes use `LlmRuntimeConnectionObserver` and
`LlmRuntimeConnector`, implemented by `LlmRuntimeService`. The ownership path
is `routes -> LlmService -> LlmRuntimeService queue -> LlmRuntime ->
LmStudioRuntime -> SDK`. The composition root creates `LlmRuntimeService`
without contacting LM Studio. After the HTTP listener opens, an `onListen` hook
makes one connection attempt; later attempts happen only through
`POST /api/v1/llm/runtime/connect`. The runtime service drains accepted
operations before releasing its runtime; releasing it closes the SDK client
without unloading models or stopping LM Studio.

The connection status is `connecting` until the first attempt settles,
`connected` while a runtime is held, and `unreachable` after a failed attempt
or after a held runtime stops answering. Model operations are refused with
`503` `urn:lys:problem:llm:runtime-unavailable` unless the status is
`connected`. When a runtime call fails during a model operation, the service
probes the runtime before the queue moves on and releases it if LM Studio no
longer answers. Refresh keeps a runtime that still answers and otherwise
acquires a new one; concurrent refreshes share one attempt.

`LmStudioRuntime.create()` still waits for LM Studio to answer its version
query, so a held runtime was always available when acquired. The installed SDK
cannot cancel a pending version query, so an attempt and the queue behind it
have no completion deadline; a nonresponding LM Studio can keep an attempt or
shutdown pending. A refused loopback port fails immediately. SDK messages
queued during an outage can be sent after a reconnect; see
[issue #81](https://github.com/w3lt/lys/issues/81).

The backend currently assumes a local LM Studio runtime on loopback.

`GET /api/v1/llm/:modelId/health` uses the same service queue and makes one fresh
loaded-inventory query. It reports `ready` when the validated snapshot contains
the requested canonical key. An absent key reports `model-not-loaded`; a query
that cannot establish loaded state reports `runtime-unavailable`. The check
does not generate text or change which models are loaded, and does not involve
`ChatService`. It establishes current availability, not future inference success.
See the [health response contract](/reference/api/#model-health-responses).

## Failure behavior

| Condition                                                                                                                    | Current behavior                                                                                                                         |
| ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Chat SSE connection closes                                                                                                   | Only that follower ends; the reply and its title keep generating and are stored.                                                         |
| Reply-stop request                                                                                                           | The reply's upstream request is aborted, the reply is stored interrupted, and followers receive `interrupted`; the title task continues. |
| Model operation or health-check client disconnects                                                                           | Accepted work continues until success or failure; user cancellation is unavailable.                                                      |
| LLM runtime queue already has nine accepted operations (including connection attempts)                                       | New inventory/health/load/unload requests receive `503` with `urn:lys:problem:llm:service-busy` before acceptance.                       |
| LM Studio is not connected                                                                                                   | List, load, unload, and health requests receive `503` with `urn:lys:problem:llm:runtime-unavailable` before acceptance.                  |
| A runtime call fails and LM Studio stopped answering                                                                         | The runtime is released, the status becomes `unreachable`, and a rejected request receives the runtime-unavailable `503`.                |
| A request resolves after a failed runtime call; the probe or release then fails                                              | The response keeps its result; the backend logs the probe or release failure at `error`.                                                 |
| A reply round does not fit the loaded model, or its model is not loaded                                                      | The round is not sent; the reply is stored failed and followers receive an `error` that says why.                                        |
| A reply round cannot be measured (LM Studio not connected, queue full)                                                       | The round is not sent; the reply is stored failed and followers receive the general `error`.                                             |
| Model stream ends without a finish reason                                                                                    | The route treats it as an error and may emit `error`.                                                                                    |
| Assistant row was deleted or already finalized                                                                               | Late writes return false without recreating data.                                                                                        |
| Assistant terminal state cannot be persisted                                                                                 | The task aggregates the original and storage failures, plus a failed fallback's, and rejects; the generation logs it. No final event.    |
| Unknown finish reason                                                                                                        | The backend throws instead of silently coercing it.                                                                                      |
| Title generation produces no usable title                                                                                    | The task logs a warning and sends no `error` or `title` event; a later turn retries if the conversation is still untitled.               |
| A generated title cannot be saved                                                                                            | The task logs an error and sends no `title` event; a later turn retries if the conversation is still untitled.                           |
| A stored title cannot be sent after turn start                                                                               | That follower ends silently while generation continues; a later turn attempts reconciliation again.                                      |
| A follower falls 4,096 events behind                                                                                         | That follower closes without a final event while generation continues; following the reply again returns its stored state.               |
| A chat request's attachment is neither UTF-8 text nor a PNG, JPEG, or WebP image                                             | The route answers `400` with `urn:lys:problem:chat:attachment-unsupported`; nothing is stored or written.                                |
| An image is attached for a model without vision, or for one the inventory does not list                                      | The route answers `409` with `urn:lys:problem:chat:image-needs-vision`; nothing is stored or written.                                    |
| LM Studio is not connected, or the queue is full, while a request that involves an attachment reads the model's capabilities | The route answers the runtime-unavailable or service-busy `503` problem; nothing is stored or written.                                   |
| An attachment file cannot be written                                                                                         | The message's folder and the files written into it are deleted, and the route rethrows; nothing is stored.                               |
| A turn cannot be stored after its attachment files were written                                                              | The message's folder is deleted again and the route answers `500`; a folder that cannot be deleted fails the request with both failures. |
| A stored attachment's file is missing from disk                                                                              | An image becomes a placeholder sentence in its message; a read of a text file fails with a result the model reads. The turn goes on.     |
| A deleted conversation's attachment folder cannot be removed                                                                 | The delete still answers `204`; the backend logs the failure with its cause at `error`, and the folder stays.                            |
| Starting a turn fails for another reason                                                                                     | The route rethrows; Fastify logs it and responds `500` if no event was sent. Written rows stay.                                          |

See the [provider cancellation policy](/architecture/providers/#cancellation-policy)
for the separate inference and model-management lifetimes.
