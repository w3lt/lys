Lys currently persists a SQLite database of conversations and agent
definitions, a small JSON settings file, one desktop theme preference, and the
images vmo runs its page-reading VMs from.

## Persistent artifacts

| Artifact         | Owner           | Location                                                      | Purpose                                                                                                                                                                                              |
| ---------------- | --------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend database | Fastify backend | `$LYS_HOME/lys_db.sqlite`                                     | Stores conversations, their messages and reply parts, attachment records, sources, and agents.                                                                                                       |
| Attachment files | Fastify backend | `$LYS_HOME/attachments/<conversation id>/<message id>/<name>` | Stores each file sent with a user message under its own name; written before the turn is stored and removed with the conversation. See [attachments](/architecture/backend/#attachments).            |
| Settings JSON    | Tauri host      | `$LYS_HOME/settings.json`                                     | Stores the runtime, model, generation, load, secrets, tools, and MCP groups.                                                                                                                         |
| Theme preference | Desktop UI      | WebView `localStorage`, key `lys.theme`                       | Stores `dark` or `light`; invalid or unavailable storage falls back to `dark`.                                                                                                                       |
| vmo image store  | vmo             | `~/Library/Application Support/com.w3lt.lys-vmo`              | Holds `vminit`, the VMs' boot filesystem unpacked from it, the reader image, and running VMs' files; each start deletes every other image. See [vmo's image store](/operate/data/#vmos-image-store). |

## SQLite ownership

Only the backend reads or writes the database directly.
`SqliteDatabase` (`apps/backend/src/infrastructure/database/`) owns the
connection, its schema version, and closing it; the composition root opens it
once and closes it after the LLM runtime service and before the chat service.
Stores borrow read and write transactions that cannot close the connection or
end a transaction early. The conversation records in
`src/infrastructure/database/conversations/` own every query on the
conversation tables, and the agent records in
`src/infrastructure/database/agents/` own every query on the `agents` table; the
shared migration list in `migrations.ts` owns every
table's schema. The database
compiles each distinct SQL text once and keeps the statement until it closes.
Each operation receives its own statement compiler, which refuses every request
once that operation returns, even inside a later operation. Outside a write
transaction the connection refuses every change
(`PRAGMA query_only`), so a read cannot write and a statement kept beyond its
operation cannot change data.

| Table                      | Owned by                    | Notes                                                                                                                                                                                                              |
| -------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `conversations`            | SQLite conversation records | One row per conversation, including `title`, `agent_code`, `created_at`, and `updated_at`.                                                                                                                         |
| `conversation_messages`    | SQLite conversation records | Ordered user messages and replies, with each reply's `status`, `finish_reason`, and `model`, and each reply's reasoning, text, and tool-call parts as rows under it.                                               |
| `conversation_sources`     | SQLite conversation records | One row per numbered web source of a conversation: `number`, `url`, and `title`, each number and URL once.                                                                                                         |
| `conversation_attachments` | SQLite conversation records | One row per attachment of a user message: `number`, `name`, `kind`, `size_bytes`, and an image's `media_type`, `width`, and `height`; each number once per conversation, each name once per message ignoring case. |
| `agents`                   | SQLite agent records        | One row per agent definition, keyed by its `code`, with `name`, `bio`, `system_prompt`, `created_at`, `updated_at`, and `deleted_at`, the time a deleted agent was deleted; a deleted agent's row stays.           |

The desktop does not query SQLite directly and the Tauri host does not proxy
conversation SQL. The backend creates four SQLite record providers over the
shared database, for history reading, history editing, turns, and reply parts,
and wraps each in a conversation service in `src/modules/conversation/`. Each
service keeps the decisions (identities, timestamps, validation, superseding a
streaming reply, list cursors) behind records it declares in `records.ts`, and
contains no SQL. Each service is exposed as its own application service.
`AttachmentFileStore` (`src/modules/attachment/attachmentFileStore.ts`) owns
the attachment files outside SQLite: the chat route has it write a message's
files before the turn's transaction, the agent context and the attachment
reader read them through it, and the delete route removes a conversation's
folder through it once the rows are gone. Loading a conversation reads only
the rows.
The agent service `AgentService` (`src/modules/agent/agentService.ts`) uses
`SqliteAgentRecordStore` the same way: it validates each definition or change,
reads the current time once per change, and lists and stores agents through
records it declares in `records.ts`. Unlike the conversation records, the
agent records are just two interfaces, `AgentRecordStore` for listing,
lookup, and changes and `AgentRecordSearcher` for search: the service is
their only consumer and uses every operation of both, while the routes
receive narrow capabilities of the service instead. Deleting an agent only sets its `deleted_at`, so its code is
never free again and the built-in agents can still look it up; listings,
counts, and changes skip it. The service is not a database service: it also owns the
built-in agents Caliginia and Lysiptera, which are never stored, and refuses
to store another agent under their codes `caliginia` and `lysiptera`. It is
decorated as `app.agentService`; the agent routes in
`src/modules/agent/routes/` call it. The agent runtime service, decorated as
`app.agentRuntimeService`, reads agents through it for the chat routes and
keeps the [live agents](/architecture/backend/#live-agents) and the requests
they work on in memory only; nothing of them is stored.
Every borrowed operation fails once the database closes,
and the database remains open until every reply generation has stored its final
state.

## Migration model

The backend applies schema changes from an in-memory `databaseMigrations` array.
On startup the database owner:

1. Opens the SQLite file with foreign keys enabled.
2. Acquires a write transaction and reads `PRAGMA user_version`.
3. Rejects unsupported future versions or applies each missing migration in order.
4. Records the latest version, 11, and commits; a migration failure rolls back
   all pending work.
5. Switches to write-ahead logging with `synchronous = NORMAL`. A database from
   a newer version was refused in step 3, before anything changed its file.
6. Turns on write protection, which only a write transaction lifts.
7. Installs an authorizer that refuses transaction-control SQL, including
   savepoints, and changes to write protection from store code.

The conversation services are then created over SQLite records on the open
database. Turn persistence comes first: in one write transaction it changes
remaining streaming assistants to interrupted with a fresh timestamp, and
their waiting and running tool calls to interrupted with their own
timestamps kept, without changing conversation activity time. The record reader then registers
its search function, and the agent service is created over its records.

The current migrations create the three conversation tables, add two
message indexes (one for each conversation's history order, and a unique one
for the positions of each reply's parts), and install triggers that keep
`conversations.updated_at` current. Historical
migrations remain unchanged; version 4 restricts the conversation timestamp
trigger to explicit activity updates, so title edits preserve ordering, and
version 5 restricts the message-update trigger to text changes, so status-only
updates preserve it too. Version 6 adds the `agents` table and changes no
existing row. Version 9 rebuilds the message table so a reply's reasoning,
text, and tool calls are rows of their own under the reply's row, moves each
stored reply's text into one text part, and adds `conversation_sources`; it
cannot be undone. Version 10 adds `conversation_attachments`. Version 11 adds
`agents.deleted_at`; agents deleted before it are gone, and their codes stay
free.
Turn creation is atomic and first interrupts a reply still streaming in the same
conversation: the turn service runs it as one callback inside one write
transaction of the turn records, which refuse every call once the callback
returns. The turn service reads the current time once per operation, and every
value a turn builds carries that time; the message-insert trigger then moves
the conversation's activity time forward, to a later time when the message's
time is not later than the stored one. A rename validates
the renamed conversation before it commits, so an invalid stored row rolls the
rename back. Every reply part, fragment, tool call change, and source is
committed before it is sent to any stream following the reply. The fragment
`UPDATE`, like every statement, is compiled on its first use and reused; each
write runs in one write transaction, guarded by the reply still streaming.
Finalizing a reply marks its waiting and running tool calls interrupted in
the same transaction.

## Settings ownership

The settings JSON is a separate host-managed artifact. The backend reads only
the Tavily API key, the Just run list (`tools.justRun`), and the `mcp` group
from it, and never writes it. The desktop reaches it through Tauri commands.

Generation, load configuration, tool approval, and runtime startup switch
edits are saved automatically. Each save reads the document already on disk
and replaces only its own part, preserving the rest: a generation save
replaces the `generation` group, a load configuration save replaces
`loadConfiguration.models` and keeps `loadConfiguration.default`, which only a
hand edit changes, a tool approval save replaces the `tools` group, and a
startup switch save replaces `runtime.autoStartBackend` and
`runtime.autoStartVmo` and keeps the rest of `runtime`. The other runtime
edits, such as default-model selection, remain session-only in the desktop.
Saving a server, or removing one, in Settings → MCP reads the document on
disk the same way and replaces only the `mcp` group.
See the [configuration reference](/reference/configuration/#persisted-settings-json)
for the current shape and defaults.
